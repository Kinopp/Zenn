# 問題7-1：現在日時（DATE型）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
データベースのサーバー、またはセッションの現在日付（DATE型）を取得してください。
Oracle Databaseにおける基本的なシステム日付の取得方法を確認します。

## 期待する結果
| NOW                  | 
| -------------------- | 
| 2026-03-07T23:42:48Z | 

> 表示される値は、SQLを実行した際の日時によって変動します。

## 解答例
```sql:例1：SYSDATEで取得
SELECT
    SYSDATE AS "NOW"
FROM
    dual
```
```sql:例2：CURRENT_DATEで取得
SELECT
    CURRENT_DATE AS "NOW"
FROM
    dual
```
```sql:例3：FROM DUALを省略（23c以降）
SELECT
    SYSDATE AS "NOW"
```

## 解説
SQLにおいて日付の扱いは、売上集計や期限管理など、ビジネスロジックの要（かなめ）となります。
Oracleで現在の日時を取得する、最も基本的かつ重要な関数の違いを整理しましょう。

### 1. 文法解説：SYSDATE と CURRENT_DATE

現在の日時を返す関数には、主に以下の2つがあります。

#### ① SYSDATE（システム日付）
最も一般的に使われる関数です。
* **値のソース**: **データベースが稼働しているサーバー（OS）** の現在時刻を返します。
* **特徴**: サーバーが日本にあれば日本時間を返します。設定に依存するため、常に一定の基準で動きます。

#### ② CURRENT_DATE（セッション日付）
ユーザーごとに異なる結果を返す可能性がある関数です。
* **値のソース**: **接続しているユーザー（セッション）のタイムゾーン**における現在時刻を返します。
* **特徴**: 例えばサーバーが東京にあっても、ニューヨークから接続しているユーザーがタイムゾーンを設定していれば、ニューヨークの時刻が表示されます。

### 2. DUAL テーブルの正体
解答例で使われている `FROM dual` ですが、これはOracle特有の **「ダミーテーブル」** です。

* **なぜ必要か？**: Oracleの `SELECT` 文は、必ず `FROM` 句でテーブルを指定しなければならないというルールがあります。
* **DUALの中身**: `DUMMY` というカラムが1つ、行が1行だけ入っている特別なテーブルです。
* **使い道**: 今回のように「定数」や「関数の結果」だけを確認したいときに、計算台として利用します。

> **Oracle 23c の新機能**
> 解答例3にある通り、最新の **Oracle Database 23c** からは、ついに `FROM dual` を省略できるようになりました！他のデータベース（PostgreSQLやSQL Serverなど）の書き方に近づき、よりシンプルに記述できるようになっています。

### 3. 実務での注意点：DATE型は「時刻」も持っている
期待する結果の形式（`2026-03-07T23:42:48Z`）からも分かる通り、Oracleの **DATE型は日付だけでなく「秒」までの時刻情報も含んでいます。**

「今日の日付のデータだけ欲しい」と思って `WHERE hire_date = SYSDATE` と書いてしまうと、**時刻までぴったり一致しない限りヒットしない**というミスがよく起こります。日付だけを比較したい場合は、後ほど登場する `TRUNC` 関数で時刻を切り捨てるのが鉄則です。

# 問題7-2：現在日時（TIMESTAMP型）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
データベースのサーバー、またはセッションの現在日付（TIMESTAMP型）を取得してください。
DATE型よりも精度の高い（秒未満を含む）日時情報の取得方法を確認します。


## 期待する結果
| NOW                         | 
| --------------------------- | 
| 2026-03-07T23:57:37.027035Z | 


> 表示される値は、SQLを実行した際の日時によって変動します。

## 解答例
```sql:例1：SYSTIMESTAMPで取得
SELECT
    SYSTIMESTAMP AS "NOW"
FROM
    dual
```
```sql:例2：CURRENT_TIMESTAMPで取得
SELECT
    CURRENT_TIMESTAMP AS "NOW"
FROM
    dual
```
```sql:例3：LOCALTIMESTAMPで取得
SELECT
    LOCALTIMESTAMP AS "NOW"
FROM
    dual
```

## 解説
前回の `DATE` 型に続き、今回はさらに高精度な **`TIMESTAMP` 型**を取得する関数の解説です。
実務では「ミリ秒単位のログ記録」や「タイムゾーンをまたぐグローバルなシステム」で、この `TIMESTAMP` 系関数が必須となります。

### 1. 文法解説：3つの TIMESTAMP 関数の違い
解答例にある3つの関数は、**「どこの時間を基準にするか」** と **「タイムゾーン情報を含めるか」** という点が異なります。

| 関数名 | 基準（どこから取るか） | タイムゾーン情報 | 特徴 |
| :--- | :--- | :--- | :--- |
| **`SYSTIMESTAMP`** | データベースサーバー | **あり** | サーバーのOS時刻＋サーバーの時差を返す。 |
| **`CURRENT_TIMESTAMP`** | 接続ユーザー（セッション） | **あり** | ユーザー設定の時刻＋その時差を返す。 |
| **`LOCALTIMESTAMP`** | 接続ユーザー（セッション） | **なし** | 時刻はユーザー設定だが、時差データは持たない。 |

### 2. DATE型 vs TIMESTAMP型
「どっちを使えばいいの？」と迷うこともあるかと思いますが、大きな違いは2つです。

1.  **精度の違い**:
    * `DATE` 型は「秒」まで。
    * `TIMESTAMP` 型は **「10億分の1秒（ナノ秒）」** まで記録できます。
2.  **時差（タイムゾーン）の扱い**:
    * `DATE` 型は時差を持ちません。
    * `TIMESTAMP WITH TIME ZONE` を使えば、「それがどこの国の20時なのか」を保持できます。

### 3. 実務での使い分け

* **`SYSTIMESTAMP`**: 「サーバーにデータが書き込まれた絶対的な瞬間」を記録したい場合（更新ログ、監査トレースなど）。
* **`CURRENT_TIMESTAMP`**: 「東京のユーザーには日本時間、ロンドンのユーザーには現地時間」で現在時刻を表示・登録したいアプリの場合。
* **`LOCALTIMESTAMP`**: 時差情報は不要だが、秒以下の細かい精度（ミリ秒など）だけが欲しい場合。

> **ミリ秒が表示されない？**
> 実行環境（ツール）の設定によっては、`TIMESTAMP` を取得しても秒までしか表示されないことがあります。その場合は、後ほど学ぶ `TO_CHAR` 関数を使ってフォーマットを指定することで、`.027035` のような細かい数値までしっかり確認できるようになります。

# 問題7-3：日付のフォーマット

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマの`JOB_HISTORY`テーブルからすべてのデータを取得してください。
その際、日付型の項目である`START_DATE`と`END_DATE`を、**「YYYY-MM-DD」形式**（例：2026-05-11）の文字列に変換して表示してください。なお、結果の表示順は問いません。


## 期待する結果
| EMPLOYEE_ID | START_DATE | END_DATE   | 
| ----------- | ---------- | ---------- | 
| 102         | 2011-01-13 | 2016-07-24 | 
| 101         | 2007-09-21 | 2011-10-27 | 
| 101         | 2011-10-28 | 2015-03-15 | 
| 201         | 2014-02-17 | 2017-12-19 | 
| 114         | 2016-03-24 | 2017-12-31 | 
| 122         | 2017-01-01 | 2017-12-31 | 
| 200         | 2005-09-17 | 2011-06-17 | 
| 176         | 2016-03-24 | 2016-12-31 | 
| 176         | 2017-01-01 | 2017-12-31 | 
| 200         | 2012-07-01 | 2016-12-31 | 

## 解答例
```sql
SELECT
    employee_id,
    TO_CHAR(start_date, 'YYYY-MM-DD') AS start_date,
    TO_CHAR(end_date, 'YYYY-MM-DD')   AS end_date
FROM
    hr.job_history
```

## 解説
日付データをそのまま表示すると、データベースの設定（NLS_DATE_FORMAT）によって「07-MAY-26」だったり「26/05/07」だったりとバラバラになりがちです。
そこで登場するのが、日付を自由自在な見た目に変換する **`TO_CHAR`関数** です。これさえマスターすれば、どんなレポート作成も怖くありません！

### 1. 文法解説：TO_CHAR 関数（日付 → 文字列）
日付型（DATEやTIMESTAMP）のデータを、指定したフォーマットの「文字列」に変換します。

```sql
TO_CHAR( [日付データ], '[フォーマットマスク]' )
```

#### ① フォーマットマスクのルール
今回使用した `'YYYY-MM-DD'` の意味は以下の通りです。

| マスク | 意味 | 例（2026年5月7日の場合） |
| :--- | :--- | :--- |
| **`YYYY`** | 西暦4桁 | 2026 |
| **`MM`** | 月（2桁） | 05 |
| **`DD`** | 日（2桁） | 07 |
| **`-`** | 区切り文字 | そのまま表示される |


### 2. よく使うフォーマットのバリエーション
実務でよくリクエストされる「型」をいくつか紹介します。

* **日本でおなじみの形式**: `'YYYY/MM/DD'` → `2026/05/07`
* **時刻まで含める**: `'YYYY-MM-DD HH24:MI:SS'` → `2026-05-07 15:30:45`
* **年月のみ**: `'YYYYMM'` → `202605`
* **曜日を入れる**: `'YYYY-MM-DD (DY)'` → `2026-05-07 (木)` ※言語設定に依存します

### 3. なぜ SQL 側でフォーマットするのか？
「アプリ側のプログラムで整形すればいいのでは？」と思うかもしれませんが、SQL側でやるメリットは大きいです。

1.  **データの統一感**: どのツールで出力しても、期待通りの形式（ハイフン区切りなど）でデータが出てくる。
2.  **グループ化に便利**: `TO_CHAR(hire_date, 'YYYY')` で抽出すれば、そのまま「年別の集計」に利用できる。
3.  **そのまま CSV 出力**: Excel などで開いたとき、日付として正しく認識されやすい形式で書き出せる。

> **注意：型が変わる！**
> `TO_CHAR` を使った後のデータは、**「日付型」ではなく「文字列型」** になっています。そのため、この結果を使って「1日足す」といった日付計算をしようとするとエラーになるので注意しましょう。計算は `TO_CHAR` する前に済ませるのが鉄則です！

# 問題7-4：年、月、日の抽出

### 難易度：★★☆☆☆ (Lv.2)

## 問題

OEスキーマの`CUSTOMERS`テーブルより、**1985年生まれ**の顧客を取得し、以下のルールに従って表示してください。なお、結果の表示順は問いません。

**【編集ルール】**

* **ID**：`CUSTOMER_ID`を表示する。
* **NAME**：`CUST_FIRST_NAME`と`CUST_LAST_NAME`を半角スペースを挟んで結合する。
* **BIRTHDAY**：`DATE_OF_BIRTH`を「〇〇〇〇年〇月〇日」という形式の文字列に変換する。
* 月や日が1桁の場合、先頭の「0」は表示しないこと（例：05月→5月）。

## 期待する結果
| ID  | NAME             | BIRTHDAY      | 
| --- | ---------------- | ------------- | 
| 215 | Orson Perkins    | 1985年5月24日 | 
| 253 | Sally Bogart     | 1985年1月14日 | 
| 255 | Brooke Shepherd  | 1985年2月13日 | 
| 328 | Hannah Field     | 1985年10月6日 | 
| 838 | Alfred Nicholson | 1985年1月25日 | 
| 913 | Bob Sharif       | 1985年1月10日 | 


## 解答例
```sql:例1：TO_CHARを使用（従来のやり方）
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    TO_CHAR(date_of_birth, 'YYYY') || '年' || 
      TO_CHAR(date_of_birth,'FMMM') || '月' ||
        TO_CHAR(date_of_birth, 'FMDD') || '日' AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN TO_DATE('1985-01-01', 'YYYY-MM-DD') 
                      AND TO_DATE('1985-12-31', 'YYYY-MM-DD')
ORDER BY
    id
```
```sql:例2：TO_CHARを使用（スマートなやり方）
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    TO_CHAR(date_of_birth, 'YYYY"年"FMMM"月"DD"日"') AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN TO_DATE('1985-01-01', 'YYYY-MM-DD') 
                      AND TO_DATE('1985-12-31', 'YYYY-MM-DD')
ORDER BY
    id
```
```sql:例3：EXTRACTを使用
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    EXTRACT(YEAR FROM date_of_birth) || '年' || 
      EXTRACT(MONTH FROM date_of_birth) || '月' ||
        EXTRACT(DAY FROM date_of_birth) || '日' AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN date'1985-01-01' 
                      AND date'1985-12-31'
ORDER BY
    id
```


## 解説
日付データを扱う上で避けては通れない「年・月・日の個別抽出」と「日本語フォーマットへの整形」です。解答例には、実務で役立つ3つのアプローチが示されています。
特に **「01月」を「1月」と表示させるテクニック** など、細かいこだわりが詰まった問題です。

### 1. 文法解説：TO_CHAR関数の「FM」と「" "」
解答例2は、Oracleの `TO_CHAR` 関数の機能をフル活用した最もスマートな書き方です。

#### ① FM (Fill Mode) モディファイア
通常、`MM` や `DD` は「01」「05」のように2桁で表示されます（先頭ゼロ埋め）。これを「1」「5」のように数字だけ表示したい場合は、先頭に **`FM`** を付けます。
* **`TO_CHAR(date, 'MM')`** → 05
* **`TO_CHAR(date, 'FMMM')`** → 5

#### ② フォーマット内での文字列（" "）
`TO_CHAR` のフォーマットマスクの中で、「年」や「月」といった特定の文字をそのまま表示させたい場合は、その文字を **`" "`（ダブルクォーテーション）** で囲みます。
これを使えば、例1のように `||` で結合しなくても一発で整形が可能です。


### 2. 文法解説：EXTRACT 関数
解答例3で使われている `EXTRACT` は、日付から特定の要素を「数値型」として取り出すための標準的な関数です。

```sql
EXTRACT(YEAR FROM [日付])  -- 年を数値で取得
EXTRACT(MONTH FROM [日付]) -- 月を数値で取得
EXTRACT(DAY FROM [日付])   -- 日を数値で取得
```

* **特徴**: 結果が「数値」として返ってくるため、そのまま「1月」と表示されます（先頭に0がつきません）。
* **メリット**: 数値として計算（例：誕生月が偶数か判定など）に使う場合に非常に便利です。

### 3. 日付定数（Date Literals）の活用
解答例3のWHERE句に注目してください。

```sql
WHERE date_of_birth BETWEEN date'1985-01-01' AND date'1985-12-31'
```

`TO_DATE` を使わずに、**`date'YYYY-MM-DD'`** と書く方法です。これは「日付リテラル」と呼ばれ、ISO標準の形式で日付を直感的に書けるため、コードの可読性が非常に高まります。

### 4. どのアプローチが最強か？
実務での使い分けを整理しましょう。

| 手法 | おすすめ度 | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **`TO_CHAR` (例2)** | ★★★ | **最強。** 1つの関数で複雑な整形が完結し、コードが最も短くなる。 | フォーマットマスクの記法（FMや" "）を覚える必要がある。 |
| **`EXTRACT` (例3)** | ★★☆ | 数値として要素を取り出せる。標準SQLに近く、他DBでも通用しやすい。 | 表示用に文字と結合する場合、記述が長くなりがち。 |
| **結合 (例1)** | ★☆☆ | 仕組みが単純で分かりやすい。 | 関数を何度も呼ぶため、冗長で効率が少し悪い。 |

> **実務での一工夫**
> 今回のように「1985年」のデータを取る場合、`TO_CHAR(date_of_birth, 'YYYY') = '1985'` と書いても正解ですが、`BETWEEN` を使うほうがデータベースの索引（インデックス）を効率よく使えるため、速度面で有利になることが多いですよ！

### 日付リテラル（ANSI日付リテラル）
**「日付リテラル（ANSI日付リテラル）」** は、`TO_DATE` 関数を使わずに、よりシンプルかつ標準的な形式で日付を指定する方法です。

結論から言うと、**「時間は不要で、決まった形式（YYYY-MM-DD）で書きたい時」** に非常に便利です。

### 日付リテラルの書き方

構文は非常にシンプルです。

```sql
DATE 'YYYY-MM-DD'
```

#### 具体的な例

```sql
-- TO_DATEを使う場合
SELECT * FROM orders WHERE order_date >= TO_DATE('2024-01-01', 'YYYY-MM-DD');

-- 日付リテラルを使う場合
SELECT * FROM orders WHERE order_date >= DATE '2024-01-01';
```
<br>
### DATEリテラルの特徴と注意点
`TO_DATE` と比較して、いくつか守らなければならないルールがあります。
<br>
#### 1. フォーマットは「YYYY-MM-DD」固定

日付リテラルを使う場合、フォーマットを自由に変えることはできません。必ず **西暦4桁-月2桁-日2桁** で書く必要があります。

* ⭕ `DATE '2024-03-15'`
* ❌ `DATE '2024/03/15'` （スラッシュはエラー）
* ❌ `DATE '24-03-15'` （2桁年はエラー）
<br>
#### 2. 時・分・秒を含めることはできない

`DATE` というキーワードを使いますが、日付リテラルで指定できるのは「年月日」までです。時刻（00:00:01など）を指定したい場合は、**TIMESTAMPリテラル** を使う必要があります。

```sql
-- 時刻まで指定したい場合
SELECT TIMESTAMP '2024-03-15 10:30:00' FROM DUAL;
```
<br>
#### 3. 関数ではなく「定数」として扱われる

`TO_DATE` は実行時に文字列を日付に変換する「処理」が走りますが、日付リテラルはデータベースが最初から日付として認識します。そのため、ごく僅かですがパフォーマンス的に有利な場合があります（通常は気にするほどではありません）。

<br>
### どっちを使うべき？（比較表）

| 特徴 | DATEリテラル | TO_DATE関数 |
| --- | --- | --- |
| **書きやすさ** | 短くてスッキリする | 少し長い |
| **フォーマット** | `YYYY-MM-DD` 固定 | 自由自在（スラッシュ等も可） |
| **時刻の指定** | 不可（TIMESTAMPなら可） | 可能 |
| **動的な指定** | 不向き（固定値用） | 変数やカラムを渡せる |
| **標準規格** | ANSI標準（他DBでも通じやすい） | Oracle独自 |

<br>
### 使い分けのガイドライン

* **プログラム内の固定値や、手動でサクッとクエリを投げる時**
* `DATE '2024-01-01'` がおすすめ。読みやすく、タイプ数も少ないです。
<br>
* **画面からの入力値や、特殊な形式の文字列を扱う時**
* `TO_DATE(:input_val, 'YYYY/MM/DD')` を使いましょう。

# 問題7-5：日付の加算

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、職種（`JOB_ID`）が「AD_VP」の従業員を対象として、採用日（`HIRE_DATE`）を基準に以下の日付を取得してください。

**【取得内容】**

* **HIRE_DATE**：採用日
* **HIRE_DATE + 2DAY**：採用日の2日後の日付
* **HIRE_DATE + 2MONTH**：採用日の2ヶ月後の日付
* **HIRE_DATE + 2YEAR**：採用日の2年後の日付

※すべて「YYYY-MM-DD」形式の文字列に変換して表示してください。

## 期待する結果
| EMPLOYEE_ID | NAME       | HIRE_DATE  | HIRE_DATE + 2DAY | HIRE_DATE + 2MONTH | HIRE_DATE + 2YEAR | 
| ----------- | ---------- | ---------- | ---------------- | ------------------ | ----------------- | 
| 101         | Neena Yang | 2015-09-21 | 2015-09-23       | 2015-11-21         | 2017-09-21        | 
| 102         | Lex Garcia | 2011-01-13 | 2011-01-15       | 2011-03-13         | 2013-01-13        |


## 解答例
```sql
SELECT
    employee_id,
    first_name || ' ' || last_name as name,
    TO_CHAR(hire_date, 'YYYY-MM-DD')                   AS "HIRE_DATE",
    TO_CHAR(hire_date + 2, 'YYYY-MM-DD')               AS "HIRE_DATE + 2DAY",
    TO_CHAR(ADD_MONTHS(hire_date, 2), 'YYYY-MM-DD')    AS "HIRE_DATE + 2MONTH",
    TO_CHAR(ADD_MONTHS(hire_date, 2*12), 'YYYY-MM-DD') AS "HIRE_DATE + 2YEAR"
FROM
    hr.employees
WHERE
    job_id = 'AD_VP';
```

## 解説
いよいよ日付の「計算」ですね。Oracle SQLにおいて日付は単なるデータではなく、数値のように足したり引いたりできる便利な存在です。
今回のポイントは、**「単位（日・月・年）によって計算方法が異なる」** という点です。ここを整理すると、日付操作のマスターに大きく近づきます。


### 1. 文法解説：単位ごとの加算ルール

#### ① 「日」の加算：もっともシンプル
OracleのDATE型は内部的に数値として扱われており、**「1 = 1日」** を意味します。そのため、日数を足したいときは単に算術演算子（`+`）を使うだけです。
* **`hire_date + 2`** → 2日後
* **`hire_date - 1`** → 1日前（昨日）

### ② 「月」の加算：ADD_MONTHS 関数
月を足す場合は、単純に「+ 30」とはいきません。月によって30日だったり31日だったり、はたまた2月は28日だったりするからです。そこで、**`ADD_MONTHS`** 関数を使います。

```sql
ADD_MONTHS( [日付], [足したい月数] )
```
* **賢いポイント**: 月末（例：1月31日）に1ヶ月足すと、正しく「2月28日（または29日）」を返してくれるなど、カレンダーの不規則性を自動で吸収してくれます。

### ③ 「年」の加算：月の応用
「2年後」を求める専用の関数は（実は）ありません。そのため、**「1年 = 12ヶ月」** というルールを利用して、`ADD_MONTHS` で計算するのが一般的です。
* **`ADD_MONTHS(hire_date, 2 * 12)`** → 24ヶ月後 ＝ 2年後


### 2. 知っておくと得する「INTERVAL」定数
解答例のやり方は非常に「Oracleらしい」伝統的な書き方ですが、最近の実務（特に他DBへの移行も考慮する場合）では、より英語に近い表現の **`INTERVAL`** を使うことも増えています。

```sql
-- こう書くこともできます
hire_date + INTERVAL '2' DAY    -- 2日後
hire_date + INTERVAL '2' MONTH  -- 2ヶ月後
hire_date + INTERVAL '2' YEAR   -- 2年後
```
※ただし、`INTERVAL` は「1月31日の1ヶ月後」などを計算しようとするとエラーを出す場合があるなど、挙動がシビアです。まずは解答例の **`ADD_MONTHS`** を使いこなせるようになるのが上達の近道です！

### 3. 実務での活用シーン
* **期限管理**: `shipping_date + 3` （発送から3日後を到着予定日にする）
* **契約更新**: `ADD_MONTHS(contract_date, 12)` （1年後の更新日を算出する）
* **年齢計算**: 誕生日と現在の日付を `ADD_MONTHS` を使って比較する


> **TO_CHAR を忘れずに！**
> 解答例のように、計算した結果を最後に `TO_CHAR` で整形してあげると、レポートとして完璧な見た目になります。計算を先に済ませてから、最後に「お化粧（整形）」をするのがSQLの基本順序です。

# 問題7-6：期間の算出

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`JOB_HISTORY`テーブルより、各職務の開始日（`START_DATE`）から終了日（`END_DATE`）までの期間を算出し、「〇年〇ヶ月」という形式で取得してください。なお、結果の表示順は問いません。

**【算出のヒント】**

* 2つの日付間の月数を求めるには `MONTHS_BETWEEN` 関数を使用します。
* 月数を12で割った商を「年」、12で割った余りを「ヶ月」として算出してください。
* 月数の端数は切り捨てて計算してください。

## 期待する結果
| EMPLOYEE_ID | JOB_ID     | 期間      | 
| ----------- | ---------- | --------- | 
| 102         | IT_PROG    | 5年6ヶ月  | 
| 101         | AC_ACCOUNT | 4年1ヶ月  | 
| 101         | AC_MGR     | 3年4ヶ月  | 
| 201         | MK_REP     | 3年10ヶ月 | 
| 114         | ST_CLERK   | 1年9ヶ月  | 
| 122         | ST_CLERK   | 0年11ヶ月 | 
| 200         | AD_ASST    | 5年9ヶ月  | 
| 176         | SA_REP     | 0年9ヶ月  | 
| 176         | SA_MAN     | 0年11ヶ月 | 
| 200         | AC_ACCOUNT | 4年5ヶ月  | 

## 解答例
```sql
SELECT
    employee_id,
    job_id,
    TRUNC(MONTHS_BETWEEN(end_date, start_date) / 12) || '年' || 
      MOD(TRUNC(MONTHS_BETWEEN(end_date, start_date)), 12) || 'ヶ月' 
                                                           AS "期間"
FROM
    hr.job_history
```

## 解説
今回は日付の「差」を求める計算です。単に「何日間」を出すのは簡単ですが、「○年○ヶ月」という形式にするには、算数の「割り算」と「余り」の考え方をSQLで表現するパズル的なテクニックが必要になります。

### 1. 文法解説：MONTHS_BETWEEN 関数
日付同士の期間を計算する際、もっとも強力な味方が **`MONTHS_BETWEEN`** です。

```sql
MONTHS_BETWEEN( [後の日付], [前の日付] )
```

* **戻り値**: 2つの日付の間の**月数**を数値で返します。
* **特徴**: 31日の月も30日の月も考慮して「1.5ヶ月」のように小数点を含めて正確に算出してくれます。


### 2. ロジックの解剖：どうやって「年」と「ヶ月」に分けるか？
解答例の計算式を、102番の従業員（5年6ヶ月）を例に分解してみましょう。
まず、`MONTHS_BETWEEN` の結果が仮に **66.5ヶ月** だったとします。

#### ① 「年」を出す
1年は12ヶ月なので、全体の月数を12で割り、小数点以下を切り捨てます。
$$\text{TRUNC}(66.5 / 12) = \text{TRUNC}(5.541\dots) \rightarrow \mathbf{5}$$

#### ② 「ヶ月」を出す
「年」として計算しきれなかった「余りの月数」を求めます。
ここで便利なのが、余りを計算する **`MOD` 関数** です。
$$\text{MOD}(\text{TRUNC}(66.5), 12) \rightarrow 66 \div 12 = 5 \text{ 余り } \mathbf{6}$$

> **なぜ2回も TRUNC が必要なのか？**
> `MONTHS_BETWEEN` は「30.5」のように端数を返すことがあります。そのまま `MOD` に入れると「余り 6.5」になってしまうため、一度 `TRUNC` で「整数（月数）」に丸めてから、12で割った余り（0〜11ヶ月）を出すのがポイントです。

### 3. 実務での活用シーン
この計算は、人事システムや顧客管理システムで非常に重宝します。

* **勤続年数**: 「入社から現在まで、何年何ヶ月働いているか」
* **ローン・分割払い**: 「支払い開始から現在まで、何年何ヶ月経過したか」
* **年齢計算**: 誕生月を考慮した厳密な年齢表示。

### 4. 実行結果の確認
期待する結果を見ると、122番の従業員のように「0年11ヶ月」と表示されています。
もし `TRUNC(... / 12)` をせずに `MONTHS_BETWEEN` だけを使っていたら、人間には直感的に分かりにくい「0.916...年」のような数値になってしまいます。

このように、**「DBが計算しやすい値（月数）」を「人間が理解しやすい形式（年・月）」へ変換する** スキルは、レポート作成の現場で非常に高く評価されます！

さて、日付の「差」の計算はマスターできましたか？
次は、日付の「最後」の日を求める（2月が28日か29日か気にせず取得できる）便利な関数、**`LAST_DAY`** などに挑戦してみますか？

# 問題7-8：日時の範囲指定

### 難易度：★★☆☆☆ (Lv.2)

## 問題

COスキーマの`ORDERS`テーブルより、注文日時（`ORDER_TMS`）が**2021年6月**であるデータを取得してください。
ただし、対象とする顧客は`CUSTOMER_ID`が350から359までの範囲に該当するレコードに限定します。なお、結果の表示順は問いません。

**【ポイント】**

* `TIMESTAMP`リテラルを使用して範囲を指定してください。
* 索引を効率的に使用するため、列側（`ORDER_TMS`）に関数（`TO_CHAR`など）を適用せず、比較演算子（`>=` および `<`）を用いた条件式を作成してください。


## 期待する結果
| CUSTOMER_ID | ORDER_TMS                   | 
| ----------- | --------------------------- | 
| 351         | 2021-06-03T16:04:46.024146Z | 
| 354         | 2021-06-08T04:17:12.071275Z | 
| 350         | 2021-06-13T18:10:25.420066Z | 
| 352         | 2021-06-30T18:09:40.698324Z | 

## 解答例
```sql
SELECT
    customer_id,
    order_tms
FROM
    co.orders
WHERE
    customer_id BETWEEN 350 AND 359
    AND order_tms >= TIMESTAMP '2021-06-01 00:00:00'
    AND order_tms  < TIMESTAMP '2021-07-01 00:00:00'
```

## 解説
今回は、大量のデータの中から特定の「期間」を、**データベースに負荷をかけず、かつ正確に** 抜き出すための実践的なテクニックですね。
一見シンプルですが、この書き方にはエンジニアの「現場の知恵」が詰まっています。

### 1. 核心：なぜ「BETWEEN」ではなく「>=」と「<」なのか？
日付やタイムスタンプの範囲指定で、最も間違いが少なく、かつ推奨されるのがこの **「以上・未満」** の組み合わせです。

#### ① 0.000001秒の漏れも許さない
もし、`BETWEEN '2021-06-01' AND '2021-06-30'` と書いてしまうと、**「6月30日の 00:00:00」** までのデータしか取れず、それ以降（18:00など）のデータがすべて漏れてしまいます。

かといって、`AND '2021-06-30 23:59:59'` と書くのも危険です。`TIMESTAMP`型はミリ秒やナノ秒単位まで保持しているため、その「最後の1秒」の中にデータが存在する可能性があるからです。

> **「翌月の1日 0時 未満」と指定する**
> こうすることで、6月30日のギリギリ最後の瞬間までを完璧に、漏れなくカバーすることができます。これがプロの書き方です。

### 2. 文法解説：TIMESTAMPリテラル

解答例で使用されている `TIMESTAMP 'YYYY-MM-DD HH24:MI:SS'` という書き方は、**TIMESTAMPリテラル**と呼ばれます。

* **メリット**: `TO_TIMESTAMP` 関数を使わずに、文字列を直接タイムスタンプ型として認識させることができます。
* **記述の簡潔さ**: 余計な関数を挟まないため、クエリが非常に読みやすくなります。


### 3. 実務での重要ポイント：インデックス・フレンドリー

「6月のデータが欲しいなら、`WHERE TO_CHAR(order_tms, 'YYYYMM') = '202106'` でもいいのでは？」と思うかもしれません。
たしかに結果は同じになりますが、実務（特に数千万件のデータがある場合）では**NG**とされることが多いです。

#### なぜ TO_CHAR はダメなのか？
カラムを関数（`TO_CHAR`など）で加工してしまうと、そのカラムに貼られた**索引（インデックス）が使えなくなる**からです。

* **関数を使う場合**: 全行を一度文字に変換してから比較するため、非常に時間がかかります。
* **範囲指定（解答例）**: インデックスを使って、対象の期間まで一気にジャンプできるため、**圧倒的に高速**です。

### 4. 期待する結果の確認
期待する結果を見ると、6月3日、8日、13日、30日と、しっかり1ヶ月分のデータが取得できています。特に30日の `18:09:40...` というデータは、もし「30日の0時まで」という指定ミスをしていたら消えていたはずのデータです。

この「以上・未満」のセットは、日付だけでなく数値の範囲指定などでも役立つ一生モノのスキルです！

## 解答例
```sql
SELECT
    employee_id,
    hire_date,
    TO_CHAR(TRUNC(hire_date),      'YYYY-MM-DD') AS "その日(秒以下切り捨て)",
    TO_CHAR(TRUNC(hire_date,'MM'), 'YYYY-MM-DD') AS "その月の初日",
    TO_CHAR(TRUNC(hire_date,'YY'), 'YYYY-MM-DD') AS "その年の初日",
    TO_CHAR(TRUNC(hire_date, 'Q'), 'YYYY-MM-DD') AS "その四半期の初日",
    TO_CHAR(TRUNC(hire_date,'IW'), 'YYYY-MM-DD') AS "その週の月曜日"
FROM
    hr.employees
WHERE
    employee_id < 110
```

## 解説
今回は、日付データを意図した単位で「丸める」ための最重要関数、**`TRUNC`（トランク）関数**の解説です。
「今月分の売上だけ集計したい」「週ごとのレポートを作りたい」といった実務の現場では、この関数が八面六臂の活躍を見せます。

### 1. 文法解説：TRUNC 関数（日付）
`TRUNC` 関数は、指定した「書式モデル」に基づいて、それ以下の単位をすべて切り捨てます。

```sql
TRUNC( [日付データ], '[書式モデル]' )
```

#### ① 書式モデルと切り捨てのルール
引数を変えるだけで、自由自在に「基準日」を作り出すことができます。

| 書式モデル | 切り捨ての単位 | 結果 |
| :--- | :--- | :--- |
| **（なし）** | 時刻（時・分・秒） | その日の **00:00:00** になる |
| **`'MM'`** | 日 | その月の **1日** になる |
| **`'Q'`** | 月・日 | その **四半期の初日** (1, 4, 7, 10月の1日) になる |
| **`'YY'`** | 月・日 | その年の **1月1日** になる |
| **`'IW'`** | 日 | その週の **月曜日** (ISO週基準) になる |


### 2. ここがポイント：なぜ TRUNC が必要なのか？
Oracleの `DATE` 型は、目に見えていなくても内部的に必ず「時・分・秒」を持っています。

* **問題点**: `2013-06-17 15:30:00` と `2013-06-17 00:00:00` は、人間には同じ日に見えますが、SQLの比較（`=`）では「一致しない」と判定されてしまいます。
* **解決策**: `TRUNC` を使うことで、すべてのデータの時刻を強制的に `00:00:00` に揃えることができます。これにより、日付単位での正しい比較やグループ化（`GROUP BY`）が可能になるのです。

### 3. 実務での活用シーン：レポート作成の裏技
#### ① 週報・月報の作成
「月別の売上合計」を出したいときは、`GROUP BY TRUNC(order_date, 'MM')` と書くだけで、1ヶ月分のデータがすべて「その月の1日」というラベルでひとまとめになります。

#### ② 「今週の月曜日」を求める
`TRUNC(SYSDATE, 'IW')` を使えば、今日が何曜日であっても、システムが自動的に「今週の月曜日」を特定してくれます。

### 4. 実行結果の確認
期待する結果の103番（2016-01-03）を見てみましょう。
* **その月の初日**: 1月1日
* **その週の月曜日**: **2015-12-28**
1月3日は日曜日なので、その週の始まりである前の年の12月28日（月曜日）までしっかり遡って計算されていますね。これが `IW` モデルの賢いところです。

> **TO_CHAR との組み合わせ**
> 解答例では `TO_CHAR(TRUNC(...))` と入れ子にしています。これは、`TRUNC` で計算した「日付型」のデータを、最終的に人間が見やすい「文字列」として表示するための、実務でよく使われるコンビネーションです。
