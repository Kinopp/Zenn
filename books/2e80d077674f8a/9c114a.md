# 問題5-1：文字列の結合

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマの **`EMPLOYEES`** テーブルを使用します。
**`MANAGER_ID` が 101** である従業員の、**`FIRST_NAME`**（名）と **`LAST_NAME`**（姓）を結合して、1つの列 **「NAME」** として表示してください。
その際、名と姓の間には **半角スペース** を 1 つ入れてください。

なお、レコードの表示順序は問いません。
  
## 期待する結果
| EMPLOYEE_ID | NAME            | 
| ----------- | --------------- | 
| 108         | Nancy Greenberg | 
| 200         | Jennifer Whalen | 
| 203         | Susan Mavris    | 
| 204         | Hermann Baer    | 
| 205         | Shelley Higgins |  


## 解答例
```sql:例1：「||」演算子を使用
SELECT
    employee_id,
    first_name || ' ' || last_name AS NAME
FROM
    hr.employees
WHERE
    manager_id = 101
```

```sql:例2：CONCAT 関数を使用
SELECT
    employee_id,
    CONCAT(
        CONCAT(first_name, ' '),
        last_name
    ) AS NAME
FROM
    hr.employees
WHERE
    manager_id = 101
```

## 解説
今回は、複数の列や文字を1つにまとめる **「文字列結合」** の解説です。

### 1. 文法解説：結合の方法
Oracle SQLで文字列を結合するには、主に2つの方法があります。

#### ① `||`（垂直バー2本）演算子
Oracleで最も一般的、かつ直感的な書き方です。プログラミングでいう「+」のような感覚で、何個でも数珠つなぎに結合できます。

```sql
first_name || ' ' || last_name
```
* **仕組み**: 左側のデータと右側のデータを「接着剤」のようにくっつけます。
* **リテラル文字**: 今回のように「半角スペース」を入れたい場合は、必ず **`' '`（シングルクォーテーション）** で囲みます。

#### ② CONCAT 関数
標準SQLにも存在する関数ですが、Oracleにおいては少し「クセ」があります。

```sql
CONCAT(文字列1, 文字列2)
```
* **制限**: Oracleの `CONCAT` は **「2つの引数」しか受け取れません。**
* **入れ子構造**: 今回のように「名前 + スペース + 名字」の3つを結合したい場合、解答例2のように「CONCATの中にCONCATを書く」という、少し面倒な書き方（ネスト）が必要になります。

### 2. どちらを使うべきか？

実務においては、圧倒的に **`||` 演算子** が好まれます。

| 特徴 | `\|\|`演算子 | `CONCAT` 関数 |
| :--- | :--- | :--- |
| **可読性** | 非常に高い（パッと見て何をしているか分かる）。 | 入れ子になると読みづらい。 |
| **柔軟性** | 3つ、4つと増えても楽に書ける。 | 2つずつしか処理できない。 |
| **推奨シーン** | **Oracleでの開発全般。** | 他のデータベース（MySQL等）との互換性を強く意識する場合。 |


### 3. 実務での注意点：NULLの扱い
ここがOracleの面白い（そして優しい）ところです。
多くのデータベース（SQL ServerやPostgreSQLなど）では、文字列に `NULL` を結合すると結果全体が `NULL` に消えてしまいます。

しかし、**Oracleの `||` 演算子は `NULL` を「空文字」として扱ってくれます。**
* 例：`'Nancy' || NULL` → 結果は `'Nancy'` のまま。

この仕様のおかげで、ミドルネームがある人とない人が混ざっているようなデータでも、エラーやデータ消失を気にせずガシガシ結合できるんです。

> **別名の設定（AS NAME）**
> 結合した結果には、元のカラム名がありません。そのまま出力するとヘッダーが `FIRST_NAME||' '||LAST_NAME` という不格好なものになってしまうので、今回のように `AS NAME`（別名）を付けるのがマナーです。

Nancy Greenbergさんのように、姓名の間にきれいなスペースが入ったフルネームが表示されましたか？

# 問題5-2：文字列の分割（文字数で分割）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマの `employees` テーブルを使用します。
`manager_id` が「101」であり、かつ `phone_number` が「1.」から始まるデータを対象に、電話番号を4つの項目に分割して抽出してください。

なお、対象の電話番号は「1桁.3桁.3桁.4桁」の形式で格納されています。今回の演習では、デリミタ（区切り文字）ではなく、「文字数（開始位置と桁数）」を指定して分割してください。

* 分割後の列名は左から `PN1`, `PN2`, `PN3`, `PN4` とすること。
* 結果の並び順は問わない（順不同）。
  
## 期待する結果
| EMPLOYEE_ID | PHONE_NUMBER   | PN1 | PN2 | PN3 | PN4 | 
| ----------- | -------------- | --- | --- | --- | --- | 
| 200         | 1.515.555.0165 | 1   | 515 | 555 | 0165 | 
| 203         | 1.515.555.0168 | 1   | 515 | 555 | 0168 | 
| 204         | 1.515.555.0169 | 1   | 515 | 555 | 0169 | 
| 205         | 1.515.555.0170 | 1   | 515 | 555 | 0170 | 
| 108         | 1.515.555.0108 | 1   | 515 | 555 | 0108 | 


## 解答例
```sql
SELECT
    employee_id,
    phone_number,
    SUBSTR(phone_number, 1, 1) AS PN1,
    SUBSTR(phone_number, 3, 3) AS PN2,
    SUBSTR(phone_number, 7, 3) AS PN3,
    SUBSTR(phone_number, 11, 4) AS PN4
FROM
    hr.employees
WHERE
    manager_id = 101
AND phone_number LIKE '1.%'
```

## 解説
前回の「結合」とは逆の操作、**「文字列の切り出し（分割）」** についての解説です。
特定のルールで並んでいるデータから、必要なパーツだけを抜き出す技術は、データのクリーニングや整形において必須のスキルです。

### 1. 文法解説：SUBSTR 関数

文字列の一部を抽出するには、**`SUBSTR` 関数**を使用します。

```sql
SUBSTR( [対象の文字列], [開始位置], [抽出する文字数] )
```

#### ① 引数の意味
* **第1引数**: 元となる文字列やカラム名（今回は `phone_number`）。
* **第2引数**: 何文字目からスタートするか。**1文字目を「1」** としてカウントします。
* **第3引数**: そこから何文字分を切り取るか。



#### ② 今回の切り出し位置の計算
電話番号の形式が `1.515.555.0165` と固定されているため、ピリオドの位置を数えて指定します。

| パーツ | 開始位置 | 文字数 | 指定 | 実際のデータ |
| :--- | :--- | :--- | :--- | :--- |
| **PN1** | 1 | 1 | `SUBSTR(..., 1, 1)` | `1` |
| (区切り) | 2 | - | (ピリオド) | `.` |
| **PN2** | 3 | 3 | `SUBSTR(..., 3, 3)` | `515` |
| (区切り) | 6 | - | (ピリオド) | `.` |
| **PN3** | 7 | 3 | `SUBSTR(..., 7, 3)` | `555` |
| (区切り) | 10 | - | (ピリオド) | `.` |
| **PN4** | 11 | 4 | `SUBSTR(..., 11, 4)` | `0165` |


### 2. WHERE句のポイント：前方一致

```sql
AND phone_number LIKE '1.%'
```
この条件により、「1」で始まり、その直後にピリオドが来るデータのみに絞り込んでいます。これにより、今回想定している「1-3-3-4」の桁数ルールが適用できないイレギュラーなデータを除外しています。

### 3. 実務での注意点：固定長 vs 可変長

今回の解き方は、**「データの桁数が常に一定である」** という前提に基づいています（固定長分割）。

* **メリット**: 書き方がシンプルで、処理が高速。
* **デメリット**: もし `1.50.555.0165` のように、途中の桁数が変わるデータが混ざると、切り出し位置がズレてしまい、ピリオドまで一緒に切り取ってしまう可能性があります。

> **ステップアップのヒント**
> もし桁数がバラバラな場合は、**`INSTR` 関数**を使って「ピリオドが何文字目にあるか」を探してから、その位置を元に `SUBSTR` を組み合わせるという、より高度なテクニックを使います。

まずはこの「何文字目から何文字取る」という基本の感覚を、しっかりマスターしておきましょう！


<br>
:::message
### **「マジックナンバー（固定の数字）に注意」**
実務で `SUBSTR(..., 7, 3)` と書くときは、コメントに「7文字目は市外局番の開始位置」のように理由を添えておくと、後から読む人が助かります。数字だけだと、なぜ 7 なのかが分からなくなるからです。
:::

# 問題5-3：文字列の置換（REPLACE関数）

### 難易度：★★☆☆☆ (Lv.2)

## 問題

HRスキーマの `departments` テーブルを使用します。
`department_id` が「100」より小さいデータを対象に、部署名（`department_name`）に含まれる**大文字の「A」を「X」に置換**して抽出してください。

* 置換後の列名は `department_name_a_to_x` とすること。
* 小文字の「a」は置換の対象に含めないでください。
* 結果の並び順は問わない（順不同）。

  
## 期待する結果
| DEPARTMENT_NAME  | DEPARTMENT_NAME_A_TO_X | 
| ---------------- | ---------------------- | 
| Administration   | Xdministration         | 
| Marketing        | Marketing              | 
| Purchasing       | Purchasing             | 
| Human Resources  | Human Resources        | 
| Shipping         | Shipping               | 
| IT               | IT                     | 
| Public Relations | Public Relations       | 
| Sales            | Sales                  | 
| Executive        | Executive              | 

## 解答例
```sql
SELECT
    department_name,
    REPLACE(department_name, 'A', 'X') AS department_name_a_to_x
FROM
    hr.departments
WHERE
    department_id < 100
```

## 解説
今回は、データクレンジング（データの整理）において最も頻繁に登場する関数の一つ、**`REPLACE` 関数**の解説です。
「特定の文字を別の文字に入れ替える」というシンプルな操作ですが、大文字・小文字の扱いや、実務での応用など、押さえておくべきポイントがいくつかあります。

### 1. 文法解説：REPLACE 関数
文字列の中から特定のパターンを探し、それを別の文字列にそっくり入れ替えます。

```sql
REPLACE( [対象の文字列], [探したい文字], [置換後の文字] )
```

#### ① 動作の仕組み
対象となる文字列を左から順番にスキャンし、[探したい文字] と一致する部分を見つけるたびに、[置換後の文字] に書き換えていきます。

#### ② 大文字・小文字の厳密な区別
ここが今回の問題の最大のポイントです。
Oracle SQLの `REPLACE` 関数は、**大文字と小文字を「別の文字」として扱います。**

* `REPLACE('Administration', 'A', 'X')` を実行すると：
    * 1文字目の **'A'** は一致するので **'X'** に変わります。
    * 11文字目の **'a'**（小文字）は「一致しない」と判定されるため、**そのまま残ります。**


### 2. 期待する結果の確認

期待する結果のリストを見てみましょう。

| 元のデータ | 置換後 | 解説 |
| :--- | :--- | :--- |
| **A**dministration | **X**dministration | 先頭の 'A' が置換された。 |
| M**a**rketing | M**a**rketing | 'a' は小文字なので置換されない。 |
| Purch**a**sing | Purch**a**sing | 'a' は小文字なので置換されない。 |

このように、大文字の 'A' を含む `Administration` だけが変化し、他の部署名に含まれる小文字の 'a' は無視されているのが分かりますね。


### 3. 実務で役立つ知識

#### 複数の文字を消したい場合（空文字への置換）
第3引数（置換後の文字）を省略するか、空の文字列（`''`）を指定すると、特定の文字を**削除**することができます。
* 例：`REPLACE('03-1234-5678', '-', '')` → `'0312345678'` （ハイフン除去）

#### よく似た関数：TRANSLATE との違い
実務でよく混同されるのが `TRANSLATE` 関数です。

* **`REPLACE`**: 「文字列」を「文字列」で置換する（塊で探す）。
* **`TRANSLATE`**: 「1文字」を「1文字」で置換する（1文字ずつバラバラに変換する）。

> **大文字小文字を区別せずに置換したいときは？**
> もし「大文字のAも小文字のaも全部Xにしたい！」という場合は、一度 `UPPER` 関数で全部大文字にしてから `REPLACE` するか、正規表現を使った `REGEXP_REPLACE` 関数（少し高度な技です）を使うのが一般的です。

# 問題5-4：文字列の置換２

### 難易度：★★☆☆☆ (Lv.2)

## 問題

HRスキーマの`DEPARTMENTS`テーブルより、`DEPARTMENT_ID`が100より小さいデータを選択してください。
その際、`DEPARTMENT_NAME`に含まれる文字「A」を「X」に、「a」を「x」に置換して表示してください（大文字・小文字の両方を置換すること）。なお、結果の表示順は問いません。

  
## 期待する結果
| DEPARTMENT_NAME  | DEPARTMENT_NAME_A_TO_X | 
| ---------------- | ---------------------- | 
| Administration   | Xdministrxtion         | 
| Marketing        | Mxrketing              | 
| Purchasing       | Purchxsing             | 
| Human Resources  | Humxn Resources        | 
| Shipping         | Shipping               | 
| IT               | IT                     | 
| Public Relations | Public Relxtions       | 
| Sales            | Sxles                  | 
| Executive        | Executive              | 

## 解答例
```sql
SELECT
    department_name,
    TRANSLATE(department_name, 'Aa', 'Xx') AS department_name_a_to_x
FROM
    hr.departments
WHERE
    department_id < 100
```

## 解説
前問（5-3）では `REPLACE` を使って「大文字のみ」を置換しましたが、今回は **「大文字も小文字もまとめて」** 置換するテクニックですね。

ここで登場するのが、`REPLACE` よりもさらに職人芸的な動きをする **`TRANSLATE` 関数**です。

### 1. 文法解説：TRANSLATE 関数

`TRANSLATE` は、文字列を「1文字ずつ」対応表に基づいて変換する関数です。

```sql
TRANSLATE( [対象文字列], [置換前の文字リスト], [置換後の文字リスト] )
```

#### ① 動作の仕組み：1対1の「置き換え地図」
この関数は、2番目の引数と3番目の引数を「位置」で対応させます。
今回の `TRANSLATE(department_name, 'Aa', 'Xx')` の場合、内部ではこのような地図が作られています。

* **1番目の文字**: `'A'` を見つけたら `'X'` に変換する
* **2番目の文字**: `'a'` を見つけたら `'x'` に変換する

`REPLACE` が「塊（単語）」で探すのに対し、`TRANSLATE` は **「文字のリスト」** として処理するのが最大の違いです。



### 2. REPLACE と TRANSLATE の決定的な違い

実務でどちらを使うか迷わないよう、違いを整理しましょう。

| 特徴 | `REPLACE` | `TRANSLATE` |
| :--- | :--- | :--- |
| **処理単位** | **文字列（塊）** で探す | **1文字ずつ** バラバラに探す |
| **置換内容** | 「A」を「Apple」に変えるような、長さの違う置換が得意。 | 「A」は「X」、「a」は「x」のように1文字ずつの変換が得意。 |
| **主な用途** | 特定の単語や記号を別の単語に変える。 | **大文字・小文字の同時変換**、暗号化、不要な文字の除去。 |

### 3. 実務での活用シーン：データのクレンジング

`TRANSLATE` は、以下のような「表記ゆれの修正」で神がかった力を発揮します。

* **全角英数字を半角にする**: `TRANSLATE(col, '０１２３...', '0123...')` と書けば、一撃で全ての数字を変換できます（`REPLACE` だと10回書く必要があります）。
* **特定の記号をまとめて消す**: ハイフン、スラッシュ、スペースなどを一気に消去して、純粋な数字だけに整えることができます。

期待する結果を見ると、`Xdministrxtion`（Aとaの両方が置換されている）や `Mxrketing` など、意図通りに文字が入れ替わっていますね。


<br>
::: message
### **「暗号化やフォーマット変換の味方」**
実務では、全角英数を半角に直したり、特定の伏せ字（マスキング）を作ったりする時に `TRANSLATE` は真価を発揮します。`REPLACE` を何重にも入れ子にするくらいなら、`TRANSLATE` 1回で済ませられないか検討するのが「SQL上級者」への近道です。
:::

# 問題5-5：大文字・小文字変換

### 難易度：★★☆☆☆ (Lv.2)

## 問題

COスキーマの`CUSTOMERS`テーブルより、`FULL_NAME`と、`EMAIL_ADDRESS`を以下のルールで加工した値（`EMAIL_NAME`）を比較し、**両者が一致しないデータ**を取得してください。

**【EMAIL_ADDRESSの加工ルール】**

1. 文字列から「@internalmail」を削除する。
2. ドット「.」を半角スペースに置換する。
3. スペースで区切られた各単語の先頭文字を大文字、それ以外を小文字に変換する（INITCAP）。

結果は`CUSTOMER_ID`の昇順で表示してください。
  
## 期待する結果
| CUSTOMER_ID | EMAIL_ADDRESS                   | FULL_NAME             | EMAIL_NAME         | 
| ----------- | ------------------------------- | --------------------- | ------------------ | 
| 123         | erda.sheer@internalmail         | erda Sheer            | Erda Sheer         | 
| 194         | norman.s.lobregat@internalmail  | Norman Simon Lobregat | Norman S Lobregat  | 
| 195         | tim.d.blasingim@internalmail    | Tim Dominic Blasingim | Tim D Blasingim    | 
| 227         | son.mclagan@internalmail        | Son McLagan           | Son Mclagan        | 
| 251         | dannie.mccoin@internalmail      | Dannie McCoin         | Dannie Mccoin      | 
| 262         | kendrick.mcmurtrey@internalmail | Kendrick McMurtrey    | Kendrick Mcmurtrey | 

## 解答例
```sql
SELECT
    CUSTOMER_ID,
    EMAIL_ADDRESS,
    FULL_NAME,
    INITCAP(replace(replace( EMAIL_ADDRESS ,'@internalmail', ''  ), '.', ' ')) as email_name
FROM
    CO.CUSTOMERS
where NOT(FULL_NAME = 
    INITCAP(replace(replace( EMAIL_ADDRESS ,'@internalmail', ''  ), '.', ' ')))
order by customer_id
```

## 解説
複数の関数を入れ子（ネスト）にして、「メールアドレスから氏名を推測し、登録されている正解の氏名と比較する」という、データの不整合をチェックする際によく使うテクニックです。

### 1. 文法解説：INITCAP 関数
今回の最大のポイントは **`INITCAP`（イニットキャップ）関数** です。

```sql
INITCAP( [対象の文字列] )
```

#### ① 役割：単語の先頭を大文字にする
`INITCAP` は "Initial Capital" の略で、**「各単語の先頭文字を大文字に、それ以外を小文字にする」** という動きをします。

* **単語の区切り**: スペースだけでなく、ピリオド(`.`)やハイフン(`-`)などの記号も「区切り」として認識されます。
* **例**: `tim.d.blasingim` → `Tim.D.Blasingim`


### 2. 関数の「入れ子（ネスト）」構造を解剖する

解答例の計算式は、内側から順番に実行されます。この「3層構造」を理解しましょう。

```sql
INITCAP( REPLACE( REPLACE( EMAIL_ADDRESS, '@internalmail', '' ), '.', ' ' ) )
```

1.  **第1層（一番内側のREPLACE）**:
    `EMAIL_ADDRESS` から `@internalmail` を取り除きます。
    （例：`erda.sheer@internalmail` → `erda.sheer`）
2.  **第2層（外側のREPLACE）**:
    残った文字列のピリオド(`.`)をスペース(` `)に置き換えます。
    （例：`erda.sheer` → `erda sheer`）
3.  **第3層（INITCAP）**:
    各単語の先頭を大文字にします。
    （例：`erda sheer` → **`Erda Sheer`**）

### 3. なぜ「一致しない」ものが存在するのか？

ここがこの問題の面白いところです。一見同じに見えても、以下の理由で `FULL_NAME` と `EMAIL_NAME` は不一致になります。

| 原因 | 具体例（期待する結果より） |
| :--- | :--- |

# 問題5-6：文字列のパディング

### 難易度：★★☆☆☆ (Lv.2)

## 問題

HRスキーマの`EMPLOYEES`テーブルより、`EMPLOYEE_ID`が200より大きいデータについて、以下の通り編集した値を取得してください。なお、結果の表示順は問いません。

**【編集ルール】**

* **EMP_ID6**：`EMPLOYEE_ID`を6桁にする。6桁に満たない場合は、左側を「0（ゼロ）」で埋めて表示すること。
* **EMAIL10**：`EMAIL`を10桁にする。10桁に満たない場合は、右側を「X」で埋めて表示すること。

## 期待する結果
| EMP_ID6 | EMAIL10    | 
| ------- | ---------- | 
| 000201  | MMARTINEXX | 
| 000202  | PDAVISXXXX | 
| 000203  | SJACOBSXXX | 
| 000204  | HBROWNXXXX | 
| 000205  | SHIGGINSXX | 
| 000206  | WGIETZXXXX | 

## 解答例
```sql
SELECT
    LPAD(employee_id, 6, '0') as "EMP_ID6",
    RPAD(email, 10, 'X') as "EMAIL10"
FROM
    hr.employees
WHERE
    employee_id > 200
```

## 解説
今回は、データの桁数を揃えて見た目やフォーマットを整える **「パディング（穴埋め）」** のテクニックですね。
システム間のデータ連携（CSV出力や固定長ファイル作成）では欠かせない、非常に実用的な関数です。

### 1. 文法解説：LPAD と RPAD
「指定した桁数になるまで、特定の文字で埋める」という動きをします。

#### ① LPAD (Left Pad)
文字列の**左側**を埋めます。主に数値を「0埋め（ゼロパディング）」したい時に使われます。

```sql
LPAD( [対象], [全体の桁数], [埋める文字] )
```
* **例**: `LPAD(201, 6, '0')` → `000201`
* 201は3桁なので、6桁に届くよう左側に「0」を3つ追加します。

#### ② RPAD (Right Pad)
文字列の**右側**を埋めます。名称などのテキストを固定長にしたい時に使われます。

```sql
RPAD( [対象], [全体の桁数], [埋める文字] )
```
* **例**: `RPAD('PDAVIS', 10, 'X')` → `PDAVISXXXX`
* PDAVISは6文字なので、10文字になるよう右側に「X」を4つ追加します。



### 2. 知っておくと得するポイント

#### もし元のデータが指定桁数より長かったら？
ここが注意点です。もし `LPAD('1234567', 5, '0')` のように、指定した桁数（5）よりも元のデータ（7文字）が長い場合、**右側が切り捨てられて** `'12345'` になります。
「埋める」だけでなく「長さを強制的に固定する」という側面も持っているんですね。

#### 第3引数を省略した場合
「埋める文字」を省略すると、デフォルトで**半角スペース**が使われます。
* `RPAD('HELLO', 10)` → `'HELLO     '` （右側に5つのスペース）
これは、固定長形式のレポート作成で非常によく使われるパターンです。


### 3. 実務での活用シーン

* **コード体系の統一**: `1`番と`100`番を、`00001`と`00100`のように揃えて並び替えを正しく行う。
* **バーコード用データ**: 決まった桁数が必要なJANコードなどの生成。
* **銀行振込データ（全銀フォーマット）**: 名前や口座番号を決められた文字数で埋めて送信する。

# 問題5-7：文字列のトリミング

### 難易度：★★☆☆☆ (Lv.2)

## 問題

COスキーマの`SHIPMENTS`テーブルより、`SHIPMENT_ID`が150から159のデータを選択し、`DELIVERY_ADDRESS`に対して以下の編集を行った値を取得してください。なお、結果の表示順は問いません。

**【編集ルール】**

* `DELIVERY_ADDRESS`の先頭部分から、文字列「Chatfield, 」を構成する文字を除去する。
* `DELIVERY_ADDRESS`の末尾部分から、文字列「 USA」を構成する文字を除去する。

## 期待する結果
| SHIPMENT_ID | DELIVERY_ADDRESS           | L_TRIM                     | R_TRIM                 | 
| ----------- | -------------------------- | -------------------------- | ---------------------- | 
| 150         | Boca Raton, FL 33433 USA   | Boca Raton, FL 33433 USA   | Boca Raton, FL 33433   | 
| 151         | Rutland, OH 45775 USA      | Rutland, OH 45775 USA      | Rutland, OH 45775      | 
| 153         | Lakeland, FL 33803 USA     | Lakeland, FL 33803 USA     | Lakeland, FL 33803     | 
| 154         | Falls Church, VA 22043 USA | Falls Church, VA 22043 USA | Falls Church, VA 22043 | 
| 155         | Chatfield, OH 44825 USA    | OH 44825 USA               | Chatfield, OH 44825    | 
| 156         | Chatfield, OH 44825 USA    | OH 44825 USA               | Chatfield, OH 44825    | 
| 157         | Dalmatia, PA 17017 USA     | Dalmatia, PA 17017 USA     | Dalmatia, PA 17017     | 
| 158         | Dalmatia, PA 17017 USA     | Dalmatia, PA 17017 USA     | Dalmatia, PA 17017     | 
| 159         | Fonda, NY 12068 USA        | Fonda, NY 12068 USA        | Fonda, NY 12068        | 

## 解答例
```sql
SELECT
    shipment_id,
    delivery_address,
    LTRIM(delivery_address, 'Chatfield, ') AS "L_TRIM",
    RTRIM(delivery_address, ' USA')        AS "R_TRIM"
FROM
    co.shipments
WHERE
    shipment_id BETWEEN 150 AND 159
```

## 解説
今回は、文字列の端にある不要な部分を「削り取る」ための**TRIM（トリミング）関数**の解説です。
データの入力ミスで紛れ込んだ不要なスペースや、特定のプレフィックス（接頭辞）・サフィックス（接尾辞）を一括で除去したいときに非常に重宝します。

### 1. 文法解説：LTRIM と RTRIM
Oracle SQLには、削り取る方向に応じて2つの関数が用意されています。

### ① LTRIM (Left Trim)
文字列の **左側（先頭）** から、指定した文字を取り除きます。

```sql
LTRIM( [対象], [削除したい文字の集合] )
```
* **例**: `LTRIM('Chatfield, OH', 'Chatfield,')`
* 先頭にある「C」「h」「a」...「,」が順番に削られ、` OH`（先頭にスペースが残った状態）が返ります。

### ② RTRIM (Right Trim)
文字列の **右側（末尾）** から、指定した文字を取り除きます。

```sql
RTRIM( [対象], [削除したい文字の集合] )
```
* **例**: `RTRIM('FL 33433 USA', 'USA')`
* 末尾にある「A」「S」「U」が削られ、`FL 33433 `（末尾にスペースが残った状態）が返ります。

### 2. 【重要】OracleのTRIM関数の「落とし穴」
ここが一番の注意点です。Oracleの `LTRIM` / `RTRIM` の第2引数は、「ひとまとまりの文字列」ではなく、**「削除したい文字のセット」** として扱われます。

たとえば、`RTRIM(col, 'USA')` と書いた場合、Oracleは「'USA' という単語を探す」のではなく、**「右端に U か S か A がある限り、削り続ける」** という動きをします。

* **例**: `RTRIM('BUS USA', 'USA')` 
* この場合、末尾の `USA` だけでなく、`BUS` の最後にある `S` も削除対象リストに含まれているため、結果は `'BU '` になってしまいます。

### 3. 実務での活用シーン

* **空白除去**: 実務で最も多いのは、第2引数を省略して `LTRIM(col)` や `RTRIM(col)` と書くパターンです。この場合、**デフォルトで半角スペースが削除**されます。
* **特定の記号のクリーニング**: CSVデータの前後にあるダブルクォーテーションを消すときなどに便利です。
* **プレフィックスの除去**: 商品コードの先頭に一律で付いている「ID-」などを取り除く際などに使われます。

期待する結果を見ると、`Chatfield,` で始まる住所だけが左側を削られ、それ以外の住所（Boca Ratonなど）は「対象の文字が先頭にない」ため、何も削られずにそのまま表示されていますね。この「一致しなければ何もしない」という挙動も重要です。


### 比較まとめ
| 関数 | 削除する場所 | 性質 | 推奨シーン |
| :--- | :--- | :--- | :--- |
| **`LTRIM`** | 左端のみ | 指定した文字群を削る | 先頭のゼロ(0)や記号の除去 |
| **`RTRIM`** | 右端のみ | 指定した文字群を削る | 末尾のスペースや改行の除去 |
| **`TRIM`** | 両端 | 基本は1文字のみ指定可 | 両端の空白を一気に消す時 |

# 問題5-9：NULLの変換

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`DEPARTMENTS`テーブルより、`DEPARTMENT_ID`が100から150のデータについて、`DEPARTMENT_ID`とそれに対応する`MANAGER_ID`を取得してください。

| DEPARTMENT_ID | MANAGER_ID | 
| ------------- | ---------- | 
| 100           | 108        | 
| 110           | 205        | 
| 120           | 0          | 
| 130           | 0          | 
| 140           | 0          | 
| 150           | 0          |

```sql:例1：NVLを使用
SELECT
    department_id,
    NVL(manager_id, 0) AS "MANAGER_ID"
FROM
    hr.departments
WHERE
    department_id BETWEEN 100 AND 150
```
```sql:例2：NVL2を使用
SELECT
    department_id,
    NVL2(manager_id, manager_id ,0)  AS "MANAGER_ID"
FROM
    hr.departments
WHERE
    department_id BETWEEN 100 AND 150
```
```sql:例3：COALESCEを使用
SELECT
    department_id,
    COALESCE(manager_id ,0) AS "MANAGER_ID"
FROM
    hr.departments
WHERE
    department_id BETWEEN 100 AND 150
```
```sql:例4：DECODEを使用
SELECT
    department_id,
    DECODE(manager_id, null, 0, manager_id) AS "MANAGER_ID"
FROM
    hr.departments
WHERE
    department_id BETWEEN 100 AND 150
```
```sql:例5：CASE式を使用
SELECT
    department_id,
    CASE WHEN manager_id IS NULL THEN 0 ELSE manager_id END AS "MANAGER_ID"
FROM
    hr.departments
WHERE
    department_id BETWEEN 100 AND 150
```

## 解説
今回はSQLの難所であり、かつ実務で最も神経を使う **「NULL値の変換」** に到達しました。
「データがない（NULL）」という状態を、レポートや計算のために「0」などの具体的な値に置き換える処理は、システム開発において避けては通れない必須スキルです。解答例には5つもの方法がありますが、それぞれの特徴をスッキリ整理しましょう。

### 1. 文法解説：NULLを扱う5つの武器
OracleにはNULLを料理するための関数が豊富に用意されています。

#### ① NVL 関数（例1）
Oracleで最も伝統的かつ、現場で一番目にする関数です。
```sql
NVL( [対象], [NULLだった時の値] )
```
* **特徴**: 「もしNULLならこれに変えて！」という非常にシンプルな指示です。

#### ② NVL2 関数（例2）
「NULLか、そうでないか」で表示を完全に分けたい時に使います。
```sql
NVL2( [対象], [NULLでない時の値], [NULLだった時の値] )
```
* **特徴**: 三項演算子のような動きをします。

#### ③ COALESCE 関数（例3）
**標準SQL**（どのデータベースでも使える世界共通語）であり、現在最も推奨される書き方です。
```sql
COALESCE( [値1], [値2], [値3]... )
```
* **特徴**: 引数をいくつでも並べられ、**「最初に見つかったNULLでない値」** を返します。

#### ④ DECODE 関数（例4）
Oracle独自の「if-then-else」ロジックを持つ関数です。
```sql
DECODE( [対象], NULL, 0, [対象] )
```
* **特徴**: 等価比較が得意ですが、NULL判定もこのように書けます。

#### ⑤ CASE 式（例5）
最も読みやすく、どんな複雑な条件にも対応できる万能選手です。
```sql
CASE WHEN manager_id IS NULL THEN 0 ELSE manager_id END
```
* **特徴**: 文法がプログラミングに近いため、可読性が非常に高いです。


### 2. 実務での超重要ポイント：データ型の不一致
NULL変換関数を使うとき、初心者が最もハマる罠がこれです。

> **「型」を合わせないとエラーになる！**
> `NVL(manager_id, 'なし')` と書くと、Oracleに怒られます。
> `manager_id` が **数値型** なら、変換後の値も **数値（0など）** でなければなりません。
> もし「なし」という文字列にしたいなら、`NVL(TO_CHAR(manager_id), 'なし')` のように、まず型を変換する必要があります。

### 3. 結局どれを使えばいいの？
現場での使い分けの目安は以下の通りです。

| 関数 | おすすめ度 | 選ぶ理由 |
| :--- | :--- | :--- |
| **`COALESCE`** | ★★★ | **標準SQL**なので、将来別のDB（PostgreSQL等）を使う際もそのまま役立つ。 |
| **`NVL`** | ★★★ | 記述が一番短くて済む。Oracleエンジニアの間では「共通言語」。 |
| **`CASE`** | ★★☆ | 複雑なロジックが混ざる時に、誰が見ても分かりやすい。 |
| **`DECODE`** | ★☆☆ | 昔のシステム（レガシーシステム）の保守ではよく見かける。 |

### 4. 実行結果の確認
期待する結果を見ると、本来はマネージャーがいないはずの `Department_id` 120番以降に、しっかり「0」という数字が入っていますね。
これで、この結果をそのままExcelに貼り付けて合計計算などをしても、エラーにならずに処理できるようになります。

```sql
    income_level,
    -- 1番目の項目（レベル記号など）
    TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 1)) AS rank,
    -- 2番目の項目（下限値など）
    CASE
        WHEN ( REGEXP_LIKE ( income_level,
                             'Below' ) ) THEN
            '<'
        WHEN ( REGEXP_LIKE ( income_level,
                             'above' ) ) THEN
            REGEXP_REPLACE(
                TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 2)),
                '[^0-9]',
                ''
            )
        ELSE
            TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 2))
    END                                               AS "LOWER",

    -- 3番目の項目（上限値など）
    CASE
        WHEN ( REGEXP_LIKE ( income_level,
                             'Below' ) ) THEN
            REGEXP_REPLACE(
                TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 2)),
                '[^0-9]',
                ''
            )
        WHEN ( REGEXP_LIKE ( income_level,
                             'above' ) ) THEN
            '>='
        ELSE
            TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 3))
    END                                               AS "UPPER"
FROM
    oe.customers
WHERE customer_id BETWEEN  150 AND 159
```

## 解説
この問題は、不規則な形式で保存されている文字列から、**正規表現（Regular Expression）** を駆使して特定のパターンを抜き出す、非常に高度なデータ加工技術を求めています。
実務でも「自由入力に近い備考欄から数値だけ抜き出す」といった場面で、このスキルは「魔法」のように役立ちます。

### 1. 文法解説：Oracleの正規表現関数
今回の解答例では、Oracleが提供する強力な3つの正規表現関数が「三種の神器」として使われています。


#### ① REGEXP_SUBSTR
指定したパターンに一致する「部分文字列」を切り出します。
* **`'[^:-]+'` の意味**:
    * `[^ ... ]` は「～以外の文字」という意味です。
    * つまり「**コロン(`:`)でもハイフン(`-`)でもない文字**が1つ以上続く塊」を探しています。
* **`1, n`**: 1文字目から探し始めて、**n番目**に見つかった塊を取得します。これで「記号で区切られたパーツ」を順番に指定できるわけです。

#### ② REGEXP_LIKE
`LIKE` 演算子の進化版です。
* **`REGEXP_LIKE(income_level, 'Below')`**: 文字列の中に「Below」というパターンが含まれているかどうかを真偽値で返します。`CASE`式の条件分岐のトリガーとして非常に優秀です。

#### ③ REGEXP_REPLACE
パターンに一致する部分を別の文字（または空）に置き換えます。
* **`'[^0-9]'` の意味**: 「**数字以外**」のすべての文字を指します。
* これを `''`（空文字）に置換することで、「Below 30,000」から「30000」だけを抽出する、といった**数値抽出**を実現しています。


### 2. カラム別：ロジックの徹底解剖
このクエリがどうやって複雑な条件をさばいているか、整理しましょう。

#### ① RANK（一番左のパーツ）
```sql
TRIM(REGEXP_SUBSTR(income_level, '[^:-]+', 1, 1))
```
単純に、最初の区切り記号（`:`）の前にある文字を抜き出して空白を消すだけなので、ここはシンプルです。

#### ② LOWER（下限値）
`CASE`式を使って3パターンを切り分けています。
* **パターン「Below X」**: `REGEXP_LIKE`で「Below」を検知し、固定文字 **`<`** を表示。
* **パターン「X and above」**: `REGEXP_REPLACE`で「and above」やカンマなどの「数字以外」をすべて除去し、純粋な数値だけを残す。
* **通常形式**: 2番目の塊（数値）をそのまま取得。

#### ③ UPPER（上限値）
* **パターン「Below X」**: LOWERと同様に数字以外を除去して **数値** を表示。
* **パターン「X and above」**: 固定文字 **`>=`** を表示。
* **通常形式**: 3番目の塊（数値）を取得。

### 3. SUBSTRとの違い
今回のように「数値の桁数がバラバラ（30,000だったり300,000だったり）」で「特定の単語（Belowなど）が混ざる」場合、通常の関数だと `CASE` 式や位置計算が何重にもなり、非常に読みづらいコードになってしまいます。
**「パターンの共通項を見つけ出し、正規表現でスマートに表現する」**
これができるかどうかが、初級者と上級者を分ける大きな壁です。

> **実務でのアドバイス**
> 正規表現は非常に強力ですが、処理速度は通常の `SUBSTR` よりも少しだけ遅くなります。数百万件のデータをミリ秒単位で処理するような場面では注意が必要ですが、今回のようなレポート作成やデータ移行の場面では、この「可読性の高い（読みやすい）正規表現」こそが正義です。

# 【完全版】問題5-11：文字列のマスキング（シーザー暗号風の変換）

### 難易度：★★★☆☆ (Lv.3)

## 問題
ERスキーマの`EMPLOYEE`テーブルより、`DEPARTMENT_ID`が100の従業員を対象に、`FIRST_NAME`、`LAST_NAME`、`EMAIL`、`PHONE_NUMBER`を取得してください。

ただし、取得する際には以下のルールに従って**マスキング**を施してください。

* 対象カラムの**先頭3文字**がアルファベットまたは数字の場合、その3文字をそれぞれ**2文字分後ろにずらす**。
* 2文字ずらした際、アルファベット（z/Z）や数字（9）の最後を超える場合は、**先頭（a/A/0）に戻る**。
* （例1）**aBz**D → **cDb**D
* （例2）**089**123 → **201**123

## 期待する結果
| EMPLOYEE_ID | FIRST_NAME  | LAST_NAME | EMAIL    | PHONE_NUMBER   | 
| ----------- | ----------- | --------- | -------- | -------------- | 
| 108         | Pcpcy       | Itwenberg | PITUENBE | 3.715.555.0108 | 
| 109         | Fcpiel      | Hcxiet    | FHCVIET  | 3.715.555.0109 | 
| 110         | Lqjn        | Ejgn      | LEJEN    | 3.715.555.0110 | 
| 111         | Kuoael      | Uekarra   | KUEIARRA | 3.715.555.0111 | 
| 112         | Lque Manuel | Wtoan     | LOWRMAN  | 3.715.555.0112 | 
| 113         | Nwks        | Rqrp      | NRQPP    | 3.715.555.0113 | 

## 解答例
```sql
WITH
    FUNCTION masking_value (
        p_value IN VARCHAR2
    ) RETURN VARCHAR2
        DETERMINISTIC
    IS
    BEGIN
        RETURN
            CASE
                WHEN REGEXP_LIKE ( SUBSTR(p_value, 1, 3),
                                   '[a-zA-Z0-9]' )THEN
                    TRANSLATE(
                        SUBSTR(p_value, 1, 3),
                        'abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789',
                        'cdefghijklmnopqrstuvwxyzabCDEFGHIJKLMNOPQRSTUVWXYZAB2345678901'
                    )
                    || SUBSTR(p_value,
                              4,
                              LENGTH(p_value))
                ELSE
                    p_value
            END;
    END;

SELECT
    employee_id,
    masking_value(first_name)   AS first_name,
    masking_value(last_name)    AS last_name,
    masking_value(email)        AS email,
    masking_value(phone_number) AS phone_number
FROM
    hr.employees
WHERE
    department_id = 100
```

## 解説
これは単なる文字列操作の域を超えて、**「シーザー暗号（シフト暗号）」** のようなロジックをSQLの中に組み込む、非常に実践的かつ高度な問題です。
特に、Oracle 12c R1から導入された **「WITH句内での関数定義（PL/SQL関数）」** を使っている点が、プロレベルのテクニックと言えます。

### 1. 文法解説：WITH句での関数定義（PL/SQL）
通常、関数はデータベースに「CREATE FUNCTION」して保存しますが、このクエリではSQL実行の間だけ有効な **「使い捨て関数」** を定義しています。

```sql
WITH
    FUNCTION masking_value ( p_value IN VARCHAR2 ) RETURN VARCHAR2 ...
SELECT ...
```

#### ① なぜこれを使うのか？
* **再利用性**: 今回のように `first_name` や `email` など、**複数のカラムに全く同じ複雑なロジック**を適用したい場合、SQL本体がスッキリします。
* **メンテナンス性**: ロジックを一箇所にまとめられるため、「3文字ではなく4文字にしたい」といった変更にも即座に対応できます。
* **権限の問題**: 開発環境などで、永久的な関数を作成する権限がない場合でも、この方法なら実行可能です。

### 2. ロジックの核心：TRANSLATEによる「ずらし」

この問題のメインエンジンは、問題5-4でも登場した **`TRANSLATE` 関数** です。

```sql
TRANSLATE(
    SUBSTR(p_value, 1, 3),
    'abcdef...xyz...012...89',  -- 元の並び
    'cdefgh...zab...234...01'   -- 2文字ずらした並び
)
```

#### 「先頭に戻る」仕組み
ここが「ずらし（シフト）」のポイントです。
* **アルファベット**: `'...xyz'` に対して `'...zab'` を対応させることで、`y` は `a` に、`z` は `b` にループ（ラップアラウンド）させています。
* **数字**: `'...89'` に対して `'...01'` を対応させることで、`9` の次は `1` （2つずれて `1`）になるように設計されています。


### 3. その他の重要テクニック

#### ① REGEXP_LIKE でのチェック
`SUBSTR(p_value, 1, 3)` に対して正規表現 `[a-zA-Z0-9]` を使っています。これは「先頭3文字の中に、アルファベットか数字が**少なくとも1つ含まれているか**」を判定しています。
※厳密には「3文字すべてが該当するか」を判定するにはもう少し工夫が必要ですが、今回の実データ（名前や電話番号）を扱う上では十分なガードレールとして機能しています。

#### ② DETERMINISTIC キーワード
関数定義にある `DETERMINISTIC` は、「同じ入力値に対しては、必ず同じ結果を返す」ことをデータベースに伝えます。
* **メリット**: これを付けると、Oracleが結果をキャッシュしてくれるため、大量のデータを処理する際に**劇的にパフォーマンスが向上**します（同じ「Steven」という名前が100人いても、計算は1回で済みます）。


### 4. 期待する結果の読み解き

結果セットを見ると、面白い変化が起きています。

* **FIRST_NAME**: `Nancy` (108番) → `N`が2つずれて `P`、`a`が2つずれて `c`、`n`が2つずれて `p`。結果、`Pcpcy`。
* **PHONE_NUMBER**: `1.515...` → `1`がずれて `3`、`.`（記号）は `TRANSLATE` のリストにないのでそのまま。結果、`3.715...`（※解答例のリストではなぜか `3.7` になっていますが、ロジック上は `1` が `3` になる動きが正解です）。
  
> **実務でのセキュリティ**
> このような「可逆的（ルールを知っていれば戻せる）」なマスキングは、開発環境で本番に近いデータを使ってテストしたい時によく使われます。完全に隠したい場合は、一方向の「ハッシュ化」など別の手法を使います。

# 【完全版】問題5-12：文字列中の特定文字のカウント

### 難易度：★★★☆☆ (Lv.3)

## 問題
OEスキーマの`CUSTOMERS`テーブルより、メールアドレス（`CUST_EMAIL`）の中に文字列「**XI**」が1つ以上含まれるレコードを取得してください。
出力には、メールアドレス本体と、その中に「XI」がいくつ含まれているかを示すカウント数（`CNT`）を表示してください。なお、結果の表示順は問いません。

## 期待する結果
| CUST_EMAIL                             | CNT | 
| -------------------------------------- | --- | 
| Sean.Stockwell@PYRRHULOXIA.EXAMPLE.COM | 1   | 
| Mary.Collins@PYRRHULOXIA.EXAMPLE.COM   | 1   | 
| Goldie.Slater@PYRRHULOXIA.EXAMPLE.COM  | 1   | 
| Kelly.Quinlan@PYRRHULOXIA.EXAMPLE.COM  | 1   | 
| Bryan.Huston@PYRRHULOXIA.EXAMPLE.COM   | 1   | 

## 解答例
```sql:例1:LENGTH と REPLACE により算出
WITH co_num AS (
    SELECT
        cust_email,
        -- (元の長さ - 置換後の長さ) / 探したい単語の長さ
        (LENGTH(cust_email) - LENGTH(REPLACE(cust_email, 'XI', '')))/LENGTH('XI') cnt
    FROM
        oe.customers
)
SELECT
    *
FROM
    co_num
WHERE
    cnt > 0
```
```sql:例2:REGEXP_COUNTを使用
WITH co_num AS (
    SELECT
        cust_email,
        REGEXP_COUNT(cust_email, 'XI') cnt
    FROM
        oe.customers
)
SELECT
    *
FROM
    co_num
WHERE
    cnt > 0
```

## 解説
今回は、文字列の中に特定のワードが「何個含まれているか」を数えるテクニックです。

### 1. 文法解説：引き算で個数を出す「伝統的ロジック」
解答例1の考え方は、プログラミングや古いSQL環境でも使われる非常に有名なハックです。

```sql
(LENGTH(元の文字列) - LENGTH(REPLACE(元の文字列, '探したい文字', ''))) / LENGTH('探したい文字')
```

#### ① なぜこれで個数がわかるのか？
一言で言うと、**「ターゲットを消したことで、どれだけ短くなったか？」** を計算しています。

1.  **`LENGTH(cust_email)`**: 
    元のメールアドレスの文字数。
2.  **`REPLACE(cust_email, 'XI', '')`**: 
    文字列から「XI」をすべて消去した状態。
3.  **引き算**: 
    「元の長さ」から「消した後の長さ」を引くと、**消えた文字の合計数**が出ます。
4.  **割り算**: 
    「XI」は2文字なので、合計数を2で割ることで「何個のXIが消えたか（＝何個含まれていたか）」が判明します。


### 2. 文法解説：専用関数 REGEXP_COUNT
解答例2は、Oracle 11gから導入された正規表現専用の関数です。

```sql
REGEXP_COUNT( [対象], [パターン] )
```

* **メリット**: 面倒な計算式を書く必要がなく、一発で個数を返してくれます。
* **柔軟性**: 単なる文字だけでなく、「数字が何個あるか」や「大文字が何個あるか」といった複雑なパターン（正規表現）のカウントも可能です。

### 3. どちらを使うべきか？（実務での判断）

| 特徴 | 解答例1（LENGTH + REPLACE） | 解答例2（REGEXP_COUNT） |
| :--- | :--- | :--- |
| **可読性** | 初見では何をしているか分かりにくい。 | **一目で「カウントしている」と分かる。** |
| **汎用性** | 古いデータベースや他の製品（MySQL等）でも動く。 | Oracle 11g以降の専用機能。 |
| **パフォーマンス** | 文字列が非常に長い場合、こちらの方が高速な傾向がある。 | 正規表現エンジンを通すため、微差だが負荷が高い。 |


> **現代の現場では...**
> 基本的には **`REGEXP_COUNT`** を推奨します。コードが短くなることでバグが減り、他のエンジニアが読んだときに意図が即座に伝わるからです。

### 4. WITH句による「使い回し」の工夫

解答例では両方とも **`WITH` 句（共通テーブル式）** を使っていますね。

1.  まず `co_num` という仮のテーブルの中で `cnt` を計算する。
2.  その後のメインの `SELECT` で `cnt > 0` のものを絞り込む。

こうすることで、WHERE句の中で同じ長い計算式を二度書かずに済み、スッキリとした美しいクエリになっています。
