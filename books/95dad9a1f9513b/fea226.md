# 問題7-1：現在日時（DATE型）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
データベースのサーバー、またはセッションの現在日付（DATE型）を取得してください。
Oracle Databaseにおける基本的なシステム日付の取得方法を確認します。

## 期待する結果
| NOW                  | 
| -------------------- | 
| 2026-03-07T23:42:48Z | 

> 表示される値は、SQLを実行した際の日時によって変動します。

## 解答例
```sql:例1：SYSDATEで取得
SELECT
    SYSDATE AS "NOW"
FROM
    dual
```
```sql:例2：CURRENT_DATEで取得
SELECT
    CURRENT_DATE AS "NOW"
FROM
    dual
```
```sql:例3：FROM DUALを省略（23c以降）
SELECT
    SYSDATE AS "NOW"
```

## 解説
SQLにおいて日付の扱いは、売上集計や期限管理など、ビジネスロジックの要（かなめ）となります。
Oracleで現在の日時を取得する、最も基本的かつ重要な関数の違いを整理しましょう。

### 1. 文法解説：SYSDATE と CURRENT_DATE

現在の日時を返す関数には、主に以下の2つがあります。

#### ① SYSDATE（システム日付）
最も一般的に使われる関数です。
* **値のソース**: **データベースが稼働しているサーバー（OS）** の現在時刻を返します。
* **特徴**: サーバーが日本にあれば日本時間を返します。設定に依存するため、常に一定の基準で動きます。

#### ② CURRENT_DATE（セッション日付）
ユーザーごとに異なる結果を返す可能性がある関数です。
* **値のソース**: **接続しているユーザー（セッション）のタイムゾーン**における現在時刻を返します。
* **特徴**: 例えばサーバーが東京にあっても、ニューヨークから接続しているユーザーがタイムゾーンを設定していれば、ニューヨークの時刻が表示されます。

### 2. DUAL テーブルの正体
解答例で使われている `FROM dual` ですが、これはOracle特有の **「ダミーテーブル」** です。

* **なぜ必要か？**: Oracleの `SELECT` 文は、必ず `FROM` 句でテーブルを指定しなければならないというルールがあります。
* **DUALの中身**: `DUMMY` というカラムが1つ、行が1行だけ入っている特別なテーブルです。
* **使い道**: 今回のように「定数」や「関数の結果」だけを確認したいときに、計算台として利用します。

> **Oracle 23c の新機能**
> 解答例3にある通り、最新の **Oracle Database 23c** からは、ついに `FROM dual` を省略できるようになりました！他のデータベース（PostgreSQLやSQL Serverなど）の書き方に近づき、よりシンプルに記述できるようになっています。

### 3. 実務での注意点：DATE型は「時刻」も持っている
期待する結果の形式（`2026-03-07T23:42:48Z`）からも分かる通り、Oracleの **DATE型は日付だけでなく「秒」までの時刻情報も含んでいます。**

「今日の日付のデータだけ欲しい」と思って `WHERE hire_date = SYSDATE` と書いてしまうと、**時刻までぴったり一致しない限りヒットしない**というミスがよく起こります。日付だけを比較したい場合は、後ほど登場する `TRUNC` 関数で時刻を切り捨てるのが鉄則です。

# 問題7-2：現在日時（TIMESTAMP型）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
データベースのサーバー、またはセッションの現在日付（TIMESTAMP型）を取得してください。
DATE型よりも精度の高い（秒未満を含む）日時情報の取得方法を確認します。


## 期待する結果
| NOW                         | 
| --------------------------- | 
| 2026-03-07T23:57:37.027035Z | 


> 表示される値は、SQLを実行した際の日時によって変動します。

## 解答例
```sql:例1：SYSTIMESTAMPで取得
SELECT
    SYSTIMESTAMP AS "NOW"
FROM
    dual
```
```sql:例2：CURRENT_TIMESTAMPで取得
SELECT
    CURRENT_TIMESTAMP AS "NOW"
FROM
    dual
```
```sql:例3：LOCALTIMESTAMPで取得
SELECT
    LOCALTIMESTAMP AS "NOW"
FROM
    dual
```

## 解説
前回の `DATE` 型に続き、今回はさらに高精度な **`TIMESTAMP` 型**を取得する関数の解説です。
実務では「ミリ秒単位のログ記録」や「タイムゾーンをまたぐグローバルなシステム」で、この `TIMESTAMP` 系関数が必須となります。

### 1. 文法解説：3つの TIMESTAMP 関数の違い
解答例にある3つの関数は、**「どこの時間を基準にするか」** と **「タイムゾーン情報を含めるか」** という点が異なります。

| 関数名 | 基準（どこから取るか） | タイムゾーン情報 | 特徴 |
| :--- | :--- | :--- | :--- |
| **`SYSTIMESTAMP`** | データベースサーバー | **あり** | サーバーのOS時刻＋サーバーの時差を返す。 |
| **`CURRENT_TIMESTAMP`** | 接続ユーザー（セッション） | **あり** | ユーザー設定の時刻＋その時差を返す。 |
| **`LOCALTIMESTAMP`** | 接続ユーザー（セッション） | **なし** | 時刻はユーザー設定だが、時差データは持たない。 |

### 2. DATE型 vs TIMESTAMP型
「どっちを使えばいいの？」と迷うこともあるかと思いますが、大きな違いは2つです。

1.  **精度の違い**:
    * `DATE` 型は「秒」まで。
    * `TIMESTAMP` 型は **「10億分の1秒（ナノ秒）」** まで記録できます。
2.  **時差（タイムゾーン）の扱い**:
    * `DATE` 型は時差を持ちません。
    * `TIMESTAMP WITH TIME ZONE` を使えば、「それがどこの国の20時なのか」を保持できます。

### 3. 実務での使い分け

* **`SYSTIMESTAMP`**: 「サーバーにデータが書き込まれた絶対的な瞬間」を記録したい場合（更新ログ、監査トレースなど）。
* **`CURRENT_TIMESTAMP`**: 「東京のユーザーには日本時間、ロンドンのユーザーには現地時間」で現在時刻を表示・登録したいアプリの場合。
* **`LOCALTIMESTAMP`**: 時差情報は不要だが、秒以下の細かい精度（ミリ秒など）だけが欲しい場合。

> **ミリ秒が表示されない？**
> 実行環境（ツール）の設定によっては、`TIMESTAMP` を取得しても秒までしか表示されないことがあります。その場合は、後ほど学ぶ `TO_CHAR` 関数を使ってフォーマットを指定することで、`.027035` のような細かい数値までしっかり確認できるようになります。

# 問題7-3：日付のフォーマット

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマの`JOB_HISTORY`テーブルからすべてのデータを取得してください。
その際、日付型の項目である`START_DATE`と`END_DATE`を、**「YYYY-MM-DD」形式**（例：2026-05-11）の文字列に変換して表示してください。なお、結果の表示順は問いません。


## 期待する結果
| EMPLOYEE_ID | START_DATE | END_DATE   | 
| ----------- | ---------- | ---------- | 
| 102         | 2011-01-13 | 2016-07-24 | 
| 101         | 2007-09-21 | 2011-10-27 | 
| 101         | 2011-10-28 | 2015-03-15 | 
| 201         | 2014-02-17 | 2017-12-19 | 
| 114         | 2016-03-24 | 2017-12-31 | 
| 122         | 2017-01-01 | 2017-12-31 | 
| 200         | 2005-09-17 | 2011-06-17 | 
| 176         | 2016-03-24 | 2016-12-31 | 
| 176         | 2017-01-01 | 2017-12-31 | 
| 200         | 2012-07-01 | 2016-12-31 | 

## 解答例
```sql
SELECT
    employee_id,
    TO_CHAR(start_date, 'YYYY-MM-DD') AS start_date,
    TO_CHAR(end_date, 'YYYY-MM-DD')   AS end_date
FROM
    hr.job_history
```

## 解説
日付データをそのまま表示すると、データベースの設定（NLS_DATE_FORMAT）によって「07-MAY-26」だったり「26/05/07」だったりとバラバラになりがちです。
そこで登場するのが、日付を自由自在な見た目に変換する **`TO_CHAR`関数** です。これさえマスターすれば、どんなレポート作成も怖くありません！

### 1. 文法解説：TO_CHAR 関数（日付 → 文字列）
日付型（DATEやTIMESTAMP）のデータを、指定したフォーマットの「文字列」に変換します。

```sql
TO_CHAR( [日付データ], '[フォーマットマスク]' )
```

#### ① フォーマットマスクのルール
今回使用した `'YYYY-MM-DD'` の意味は以下の通りです。

| マスク | 意味 | 例（2026年5月7日の場合） |
| :--- | :--- | :--- |
| **`YYYY`** | 西暦4桁 | 2026 |
| **`MM`** | 月（2桁） | 05 |
| **`DD`** | 日（2桁） | 07 |
| **`-`** | 区切り文字 | そのまま表示される |


### 2. よく使うフォーマットのバリエーション
実務でよくリクエストされる「型」をいくつか紹介します。

* **日本でおなじみの形式**: `'YYYY/MM/DD'` → `2026/05/07`
* **時刻まで含める**: `'YYYY-MM-DD HH24:MI:SS'` → `2026-05-07 15:30:45`
* **年月のみ**: `'YYYYMM'` → `202605`
* **曜日を入れる**: `'YYYY-MM-DD (DY)'` → `2026-05-07 (木)` ※言語設定に依存します

### 3. なぜ SQL 側でフォーマットするのか？
「アプリ側のプログラムで整形すればいいのでは？」と思うかもしれませんが、SQL側でやるメリットは大きいです。

1.  **データの統一感**: どのツールで出力しても、期待通りの形式（ハイフン区切りなど）でデータが出てくる。
2.  **グループ化に便利**: `TO_CHAR(hire_date, 'YYYY')` で抽出すれば、そのまま「年別の集計」に利用できる。
3.  **そのまま CSV 出力**: Excel などで開いたとき、日付として正しく認識されやすい形式で書き出せる。

> **注意：型が変わる！**
> `TO_CHAR` を使った後のデータは、**「日付型」ではなく「文字列型」** になっています。そのため、この結果を使って「1日足す」といった日付計算をしようとするとエラーになるので注意しましょう。計算は `TO_CHAR` する前に済ませるのが鉄則です！

# 問題7-4：年、月、日の抽出

### 難易度：★★☆☆☆ (Lv.2)

## 問題

OEスキーマの`CUSTOMERS`テーブルより、**1985年生まれ**の顧客を取得し、以下のルールに従って表示してください。なお、結果の表示順は問いません。

**【編集ルール】**

* **ID**：`CUSTOMER_ID`を表示する。
* **NAME**：`CUST_FIRST_NAME`と`CUST_LAST_NAME`を半角スペースを挟んで結合する。
* **BIRTHDAY**：`DATE_OF_BIRTH`を「〇〇〇〇年〇月〇日」という形式の文字列に変換する。
* 月や日が1桁の場合、先頭の「0」は表示しないこと（例：05月→5月）。

## 期待する結果
| ID  | NAME             | BIRTHDAY      | 
| --- | ---------------- | ------------- | 
| 215 | Orson Perkins    | 1985年5月24日 | 
| 253 | Sally Bogart     | 1985年1月14日 | 
| 255 | Brooke Shepherd  | 1985年2月13日 | 
| 328 | Hannah Field     | 1985年10月6日 | 
| 838 | Alfred Nicholson | 1985年1月25日 | 
| 913 | Bob Sharif       | 1985年1月10日 | 


## 解答例
```sql:例1：TO_CHARを使用（従来のやり方）
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    TO_CHAR(date_of_birth, 'YYYY') || '年' || 
      TO_CHAR(date_of_birth,'FMMM') || '月' ||
        TO_CHAR(date_of_birth, 'FMDD') || '日' AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN TO_DATE('1985-01-01', 'YYYY-MM-DD') 
                      AND TO_DATE('1985-12-31', 'YYYY-MM-DD')
ORDER BY
    id
```
```sql:例2：TO_CHARを使用（スマートなやり方）
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    TO_CHAR(date_of_birth, 'YYYY"年"FMMM"月"DD"日"') AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN TO_DATE('1985-01-01', 'YYYY-MM-DD') 
                      AND TO_DATE('1985-12-31', 'YYYY-MM-DD')
ORDER BY
    id
```
```sql:例3：EXTRACTを使用
SELECT
    customer_id       AS id,
    cust_first_name || ' ' || cust_last_name AS NAME,
    EXTRACT(YEAR FROM date_of_birth) || '年' || 
      EXTRACT(MONTH FROM date_of_birth) || '月' ||
        EXTRACT(DAY FROM date_of_birth) || '日' AS BIRTHDAY
FROM
    oe.customers
WHERE
    date_of_birth BETWEEN date'1985-01-01' 
                      AND date'1985-12-31'
ORDER BY
    id
```


## 解説
日付データを扱う上で避けては通れない「年・月・日の個別抽出」と「日本語フォーマットへの整形」です。解答例には、実務で役立つ3つのアプローチが示されています。
特に **「01月」を「1月」と表示させるテクニック** など、細かいこだわりが詰まった問題です。

### 1. 文法解説：TO_CHAR関数の「FM」と「" "」
解答例2は、Oracleの `TO_CHAR` 関数の機能をフル活用した最もスマートな書き方です。

#### ① FM (Fill Mode) モディファイア
通常、`MM` や `DD` は「01」「05」のように2桁で表示されます（先頭ゼロ埋め）。これを「1」「5」のように数字だけ表示したい場合は、先頭に **`FM`** を付けます。
* **`TO_CHAR(date, 'MM')`** → 05
* **`TO_CHAR(date, 'FMMM')`** → 5

#### ② フォーマット内での文字列（" "）
`TO_CHAR` のフォーマットマスクの中で、「年」や「月」といった特定の文字をそのまま表示させたい場合は、その文字を **`" "`（ダブルクォーテーション）** で囲みます。
これを使えば、例1のように `||` で結合しなくても一発で整形が可能です。


### 2. 文法解説：EXTRACT 関数
解答例3で使われている `EXTRACT` は、日付から特定の要素を「数値型」として取り出すための標準的な関数です。

```sql
EXTRACT(YEAR FROM [日付])  -- 年を数値で取得
EXTRACT(MONTH FROM [日付]) -- 月を数値で取得
EXTRACT(DAY FROM [日付])   -- 日を数値で取得
```

* **特徴**: 結果が「数値」として返ってくるため、そのまま「1月」と表示されます（先頭に0がつきません）。
* **メリット**: 数値として計算（例：誕生月が偶数か判定など）に使う場合に非常に便利です。

### 3. 日付定数（Date Literals）の活用
解答例3のWHERE句に注目してください。

```sql
WHERE date_of_birth BETWEEN date'1985-01-01' AND date'1985-12-31'
```

`TO_DATE` を使わずに、**`date'YYYY-MM-DD'`** と書く方法です。これは「日付リテラル」と呼ばれ、ISO標準の形式で日付を直感的に書けるため、コードの可読性が非常に高まります。

### 4. どのアプローチが最強か？
実務での使い分けを整理しましょう。

| 手法 | おすすめ度 | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **`TO_CHAR` (例2)** | ★★★ | **最強。** 1つの関数で複雑な整形が完結し、コードが最も短くなる。 | フォーマットマスクの記法（FMや" "）を覚える必要がある。 |
| **`EXTRACT` (例3)** | ★★☆ | 数値として要素を取り出せる。標準SQLに近く、他DBでも通用しやすい。 | 表示用に文字と結合する場合、記述が長くなりがち。 |
| **結合 (例1)** | ★☆☆ | 仕組みが単純で分かりやすい。 | 関数を何度も呼ぶため、冗長で効率が少し悪い。 |

> **実務での一工夫**
> 今回のように「1985年」のデータを取る場合、`TO_CHAR(date_of_birth, 'YYYY') = '1985'` と書いても正解ですが、`BETWEEN` を使うほうがデータベースの索引（インデックス）を効率よく使えるため、速度面で有利になることが多いですよ！

### 日付リテラル（ANSI日付リテラル）
**「日付リテラル（ANSI日付リテラル）」** は、`TO_DATE` 関数を使わずに、よりシンプルかつ標準的な形式で日付を指定する方法です。

結論から言うと、**「時間は不要で、決まった形式（YYYY-MM-DD）で書きたい時」** に非常に便利です。

### 日付リテラルの書き方

構文は非常にシンプルです。

```sql
DATE 'YYYY-MM-DD'
```

#### 具体的な例

```sql
-- TO_DATEを使う場合
SELECT * FROM orders WHERE order_date >= TO_DATE('2024-01-01', 'YYYY-MM-DD');

-- 日付リテラルを使う場合
SELECT * FROM orders WHERE order_date >= DATE '2024-01-01';
```
<br>
### DATEリテラルの特徴と注意点
`TO_DATE` と比較して、いくつか守らなければならないルールがあります。
<br>
#### 1. フォーマットは「YYYY-MM-DD」固定

日付リテラルを使う場合、フォーマットを自由に変えることはできません。必ず **西暦4桁-月2桁-日2桁** で書く必要があります。

* ⭕ `DATE '2024-03-15'`
* ❌ `DATE '2024/03/15'` （スラッシュはエラー）
* ❌ `DATE '24-03-15'` （2桁年はエラー）
<br>
#### 2. 時・分・秒を含めることはできない

`DATE` というキーワードを使いますが、日付リテラルで指定できるのは「年月日」までです。時刻（00:00:01など）を指定したい場合は、**TIMESTAMPリテラル** を使う必要があります。

```sql
-- 時刻まで指定したい場合
SELECT TIMESTAMP '2024-03-15 10:30:00' FROM DUAL;
```
<br>
#### 3. 関数ではなく「定数」として扱われる

`TO_DATE` は実行時に文字列を日付に変換する「処理」が走りますが、日付リテラルはデータベースが最初から日付として認識します。そのため、ごく僅かですがパフォーマンス的に有利な場合があります（通常は気にするほどではありません）。

<br>
### どっちを使うべき？（比較表）

| 特徴 | DATEリテラル | TO_DATE関数 |
| --- | --- | --- |
| **書きやすさ** | 短くてスッキリする | 少し長い |
| **フォーマット** | `YYYY-MM-DD` 固定 | 自由自在（スラッシュ等も可） |
| **時刻の指定** | 不可（TIMESTAMPなら可） | 可能 |
| **動的な指定** | 不向き（固定値用） | 変数やカラムを渡せる |
| **標準規格** | ANSI標準（他DBでも通じやすい） | Oracle独自 |

<br>
### 使い分けのガイドライン

* **プログラム内の固定値や、手動でサクッとクエリを投げる時**
* `DATE '2024-01-01'` がおすすめ。読みやすく、タイプ数も少ないです。
<br>
* **画面からの入力値や、特殊な形式の文字列を扱う時**
* `TO_DATE(:input_val, 'YYYY/MM/DD')` を使いましょう。

# 問題7-5：日付の加算

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、職種（`JOB_ID`）が「AD_VP」の従業員を対象として、採用日（`HIRE_DATE`）を基準に以下の日付を取得してください。

**【取得内容】**

* **HIRE_DATE**：採用日
* **HIRE_DATE + 2DAY**：採用日の2日後の日付
* **HIRE_DATE + 2MONTH**：採用日の2ヶ月後の日付
* **HIRE_DATE + 2YEAR**：採用日の2年後の日付

※すべて「YYYY-MM-DD」形式の文字列に変換して表示してください。

## 期待する結果
| EMPLOYEE_ID | NAME       | HIRE_DATE  | HIRE_DATE + 2DAY | HIRE_DATE + 2MONTH | HIRE_DATE + 2YEAR | 
| ----------- | ---------- | ---------- | ---------------- | ------------------ | ----------------- | 
| 101         | Neena Yang | 2015-09-21 | 2015-09-23       | 2015-11-21         | 2017-09-21        | 
| 102         | Lex Garcia | 2011-01-13 | 2011-01-15       | 2011-03-13         | 2013-01-13        |


## 解答例
```sql
SELECT
    employee_id,
    first_name || ' ' || last_name as name,
    TO_CHAR(hire_date, 'YYYY-MM-DD')                   AS "HIRE_DATE",
    TO_CHAR(hire_date + 2, 'YYYY-MM-DD')               AS "HIRE_DATE + 2DAY",
    TO_CHAR(ADD_MONTHS(hire_date, 2), 'YYYY-MM-DD')    AS "HIRE_DATE + 2MONTH",
    TO_CHAR(ADD_MONTHS(hire_date, 2*12), 'YYYY-MM-DD') AS "HIRE_DATE + 2YEAR"
FROM
    hr.employees
WHERE
    job_id = 'AD_VP';
```

## 解説
いよいよ日付の「計算」ですね。Oracle SQLにおいて日付は単なるデータではなく、数値のように足したり引いたりできる便利な存在です。
今回のポイントは、**「単位（日・月・年）によって計算方法が異なる」** という点です。ここを整理すると、日付操作のマスターに大きく近づきます。


### 1. 文法解説：単位ごとの加算ルール

#### ① 「日」の加算：もっともシンプル
OracleのDATE型は内部的に数値として扱われており、**「1 = 1日」** を意味します。そのため、日数を足したいときは単に算術演算子（`+`）を使うだけです。
* **`hire_date + 2`** → 2日後
* **`hire_date - 1`** → 1日前（昨日）

### ② 「月」の加算：ADD_MONTHS 関数
月を足す場合は、単純に「+ 30」とはいきません。月によって30日だったり31日だったり、はたまた2月は28日だったりするからです。そこで、**`ADD_MONTHS`** 関数を使います。

```sql
ADD_MONTHS( [日付], [足したい月数] )
```
* **賢いポイント**: 月末（例：1月31日）に1ヶ月足すと、正しく「2月28日（または29日）」を返してくれるなど、カレンダーの不規則性を自動で吸収してくれます。

### ③ 「年」の加算：月の応用
「2年後」を求める専用の関数は（実は）ありません。そのため、**「1年 = 12ヶ月」** というルールを利用して、`ADD_MONTHS` で計算するのが一般的です。
* **`ADD_MONTHS(hire_date, 2 * 12)`** → 24ヶ月後 ＝ 2年後


### 2. 知っておくと得する「INTERVAL」定数
解答例のやり方は非常に「Oracleらしい」伝統的な書き方ですが、最近の実務（特に他DBへの移行も考慮する場合）では、より英語に近い表現の **`INTERVAL`** を使うことも増えています。

```sql
-- こう書くこともできます
hire_date + INTERVAL '2' DAY    -- 2日後
hire_date + INTERVAL '2' MONTH  -- 2ヶ月後
hire_date + INTERVAL '2' YEAR   -- 2年後
```
※ただし、`INTERVAL` は「1月31日の1ヶ月後」などを計算しようとするとエラーを出す場合があるなど、挙動がシビアです。まずは解答例の **`ADD_MONTHS`** を使いこなせるようになるのが上達の近道です！

### 3. 実務での活用シーン
* **期限管理**: `shipping_date + 3` （発送から3日後を到着予定日にする）
* **契約更新**: `ADD_MONTHS(contract_date, 12)` （1年後の更新日を算出する）
* **年齢計算**: 誕生日と現在の日付を `ADD_MONTHS` を使って比較する


> **TO_CHAR を忘れずに！**
> 解答例のように、計算した結果を最後に `TO_CHAR` で整形してあげると、レポートとして完璧な見た目になります。計算を先に済ませてから、最後に「お化粧（整形）」をするのがSQLの基本順序です。

# 問題7-6：期間の算出

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`JOB_HISTORY`テーブルより、各職務の開始日（`START_DATE`）から終了日（`END_DATE`）までの期間を算出し、「〇年〇ヶ月」という形式で取得してください。なお、結果の表示順は問いません。

**【算出のヒント】**

* 2つの日付間の月数を求めるには `MONTHS_BETWEEN` 関数を使用します。
* 月数を12で割った商を「年」、12で割った余りを「ヶ月」として算出してください。
* 月数の端数は切り捨てて計算してください。

## 期待する結果
| EMPLOYEE_ID | JOB_ID     | 期間      | 
| ----------- | ---------- | --------- | 
| 102         | IT_PROG    | 5年6ヶ月  | 
| 101         | AC_ACCOUNT | 4年1ヶ月  | 
| 101         | AC_MGR     | 3年4ヶ月  | 
| 201         | MK_REP     | 3年10ヶ月 | 
| 114         | ST_CLERK   | 1年9ヶ月  | 
| 122         | ST_CLERK   | 0年11ヶ月 | 
| 200         | AD_ASST    | 5年9ヶ月  | 
| 176         | SA_REP     | 0年9ヶ月  | 
| 176         | SA_MAN     | 0年11ヶ月 | 
| 200         | AC_ACCOUNT | 4年5ヶ月  | 

## 解答例
```sql
SELECT
    employee_id,
    job_id,
    TRUNC(MONTHS_BETWEEN(end_date, start_date) / 12) || '年' || 
      MOD(TRUNC(MONTHS_BETWEEN(end_date, start_date)), 12) || 'ヶ月' 
                                                           AS "期間"
FROM
    hr.job_history
```

## 解説
今回は日付の「差」を求める計算です。単に「何日間」を出すのは簡単ですが、「○年○ヶ月」という形式にするには、算数の「割り算」と「余り」の考え方をSQLで表現するパズル的なテクニックが必要になります。

### 1. 文法解説：MONTHS_BETWEEN 関数
日付同士の期間を計算する際、もっとも強力な味方が **`MONTHS_BETWEEN`** です。

```sql
MONTHS_BETWEEN( [後の日付], [前の日付] )
```

* **戻り値**: 2つの日付の間の**月数**を数値で返します。
* **特徴**: 31日の月も30日の月も考慮して「1.5ヶ月」のように小数点を含めて正確に算出してくれます。


### 2. ロジックの解剖：どうやって「年」と「ヶ月」に分けるか？
解答例の計算式を、102番の従業員（5年6ヶ月）を例に分解してみましょう。
まず、`MONTHS_BETWEEN` の結果が仮に **66.5ヶ月** だったとします。

#### ① 「年」を出す
1年は12ヶ月なので、全体の月数を12で割り、小数点以下を切り捨てます。
$$\text{TRUNC}(66.5 / 12) = \text{TRUNC}(5.541\dots) \rightarrow \mathbf{5}$$

#### ② 「ヶ月」を出す
「年」として計算しきれなかった「余りの月数」を求めます。
ここで便利なのが、余りを計算する **`MOD` 関数** です。
$$\text{MOD}(\text{TRUNC}(66.5), 12) \rightarrow 66 \div 12 = 5 \text{ 余り } \mathbf{6}$$

> **なぜ2回も TRUNC が必要なのか？**
> `MONTHS_BETWEEN` は「30.5」のように端数を返すことがあります。そのまま `MOD` に入れると「余り 6.5」になってしまうため、一度 `TRUNC` で「整数（月数）」に丸めてから、12で割った余り（0〜11ヶ月）を出すのがポイントです。

### 3. 実務での活用シーン
この計算は、人事システムや顧客管理システムで非常に重宝します。

* **勤続年数**: 「入社から現在まで、何年何ヶ月働いているか」
* **ローン・分割払い**: 「支払い開始から現在まで、何年何ヶ月経過したか」
* **年齢計算**: 誕生月を考慮した厳密な年齢表示。

### 4. 実行結果の確認
期待する結果を見ると、122番の従業員のように「0年11ヶ月」と表示されています。
もし `TRUNC(... / 12)` をせずに `MONTHS_BETWEEN` だけを使っていたら、人間には直感的に分かりにくい「0.916...年」のような数値になってしまいます。

このように、**「DBが計算しやすい値（月数）」を「人間が理解しやすい形式（年・月）」へ変換する** スキルは、レポート作成の現場で非常に高く評価されます！

# 問題7-8：日時の範囲指定

### 難易度：★★☆☆☆ (Lv.2)

## 問題

COスキーマの`ORDERS`テーブルより、注文日時（`ORDER_TMS`）が**2021年6月**であるデータを取得してください。
ただし、対象とする顧客は`CUSTOMER_ID`が350から359までの範囲に該当するレコードに限定します。なお、結果の表示順は問いません。

**【ポイント】**

* `TIMESTAMP`リテラルを使用して範囲を指定してください。
* 索引を効率的に使用するため、列側（`ORDER_TMS`）に関数（`TO_CHAR`など）を適用せず、比較演算子（`>=` および `<`）を用いた条件式を作成してください。


## 期待する結果
| CUSTOMER_ID | ORDER_TMS                   | 
| ----------- | --------------------------- | 
| 351         | 2021-06-03T16:04:46.024146Z | 
| 354         | 2021-06-08T04:17:12.071275Z | 
| 350         | 2021-06-13T18:10:25.420066Z | 
| 352         | 2021-06-30T18:09:40.698324Z | 

## 解答例
```sql
SELECT
    customer_id,
    order_tms
FROM
    co.orders
WHERE
    customer_id BETWEEN 350 AND 359
    AND order_tms >= TIMESTAMP '2021-06-01 00:00:00'
    AND order_tms  < TIMESTAMP '2021-07-01 00:00:00'
```

## 解説
今回は、大量のデータの中から特定の「期間」を、**データベースに負荷をかけず、かつ正確に** 抜き出すための実践的なテクニックですね。
一見シンプルですが、この書き方にはエンジニアの「現場の知恵」が詰まっています。

### 1. 核心：なぜ「BETWEEN」ではなく「>=」と「<」なのか？
日付やタイムスタンプの範囲指定で、最も間違いが少なく、かつ推奨されるのがこの **「以上・未満」** の組み合わせです。

#### ① 0.000001秒の漏れも許さない
もし、`BETWEEN '2021-06-01' AND '2021-06-30'` と書いてしまうと、**「6月30日の 00:00:00」** までのデータしか取れず、それ以降（18:00など）のデータがすべて漏れてしまいます。

かといって、`AND '2021-06-30 23:59:59'` と書くのも危険です。`TIMESTAMP`型はミリ秒やナノ秒単位まで保持しているため、その「最後の1秒」の中にデータが存在する可能性があるからです。

> **「翌月の1日 0時 未満」と指定する**
> こうすることで、6月30日のギリギリ最後の瞬間までを完璧に、漏れなくカバーすることができます。これがプロの書き方です。

### 2. 文法解説：TIMESTAMPリテラル

解答例で使用されている `TIMESTAMP 'YYYY-MM-DD HH24:MI:SS'` という書き方は、**TIMESTAMPリテラル**と呼ばれます。

* **メリット**: `TO_TIMESTAMP` 関数を使わずに、文字列を直接タイムスタンプ型として認識させることができます。
* **記述の簡潔さ**: 余計な関数を挟まないため、クエリが非常に読みやすくなります。


### 3. 実務での重要ポイント：インデックス・フレンドリー

「6月のデータが欲しいなら、`WHERE TO_CHAR(order_tms, 'YYYYMM') = '202106'` でもいいのでは？」と思うかもしれません。
たしかに結果は同じになりますが、実務（特に数千万件のデータがある場合）では**NG**とされることが多いです。

#### なぜ TO_CHAR はダメなのか？
カラムを関数（`TO_CHAR`など）で加工してしまうと、そのカラムに貼られた**索引（インデックス）が使えなくなる**からです。

* **関数を使う場合**: 全行を一度文字に変換してから比較するため、非常に時間がかかります。
* **範囲指定（解答例）**: インデックスを使って、対象の期間まで一気にジャンプできるため、**圧倒的に高速**です。

### 4. 期待する結果の確認
期待する結果を見ると、6月3日、8日、13日、30日と、しっかり1ヶ月分のデータが取得できています。特に30日の `18:09:40...` というデータは、もし「30日の0時まで」という指定ミスをしていたら消えていたはずのデータです。

この「以上・未満」のセットは、日付だけでなく数値の範囲指定などでも役立つ一生モノのスキルです！

```sql
    TO_CHAR(TRUNC(hire_date),      'YYYY-MM-DD') AS "その日(秒以下切り捨て)",
    TO_CHAR(TRUNC(hire_date,'MM'), 'YYYY-MM-DD') AS "その月の初日",
    TO_CHAR(TRUNC(hire_date,'YY'), 'YYYY-MM-DD') AS "その年の初日",
    TO_CHAR(TRUNC(hire_date, 'Q'), 'YYYY-MM-DD') AS "その四半期の初日",
    TO_CHAR(TRUNC(hire_date,'IW'), 'YYYY-MM-DD') AS "その週の月曜日"
FROM
    hr.employees
WHERE
    employee_id < 110
```

## 解説
今回は、日付データを意図した単位で「丸める」ための最重要関数、**`TRUNC`（トランク）関数**の解説です。
「今月分の売上だけ集計したい」「週ごとのレポートを作りたい」といった実務の現場では、この関数が八面六臂の活躍を見せます。

### 1. 文法解説：TRUNC 関数（日付）
`TRUNC` 関数は、指定した「書式モデル」に基づいて、それ以下の単位をすべて切り捨てます。

```sql
TRUNC( [日付データ], '[書式モデル]' )
```

#### ① 書式モデルと切り捨てのルール
引数を変えるだけで、自由自在に「基準日」を作り出すことができます。

| 書式モデル | 切り捨ての単位 | 結果 |
| :--- | :--- | :--- |
| **（なし）** | 時刻（時・分・秒） | その日の **00:00:00** になる |
| **`'MM'`** | 日 | その月の **1日** になる |
| **`'Q'`** | 月・日 | その **四半期の初日** (1, 4, 7, 10月の1日) になる |
| **`'YY'`** | 月・日 | その年の **1月1日** になる |
| **`'IW'`** | 日 | その週の **月曜日** (ISO週基準) になる |


### 2. ここがポイント：なぜ TRUNC が必要なのか？
Oracleの `DATE` 型は、目に見えていなくても内部的に必ず「時・分・秒」を持っています。

* **問題点**: `2013-06-17 15:30:00` と `2013-06-17 00:00:00` は、人間には同じ日に見えますが、SQLの比較（`=`）では「一致しない」と判定されてしまいます。
* **解決策**: `TRUNC` を使うことで、すべてのデータの時刻を強制的に `00:00:00` に揃えることができます。これにより、日付単位での正しい比較やグループ化（`GROUP BY`）が可能になるのです。

### 3. 実務での活用シーン：レポート作成の裏技
#### ① 週報・月報の作成
「月別の売上合計」を出したいときは、`GROUP BY TRUNC(order_date, 'MM')` と書くだけで、1ヶ月分のデータがすべて「その月の1日」というラベルでひとまとめになります。

#### ② 「今週の月曜日」を求める
`TRUNC(SYSDATE, 'IW')` を使えば、今日が何曜日であっても、システムが自動的に「今週の月曜日」を特定してくれます。

### 4. 実行結果の確認
期待する結果の103番（2016-01-03）を見てみましょう。
* **その月の初日**: 1月1日
* **その週の月曜日**: **2015-12-28**
1月3日は日曜日なので、その週の始まりである前の年の12月28日（月曜日）までしっかり遡って計算されていますね。これが `IW` モデルの賢いところです。

> **TO_CHAR との組み合わせ**
> 解答例では `TO_CHAR(TRUNC(...))` と入れ子にしています。これは、`TRUNC` で計算した「日付型」のデータを、最終的に人間が見やすい「文字列」として表示するための、実務でよく使われるコンビネーションです。

# 問題7-10：月末の算出

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、`EMPLOYEE_ID`が105以下の従業員を対象として、以下の値を計算してください。なお、結果の表示順は問いません。

**【取得内容】**

* **NAME**：`FIRST_NAME`と`LAST_NAME`を半角スペースで結合。
* **HIRE_DATE**：採用日。
* **MONTH_END**：採用日の**属する月の末日**。
* **DAYS_REMAINING**：採用日から数えて、**その月が残り何日あったか**（末日 - 採用日）。

※日付はすべて「YYYY-MM-DD」形式の文字列に変換して表示してください。

## 期待する結果
| EMPLOYEE_ID | NAME            | HIRE_DATE  | MONTH_END  | DAYS_REMAINING | 
| ----------- | --------------- | ---------- | ---------- | -------------- | 
| 100         | Steven King     | 2013-06-17 | 2013-06-30 | 13             | 
| 101         | Neena Yang      | 2015-09-21 | 2015-09-30 | 9              | 
| 102         | Lex Garcia      | 2011-01-13 | 2011-01-31 | 18             | 
| 103         | Alexander James | 2016-01-03 | 2016-01-31 | 28             | 
| 104         | Bruce Miller    | 2017-05-21 | 2017-05-31 | 10             | 
| 105         | David Williams  | 2015-06-25 | 2015-06-30 | 5              | 


## 解答例
```sql
SELECT
    employee_id,
    first_name || ' ' || last_name AS name,
    TO_CHAR(hire_date, 'YYYY-MM-DD') AS hire_date,
    TO_CHAR(LAST_DAY(hire_date), 'YYYY-MM-DD') AS month_end,
    LAST_DAY(hire_date) - hire_date AS days_remaining
FROM
    hr.employees
WHERE
    employee_id <= 105
```

## 解説
今回は「月末の算出」についてです。
この問題は、Oracle SQLの強力な日付関数である`LAST_DAY`の活用と、**日付同士の算術演算**をマスターします。

### 1. クエリーの解説：日付の「境界線」を操る
このクエリーは、システムが保持している「採用日」という点から、その月という「枠組み」の終点を見つけ出し、残りの期間を算出するロジックを組み立てています。

#### クエリーの特徴
* **動的な月末の特定：** 2月（うるう年含む）や31日まである月など、月によって異なる末日を関数一つで自動判定しています。
* **日付の引き算：** Oracleにおける「日付 - 日付」の結果が「日数（数値）」になる特性を利用して、残りの日数を算出しています。
* **表示の統一：** 計算後の日付データを `TO_CHAR` で整形し、レポートとしての可読性を高めています。

### ポイント

1. **`LAST_DAY` 関数の魔法：** 引数として渡された日付が「何月か」を判断し、その月の最終日の日付を返します。
2. **残日数の計算：** `LAST_DAY(hire_date) - hire_date` の部分です。
* 例えば、末日が31日で採用日が20日の場合、結果は `11` となります。


3. **結合とフォーマット：** 文字列結合 `||` と、日付書式 `'YYYY-MM-DD'` の指定により、期待される結果通りの外見を作っています。

### 2. 文法解説：キーとなる関数とルール

#### **LAST_DAY(date)**：月末を取得する
指定した日付が含まれる月の、最終日の日付を返す関数です。

* **特徴：** うるう年の2月29日なども自動的に計算してくれるため、自前でカレンダーロジックを書く必要がありません。
* **戻り値：** `DATE` 型です。

#### **日付の算術演算**：日数計算のルール

Oracle SQLでは、日付型に対して足し算や引き算が可能です。

* **日付 - 日付 = 数値（日数）**：
この問題のコアです。二つの日付の間に何日の差があるかを「整数」で返します。
* **日付 + 数値 = 日付**：
「3日後」などを求めたい場合に使います。

#### **TO_CHAR(date, 'format')**：文字列への変換

日付型のデータをそのまま表示すると、データベースの設定（NLS_DATE_FORMAT）に依存した形式で表示されてしまいます。

> **「見た目」は最後に整える**
> 計算処理（`LAST_DAY - hire_date`）は `DATE` 型のままで行い、表示用の列だけを `TO_CHAR` で囲むのが正解です。計算する前に `TO_CHAR` で文字列にしてしまうと、引き算ができなくなるので注意しましょう。

### ワンポイント・アドバイス
実務では、今回のように「その月の残り日数」を出す処理は、「月額料金の日割り計算」**や**「月末締め処理の判定ロジック」などで非常によく使われます。

> `LAST_DAY(hire_date) - hire_date`

# 問題7-11：時差の壁を超える（タイムゾーン変換）

### 難易度：★★★☆☆ (Lv.3)

## 問題
グローバルに展開するECサイト（OEスキーマ）では、注文日時がタイムゾーン付きの形式（`TIMESTAMP WITH LOCAL TIME ZONE`）で管理されています。
本社の監査レポートを作成するにあたり、各地域のユーザー環境で入力された注文日時を、明示的に「ロンドン時間（Europe/London）」**と**「日本時間（Asia/Tokyo）」に統一して並列で確認する必要があります。データの国際化（I18N）に対応する必須テクニックを学びます。

`OE.ORDERS` テーブルより、顧客ID（`CUSTOMER_ID`）が `101` のレコードを対象として、注文日時（`ORDER_DATE`）を以下の3つの形式で出力してください。なお、結果の表示順は問いません。

1. **セッション時間**：元の `ORDER_DATE` をそのまま表示
2. **ロンドン時間**：`ORDER_DATE` を `Europe/London` タイムゾーンに変換して表示
3. **日本時間**：`ORDER_DATE` を `Asia/Tokyo` タイムゾーンに変換して表示

## 期待する結果
| ORDER_ID | セッション時間      | ロンドン時間                      | 日本時間                       | 
| -------- | ------------------- | --------------------------------- | ------------------------------ | 
| 2458     | 2007-08-16 14:34:12 | 2007-08-16 15:34:12 EUROPE/LONDON | 2007-08-16 23:34:12 ASIA/TOKYO | 
| 2447     | 2008-07-27 07:59:10 | 2008-07-27 08:59:10 EUROPE/LONDON | 2008-07-27 16:59:10 ASIA/TOKYO | 
| 2413     | 2008-03-29 12:34:04 | 2008-03-29 12:34:04 EUROPE/LONDON | 2008-03-29 21:34:04 ASIA/TOKYO | 
| 2430     | 2007-10-02 05:18:36 | 2007-10-02 06:18:36 EUROPE/LONDON | 2007-10-02 14:18:36 ASIA/TOKYO |


## 解答例
```sql
SELECT
    order_id,
    TO_CHAR(order_date, 'YYYY-MM-DD HH24:MI:SS') AS "セッション時間",
    TO_CHAR(order_date AT TIME ZONE 'Europe/London', 'YYYY-MM-DD HH24:MI:SS TZR') AS "ロンドン時間",
    TO_CHAR(order_date AT TIME ZONE 'Asia/Tokyo', 'YYYY-MM-DD HH24:MI:SS TZR') AS "日本時間"
FROM
    oe.orders
WHERE
    customer_id = 101
```

## 解説
今回の課題は、グローバルシステムの開発やデータ分析において避けては通れない「タイムゾーン（時差）の変換」です。
世界中で利用されるECサイトやWebサービスでは、データが「どこの国の時間で記録されたか」を正しく扱い、レポート作成時には基準となる時間に揃える必要があります。
解答例のコードをもとに、Oracle SQLで時差をエレガントに操る **`AT TIME ZONE`** の仕組みを解説します。

### 1. スクリプトの解説：世界標準時とサマータイムの自動計算

このクエリの核心は、**`AT TIME ZONE`** 句と、それを人間が見やすい文字列に変換する **`TO_CHAR`** の組み合わせです。

#### タイムゾーン変換の基本構文

```sql
order_date AT TIME ZONE 'Asia/Tokyo'
```

この一文だけで、Oracle内部で時差の計算が自動的に行われます。
元の `order_date` のデータ型（`TIMESTAMP WITH LOCAL TIME ZONE`）が持つ絶対的な時間（UTC：世界標準時ベース）を基準に、指定した地域（'Asia/Tokyo' や 'Europe/London'）のローカル時間に時計の針を動かしてくれます。

#### サマータイム（夏時間）の自動判別

期待する結果の「ロンドン時間」に注目してみましょう。非常によくできたデータであることが分かります。

* **2007-08-16（8月）**:
「セッション時間」が `14:34:12` に対し、「ロンドン時間」は `15:34:12` と **1時間進んで** います（サマータイム適用中）。
* **2008-03-29（3月）**:
「セッション時間」が `12:34:04` に対し、「ロンドン時間」も `12:34:04` で **時差がありません**（標準時適用中）。

このように、単に「○時間足す」という固定の計算ではなく、**その日付がサマータイム期間内かどうかまでOracleが自動で判定**して変換してくれます。


### 2. 文法・テクニックのポイント

#### ① TZR フォーマットマスク
`TO_CHAR` の第2引数に含まれている **`TZR`**（Time Zone Region）がポイントです。

```sql
'YYYY-MM-DD HH24:MI:SS TZR'
```

これを出力フォーマットの末尾に入れておくことで、結果に `EUROPE/LONDON` や `ASIA/TOKYO` といった**タイムゾーンの地域名が明示的に付与**されます。これがあるだけで、会議資料や監査レポートとしての信頼性がグッと上がります。

#### ② TIMESTAMP 型の三兄弟

Oracleの日時データ型にはいくつかの種類があり、実務での使い分けが重要です。

| データ型 | 特徴 | 今回のパターンの挙動 |
| --- | --- | --- |
| **`DATE`** | 時差の概念を持たない（日本ローカルのシステム向き） | タイムゾーン変換は直接使えない。 |
| **`TIMESTAMP WITH TIME ZONE`** | データ自体に「+09:00」などの時差情報を**保持して**保存する。 | 保存された時点の時差がそのまま見える。 |
| **`TIMESTAMP WITH LOCAL TIME ZONE`** | DBにはUTCで保存され、取り出す時に**セッション（接続元）の時差に自動変換**される。 | 今回の「セッション時間」がこれ。接続環境によって見た目が変わる。 |

> 今回の `ORDER_DATE` は3つ目の `WITH LOCAL TIME ZONE` です。そのため、見る人の環境（セッション）によって「セッション時間」の初期表示は変わりますが、後ろの2つのように `AT TIME ZONE` を明示すれば、世界中どこのサーバーからクエリを叩いても**絶対に同じロンドン時間・日本時間が出力**されます。

### 3. 実務でのアドバイス：セッション自体の時間を変える技
もしレポート全体の時間をすべて日本時間に統一したい場合、すべての列に `AT TIME ZONE` を書くのは面倒です。その場合は、クエリを実行する前に**セッション自体のタイムゾーンを切り替える**という一手があります。

```sql
-- セッションのタイムゾーンを日本時間に設定
ALTER SESSION SET TIME_ZONE = 'Asia/Tokyo';

-- この後なら、普通にSELECTするだけで日本時間で表示される
SELECT order_id, order_date FROM oe.orders;
```

システム開発の実務では、JavaやPHPなどのアプリケーション側からDBに接続した直後にこの `ALTER SESSION` を発行し、ユーザーの国に合わせた時間を一発で表示させる手法がよく使われます。

# 問題7-12：支払締め日の自動計算（特定曜日の算出）

### 難易度：★★★☆☆ (Lv.3)

## 問題
HR（人事）システムにおいて、新入社員の研修完了日や配属日（`HIRE_DATE`）を起点として、社内の機材手配やアカウント発行の締め処理を行います。

HRスキーマ`EMPLOYEES` テーブルの、従業員ID（`EMPLOYEE_ID`）が `100` から `104` のメンバーを対象に、採用日（`HIRE_DATE`）と、「その採用日以降で、最初に到来する金曜日の日付」を求めてください。
ただし、入社日自体が金曜日であった場合は、その当日ではなく「翌週の金曜日」を取得してください。結果は「YYYY-MM-DD」形式の文字列で、従業員IDの昇順でソートしてください。

## 期待する結果
| EMPLOYEE_ID | FIRST_NAME | HIRE_DATE       | NEXT_FRIDAY | 
| ----------- | ---------- | --------------- | ----------- | 
| 100         | Steven     | 2013-06-17 (月) | 2013-06-21  | 
| 101         | Neena      | 2015-09-21 (月) | 2015-09-25  | 
| 102         | Lex        | 2011-01-13 (木) | 2011-01-14  | 
| 103         | Alexander  | 2016-01-03 (日) | 2016-01-08  | 
| 104         | Bruce      | 2017-05-21 (日) | 2017-05-26  | 


## 解答例
```sql
SELECT
    employee_id,
    first_name,
    TO_CHAR(hire_date, 'YYYY-MM-DD (DY)', 'NLS_DATE_LANGUAGE=JAPANESE') AS hire_date,
    TO_CHAR(NEXT_DAY(hire_date, TO_CHAR(DATE '2000-01-07', 'DAY')), 'YYYY-MM-DD') AS next_friday
FROM
    hr.employees
WHERE
    employee_id BETWEEN 100 AND 104
ORDER BY
    employee_id
```

## 解説
今回の課題は、実務の「支払処理」や「タスクスケジュール管理」で頻繁に登場する「特定曜日の自動算出」です。
カレンダーのロジックをSQLで扱う際、最も恐ろしいのが「サーバーの言語設定（NLS設定）によってクエリが動かなくなるバグ」です。解答例のコードは、その罠を美しく回避するプロのテクニックが盛り込まれています。ポイントを絞って解説します。

### 1. スクリプトの解説：NEXT_DAY関数のスマートな挙動
このクエリの主役は、次の曜日をズバリ割り出す **`NEXT_DAY` 関数** です。

#### 仕様と関数のマッチング
問題には「入社日自体が金曜日であった場合は、当日ではなく翌週の金曜日を取得する」という、一見 `CASE` 式が必要そうな条件があります。

しかし、Oracleの `NEXT_DAY(日付, 曜日)` 関数は、「指定した日付の『翌日』以降で、最初に指定の曜日になる日」を返す仕様になっています。

* **月曜日入社の場合**: 直後の金曜日（4日後）を指します。
* **金曜日入社の場合**: 当日ではなく、自動的に翌週の金曜日（7日後）を指します。

つまり、条件分岐をわざわざ書かなくても、`NEXT_DAY` 関数をそのまま使うだけで問題の要件を完全に満たすことができるのです！

### 2. 文法・テクニックのポイント：環境に負けない「曜日の指定方法」
解答例の最もエレガントな部分は、第2引数の曜日の指定方法にあります。

```sql
NEXT_DAY(hire_date, TO_CHAR(DATE '2000-01-07', 'DAY'))
```

#### なぜ直接 '金曜日' や 'FRIDAY' と書かないのか？

通常、`NEXT_DAY(hire_date, '金曜日')` と書けば動きます。しかし、このクエリを英語設定のデータベース（海外のクラウド環境など）で実行すると、「そんな曜日はない」とエラーになってしまいます。逆に `'FRIDAY'` と書くと、日本のサーバーで落ちます。

そこで、「確実に金曜日である過去の日付（2000年1月7日）」をわざわざ用意し、それを `TO_CHAR(..., 'DAY')` で切り出しています。

| 実行環境 | `TO_CHAR(DATE '2000-01-07', 'DAY')` の結果 | `NEXT_DAY` が受け取る値 |
| --- | --- | --- |
| **日本環境** | `'金曜日'` | `NEXT_DAY(hire_date, '金曜日')` ＝ 正常動作！ |
| **英語環境** | `'FRIDAY'` | `NEXT_DAY(hire_date, 'FRIDAY')` ＝ 正常動作！ |

DBサーバーが世界中のどこにあろうとも、その環境の言語に合わせた「正しい金曜日の文字列」が動的に生成されるため、**絶対にエラーにならない超堅牢なクエリ**が完成します。

### 3. 実務でのアドバイス：締め日処理のパターン
実務における「締め日」の計算では、今回のような曜日ベースのほかに、日付ベースの制御もよく使われます。

* **「毎月20日締め、翌月末払い」の「翌月末」を出したい場合**:
`LAST_DAY(ADD_MONTHS(日付, 1))`
* **「次の水曜日」を出したい場合**:
2000年1月5日が水曜日なので、`DATE '2000-01-05'` を基準に構築すればOKです。


> **曜日の文字列と言語の明示**
> 1つ前の列の `TO_CHAR(hire_date, '... (DY)', 'NLS_DATE_LANGUAGE=JAPANESE')` のように、第3引数で明示的に言語を指定する手法もあります。表示形式を統一したい場合はこちらも有効ですが、`NEXT_DAY` 関数の内部に組み込む場合は、解答例のような「確定日付から曜日を作るワザ」が非常にスマートです。

# 問題7-13：文字列から日付への安全な変換とエラーハンドリング

### 難易度：★★★☆☆ (Lv.3)

## 問題
外部システムから連携された顧客の生年月日データ（文字列型）を、自社のデータベースの `DATE` 型カラムに移行するタスクが発生しました。
しかし、外部システムのデータには、区切り文字が異なるもの（'1985/12/25'）、カレンダー上存在しない日付（'1990-02-31'）、あるいは完全なゴミデータ（'UNKNOWN'）など、不適切な文字列が混入していることが判明しました。

通常の `TO_DATE` 関数でこれらを一括変換しようとすると、1件でも不正データがあった時点で **「ORA-01843: 指定された月が無効です」** などのエラーが発生し、クエリ全体（バッチ処理）が異常終了してしまいます。
システムを絶対に止めず、不正データを `NULL` に安全にバイパスしつつ、どの行がエラーになったかを識別できる堅牢なデータ移行クエリを構築してください。

データ移行の検証用として、WITH句に`cust_migration_data`という顧客データ移行を想定した以下のテンポラリテーブル（サンプルデータ含む）を作成・使用します。

```sql
WITH cust_migration_data(customer_id, birth_str) AS(
    SELECT 101, '1980-05-15' FROM dual UNION ALL  -- 正常（期待するフォーマット）
    SELECT 102, '1985/12/25' FROM dual UNION ALL  -- 正常だが区切り文字が異なる
    SELECT 103, '1990-02-31' FROM dual UNION ALL  -- 不正（存在しない日付）
    SELECT 104, 'UNKNOWN'    FROM dual UNION ALL  -- 不正（文字列エラー）
    SELECT 105, '2000-11-30' FROM dual            -- 正常（期待するフォーマット）
)
```

`cust_migration_data` テーブルからすべてのデータを取得し、`birth_str`（文字列型）を `'YYYY-MM-DD'` フォーマットを基準として `DATE` 型に変換してください。
その際、以下の条件を満たすSQL文を作成してください。

1. 変換に成功した場合は、その日付を「YYYY-MM-DD」形式の文字列に再整形して `CONVERTED_DATE` として出力する。
2. フォーマット不正や存在しない日付などで**変換エラーになる場合は、クエリを落とさずに `NULL` を割り当てる**。
3. 新しい関数を活用し、データが正常に変換できた場合は `'VALID'`、エラーになった場合は `'INVALID'` と判定する `DATA_STATUS` 列を合わせて出力する。
4. 結果は `customer_id` の昇順でソートする。

## 期待する結果
| CUSTOMER_ID | BIRTH_STR  | CONVERTED_DATE | DATA_STATUS | 
| ----------- | ---------- | -------------- | ----------- | 
| 101         | 1980-05-15 | 1980-05-15     | VALID       | 
| 102         | 1985/12/25 | 1985-12-25     | VALID       | 
| 103         | 1990-02-31 |                | INVALID     | 
| 104         | UNKNOWN    |                | INVALID     | 
| 105         | 2000-11-30 | 2000-11-30     | VALID       | 


## 解答例
```sql
WITH cust_migration_data(customer_id, birth_str) AS(
    SELECT 101, '1980-05-15' FROM dual UNION ALL  -- 正常（期待するフォーマット）
    SELECT 102, '1985/12/25' FROM dual UNION ALL  -- 正常だが区切り文字が異なる
    SELECT 103, '1990-02-31' FROM dual UNION ALL  -- 不正（存在しない日付）
    SELECT 104, 'UNKNOWN'    FROM dual UNION ALL  -- 不正（文字列エラー）
    SELECT 105, '2000-11-30' FROM dual            -- 正常（期待するフォーマット）
)
SELECT
    customer_id,
    birth_str,
    -- 1. 安全な日付変換（エラー時はNULLを返す）
    TO_CHAR(
        TO_DATE(birth_str DEFAULT NULL ON CONVERSION ERROR, 'YYYY-MM-DD'),
        'YYYY-MM-DD'
    ) AS converted_date,
    -- 2. 変換可能かどうかの事前判定
    CASE VALIDATE_CONVERSION(birth_str AS DATE, 'YYYY-MM-DD')
        WHEN 1 THEN 'VALID'
        ELSE 'INVALID'
    END AS data_status
FROM
    cust_migration_data
ORDER BY
    customer_id
```

## 解説
この問題は、データ移行（データマイグレーション）やETL処理の実務において、極めて頻出かつ重要な「データのクレンジングとエラーハンドリング」をテーマにした問題です。
Oracle Database 12c Release 2 (12.2) 以降で導入された強力な機能を使うことで、従来はPL/SQLを組まなければ不可能だった「エラーをスルーする」処理を、SQLだけでスマートに実現しています。

### ポイント解説
このクエリの美しさは、「変換エラーが起きてもクエリを絶対に止めない」という堅牢性にあります。それを支える2つの新世代機能がポイントです。

#### 1. DEFAULT ... ON CONVERSION ERROR 句

通常の `TO_DATE(birth_str, 'YYYY-MM-DD')` では、'UNKNOWN' や '1990-02-31'（存在しない日付）が紛れ込んだ瞬間にエラー（ORA-01843など）が発生し、何百万件のバッチ処理も一瞬で異常終了してしまいます。

そこで活躍するのがこの構文です。

```sql
TO_DATE(birth_str DEFAULT NULL ON CONVERSION ERROR, 'YYYY-MM-DD')
```

このように記述すると、「もし変換エラーが起きたら、エラーにせず代わりに NULL を返して進めてくれ」という指示になります。システムを止められないデータ移行では必須のテクニックです。

#### 2. VALIDATE_CONVERSION 関数

「エラーを回避してNULLにする」だけでなく、「どの行がエラーだったか（不正データか）」をマーキングするために `VALIDATE_CONVERSION` を使用しています。

* 指定したフォーマットで正しく変換できる場合は **`1`** を返します。
* 変換エラーになる場合は **`0`** を返します。

これを `CASE` 文と組み合わせることで、クエリ内で安全に `VALIDATE` / `INVALID` のフラグを生成できます。

#### 3. 区切り文字の柔軟性（102番のデータについて）

サンプルデータの `1985/12/25` は、指定フォーマット（ハイフン区切り `'YYYY-MM-DD'`）と区切り文字が異なりますが、**`VALID` として正常に変換されています。**
Oracleの `TO_DATE` は、フォーマット文字内の句読点（ハイフン、スラッシュ、ピリオドなど）の不一致に対して、ある程度柔軟にマッチングしてくれる仕様があるためです。


### 実行のメカニズム
このクエリが不正データをどのように処理しているか、データの流れを整理しましょう。

```
[入力データ] ----------> [VALIDATE_CONVERSION] ----> (1 なら) VALID
                                              ----> (0 なら) INVALID

[入力データ] ----------> [TO_DATE (DEFAULT NULL)] -> (正常) DATE型に変換 -> TO_CHARで整形
                                              ----> (エラー) NULL にバイパス
```

このように、1つの文字列に対して「フラグ立て」と「実際の変換」を独立して安全に行っています。


### 文法上の補足

#### 昔のやり方との違い（なぜこの機能が素晴らしいのか）
この `ON CONVERSION ERROR` や `VALIDATE_CONVERSION` が導入される前（Oracle 11g以前など）は、以下のような方法をとる必要がありました。

1. **独自のPL/SQL関数を作る**: 関数内で `BEGIN ... EXCEPTION WHEN OTHERS THEN RETURN NULL; END;` のようにエラーを捕捉する。
2. **ログテーブルに吐き出す**: `DBMS_ERRLOG` パッケージを使い、エラー行を別テーブルに退避させながらインサートする。

しかし、1の方法はSQLとPL/SQLの「コンテキストスイッチ（切り替えオーバーヘッド）」が発生するため、大量データ処理では**速度が著しく低下する**という致命的な弱点がありました。

今回の解答例にあるネイティブなSQL関数を使う方法は、内部で最適化されているため**非常に高速**です。数百万件規模の移行処理でも抜群のパフォーマンスを発揮します。

# 問題7-15 タイムスタンプの「時間帯別（1時間ごと）」の切り捨て集計

### 難易度：★★★☆☆ (Lv.3)

## 問題
マーケティング部門およびインフラ管理部門から、「ECサイトにおける注文のピーク時間帯を特定したい」とのシステム分析依頼がありました。24時間のうち「何時台」に注文が集中しているかを可視化することで、サーバーのリソース増強計画や、タイムセールなどの効果的な施策を打つタイミングを決定します。

データベースに格納されている注文日時（`TIMESTAMP`型）は秒やミリ秒単位まで記録されていますが、これらを「1時間単位（〇時00分00秒）」に丸めてグループ化し、時間帯別の注文数を集計するクエリを構築してください。

COスキーマの`orders` テーブルからデータを取得し、注文日時（`order_tms`）を1時間単位（分・秒・ミリ秒を切り捨て）に丸め、時間帯ごとの注文数を集計してください。

出力にあたっては以下の条件を満たしてください。

1. 切り捨てられた日時を `ORDER_HOUR` という列名で、「YYYY-MM-DD HH24:MI:SS」形式の文字列として出力する。
2. 各時間帯の注文数を `ORDER_COUNT` 列として出力する。
3. 結果は `ORDER_HOUR` の昇順でソートする。
4. 出力対象は注文数（`ORDER_COUNT`）が2を超えるもの。

## 期待する結果
| ORDER_HOUR          | ORDER_COUNT | 
| ------------------- | ----------- | 
| 2021-05-03 18:00:00 | 3           | 
| 2021-06-29 23:00:00 | 3           | 
| 2021-09-10 10:00:00 | 3           | 
| 2021-09-30 03:00:00 | 3           | 
| 2021-10-07 03:00:00 | 3           | 
| 2021-10-11 04:00:00 | 3           | 
| 2021-10-26 20:00:00 | 3           | 
| 2021-12-04 14:00:00 | 4           | 
| 2021-12-13 09:00:00 | 3           | 
| 2022-01-07 15:00:00 | 3           | 
| 2022-01-10 18:00:00 | 3           | 
| 2022-02-28 04:00:00 | 3           | 


## 解答例
```sql
SELECT
    TO_CHAR(TRUNC(order_tms, 'HH24'), 'YYYY-MM-DD HH24:MI:SS') AS order_hour,
    COUNT(*) AS order_count
FROM
    co.orders
GROUP BY
    TRUNC(order_tms, 'HH24')
HAVING
    COUNT(*) > 2
ORDER BY
    order_hour
```

## 解説
今回のテーマは、アクセス解析やマーケティング分析で最も頻出するテクニックの一つ、「日時の切り捨て（グルーピング）集計」です。
秒やミリ秒単位まで記録された細かなタイムスタンプを、目的に応じて「1時間ごと」「1日ごと」「1ヶ月ごと」といった適切な粒度にガツンと丸めることで、データの後ろに隠れたトレンド（山と谷）をきれいに炙り出すことができます。
解答例のスマートなポイントをわかりやすく解説します。

### 1. スクリプトの解説：時間の粒度を揃える `TRUNC` の威力

このクエリの主役は、数値を丸める際にもおなじみの **`TRUNC`関数** ですが、日付やタイムスタンプに対しても絶大な威力を発揮します。

#### TRUNC関数の動き

```sql
TRUNC(order_tms, 'HH24')
```

第2引数に **`'HH24'`** を指定することで、「時（Hour）」未満の情報をすべて切り捨てます。

具体的には、内部で以下のような変換が行われています。

* `2021-05-03 18:24:59.123` $\rightarrow$ **`2021-05-03 18:00:00.000`**
* `2021-05-03 18:01:02.000` $\rightarrow$ **`2021-05-03 18:00:00.000`**

このように、バラバラだった分・秒・ミリ秒をすべて「00分00秒」に揃えてしまう（高密度化する）ことで、同じ時間帯のデータを `GROUP BY` で1行にきれいに束ねることができるようになります。


### 2. 文法・テクニックのポイント

#### ① WHERE ではなく HAVING を使う理由

問題文の条件に「出力対象は注文数が2を超えるもの」とあります。

* **`WHERE` 句**: 集計をする**前**に、生のレコードを間引く。
* **`HAVING` 句**: `GROUP BY` で集計した**後**の、まとまった数字（今回なら `COUNT(*)` ）に対して絞り込みをかける。

今回は「集計した結果、3件以上あった時間帯だけが欲しい」という要件なので、**`HAVING COUNT(*) > 2`** を使うのが正解です。

#### ② TRUNC の便利なフォーマットマスク（早見表）

実務では、上司やクライアントの要望によって切り捨てたい単位がコロコロ変わります。第2引数を書き換えるだけで対応できるようにセットで覚えておきましょう。

| 指定するマスク | 丸められる粒度 | 実務での用途 |
| --- | --- | --- |
| **`'MI'`** | 1分単位に丸める | 障害発生時の分単位のアクセス急増（スパイク）検知 |
| **`'HH24'`**（今回） | 1時間単位に丸める | サーバーリソース計画、タイムセールの時間帯分析 |
| **`'DD'`** または指定なし | 1日単位に丸める | 日次の売上報告、日別のアクティブユーザー数（DAU） |
| **`'MM'`** | 1ヶ月単位に丸める | 月次の売上推移、月別解約率の算出 |


### 3. 実務でのアドバイス：2種類の「時間帯分析」の使い分け

実務で「時間帯別のピークを知りたい」と言われた場合、実は **2つの異なるビジネスニーズ** が存在します。ここを先回りして確認できると、一気にデキるアナリスト扱いされます。

#### パターンA：日付も加味した時系列推移（今回の形）

「2021年5月3日の18時台」「2021年12月4日の14時台」のように、特定のカレンダー上の1時間を特定します。

* **メリット**: 「特定のキャンペーンを打ったあの日のあの時間、サーバーにどれだけ負荷がかかったか」といった、**スポットのイベント評価**に最適です。

#### パターンB：日付を無視した「純粋な24時間」の傾向

「何月何日かに関係なく、ウチのサイトはいつも何時台に一番人が集まるの？」という、人間の生活リズムに合わせた癖を分析します。この場合は、`TRUNC` ではなく `TO_CHAR` を使って以下のようにグループ化します。

```sql
-- 日付を無視して、純粋に「18時台」「19時台」の総計を出す
SELECT
    TO_CHAR(order_tms, 'HH24') AS order_hour_of_day,
    COUNT(*) AS order_count
FROM co.orders
GROUP BY TO_CHAR(order_tms, 'HH24')
ORDER BY order_hour_of_day;
```
