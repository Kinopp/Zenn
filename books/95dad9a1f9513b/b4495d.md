# 問題3-1：全データの取得
### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマにある REGIONS テーブルから、すべてのデータを取得してください。
なお、レコードの表示順序は問いません。

## 期待する結果
| REGION_ID | REGION_NAME | 
| --------- | ----------- | 
| 10        | Europe      | 
| 20        | Americas    | 
| 30        | Asia        | 
| 40        | Oceania     | 
| 50        | Africa      | 

## 解答例
```sql:例1：「*」を使用
SELECT
    *
FROM
    hr.regions
```
```sql:例2：全てのカラムを指定
SELECT
    region_id,
    region_name
FROM
    hr.regions
```

## 解説
今回は、SQL学習の第一歩、「全データの取得」についての解説を詳しく行います。基礎中の基礎ですが、現場でも毎日使う非常に重要なコマンドです。

### 1. 文法解説：SELECT文の基本構造

SQLでデータを取得する際、最も基本となるのがこの構造です。

```sql
SELECT
    [取得したいカラム名]
FROM
    [テーブル名]
```

#### ① SELECT句
「どの列（カラム）を取り出すか」を指定します。
* **`*`（アスタリスク）**: テーブルに含まれる**すべての列**を一度に取得します。
* **カラム名の列挙**: `region_id, region_name` のようにカンマ区切りで指定すると、特定の列だけを取得できます。

#### ② FROM句
「どのテーブルからデータを取り出すか」を指定します。
* **`hr.regions`**: ここでの `hr` は**スキーマ名**（所有者名）を指し、`regions` が**テーブル名**です。
* 自分の環境（自分のスキーマ）にあるテーブルを見る場合は、通常 `hr.` を省略して `FROM regions` と書くことも可能です。

### 2. スクリプトの使い分け：`*` vs カラム名指定
解答例にある2つの書き方には、実務上の使い分けがあります。

| 指定方法 | メリット | デメリット | 主な用途 |
| :--- | :--- | :--- | :--- |
| **`*` (アスタリスク)** | 記述が楽。テーブル定義を知らなくても全データが見れる。 | カラム増減の影響を受ける。不要なデータまで取得するため負荷がかかる。 | データのクイック確認、デバッグ時 |
| **カラム名を指定** | 必要なデータのみ取得するため高速。コードの可読性が高い。 | カラムが多いと記述が面倒。 | **本番環境のプログラム実装** |

> **実務でのアドバイス**
> 開発の現場では、原則として **「カラム名をすべて指定すること」** が推奨されます。これは、後からテーブルに新しい列が追加された際に、プログラムが予期せぬ挙動をするのを防ぐためです。

### 3. Oracle SQLの細かなルール
* **大文字・小文字の区別**: SQLのキーワード（`SELECT`, `FROM`）やテーブル名・カラム名は、基本的に大文字・小文字を区別しません。
    * `select * from regions` も `SELECT * FROM REGIONS` も同じ結果になります。

* **文末のセミコロン (`;`)**: 1つの命令の終わりを示します。ツール（SQL DeveloperやSQL*Plusなど）で複数のSQLを連続して実行する際には必須です。



<br>
:::message
### **SQLスクリプトを大文字で書くか小文字で書くか？**

SQLの文法自体は、大文字・小文字を区別しません。推奨されるスタイルとしては、可読性の観点から **「キーワードは大文字、テーブル名やカラム名は小文字」** で記述するのが良いと思います。当演習でもこのスタイルで記述いたします。
Oracle FreeSQLにはこのスタイルで記述するサポート機能があります（一部て修正が必要かもしれません）。

# 問題3-2：特定の条件に一致するデータの取得

### 難易度：★☆☆☆☆ (Lv.1)

## 問題

HRスキーマにある **`COUNTRIES`** テーブルから、**`REGION_ID` が 20** であるレコードを抽出し、**`COUNTRY_ID`** と **`COUNTRY_NAME`** の列を表示してください。
なお、レコードの表示順序は問いません。

## 期待する結果
| COUNTRY_ID | COUNTRY_NAME             | 
| ---------- | ------------------------ | 
| AR         | Argentina                | 
| BR         | Brazil                   | 
| CA         | Canada                   | 
| MX         | Mexico                   | 
| US         | United States of America | 


## 解答例
```sql
SELECT
    country_id,
    country_name
FROM
    hr.countries
WHERE
    region_id = 20
```

## 解説
今回は、前回の「全件取得」から一歩進んで、**「必要な列だけを選び（射影）」** かつ **「必要な行だけを絞り込む（選択）」** という、SQLの最も強力な機能であるフィルタリングの解説です。

### 1. 文法解説：WHERE句によるデータの絞り込み
特定の条件に一致するデータだけを取得するには、`WHERE`句を使用します。

```sql
SELECT
    [取得したいカラム名]
FROM
    [テーブル名]
WHERE
    [条件式]
```

#### ① 射影 (Projection)：SELECT句
今回は「すべての列」ではなく、`country_id` と `country_name` の2つを指定しています。
このように必要な列だけをカンマで区切って記述することで、結果セットをスリムに保つことができます。

#### ② 選択 (Selection)：WHERE句
`WHERE region_id = 20` と記述することで、`region_id` カラムの値が **20** である行のみを抽出しています。

### 2. 条件式の書き方の基本
今回の `region_id = 20` のように、数値を比較する場合はそのまま記述します。SQLで使用される主な比較演算子は以下の通りです（次章で解説）。

| 演算子 | 意味 | 例 |
| :--- | :--- | :--- |
| **`=`** | 等しい | `region_id = 20` |
| **`<>`** または **`!=`** | 等しくない | `region_id <> 10` |
| **`>`** / **`<`** | より大きい / 未満 | `region_id > 30` |
| **`>=`** / **`<=`** | 以上 / 以下 | `region_id <= 20` |

> **数値 vs 文字列の注意点**
> 今回の `region_id` は**数値型**なので `20` とそのまま書けますが、もし `country_id`（文字列型）で絞り込む場合は、`WHERE country_id = 'US'` のように**シングルクォーテーション**で囲む必要があります。


### 3. 実務的なポイント：処理の順番

SQLが実行されるとき、実は「書く順番」と「コンピュータが処理する順番」が異なります。

1.  **FROM**: まずテーブルを見る
2.  **WHERE**: 条件に合う行を絞り込む
3.  **SELECT**: 最後に必要な列を表示する

この順番を意識すると、複雑なクエリを書くときに「今どのデータが手元にあるか」が整理しやすくなります。



<br>
:::message
### **暗黙の型変換に潜む「大きな落とし穴」**
「動くから大丈夫」と多用するのは禁物です。特に注意すべきなのが パフォーマンスへの影響 です。暗黙の型変換が行われると、本来設定されている **「インデックス（索引）」が有効に機能しなくなる**ことがあります。その結果、データの検索速度が極端に落ち(※)、システム全体の大きな遅延や障害を招く恐れがあります。
この現象はエラーとして表示されないため、原因に気づきにくく、後から修正するのが非常に大変です。 **「型は最初から正しく合わせる」** のが、安全で高速なSQLを書くための基本です。
(※)データ量によっては、数百倍〜数千倍遅くなることもあります。
:::

# 問題3-3：列の別名（エイリアス）の設定

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマにある **`COUNTRIES`** テーブルから、**`REGION_ID` が 20** であるレコードを抽出してください。
その際、結果の列名（ヘッダー）を以下のように別名を設定して表示してください。
なお、レコードの表示順序は問いません。

* `COUNTRY_ID`　→　**`ID`**
* `COUNTRY_NAME`　→　**`NAME`**

## 期待する結果
| ID         | NAME                     | 
| ---------- | ------------------------ | 
| AR         | Argentina                | 
| BR         | Brazil                   | 
| CA         | Canada                   | 
| MX         | Mexico                   | 
| US         | United States of America | 


## 解答例
```sql
SELECT
    country_id as "ID",
    country_name as "NAME"
FROM
    hr.countries
WHERE
    region_id = 20
```

## 解説
今回は、出力結果の見た目を整えるために欠かせない **「別名（エイリアス）」** の設定についての解説です。

### 1. 文法解説：カラムの別名（AS句）
SELECT句で指定したカラム名の後に `AS` を付けることで、実行結果のヘッダー（見出し）を好きな名前に変更できます。

```sql
SELECT
    [元のカラム名] AS "[表示したい別名]"
FROM
    [テーブル名]
```

#### ① ASキーワード
* `AS` は「～として」という意味です。
* 実は `AS` は**省略可能**ですが、コードの可読性（読みやすさ）を高めるために、慣習的に書くことが推奨されます。

#### ② ダブルクォーテーション (`" "`) の役割
解答例で `"ID"` や `"NAME"` と囲っているのには理由があります。
Oracle SQLにおいて、ダブルクォーテーションで囲むと以下のルールが適用されます。
* **大文字・小文字を区別する**: 囲まないと自動的にすべて大文字になります。
* **スペースや記号を含められる**: `"Country ID"` のようにスペースを入れたい場合は必須です。
* **予約語を使える**: 本来SQLで特別な意味を持つ単語も、別名として使えます。

ダブルクォーテーションで囲むメリットもありますが、デメリットもあるので、実務で使用する際には注意が必要です。

### 2. 別名を使うメリット
実務において別名を設定するのは、単に「短くするため」だけではありません。

* **レポートの明確化**: システム上のカラム名（`EMP_LNAME`など）が分かりにくい場合、日本語（`"苗字"`）などに変えて見やすくします。
* **計算結果への命名**: `salary * 12`（年収計算）のような計算式の結果に、`"Annual Salary"` と名前を付けて意味を明確にします。
* **プログラム側での制御**: システム開発において、プログラムがデータを受け取る際のキー名を固定するために使います。

### 3. 注意点：WHERE句での使用不可
ここが初心者が最もハマりやすいポイントです。
**WHERE句の中で、SELECT句で定義した「別名」を使うことはできません。**

```sql
-- ❌ これはエラーになります
SELECT country_id AS "ID"
FROM hr.countries
WHERE "ID" = 'AR';  -- エラー：IDなんて列はテーブルに存在しないと言われる
```

理由は、前の問題でも触れた**実行順序**にあります。
1. `FROM`（テーブルを探す）
2. `WHERE`（行を絞り込む）← **この時点ではまだ「別名」は付いていない！**
3. `SELECT`（列を選んで**別名を付ける**）

この順番を意識すると、SQLの構造がより深く理解できるようになります。


<br>
:::message
### システム開発では " " を使わないのが無難？
結論から言うと、**「システム開発の現場では、識別子（テーブル名や列名）を " " で囲むのは避けるのが鉄則」** です。
実務でこれをやると**負の遺産**になりかねません。なぜエンジニアたちがこれほどまでに `" "` を嫌うのか、その裏にある「3つの地獄」を解説します。

<br>
#### 1. 大文字・小文字の「固定」地獄

Oracle（や多くの標準SQL）では、引用符で囲まない名前は内部的に**すべて大文字**として扱われます。

* **囲まない場合**: `SELECT user_id` も `SELECT USER_ID` も、DB側は「あ、`USER_ID` のことね」と解釈してくれます。
* **" " で囲んだ場合**: `"UserId"` と定義すると、**以後、一字一句（大文字小文字まで）完全に一致させないとエラー**になります。

**現場で起こる悲劇：**
誰かが一人でもテーブル作成時に `"UserId"` と書いてしまうと、他の開発者が `SELECT user_id ...` と書くたびに「そんな列はありません」と怒られ、デバッグに時間を無駄にさせることになります。

<br>
#### 2. プログラムコード内の「エスケープ」地獄

これが実務上の最大のデメリットかもしれません。JavaやPython、PHPなどのプログラム内でSQLを書く際、SQL文自体を文字列（`" "` や `' '`）で囲みますよね。

もしDB側に `" "` が必要な列名があると、コードはこうなります：

* **普通の書き方**:
    `sql = "SELECT user_id FROM users"`
* **" " が必要な書き方**:
    `sql = "SELECT \"UserId\" FROM \"Users\""` （言語によっては `\"` や `""` でエスケープが必要）

すべてのクエリーにこれが入ると、**視認性が最悪**になります。タイピングミスも増えますし、パッと見て何が書いてあるか分からなくなるため、バグの温床になります。

<br>
#### 3. 予約語との衝突を「許してしまう」危うさ

本来、SQLには使ってはいけない「予約語（`SELECT`, `ORDER`, `GROUP` など）」があります。

* `CREATE TABLE my_table (order NUMBER)` → **エラー（orderは予約語だから）**
* `CREATE TABLE my_table ("ORDER" NUMBER)` → **作成できてしまう**

「あ、予約語だけど `" "` で囲めば使えるじゃん！」と安易に使うと、その後の開発で **「この ORDER は命令の ORDER なのか、列名の ORDER なのか？」** と解析エンジンや人間が混乱する原因になります。

<br>
#### まとめ：なぜ「使わないのが無難」なのか

| 項目 | `" "` を使わない（標準） | `" "` を使う（非推奨） |
| :--- | :--- | :--- |
| **柔軟性** | 大文字・小文字を気にしなくて良い | 厳密に一致させる必要がある |
| **開発効率** | エスケープ不要でスッキリ書ける | エスケープだらけで読みづらい |
| **ツール親和性** | どのツールでも問題なく動く | ツールによって挙動が変わるリスクあり |
| **設計の質** | 予約語を避ける良い設計になる | 悪い設計（予約語使用）を許容してしまう |

<br>
#### 当演習の解答例では、SQLのルールをより深く理解していただくための練習として、意図的に `" "` を使って記述しているものがあります。実際のシステム開発現場での推奨ルールとは一部異なる箇所がありますので、その点をご理解いただいた上で学習を進めていただければ幸いです。

:::

# 問題3-4：データの並び替え（ORDER BY）

### 難易度：★☆☆☆☆ (Lv.1)


## 問題
OEスキーマの **`CUSTOMERS`** テーブルを使用します。
**`NLS_TERRITORY`** が **「CHINA」** である顧客を抽出し、以下の順序で並び替えて表示してください。

1. **`CUST_FIRST_NAME`** の **昇順**（小さい順）
2. `CUST_FIRST_NAME` が同じ場合は、**`CUST_LAST_NAME`** の **降順**（大きい順）

## 期待する結果
| CUSTOMER_ID | CUST_FIRST_NAME | CUST_LAST_NAME | 
| ----------- | --------------- | -------------- | 
| 981         | Daniel          | Gueney         | 
| 308         | Glenda          | Dunaway        | 
| 309         | Glenda          | Bates          | 
| 360         | Helmut          | Capshaw        | 


## 解答例
```sql:例1：カラムを指定する
SELECT
    customer_id,
    cust_first_name,
    cust_last_name
FROM
    oe.customers
WHERE
    nls_territory = 'CHINA'
ORDER BY
    cust_first_name ASC,
    cust_last_name DESC
```
```sql:例2：列順を指定する
SELECT
    customer_id,
    cust_first_name,
    cust_last_name
FROM
    oe.customers
WHERE
    nls_territory = 'CHINA'
ORDER BY
    2, 3 DESC
```

## 解説
今回は見やすく整列させる **「ソート（並び替え）」** のマスターです。この `ORDER BY` 句を使いこなせると、一気に「使えるレポート」感が出てきます。

### 1. 文法解説：ORDER BY句による並び替え
データの表示順序を制御するには、SQL文の最後に `ORDER BY` 句を追加します。

```sql
SELECT
    [カラム名]
FROM
    [テーブル名]
WHERE
    [条件]
ORDER BY
    [カラム1] [ASC | DESC],
    [カラム2] [ASC | DESC]
```

#### ① 昇順（ASC）と降順（DESC）
* **`ASC` (Ascending)**: 昇順。小さい順（1→10、A→Z、古い日付→新しい日付）。
    * ※デフォルト（省略時）はこの `ASC` になります。
* **`DESC` (Descending)**: 降順。大きい順（10→1、Z→A、新しい日付→古い日付）。

#### ② 複数カラムの指定
今回のように複数のカラムを指定した場合、**「左から順に」** 優先順位が決まります。
1.  まず `cust_first_name` で全体を並び替える。
2.  その中で同じ名前（例：Glenda）がいた場合のみ、そのグループ内で `cust_last_name` を使って並び替える。


### 2. 解答例2：列番号（位置）による指定
解答例の2つ目にある `ORDER BY 2, 3 DESC` という書き方は、実務でも時々見かけるテクニックです。

* **`2`**: SELECT句で指定した **2番目のカラム**（`cust_first_name`）を指します。
* **`3`**: SELECT句で指定した **3番目のカラム**（`cust_last_name`）を指します。
  
> **列番号指定の注意点**
> 記述は短くなりますが、後から `SELECT` 句のカラム順序を入れ替えると、並び替えの対象も変わってしまうため、**メンテナンス性は少し下がります。** 複雑なSQLを書くときは、解答例1のようにカラム名で指定する方が安全です。

### 3. SQLの実行順序
これまで学習した句をまとめると、実行順序は以下のようになります。

1.  **FROM**: どのテーブルか？
2.  **WHERE**: どの行か？
3.  **SELECT**: どの列か？（ここで別名が付く）
4.  **ORDER BY**: どの順番か？

**「`ORDER BY` は最後」**と覚えておきましょう。
実は、`ORDER BY` 句の中では、問題3-3で学んだ**「別名（エイリアス）」を使うことができます。**

```sql
-- これも動きます！
SELECT
    cust_first_name AS "FNAME"
FROM
    oe.customers
ORDER BY
    "FNAME" ASC
```

これは、`ORDER BY` が `SELECT` よりも後に処理されるからです。


<br>
:::message

### **「ASC」の使い分け基準**
SQLを書く際、「ASCは省略できるのになぜ存在するのか？」「いつ書くべきなのか？」という疑問を抱く方は少なくありません。

明確な正解が決まっているわけではありませんが、実務においてコードの美しさと読みやすさを両立させるための、ひとつの判断基準をご紹介します。
<br>
#### 1. すべての条件が「昇順」の場合

この場合は、**ASCを省略します。**
デフォルトの挙動が昇順であるため、あえて記述しないことでコードを冗長（無駄に長い状態）にせず、スッキリと見せることができます。

<br>
#### 2. 「昇順」と「降順」が混在する場合

この場合は、**ASCを省略せずに明示します。**
「ここは昇順、あそこは降順」と意図がはっきり伝わるようになり、コードの**可読性（読みやすさ）** が向上するためです。他の人がコードを見た際にも、設定ミスではないことが一目で分かります。
:::

# 問題3-5：重複データの除外（DISTINCT）

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
SHスキーマにある **`COUNTRIES`** テーブルから、**`COUNTRY_REGION`** 列のデータを取得してください。
その際、同じデータが複数表示されないよう、**重複を排除**して表示してください。
なお、レコードの表示順序は問いません。

## 期待する結果
| COUNTRY_REGION | 
| -------------- | 
| Americas       | 
| Europe         | 
| Asia           | 
| Oceania        | 
| Africa         | 
| Middle East    | 

## 解答例
```sql:例1：DISTINCTを使用
SELECT DISTINCT
    country_region
FROM
    sh.countries
```
```sql:例2：GROUP BYを使用（参考）
SELECT
    country_region
FROM
    sh.countries
GROUP BY
    country_region
```

## 解説
今回は、データ分析や集計の際に必ずと言っていいほど登場する **「重複の排除」** についての解説です。
テーブルの中には同じ値を持つ行が何件も含まれていることがありますが、そこから「どんな種類があるか」を抽出する際に非常に役立ちます。

### 1. 文法解説：SELECT DISTINCT
特定の列から重複する値を取り除き、ユニーク（一意）な値のみを取得するには `DISTINCT` キーワードを使用します。

```sql
SELECT DISTINCT
    [カラム名]
FROM
    [テーブル名]
```

#### ① DISTINCTキーワード
* `SELECT` の直後に記述します。
* 指定した列のデータを見比べて、全く同じ値がある場合は、それを1つにまとめて表示します。

#### ② 複数のカラムを指定した場合
もし `SELECT DISTINCT col1, col2` と書いた場合は、**「col1 と col2 の組み合わせ」** が重複している行が排除されます。片方の値が同じでも、もう片方が違えば別のデータとして表示されます。


### 2. 解答例2：GROUP BY との違い（参考）
解答例には `GROUP BY` を使った書き方も載っていますね。実は、**「重複をなくす」という結果だけを見れば、この2つは同じ**です。

| 機能 | 特徴 | 主な使い道 |
| :--- | :--- | :--- |
| **`DISTINCT`** | 単に重複を削るための「フィルタ」。 | 値の種類（リスト）をサッと確認したいとき。 |
| **`GROUP BY`** | データを「グループ」としてまとめる。 | 合計(`SUM`)や平均(`AVG`)などの集計とセットで使うとき。 |

実務では、今回のように「地域の一覧が見たいだけ」という場合は、意図が明確に伝わる `DISTINCT` を使うのが一般的です。

### 3. 知っておくと得するポイント

#### NULL（空の値）の扱い
`DISTINCT` を実行した際、その列に `NULL` が含まれていると、**`NULL` も1つの種類として表示されます。**
（例：10種類の大陸名と、地域が設定されていない `NULL` が混ざっている場合、結果は11行になります）

#### 実行速度について
`DISTINCT` は、裏側でデータを並び替え（ソート）たり、比較したりする処理が走るため、非常に膨大なデータに対して実行すると少し時間がかかることがあります。

### とりあえず `DISTINCT`
「とりあえず `DISTINCT`」は、多くのエンジニアが通る **「禁断の果実」** です。よく分からないけどデータが重複しているので、とりあえず`DISTINCT`で重複をなくしちゃおうという行為です。一見すると結果が綺麗になるため、問題が解決したように見えてしまいますが、実は裏で深刻な副作用を引き起こしていることが多々あります。
私は開発プロジェクトで、誰かが書いたSQLスクリプトに`DISTINCT`があると、ちょっと警戒してしまいます…

なぜ「とりあえず `DISTINCT`」が危険なのか、その理由を具体的に解説します。
<br>
### 1. 根本原因：意図しない「1対多」の結合
もっとも多いのが、結合条件の不足によって **「1行のはずが10行、100行に増えている」** ケースです。

※「結合」は後の章で出てきますので、ここでは感覚で理解できれば大丈夫です。
簡単にいうと複数のテーブルからデータを抽出することをいいます。


<br>
#### 具体例
「顧客名の一覧を出したい」と思い、顧客（`CUSTOMERS`）と販売履歴（`SALES`）を結合したとします。

```sql
-- 悪い例：DISTINCTで無理やり消す
SELECT DISTINCT c.cust_id, c.cust_last_name
FROM sh.customers c
JOIN sh.sales s ON c.cust_id = s.cust_id;
```

* **何が起きているか**: 1人の顧客が1,000回購入していれば、`JOIN` 直後の内部データではその顧客の行が**1,000行に増殖**しています。
* **DISTINCTの役割**: その増殖した1,000行を、後から無理やり1行にギュッと凝縮して「なかったこと」にしています。
<br>

### 2. 結合キーの不足に気づけない
例えば「有効な契約期間内のデータだけ出したい」のに、期間の条件（`BETWEEN`）を書き忘れて過去の全データと結合され、重複が発生したとします。

* `DISTINCT` を使うと、その「書き忘れ」という**バグ自体が隠蔽されてしまいます。**
* 本来なら「データが重複している ＝ 結合条件かフィルタが足りない」という**アラート（警告）** として受け取るべき事象を、自ら消し去っていることになります。

<br>

### 結論：`DISTINCT` は「最後の手段」

`DISTINCT` を使っていいのは、**「論理的にどうしても重複が発生する構造であり、かつそれが仕様である」** と断言できるときだけです。

もし「なぜか増えたから消す」という動機で `DISTINCT` を使いたくなったら、それは **「SQLがあなたに『結合条件か設計が間違っているよ！』と教えてくれているサイン」** だと捉えてみてください。
