## 解答例
```sql
SELECT
    LTRIM(
        SYS_CONNECT_BY_PATH(employee_id, ' <-- '),
        ' <-- '
    ) AS employee_tree
FROM
    hr.employees
START WITH
    manager_id IS NULL
CONNECT BY
    PRIOR employee_id = manager_id
```
## 解説
「階層問い合わせ（START WITH / CONNECT BY）」は、組織図や部品表（BOM）など、親子関係を持つデータを扱う際の必須テクニックです。仕組みを正しく理解しないと、無限ループや意図しないデータの欠落を招きやすいので、基本から丁寧に押さえておきましょう。

「どこから始めて（START WITH）」「どう繋ぐか（CONNECT BY）」を指定するのが基本構造です。
```sql
SELECT 
    LEVEL,              -- 階層の深さ (1, 2, 3...)
    LPAD(' ', (LEVEL-1)*2) || ENAME AS TREE, -- 見た目を整える
    EMPNO, MGR
FROM EMP
START WITH MGR IS NULL  -- ルート（社長）から開始
CONNECT BY PRIOR EMPNO = MGR; -- 「前の行の社員番号」が「今の行の上司番号」
```

```mermaid
flowchart TD
    A["100 Steven King"] --> B["101 Neena"]
    A --> C["102 Lex"]
    B --> D["108 Nancy"]
    D --> E["109 Daniel"]
    D --> F["110 John"]
```

初心者が混乱しやすいのが`PRIOR`をどちらに付けるかです。`PRIOR`は「一階層上の（親の）」と読み替えると理解しやすくなります。

| 書き方 | 読み方 | 探索方向 |
| :--- | :--- | :--- |
| `CONNECT BY PRIOR EMPNO = MGR` | （親の）社員番号＝（今の）上司番号 | トップダウン（上から下） |
| `CONNECT BY EMPNO = PRIOR MGR` | （今の）社員番号＝（親の）上司番号 | ボトムアップ（下から上） |

`CONNECT BY PRIOR EMPNO = MGR`は「（親の）社員番号＝（今の）上司番号」でトップダウン（上から下へ）の探索、`CONNECT BY EMPNO = PRIOR MGR`は「（今の）社員番号＝（親の）上司番号」でボトムアップ（下から上へ）の探索になります。

階層問い合わせで使える擬似列・関数もいくつか押さえておくと役立ちます。

| 擬似列・関数 | 役割 |
| :--- | :--- |
| `LEVEL` | 階層の深さ（1から始まる） |
| `CONNECT_BY_ISLEAF` | 末端（葉）なら1、そうでなければ0 |
| `SYS_CONNECT_BY_PATH` | ルートからの全経路を文字列で連結 |
| `ORDER SIBLINGS BY` | 兄弟間だけでソート（問題14-6で詳説） |

`LEVEL`は階層の深さを表す数値で1から始まります。`CONNECT_BY_ISLEAF`は最下層（末端）なら1、そうでなければ0を返します。`SYS_CONNECT_BY_PATH`はルートからの全経路を文字列で連結して表示します。`ORDER SIBLINGS BY`は階層構造を壊さずに、同じ親を持つ兄弟間だけでソートします（この関数は問題14-6で詳しく扱います）。

初心者が陥りやすい落とし穴もいくつかあります。

```mermaid
flowchart TD
    A["落とし穴1：WHERE句の位置"] --> A1["WHEREは階層構築後に効く
    →部下だけ残りツリーが分断される"]
    B["落とし穴2：無限ループ"] --> B1["循環データがあるとエラー
    →CONNECT BY NOCYCLEで回避（問題14-7）"]
    C["落とし穴3：パフォーマンス"] --> C1["巨大ツリーは重くなりがち
    →結合キーにインデックスが必要"]
```

1つ目は`WHERE`句と`CONNECT BY`句の順番です。`WHERE`句は「階層構造を作った後」に効くため、もし「特定の部署を除外したい」時に`WHERE`を使うと、その部署の部下たちは残ってしまいツリーが分断されます。部下ごと消したい場合は、`CONNECT BY`句の中に条件（`AND DEPTNO != 10`など）を書く必要があります。2つ目は無限ループです。データに「Aの上司はB、Bの上司はA」のような循環（サイクル）があると、Oracleはエラーを出して停止します。`CONNECT BY NOCYCLE`と記述することで、ループを検知して停止させることができます（こちらは問題14-7で詳しく扱います）。3つ目はパフォーマンスで、巨大なツリー（数万件以上の親子関係）に対して複雑な結合を行いながら`CONNECT BY`を行うとメモリを大量に消費するため、結合キー（`EMPNO`や`MGR`）にインデックスがあるか確認しておくと安心です。

| 方式 | 標準性 | 記述量 | 向いている場面 |
| :--- | :--- | :--- | :--- |
| `CONNECT BY`（Oracle独自） | Oracle専用 | 少ない | 素早く階層を出したいとき |
| 再帰CTE（`WITH`） | ANSI標準 | やや多い | 複雑な計算、他DBへの移行を考慮するとき |

Oracle 23ai（および近年のバージョン）では、標準SQLである「再帰CTE（WITH句による再帰）」も利用できます。`CONNECT BY`はOracle独自ですが短く直感的に書ける一方、再帰CTEはANSI標準で、複雑な計算やOracle以外（PostgreSQLやSQL Server）への移行を考えるならこちらが向いています。パッと階層を出したいだけなら`CONNECT BY`の記述量の少なさが便利で、複雑な処理を組み込みたいときは再帰CTEの柔軟さが活きる、という使い分けになります。

# 【完全版】問題14-4：【総合演習】カテゴリ別成長率と市場シェア分析
### 難易度：★★★★☆ (Lv.4)
## 問題

1. **データの土台作り**: カテゴリ×年別の売上を集計。
2. **形状変換（PIVOT）**: 昨対比較をしやすくするため、年を列に展開。

# 問題14-5：組織階層の逆引き（ボトムアップ探索とCONNECT_BY_ROOT）
### 難易度：★★★☆☆ (Lv.3)
## 問題

トップダウンの組織図を作るだけでなく、末端の従業員側を起点として、組織のトップ（社長）に向かって家系図を「遡る」ことで、各従業員が最終的にどの統括ラインに属しているかを一網打尽にするクエリを構築します。

## 解答例
```sql
SELECT
    CONNECT_BY_ROOT(employee_id) AS start_emp_id,
    CONNECT_BY_ROOT(first_name || ' ' || last_name) AS start_emp_name,
    LEVEL AS current_level,
    first_name || ' ' || last_name AS upward_manager_name,
    -- 最上位（ルート）の情報を動的に取得
    (
        SELECT first_name || ' ' || last_name 
        FROM hr.employees 
        WHERE manager_id IS NULL
    ) AS final_leader_name
FROM
    hr.employees
START WITH
    employee_id BETWEEN 150 AND 155
CONNECT BY
    employee_id = PRIOR manager_id
ORDER BY
    start_emp_id,
    current_level
```
## 解説
今回は「ボトムアップ（逆引き）探索」です。通常の組織図は「社長→部長→課員」というトップダウン（上から下）で探索しますが、今回のポイントは「末端の社員を起点にして、社長に向かって組織ラインを駆け上がる」点にあります。

```mermaid
flowchart BT
    A["150 Sean Tucker
    （起点：レベル1）"] --> B["145 John Singh
    （レベル2）"]
    B --> C["100 Steven King
    （レベル3：最終到達点）"]
```

このクエリの中心は、`CONNECT BY`句の`PRIOR`の位置にあります。
```sql
START WITH employee_id BETWEEN 150 AND 155
CONNECT BY employee_id = PRIOR manager_id
```

| 探索方向 | CONNECT BY句 | 意味 |
| :--- | :--- | :--- |
| トップダウン | `PRIOR employee_id = manager_id` | 「1行前の社員ID」＝「次の行の上司ID」 |
| ボトムアップ（今回） | `employee_id = PRIOR manager_id` | 「1行前の上司ID」＝「次の行の社員ID」 |

通常のトップダウン探索では`PRIOR employee_id = manager_id`（「1行前の社員ID」が「次の行の上司ID」であること）と書きますが、今回は逆です。`PRIOR manager_id`は「1行前のデータにおける上司のID」を指し、`employee_id = ...`は「次の行では、その上司IDを社員IDとして検索してね」という意味になります。これにより、「自分→自分の上司→上司の上司……」という形で家系図を遡るようにデータが抽出されていきます。

`CONNECT_BY_ROOT`の挙動にも注目してください。
```sql
CONNECT_BY_ROOT(employee_id) AS start_emp_id
```
この演算子は、その探索における「一番の根本（起点）」となった行のデータを全行にコピーする機能です。トップダウン探索であれば「社長の名前」が取れる関数ですが、今回はボトムアップ（下から上）に探索しているため、起点である「末端の従業員（自分自身）」の情報がルートとして扱われます。結果として、期待する結果の通り「誰から始まった承認ラインのデータか」を横並びに保持できます。

通常、`LEVEL`は組織の深さ（社長が1、部長が2……）を表しますが、ボトムアップ探索では「自分自身から何階層上に位置するか」という自分発信のステップ数（自分が1、直属の上司が2、その上が3……）に変わります。

今回の解答例では、最上位のボス（`FINAL_LEADER_NAME`）をスカラ・サブクエリで別途取得しています。
```sql
(SELECT ... FROM hr.employees WHERE manager_id IS NULL)
```
本来、トップダウン探索であれば`CONNECT_BY_ROOT`を使えば一撃で社長が取れますが、今回は探索が逆方向（ボトムアップ）なため、関数だけでは「探索の終着点（一番上）」を全行へ配ることができません。そこで「上司がいない人（`manager_id IS NULL`）＝社長」という絶対的なルールをサブクエリで組み合わせています。

この逆引きのテクニックは、一般的なデータ抽出だけでなく、システムのバックエンドロジックでも役立ちます。「金額が100万円を超えたから、申請者（起点）から社長（ルート）に到達するまでの全承認者のリストを動的に生成する」ワークフロー・電子決裁システム、「あるネジ（末端コンポーネント）に欠陥が見つかった際、そのネジが最終的にどの完成品（車や家電などのルート）に組み込まれているかを特定しリコール対象を絞り込む」製造業の部品構成表（BOM）逆引き、「現在の詳細記事ページ（起点）から所属するカテゴリ、トップページ（ルート）へと遡ってパンくずリストを動的に生成する」Webサイトのパンくずリストなど、応用範囲は幅広いです。

## 解説
階層問い合わせ（`CONNECT BY`）の応用テクニック、`ORDER SIBLINGS BY`（兄弟間のソート）です。

ツリー構造をSQLで扱う際に陥りやすい落とし穴があります。それは、「ツリーを出力したあとに、普通の`ORDER BY`でソートをかけると、せっかくの階層構造（親子関係）が壊れてしまう」という問題です。今回の解答例は、その崩壊を防ぎつつ、同じ親を持つ「兄弟（シブリング）」の間だけで給与順に並び替える、実務のレポート作成でよく使われるテクニックです。

```mermaid
flowchart TD
    subgraph WrongWay["普通のORDER BY salary DESCを使うと..."]
        direction TB
        A1["Steven King (24000)"] --- A2["Neena (17000)"]
        A2 --- A3["別ラインのLisa (11500)
        ← 親子関係を無視して混入！"]
    end
    subgraph RightWay["ORDER SIBLINGS BYを使うと..."]
        direction TB
        B1["Steven King"] --> B2["Neena (17000)
        ← 兄弟内で降順"]
        B1 --> B3["Lex (17000)"]
        B2 --> B4["Nancy (12008)
        ← Neenaの子だけで降順"]
    end
```

このクエリの主役は`ORDER SIBLINGS BY`句です。もし`ORDER BY salary DESC`を使ってしまうと、ツリー構造（誰が誰の部下か）をすべて無視して、全社員が単純に給与の高い順に並び替わります。社長のSteven Kingの下に、突然別ラインの部長や課員が混ざり合い、組織図としては意味をなさなくなってしまいます。一方`ORDER SIBLINGS BY salary DESC`を使うと、「Steven Kingの直属の部下（レベル2のメンバー）」という同じ親を持つ兄弟の集まりの中だけで給与の高い順にソートされ、それぞれの部下の配下（レベル3のメンバー）に移動した際にも、その兄弟間だけで給与順にソートされます。ツリーの枝分かれの形をキープしたまま、各階層の並び順だけをコントロールできるのがこのコマンドの特徴です。

今回の`EMPLOYEE_NAME`列では、視覚的に組織の深さが伝わるような文字列結合を行っています。
```sql
LPAD('-', 2 * (LEVEL - 1), '-') || LEVEL || '. ' || first_name || ' ' || last_name
```

| LEVEL | 計算式 | ハイフンの数 | 表示例 |
| :---: | :--- | :---: | :--- |
| 1（社長） | `2 * (1-1) = 0` | 0個 | `1. Steven King` |
| 2（副社長） | `2 * (2-1) = 2` | 2個 | `--2. Neena Yang` |
| 3（マネージャー） | `2 * (3-1) = 4` | 4個 | `----3. Nancy Gruenberg` |

`LPAD(文字列, 総文字数, 埋める文字)`は、指定した文字数になるまで左側を特定の文字で埋める関数です。レベル1（社長）の場合は`2 * (1 - 1) = 0`文字になるためハイフンは0個、レベル2（副社長など）の場合は`2 * (2 - 1) = 2`文字になるため左側に`--`が付与され、レベル3（マネージャーなど）の場合は`2 * (3 - 1) = 4`文字になり`----`とさらに深くインデントされます。`|| LEVEL || '. '`を後ろに繋げることで、`--2. Neena Yang`や`----3. Nancy Gruenberg`といった、現在の階層深さが数字でも見た目（ハイフンの量）でも分かる文字列が完成します。

この`ORDER SIBLINGS BY`は、「ツリー型の画面表示」のバックエンドでよく使われます。フォルダの階層構造を崩さないまま同じフォルダ内のファイルや子フォルダを名前順・更新日順・サイズ順で並べ替えるファイルシステムのディレクトリツリー、親コメントと返信（子コメント）のツリー構造を維持したまま同じ親に対する返信同士を時系列やいいね順にソートするWebサイトのコメント欄（スレッド表示）、大カテゴリ・中カテゴリ・小カテゴリの親子関係は保ったまま同じ中カテゴリに属する小カテゴリ同士を表示順の優先度に従って並べるECサイトの商品カテゴリマスタなど、応用範囲は幅広いです。

# 【完全版】問題14-7：組織データの整合性チェック（リーフ判定と循環参照の検出）
### 難易度：★★★★☆ (Lv.4)
## 問題
データ移行やシステムの統合、あるいは手動での人事マスター更新の際、「Aの上司がBで、Bの上司がCで、Cの上司がA」といった不正な「循環参照（無限ループ）」がデータに紛れ込んでしまうことがあります。
この状態のデータに対して通常の階層問い合わせを実行すると、データベースは無限ループに陥り、最悪の場合システム停止（クラッシュ）を招きます。
コンプライアンスおよびデータガバナンスの観点から、システムを安全に保護しながら不正なループデータをピンポイントで検出し、同時に「これ以上部下がいない末端の従業員（リーフ）」を特定するための、高度なデータ整合性チェッククエリを構築してください。
HRスキーマの `EMPLOYEES` テーブルの一部のデータをベースとし、インラインビュー（WITH句）を用いて**擬似的に循環参照（100番の上司が102番、102番の上司が100番）を発生させたデータソース**を使用します。
```sql
-- 本問題の検証用データソース（クエリの先頭に配置します）
WITH test_employees AS (
    SELECT 
        employee_id, 
        -- 100番（本来の社長）のマネージャーを敢えて102番に書き換えてループを偽装
        CASE WHEN employee_id = 100 THEN 102 ELSE manager_id END AS manager_id, 
        first_name || ' ' || last_name AS name 
    FROM hr.employees 
    WHERE employee_id IN (100, 101, 102, 103, 104)
)
```
上記の `test_employees` をデータソースとして参照し、`employee_id = 100` を開始地点（`START WITH`）とするトップダウンの階層問い合わせを作成してください。
出力にあたっては以下の条件を満たしてください。
1. **INDENTED_NAME**：階層レベル（`LEVEL`）に応じて、氏名の前に **「-」を2つずつ** インデントとして付与して表示する。
2. **IS_LEAF**：その従業員に部下がいない（末端ノードである）場合は `1`、部下がいる場合は `0` を出力する。
3. **IS_LOOP**：その従業員のデータが原因で **循環参照（ループ）が発生している場合は `1`**、それ以外は `0` を出力する。
4. データ内に循環参照が含まれていても、**エラー（ORA-01436）を出さずに安全にクエリを完結させる**制御を行うこと。

## 期待する結果
| EMPLOYEE_ID | INDENTED_NAME | LEVEL | IS_LEAF | IS_LOOP |
| ----------- | ------------------- | ----- | ------- | ------- |
| 100 | Steven King | 1 | 0 | 0 |
| 101 | --Neena Yang | 2 | 1 | 0 |
| 102 | --Lex Garcia | 2 | 0 | 1 |
| 103 | ----Alexander James | 3 | 0 | 0 |
| 104 | ------Bruce Miller | 4 | 1 | 0 |
