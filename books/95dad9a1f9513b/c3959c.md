# 問題6-1：四則演算

### 難易度：★☆☆☆☆ (Lv.1)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、`EMPLOYEE_ID`が100のデータに対して、給与（`SALARY`）を用いた以下の計算結果を算出してください。

**【算出内容】**

* `SALARY`に`1000`を加算した値（別名：`+`）
* `SALARY`から`1000`を減算した値（別名：`-`）
* `SALARY`に`2`を乗算した値（別名：`*`）
* `SALARY`を`3`で除算した値（別名：`/`）
* `SALARY`を`7`で除算した際の余り（別名：`余り`）

## 期待する結果
| EMPLOYEE_ID | SALARY | +     | -     | *     | /    | 余り | 
| ----------- | ------ | ----- | ----- | ----- | ---- | ---- | 
| 100         | 24000  | 25000 | 23000 | 48000 | 8000 | 4    | 

## 解答例
```sql
SELECT
    employee_id,
    salary,
    salary + 1000     AS "+",
    salary - 1000.    AS "-",
    salary * 2        AS "*",
    salary / 3        AS "/",
    MOD(salary, 7)    AS "余り"
FROM
    hr.employees
WHERE
    employee_id = 100
```

## 解説
ここからは数値データの加工、いわゆる **「計算（算術演算）」** のセクションです。
SQLは単にデータを取ってくるだけでなく、電卓のようにその場で計算して結果を出すのも得意中の得意です。

### 1. 文法解説：算術演算子とMOD関数
Oracle SQLで数値を扱う際の基本ルールは、算数やプログラミングとほぼ同じです。

#### ① 基本の四則演算
SELECT句の中に直接数式を書くことで、行ごとに計算結果を表示できます。

| 演算子 | 意味 | 例 |
| :--- | :--- | :--- |
| **`+`** | 加算（足し算） | `salary + 1000` |
| **`-`** | 減算（引き算） | `salary - 1000` |
| **`*`** | 乗算（掛け算） | `salary * 2` |
| **`/`** | 除算（割り算） | `salary / 3` |



#### ② 剰余（余り）を出す MOD 関数
割り算の「余り」を出したい場合は、記号ではなく **`MOD` 関数**を使います。

```sql
MOD(被除数, 除数)
-- 例: MOD(salary, 7) は「給与を7で割った余り」を返す
```
実務では「偶数行だけ抽出したい（`MOD(ID, 2) = 0`）」といった判定によく使われます。

### 2. ここがポイント：記号の別名（エイリアス）

今回の解答例で注目すべきは、別名の付け方です。

```sql
salary + 1000 AS "+"
```

通常、SQLの別名に `+` や `-` といった演算記号をそのまま使うことはできません（SQLが「計算の指示かな？」と勘違いしてしまうため）。
しかし、**ダブルクォーテーション（`" "`）で囲むことによって、記号そのものを列名として表示させることが可能になります。**

### 3. 実務での注意点：NULLとの計算
数値計算において、絶対に忘れてはならない **「暗黒のルール」** があります。


> **NULLに何をしてもNULLになる**
> もし `SALARY` が `NULL`（未定義）だった場合、どんな計算をしても結果はすべて `NULL` になります。
> * `NULL + 1000` → **NULL**
> * `NULL * 2`    → **NULL**
>
> 実際の開発では、`NVL` 関数などを使って「NULLだったら0として扱う」といった工夫を組み合わせて計算するのが一般的です。

### 4. 計算の優先順位
複数の計算を組み合わせる場合、算数と同じく **「掛け算・割り算」が「足し算・引き算」より先に計算されます。**
もし足し算を先にしたい場合は、`( )`（カッコ）を使いましょう。

* `salary + 1000 * 2` → 1000を2倍してから給与に足す
* `(salary + 1000) * 2` → 給与に1000足してから全体を2倍する

# 問題6-2：端数処理

### 難易度：★☆☆☆☆ (Lv.1)

## 問題

HRスキーマの`EMPLOYEES`テーブルより、`EMPLOYEE_ID`が100のデータに対して、給与（`SALARY`）を「7」で除算した結果に対し、以下の端数処理を行ってください。

**【算出内容】**

* **/**：`SALARY`を`7`で除算した生の値
* **小数点切り捨て**：小数点第2位以下を切り捨て（小数点第1位までを表示）
* **切り捨て**：小数点以下を切り捨てて整数にする
* **四捨五入**：小数点以下を四捨五入して整数にする
* **切り上げ**：小数点以下を切り上げて整数にする

## 期待する結果
| EMPLOYEE_ID | SALARY | /                  | 小数点切り捨て | 切り捨て | 四捨五入 | 切り上げ | 
| ----------- | ------ | ------------------ | -------------- | -------- | -------- | -------- | 
| 100         | 24000  | 3428.5714285714300 | 3428.5         | 3428     | 3429     | 3429     | 

## 解答例
```sql
SELECT
    employee_id,
    salary,
    salary / 7           AS "/",
    TRUNC(salary / 7, 1) AS "小数点切り捨て",
    TRUNC(salary / 7)    AS "切り捨て",
    ROUND(salary / 7)    AS "四捨五入",
    CEIL(salary / 7)     AS "切り上げ"
FROM
    hr.employees
WHERE
    employee_id = 100
```

## 解説
前問の四則演算に続き、今回は算出された数値を「どう見せるか」を制御する**端数処理（丸め処理）** の解説です。
請求書の金額計算や統計レポートなど、実務では「小数点以下をどう扱うか」というルールが厳密に決まっていることが多いため、これらの関数の使い分けは必須スキルとなります。

### 1. 文法解説：数値を整形する3つの主要関数
Oracle SQLで端数を処理する際、以下の3つの関数が主役となります。

#### ① TRUNC 関数（切り捨て）
指定した桁数より右側を、容赦なく切り捨てます。

```sql
TRUNC( [数値], [桁数] )
```
* **`TRUNC(salary / 7, 1)`**: 小数点第1位までを残し、第2位以下を捨てます。
* **`TRUNC(salary / 7)`**: 第2引数を省略すると「0」とみなされ、整数部分のみを残します。

#### ② ROUND 関数（四捨五入）
指定した桁数で、一般的な四捨五入を行います。

```sql
ROUND( [数値], [桁数] )
```
* 今回は $24000 / 7 \approx 3428.5714...$ なので、整数への四捨五入（桁数0）の結果は **3429** になります。

#### ③ CEIL 関数（切り上げ）
「天井（Ceiling）」という意味の通り、その数値以上の**最小の整数**を返します。つまり、小数点以下が少しでもあれば、正の数の場合は上の整数に繰り上がります。

```sql
CEIL( [数値] )
```
* **注意**: `CEIL` は `TRUNC` や `ROUND` と違い、**「小数点第n位で切り上げ」という桁数指定ができません。** 常に整数へ切り上げます。


### 2. 関数ごとの挙動まとめ

今回の $24000 / 7 = 3428.5714...$ を例に、結果を整理してみましょう。

| 関数・書き方 | 結果 | 処理の内容 |
| :--- | :--- | :--- |
| `TRUNC(n, 1)` | **3428.5** | 小数点第1位まで表示（2位以下をカット） |
| `TRUNC(n)` | **3428** | 整数部分のみ表示（小数点以下をカット） |
| `ROUND(n)` | **3429** | 小数点第1位が「.5」以上なので繰り上げ |
| `CEIL(n)` | **3429** | 小数点以下があるため、次の整数へ繰り上げ |

### 3. 実務での使い分けのコツ

* **消費税計算**: 基本は `TRUNC`（切り捨て）が多いですが、業界や取引先との契約によって `ROUND` や `CEIL` が指定されることもあります。
* **平均値の表示**: グラフやレポートで見やすくするために `ROUND(n, 1)`（小数点第1位まで四捨五入）などがよく使われます。
* **ページ数の計算**: 全105件のデータを「10件ずつ」表示する場合、必要なページ数は $105 / 10 = 10.5$ です。このとき `CEIL(10.5)` を使うことで、「11ページ必要」という正しい答えが導き出せます。

### 4. 補足：桁数にマイナスを指定する

実は `TRUNC` や `ROUND` は、第2引数にマイナスの値を指定することで、**「10の位」や「100の位」での処理**も可能です。

* `ROUND(3428, -2)` → **3400**（100の位で四捨五入）
* `TRUNC(3428, -3)` → **3000**（1000の位で切り捨て）

「10円未満はサービス（切り捨て）」といった日本独自の商習慣をSQLで表現する際にも便利ですよ。

<br>

:::message
### 浮動小数点誤差
SQLにおける **浮動小数点誤差（Floating Point Error）** は、特に「お金」や「在庫」を扱うエンジニアにとって、もっとも恐ろしいバグの原因の一つです。

「コンピュータは計算が得意」と思われがちですが、実は**10進数の小数を扱うのが非常に苦手**なのです。

<br>
### 1. なぜ誤差が起きるのか？（原理）
私たちは10進数（0〜9）を使いますが、コンピュータは2進数（0と1）で考えます。
10進数の「0.1」を2進数に変換しようとすると、実は **割り切れずに無限に続く「循環小数」** になってしまいます。

$$0.1_{10} = 0.0001100110011..._2$$

コンピュータはメモリ（保存場所）が有限なので、この無限に続く数字を途中で「えいや！」と切り捨てて保存します。これが**誤差の正体**です。

<br>
### 2. SQLで起きる「怪奇現象」
浮動小数点型（`FLOAT`）を使っていると、以下のようなことが起こります。

<br>
#### ① 「0.1 + 0.2」が「0.3」にならない
多くのシステムで `0.1 + 0.2` を計算すると、内部的には `0.30000000000000004` のような値になります。

<br>
#### ② 「=（イコール）」で検索してもヒットしない
「0.3」を保存したつもりでも、実際には「0.30000000000000004」なので、以下のクエリが空振ります。
```sql
-- 保存した値が 0.3 のはずなのに、1件もヒットしない！
SELECT * FROM orders WHERE total_price = 0.3;
```
<br>

#### ③ 合計が合わない
100万件のデータを足し合わせると、0.00000001の誤差が積み重なり、最終的に数円〜数十円のズレとして現れます。

<br>

### 3. 回避策：どうすればいいのか？

実務で誤差を防ぐためのルールはシンプルです。

<br>

#### 対策1：`NUMBER`型を使う
これらは「固定小数点型」と呼ばれ、10進数のまま正確に保存するように設計されています。**お金を扱うカラムには、絶対に `FLOAT` を使ってはいけません。**

*  `NUMBER(10, 2)`（全体10桁、うち小数2桁）

<br>

#### 対策2：整数で保存する
小数を扱わず、あらかじめ「最小単位（例：円なら1円、ドルなら1セント）」を整数として保存する方法です。
* `10.50ドル` → `1050`（セント単位）として保存。
* 表示するときだけ 100 で割る。
これなら誤差は 0% です。

<br>

#### 対策3：比較するときは「範囲」で指定する
どうしても `FLOAT` 型を比較しなければならないときは、`=` を使わず、誤差を許容する書き方をします。
```sql
-- 0.3 に極めて近い値を探す
WHERE price BETWEEN 0.29999 AND 0.30001;
```
:::

# 問題6-3：数値の書式設定（カンマ・通貨・ゼロ埋め）

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、`DEPARTMENT_ID`が30の従業員を対象として、給与（`SALARY`）を以下のフォーマットで表示してください。なお、レコードの表示順序は問いません。

**【表示ルール】**

* **ID**: `EMPLOYEE_ID`を表示。
* **RAW_SALARY**: `SALARY`をそのまま表示。
* **FORMAT_1**: 3桁ごとにカンマを入れ、先頭に「$」を付与する（例：$12,000）。
* **FORMAT_2**: 3桁ごとにカンマを入れ、先頭に通貨記号「¥」を付与する。
 ※セッション設定に依存せず、SQL内で明示的に「¥」を指定すること。
* **FORMAT_3**: 全10桁とし、空いた左側の桁を「0」で埋めて表示する。

## 期待する結果
| ID  | RAW_SALARY | FORMAT_1   | FORMAT_2 | FORMAT_3 | 
| --- | ---------- | -------- | -------- | ---------- | 
| 114 | 11000      | $11,000  | ¥11,000  | 0000011000 | 
| 115 | 3100       | $3,100   | ¥3,100   | 0000003100 | 
| 116 | 2900       | $2,900   | ¥2,900   | 0000002900 | 
| 117 | 2800       | $2,800   | ¥2,800   | 0000002800 | 
| 118 | 2600       | $2,600   | ¥2,600   | 0000002600 | 
| 119 | 2500       | $2,500   | ¥2,500   | 0000002500 | 


## 解答例

```sql
SELECT
    employee_id AS id,
    salary      AS raw_salary,
    TO_CHAR(salary, '$99,999')  AS format_1,
    TO_CHAR(salary, 'L99,999', 'NLS_CURRENCY = ¥')  AS format_2,
    TO_CHAR(salary, '0000000000') AS format_3
FROM
    hr.employees
WHERE
    department_id = 30
```

## 解説
### `TO_CHAR` 関数：書式モデルの解剖
数値書式（Number Format Mask）において、記号一つ一つには厳格な意味があります。

#### ① `9` と `0` の決定的な違い

* **`9`**: 有効な数字があれば表示し、なければ**空白**を返します。
* **`0`**: 有効な数字があれば表示し、なければ**ゼロ**を返します。
* `FORMAT_3` のように「固定桁数でゼロ埋めしたい」場合は、`0` を並べるのが正解です。

#### ② 通貨記号の指定（`$` と `L`）

* **`$`**: 常にドル記号を表示します。
* **`L`**: セッションの `NLS_CURRENCY` パラメータに基づいた「ローカル通貨記号」を表示します。
* 解答例にある通り、第3引数で `'NLS_CURRENCY = ¥'` と明示的に流し込む手法は、**環境（OSやセッション設定）によって記号が「$」や「￥」に化けるのを防ぐ**ための非常に実戦的なテクニックです。

### 知っておくと差がつく：`FM`（Fill Mode）修飾子

ご提示いただいた解答例を実際に実行すると、結果の先頭に「1文字分の空白」が入ることに気づきましたか？これはOracleが「正負の符号（−）」を表示するために予約しているスペースです。

もし、この余分な空白を除去して期待する結果のように左に詰めたい場合は、フォーマットの先頭に **`FM`** を付加します。

```sql
-- 空白を除去して左詰めにする例
TO_CHAR(salary, 'FM$99,999')
```

これを使うと、表示がよりタイトになり、Webアプリケーションの画面やレポートで扱いやすくなります。

# 問題6-4：データのグループ分け（バケット処理）

### 難易度：★★☆☆☆ (Lv.2)

## 問題

HRスキーマの`EMPLOYEES`テーブルを使用して、部署IDが「90」または「100」の従業員を対象に、給与（`SALARY`）に基づいた「給与ランク」を割り振ってください。

ランク付けは、以下のルールに従って算出してください。

**【グループ化のルール】**

* 給与の範囲を **「2,000以上 〜 22,000未満」** とします。
* この範囲を **「4つの等間隔なグループ（バケット）」** に分割してください。
* 各従業員が属するグループ番号（1〜4）を `SALARY_RANK` として表示します。
* なお、指定した範囲の最大値（22,000）以上の給与を受け取っている場合は、自動的に次のランクである `5` と表示されるようにしてください。

**【表示・ソート条件】**

* 氏名は `FIRST_NAME` と `LAST_NAME` を半角スペースで結合し、列名を `NAME` としてください。
* レコードの表示順序は、**「給与（`SALARY`）の降順」** としてください。

## 期待する結果
| NAME              | SALARY | SALARY_RANK | 
| ----------------- | ------ | ----------- | 
| Steven King       | 24000  | 5           | 
| Neena Yang        | 17000  | 4           | 
| Lex Garcia        | 17000  | 4           | 
| Nancy Gruenberg   | 12008  | 3           | 
| Daniel Faviet     | 9000   | 2           | 
| John Chen         | 8200   | 2           | 
| Jose Manuel Urman | 7800   | 2           | 
| Ismael Sciarra    | 7700   | 2           | 
| Luis Popp         | 6900   | 1           | 

## 解答例

```sql
SELECT
    first_name || ' ' || last_name AS name,
    salary,
    WIDTH_BUCKET(salary, 2000, 22000, 4) AS salary_rank
FROM
    hr.employees
WHERE
    department_id IN (90, 100)
ORDER BY
    salary DESC
```

## 解説
大量の数値を分析する際、「一つひとつの数字を見るのではなく、どの層に何人いるか」を把握したいことがあります。これを実現するのが **`WIDTH_BUCKET`（ウィズ・バケット）関数** です。
統計処理やレポート作成などで、数値を一定の範囲でグループ分け（バケツ分け）したい時に非常に重宝します。

### 核心となる文法：`WIDTH_BUCKET`関数

この関数の役割は、「指定した範囲を等間隔に区切り、対象の数値がどの区間（バケツ）に入るか」を計算することです。

#### 基本構文

```sql
WIDTH_BUCKET(対象カラム, 最小値, 最大値, 分割数)
```

#### この関数が返す値のルール

`WIDTH_BUCKET`は、指定された範囲の外側についても自動的にバケツを割り振る性質を持っています。

| 数値の状態 | 割り振られるバケツ番号 |
| --- | --- |
| **最小値より小さい** | `0` |
| **範囲内（最小値 $\le$ 値 $<$ 最大値）** | `1` 〜 `分割数` |
| **最大値以上** | `分割数 + 1` |


### スクリプトの解説

```sql
WIDTH_BUCKET(salary, 2000, 22000, 4) AS salary_rank
```

今回の条件（2,000〜22,000を4等分）では、1つあたりのバケツの幅は **5,000** になります。

$$(22,000 - 2,000) \div 4 = 5,000$$

具体的には以下の範囲でランクが決定されます：

* **ランク 1**: 2,000 $\le$ 給与 $<$ 7,000
* **ランク 2**: 7,000 $\le$ 給与 $<$ 12,000
* **ランク 3**: 12,000 $\le$ 給与 $<$ 17,000
* **ランク 4**: 17,000 $\le$ 給与 $<$ 22,000
* **ランク 5**: 22,000 $\le$ 給与（**オーバーフロー分**）

問題文の「22,000以上の場合は 5 と表示されるように」という条件は、この関数の標準仕様を利用するだけで解決します。


### 補足：似た関数との違い

よく似た関数に `NTILE` がありますが、動作が全く異なります。

* **`WIDTH_BUCKET`**: 「値の範囲」を等間隔に分ける（各バケツの人数はバラバラになる可能性がある）。
* **`NTILE`**: 「全体の行数」を等分に分ける（各バケツの人数が同じになるように値を割り振る）。

今回のように「給与額という絶対的な基準でランク付けしたい」場合は、`WIDTH_BUCKET` が最適です。

# 問題6-5：符号判定と絶対値による在庫分析（SIGN / ABS）

### 難易度：★★★☆☆ (Lv.3)

## 問題
物流倉庫の在庫管理において、各製品の現在の在庫数（`PRODUCT_INVENTORY`）が、設定されている「適正在庫レベル（今回は一律10個と仮定）」に対して、どの程度乖離しているかを評価するスクリプトが必要です。
単に引き算を行うだけでなく、経営陣へのレポート用に「過剰（プラス）」「不足（マイナス）」「適正（ジャスト）」という状態のラベル分けと、その純粋な乖離の幅（絶対値）を同時に算出し、一目で状況を把握できる高度な数値加工を行います。

COスキーマの`INVENTORY`テーブルより、店舗ID（`STORE_ID`）が `20` のデータを対象に、適正基準値である **「10」** と現在の在庫数（`PRODUCT_INVENTORY`）を比較し、以下のルールで一覧を作成してください。

**【算出のルール】**

* **DIFF（差分）**: `PRODUCT_INVENTORY - 10` の計算結果を表示。
* **STATUS（在庫状態）**: 差分がプラスなら `'過剰'`、マイナスなら `'不足'`、ぴったり `0` なら `'適正'` という文字列を表示してください。
* **ABS_DIFF（乖離幅）**: 不足・過剰を問わず、適正値から「何個ズレているか」の**絶対値**を算出してください。

## 解説
今回の課題は、数値データの加工において非常に便利で、かつコードをスッキリ書くための強力な味方である **`SIGN` 関数（符号判定）** と **`ABS` 関数（絶対値）** のマスターです。
実務のダッシュボードやレポート作成では、単に計算結果の数値を出すだけでなく、「異常値（大きくズレているデータ）」を視覚的に目立たせたり、人間が読めるラベルに翻訳したりする処理が求められます。
解答例のポイントを整理して解説します。

### 1. スクリプトの解説：数値の特徴を捉える2つの数学関数

このクエリでは、適正値「10」からの差分を計算したあと、その数値の「向き（プラス・マイナス）」と「距離（絶対値）」を別々の関数で綺麗に切り分けています。

#### ① SIGN 関数による符号判定

```sql
CASE SIGN(product_inventory - 10)
    WHEN  1 THEN '過剰'
    WHEN -1 THEN '不足'
    WHEN  0 THEN '適正'
END
```

`SIGN` 関数は、与えられた数値の符号に応じて、以下の **3つの値のいずれかのみ** を返す非常に割り切った関数です。

* **引数がプラスの場合**: `1`
* **引数がマイナスの場合**: `-1`
* **引数がゼロの場合**: `0`

これを利用することで、`CASE` 式を `WHEN 1`、`WHEN -1` というシンプルな値の一致判定（単純CASE式）で記述できるようになり、クエリの可読性が格段に向上します。

#### ② ABS 関数による絶対値の抽出

```sql
ABS(product_inventory - 10) AS abs_diff
```

`ABS` は絶対値（Absolute value）を返す関数です。数値からプラス・マイナスの符号を取り除き、**「0からどれだけ離れているか」という純粋な距離**に変換します。
これにより、在庫が「10個足りない（-10）」場合も「10個余っている（+10）」場合も、同じ「10」という乖離幅として扱うことができます。

### 2. 文法・テクニックのポイント

#### SIGN関数を使うメリット（検索CASE式との違い）

`SIGN` 関数を使わなくても、以下のように `CASE WHEN` 句（検索CASE式）を使って同じ結果を得ることは可能です。

```sql
-- SIGN関数を使わない場合
CASE 
    WHEN product_inventory - 10 > 0 THEN '過剰'
    WHEN product_inventory - 10 < 0 THEN '不足'
    ELSE '適正'
END
```

これでも動作は同じですが、条件式（`product_inventory - 10`）を何度も書く必要があり、数式が複雑になったときに記述ミスを誘発しやすくなります。`SIGN` 関数を使って条件式を一箇所にまとめる（カプセル化する）手法は、綺麗でバグの出にくいSQLを書くためのプロの工夫です。

#### ビジネスの視点を反映した ORDER BY

今回のソート順は **`ORDER BY abs_diff DESC`**（乖離幅の大きい順）となっています。
在庫管理において、本当に問題視すべきなのは「適正値から大きく外れている商品」です。このソート順にすることで、重大な在庫不足（-10など）や過剰在庫（+2など）がレポートの最上部に浮き上がってくるため、倉庫の担当者が「次にどのアクションを起こすべきか」を即座に判断できるようになります。

### 3. 実務での活用シーン
この `SIGN` と `ABS` のコンビは、以下のような「基準値とのブレ」を監視する業務全般で大活躍します。

* **予算実績管理**: 予算に対して実績が「上振れ」したか「下振れ」したかを `SIGN` で判定し、その金額のインパクトを `ABS` で測定する。
* **品質・温度管理**: 製造ラインの温度が基準値（例：180°C）から何度ズレているかを監視する。
* **株価・為替分析**: 前日比の騰落判定（プラス転換・マイナス転換）のフラグ立て。

# 問題6-6：比率の算出と0除算（ゼロディバイド）対策

### 難易度：★★★☆☆ (Lv.3)

## 問題
人事部門から、営業職のインセンティブ（歩合給）が総支給額に対してどの程度の割合を占めているかを調査したいという依頼がありました。
インセンティブが設定されていない（`NULL`）社員や、基本給・歩合給の合計が0になる（実務上想定される）イレギュラーなデータに対しても、SQLエラー（`ORA-01476: 除数がゼロです。`）を発生させずに、安全に比率を算出する堅牢なクエリを構築します。

HRスキーマの`EMPLOYEES`テーブルより、`JOB_ID`が「SA_MAN」の従業員、またはIDが`100`の従業員を対象として、以下の計算を行ってください。

* **TOTAL_SALARY（総支給額）**: $\text{基本給(SALARY)} + \text{歩合給(SALARY} \times \text{COMMISSION\_PCT)}$ を計算してください。なお、歩合給が`NULL`の場合は`0`として扱ってください。
* **COMMISSION_RATIO（歩合比率）**: 総支給額に占める歩合給の割合（%）を小数点第1位まで（2位以下切り捨て）で算出してください。
* **0除算対策**: 実務でのデータ不備を想定し、万が一「総支給額」が`0`または`NULL`になった場合でもエラーにせず、結果を`NULL`（または空欄）として安全に処理できるようにしてください。


## 期待する結果
| EMPLOYEE_ID | LAST_NAME | SALARY | TOTAL_SALARY | COMMISSION_RATIO | 
| ----------- | --------- | ------ | ------------ | ---------------- | 
| 100         | King      | 24000  | 24000        | 0                | 
| 145         | Singh     | 14000  | 19600        | 28.5             | 
| 146         | Partners  | 13500  | 17550        | 23               | 
| 147         | Errazuriz | 12000  | 15600        | 23               | 
| 148         | Cambrault | 11000  | 14300        | 23               | 
| 149         | Zlotkey   | 10500  | 12600        | 16.6             |

## 解答例

```sql 
SELECT
    employee_id,
    last_name,
    salary,
    salary + NVL(salary * commission_pct, 0) AS total_salary,
    TRUNC(
        (NVL(salary * commission_pct, 0) / 
         NULLIF(salary + NVL(salary * commission_pct, 0), 0)) * 100, 
        1
    ) AS commission_ratio
FROM
    hr.employees
WHERE
    job_id = 'SA_MAN'
    OR employee_id = 100
ORDER BY
    employee_id
```

## 解説
今回の課題は、実務のレポート作成や給与計算システム等で「絶対に避けては通れないバグ対策」である、**0除算（ゼロディバイド）の回避**ですね。

システムを運用していると、「基本給のマスター設定漏れで合計が0になっていた」「一時的な休職者で支給額が0だった」といったイレギュラーデータがどうしても発生します。そんなとき、クエリがエラー（`ORA-01476`）で落ちてシステムを止めてしまわないよう、SQLの側で安全に受け流すテクニックを解説します。

### 1. スクリプトの解説
このクエリのポイントは、**「不備のあるデータ（`NULL` や `0`）」を段階的に安全な形へ加工している点**にあります。

各項目の計算ロジックは以下の数式に基づいています。

* **総支給額（$Total\_Salary$）**

$$Total\_Salary = Salary + \text{NVL}(Salary \times Commission\_Pct, 0)$$


* **歩合比率（$Commission\_Ratio$）**

$$Commission\_Ratio = \frac{\text{NVL}(Salary \times Commission\_Pct, 0)}{\text{NULLIF}(Total\_Salary, 0)} \times 100$$

この分母の部分に施された工夫が、今回のクエリの心臓部です。

### 2. 文法・テクニックのポイント
#### ① NULLIF 関数による「0除算エラー」の完全防御

SQLの世界では、数値を `0` で割ると即座にシステムエラーが発生します。これを防ぐために **`NULLIF` 関数** を使用しています。

> **`NULLIF( A, B )`**
> 「A と B が**等しい場合は NULL** を返し、異なる場合は A をそのまま返す」という関数です。

今回の記述を見てみましょう。

```sql
NULLIF(salary + NVL(salary * commission_pct, 0), 0)
```

総支給額の計算結果がもし `0` だった場合、この `NULLIF` によって分母が丸ごと **`NULL`** に変換されます。

SQLには「どんな数値も、NULL で割り算をすると結果は NULL になる（エラーにはならない）」という非常に便利な特性があります。これを利用して、エラーを発生させずに結果を綺麗に空欄（`NULL`）に落ち着かせています。

#### ② NVL 関数による「NULLの伝播」のストップ

歩合給の比率（`commission_pct`）が設定されていない一般社員の場合、この列には `NULL` が入っています。
SQLでは、`NULL` が含まれる掛け算や足し算は、結果がすべて `NULL` になってしまう（これを「NULLの伝播」と呼びます）ため、**`NVL(..., 0)`** で明示的に `0` に変換しています。

* `NVL` なし： $24,000 + \text{NULL} = \text{NULL}$ （総支給額が消えてしまう！）
* `NVL` あり： $24,000 + 0 = 24,000$ （正しく計算できる！）

#### ③ TRUNC 関数による切り捨て

問題文に「小数点第1位まで（2位以下切り捨て）」とあります。四捨五入の `ROUND` ではなく、指定した桁数未満をバッサリ切り捨てる **`TRUNC` 関数** を使用し、第2引数に `1` を指定しています。

### 3. 実務でのアドバイス

実務で比率（シェア、達成率、前年比など）を計算するクエリを書くときは、「分母にくる列や数式には、無条件で `NULLIF(..., 0)` をセットする」というのを手癖（ルーティン）にしておくことを強くお勧めします。

# 問題6-7：複数列の横並び比較（GREATEST / LEAST）

### 難易度：★★★☆☆ (Lv.3)

## 問題
マーケティング部門から、商品のプロモーション価格を決定するためのデータ抽出依頼が来ました。
商品ごとに、定価（`LIST_PRICE`）から一律で「20ドル引き」にした値引き価格を検討していますが、あまりに引きすぎると最低販売保証価格（`MIN_PRICE`）を割り込んでしまい、赤字になってしまいます。
「値引き価格」と「最低価格」を横並びで比較し、より高い方の金額を「実際の販売価格」として自動採用するスマートなクエリを実装します。

| 2359       | 249        | 206       | 229         | 229         | 
| 3054       | 600        | 519       | 580         | 580         | 
| 3057       | 369        | 320       | 349         | 349         | 
| 3060       | 299        | 250       | 279         | 279         | 
| 3061       | 499        | 437       | 479         | 479         |

## 解説
今回は、知っているとSQLのコード量が劇的に減り、条件分岐がすっきりと美しくなる **`GREATEST` 関数** のマスターですね。
実務では「下限値を下回ったら下限値に固定する（床引き）」や「上限値を超えたら一律で丸める（天井制限）」といった価格やポイントの計算が頻繁に発生します。これを `CASE` 式で愚直に書くと長くなりがちですが、今回の関数を使えば一撃です。
解答例のポイントを整理して解説します。

### 1. スクリプトの解説：2つの価格を天秤にかける

このクエリの核心は、`FINAL_PRICE`（最終決定価格）を決定している **`GREATEST` 関数** のスマートな動きです。

```sql
GREATEST(list_price - 20, min_price) AS final_price
```

期待する結果のデータを観察すると、`GREATEST` 関数が完璧にピンチを救っているのが分かります。

* **ケースA：通常の値引き（例：製品ID 1726）**
* 定価 259ドル から 20ドルを引くと、値引き価格（`PROMO_PRICE`）は **`239`**。
* 最低価格（`MIN_PRICE`）の `208` と比較すると、239 の方が大きいため、最終価格は **`239`** になります（予定通り値引き成功！）。


* **ケースB：赤字ストッパー発動（例：製品ID 3155）**
* 定価 49ドル から 20ドルを引くと、値引き価格は **`29`** まで落ち込んでしまいます。
* しかし、最低価格は `42`。ここで `GREATEST(29, 42)` が実行され、より大きい **`42`** が自動採用されます。

このように、`CASE` 式による複雑な条件分岐（「もし値引き価格が最低価格を下回ったら〜」）を書くことなく、「赤字ライン（床）を下回らせない」というビジネスルールをたった1行でエレガントに実現しています。


### 2. 文法・テクニックのポイント

#### ① 「縦」の MAX と 「横」の GREATEST

SQLには最大値を求める関数が2つありますが、その方向性の違いをマスターすることがプロへの第一歩です。

| 関数 | 比較の方向 | 特徴 |
| --- | --- | --- |
| **`MAX(列名)`** | **縦方向**（複数行の比較） | `GROUP BY` などと一緒に使い、**テーブル全体の同じ列**の中から一番大きい値を探す。 |
| **`GREATEST(値1, 値2, ...)`** | **横方向**（同じ行内の比較） | **同じ1行の中にある異なる列や数式**を横並びで比較し、一番大きい値を探す。 |

#### ② 【実務の罠】NULL が混ざると全滅する

`GREATEST`（および最小値を選ぶ `LEAST`）を使う際、絶対に忘れてはならない性質があります。それは、**「比較対象の中に1つでも `NULL` があると、結果が強制的に `NULL` になる」** という点です。

もし、新商品などで `MIN_PRICE` が未入力（`NULL`）のデータが紛れ込んでいると、値引き価格がいくらであれ `FINAL_PRICE` が消えてしまいます。実務で使う場合は、以下のように `NVL` で防御力を高めておくのが安全です。

```sql
-- MIN_PRICEがNULLなら0として安全に比較するプロの書き方
GREATEST(list_price - 20, NVL(min_price, 0))
```

### 3. 実務での活用シーン：ビジネスルールの「床」と「天井」

この `GREATEST` と、対になる `LEAST`（最も小さい値を選ぶ）のコンビは、システムのロジックに「制限」をかけるときに大活躍します。

* **ポイント付与の上限制御（天井システム）**
「基本は購入額の10%をポイント付与するが、上限は1回につき5,000ポイントまで」
`LEAST(purchased_amount * 0.1, 5000)`
* **配送リードタイムの下限制御（床システム）**
「注文から出荷までの日数を計算するが、即日出荷だとしてもシステム上、最低1日は確保する」
`GREATEST(ship_date - order_date, 1)`
