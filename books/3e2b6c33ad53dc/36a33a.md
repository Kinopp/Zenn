## 概要 (Abstract)

共通情報モデル（CIM）に基づく電力系統ネットワークの複雑なモデルの継続的な開発は、様々な電力系統運用者間におけるデータの設計、運用性、およびデータ交換を扱っています 。本論文では、アクティブなCIMインスタンスとその履歴バージョンの容易な保存および管理をサポートするデータベース開発への、方法論的なアプローチを提示します 。

提案するアプローチの実装を容易にするために、**自動プログラミングのパラダイム**を適用します 。当社のコードジェネレータは、データベース上のAPI通信レイヤーの開発作業を軽減し、CIMの変更に対する迅速な対応を可能にします 。最後に、テストモデルを用いた性能コスト分析を提示します 。これを通じて、電力系統ネットワークにおけるCIMのより広い普及に貢献することを目指しています 。

* 
**キーワード:** 共通情報モデル（CIM）、データベースモデリング、コードジェネレータ、電力系統、モデルからコードへの変換

## 1. はじめに (Introduction)

電力系統は20世紀半ばからますます使用されるようになっています 。当初、電力系統は単純で孤立したシステムでした 。ネットワークの状態を監視し、電力系統の状態、入力、および出力を追跡するために、送電系統運用者（TSO）は必要なデータを提供するモデルを持つ必要がありました 。1951年、最初の欧州の協会である「欧州送電共同連合（UCTE）」が誕生しました 。UCTEの登場以降、電力の生産、輸送、および配電は異なる会社間でより分離されるようになりました 。

電力部門の送電、発電、配電、および取引活動が分離された後、運用データの容易な交換の可能性はさらに重要性を増しました 。電力市場は、国境を越えた国間の電力フローの増加を引き起こしました 。これは発電パターンの著しい変動をもたらし、あるエリアから別のエリアへ、あるいはある時間から別の時間へと、大量の電力を移動させることになりました 。そのため、近年のデータ交換は劇的に増加しています 。

UCTEが設立されて以来、電力系統を記述するためのモデルである「UCTE DEF」が広く使用されてきました 。UCTE DEFは潮流（パワーフロー）指向のモデルです 。これは電力系統のノード、ライン、および境界ノードに関する基本的かつ必要な情報のみを保持しているため、比較的単純なモデルと言えます 。UCTE DEFは20世紀半ばの欧州のTSOの要件を満たすように設計され 、長年の間は満足のいくモデルとして認識されていましたが 、近年に至ってはその単純さこそが、深刻な限界をもたらす主な原因となりました 。

UCTE DEFの限界に対処するため、1999年に電力系統向けの新しいモデルの開発が開始されました 。それが共通情報モデル（CIM）です 。CIMは現在も進化を続けているモデルであり、国際電気標準会議（IEC）によって管理されています 。開発、協力、および調整の一環として、UCTEの後継である欧州送電系統運用者ネットワーク（ENTSO-E）も、電力系統を記述するための好ましいモデルとしてCIMを受け入れました 。CIMは、システム、ネットワーク、アプリケーション、およびサービスに関する管理情報の共通の定義を提供し、拡張を可能にするネットワーク指向のモデルです 。

CIMの開発には、一連の標準が伴っています 。エネルギー市場システム向けのCIMの一部は、IEC技術委員会57、第13作業部会（TC57 WG13）が運営するIEC 61970標準によってカバーされています 。執筆時点での現在のバージョンは2.4.15であり、そのモデルのバージョンは16.25です 。本研究で参照されているプロファイルは、送電ネットワークに使用される共通グリッドモデル交換標準（CGMES）です 。以下、CIMに言及する場合は、IEC 61970、プロファイルCGMES、標準2.4.15、およびモデルバージョン16.25を指します 。

CIMモデルはUMLを介して定義されます 。CIMのインスタンスは具体的な電力系統のモデルであるため、CIMは電力系統のメタモデルを定義していると言えます 。ここでは、CIMをモデル駆動型開発（MDD）パラダイムに基づくアプローチの初期メタモデルとして捉えます 。

CIMが継続的に進化しているモデルであるという事実にもかかわらず、すでに広く受け入れられており、そのソフトウェアサポートの必要性は絶えず高まっています 。アプリケーションでCIMを使用するベンダーは、それを電力計算機能でどのように使用するかという問題だけでなく、CIMインスタンスをどのように保存するかという課題にも直面しています 。これに関しては、CIMインスタンスのリポジトリとして、初期のモデルインスタンスをデータベースに保存する方法だけでなく、その後のすべての変更をどのように追跡するかという問題もあります 。なぜなら、モデルインスタンスを以前のいくつかの状態のいずれかに復元する可能性を提供するという強い要求があるからです 。

過去の経験から、CIMインスタンスのような複雑なモデルのインスタンスのためのデータベースリポジトリの開発には、単純な解決策が存在しないことが分かっています 。このことから、本研究では、CIMは関係データベーススキーマとして実装可能であり、CIMインスタンスはデータを一切失うことなく最適化された方法で関係データベースに保存されるものと仮定します 。本研究の目的は、データの重複を伴わずにCIMインスタンスを効率的に保存し、変更を追跡し、それらを以前の状態に復元することをサポートする、汎用的なデータベースリポジトリ構造を備えた方法論的アプローチを提案することです 。当社のアプローチをサポートするために、送電網のCIM向けに開発されたソフトウェアアプリケーションを提案します 。

本論文では、関係データベース管理システム（DBMS）の下で、CIMインスタンスの現在（最新）と過去（以前）の両方の状態を保存するためのリポジトリ構造を提案します 。ここで、アクティブモデル（Active Model）**と**履歴モデル（Historical Model）という概念を導入します 。

* 
**アクティブモデル:** CIMインスタンスの現在の状態の指定をサポート 


* 
**履歴モデル:** CIMインスタンスの以前の状態の指定をサポート 



アクティブモデルと履歴モデルの開発は、当社の方法論的アプローチの2つのフェーズに組織化されています 。電力系統のCIM向けソフトウェアアプリケーションは、アクティブモデルと履歴モデルの両方を完全にサポートし 、電力エンジニアの期待や業務のロジックに適合するように設計されています 。

CIMは常に進化しているモデルであるため、このアプリケーションが簡単に保守できることは重要な要件です 。このような要件を満たすために、自動プログラミングのパラダイムを適用しました 。このようにして、データベース上にアプリケーションプログラムインターフェース（API）通信レイヤーを構築する作業を軽減し、CIMの変更に対する迅速な応答を可能にするコードジェネレータを開発しました 。これにより、コードを記述するために必要な作業量と複雑さが大幅に軽減されます 。

2. 
**電力系統におけるCIMの実際の使用に関する研究:** 当社の研究の潜在的なアプリケーションの具体的な例の探索 。


3. 
**CIMインスタンスのデータベース保存戦略に関する研究:** 適切なデータ組織の選択およびデータベースシステム開発への影響 。


4. 
**自動プログラミングパラダイムに関する研究:** 開発時間の短縮や生成されたコードの信頼性向上への影響 。



主に当社のコードジェネレータの開発に影響を与えた研究の選定を以下に提示します 。

文献[16]および[7]では、UCTE DEFからCIMへの移行におけるいくつかの重要なステップが議論されています 。IvanovとChuryは[16]において、「現在のUCTE ASCIIデータ交換フォーマット（UCTE DEF）は、いくつかのデータが不足しており、一部のネットワーク要素が適切な詳細レベルで記述されていないため、計画目的には不十分であることが判明した」と主張しています 。さらに、Brittonとde Vosは[7]において、CIMの成功裏の実装と利用が、TSO間のデータ交換の正確性、品質、および信頼性を大幅に向上させると結論付けています 。本研究では、現在のバージョンのCIM [11]が電力系統に適用されています 。さらに、BrittonとdeVosは[7]、およびBrittonらは[6]でその開発方法を提案しています 。当社のアプローチは、[16]で提案されているデータ交換プロセスに依拠しています 。

IECによって導入されて以来、CIMは電力系統において広範囲に分析され、使用されてきました 。文献[20]では、CIMは電力システムにおけるトポロジのカタログを見つけるためのアルゴリズムのデータモデルとして使用されています 。文献[8]では、電力系統ネットワークを分割するアルゴリズムのデータモデルとなっています 。文献[24]では、電力系統を制御するためのスケジューリングアルゴリズムでCIMが使用されています 。当社のアプローチも、国際的な権威機関によって推奨され、よく知られているCIMに基づいています 。

CIMは、異なるデータの粒度をサポートするのに十分な堅牢性を備えるよう設計されています 。[26]で記述されているように、**バス・ブレーカーモデル**と**ノード・ブレーカーモデル**の両方をCIMを介して表現できます 。文献[8]、[20]、および[26]は、電力工学におけるCIM利用の典型的な例を示しています 。これらは、CIMインスタンスの保存および管理のためのデータベースサポートを提供する拡張として、当社のアプローチが適用可能となる典型的なプロジェクト例です 。

本研究において特に関心の高い論文の1つは、CIMインスタンスを保存するための2つの戦略、すなわち**関係データベースアプローチ**と**RDFベースのデータベースアプローチ**の比較を提示しています 。CIM自体は公式のデータベースモデルを提供していないため、フォーカスは、十分に確立され遍在している関係データベースに対して、比較的新しいRDFベースのデータベースを使用することのメリットとデメリットを見つけることでした 。[28]で結論付けられているように、関係データベースの主な欠点は、すべてのデータをCIM-XMLフォーマットとの間でマッピングしなければならない点にあります 。しかし、速度が速いため、関係データベースの方が好まれます 。

[27]において、Ravikumarらは、当社のアプローチと同様に、オブジェクト関係マッピング（ORM）を介したCIM指向データベース（CIMODB）の設計を提案しています 。Ravikumarら[27]とSchulteら[28]の両者は、NoSQL（より正確にはRDFソリューション）の人気の高まりにもかかわらず、関係（SQL）データベースの選択を支持しています 。関係DBMSの遍在的な使用は、[9]に記載されているように、他技術（特にフェデレーションデータスキーマにおけるNoSQLなど）の使用を排除します 。他の多くの研究（[19]や[23]など）では、標準、一貫性、親しみやすさ、成熟度、およびメンテナンスの欠如を理由に、著者らはNoSQLデータベースに対してやや慎重な姿勢をとっています 。主に[27]、[28]、[9]、[19]、[10]、[23]で提示された結果に基づき、本研究では関係データベースアプローチを使用しています 。

自動プログラミングはプログラミングパラダイムとして、ソフトウェアプログラミングの非常に初期の段階から、多くのソフトウェア開発プロジェクトで頻繁に使用されてきました 。CIMは約600のクラスで記述されているため、その仕様は大規模で複雑なモデルのクラスに属します 。このようなシステムを設計する際に論理的なエラーを犯す確率は高いです 。手作業でデータベースプロシージャやAPI通信レイヤーを開発するために必要な時間も膨大になります 。したがって、DBMSの下でモデルとしてのCIMの実装プロセスをサポートするコードジェネレータの開発が必要であると特定しました 。

コードジェネレータは、入力として高レベルの記述を受け取り、低レベルのコードを生成します 。つまり、ジェネレータへの入力仕様は、生成されるコードよりも単純で短くなります 。[18]では、設計されたプロセスをよりよく反映したアプリケーションを構築するために、シーケンス図を伴うUMLが使用されています 。[1]において、AblonskisとNemuraitėは、プログラムコードを生成するためのテンプレートの合成に後で再利用できる、モデルからコードへの変換パターンを検出しています 。[3]、[12]、および[2]の著者らは、データベースモデルとテンプレートから始めて、アプリケーションのさまざまなレイヤーを生成しています 。さらに、[22]では、モデルを変換してSoftware-as-a-Serviceアプリケーションを生成するためにテンプレートが使用されています 。当社の研究では、CIMのUML表現をコードジェネレータの入力仕様として使用します 。

## 3. CIMの構造とデータ交換 (CIM structure and data exchange)

標準としてのCIMの主な目的の1つは、異なるベンダーのソフトウェアを使用するENTSO-Eのメンバーが、ENTSO-Eのビジネス活動で要求されるネットワークモデルインスタンスをどのように交換するかを定義することです 。したがって、このセクションでは、CIMモデルの内部構造と、それに基づくデータ交換のプロセスを提示します 。

CIMインスタンスはXMLファイルフォーマットで保存されます 。データは以下の**9つのファイル**に分割されます 。

* 機器 (Equipment)
* 機器境界 (Equipment Boundary)
* トポロジ (Topology)
* トポロジ境界 (Topology Boundary)
* 状態変数 (State Variables)
* ダイナミクス (Dynamics)
* 図面 (Diagrams)
* 地理データ (Geographical Data)
* 定常状態仮説 (Steady State Hypothesis) 



これら9つのファイルすべてからの情報が、1つの完全なCIMインスタンスを表します 。

CIMは、抽象クラスと具体的なクラスで構成される階層モデルです 。これらのクラスを通じて、CIMは特定の時間（毎時間）における電気電力系統の物理的性質とその状態をマッピングします 。抽象クラスはシステムの複雑さを緩和するために使用され、基本属性と関連をグループ化して定義し、システムのより汎用的なコンポーネントとそうでないコンポーネントを区別します 。

対照的に、システムの実際の（具体的な）コンポーネントは具体的なクラスによって記述され、具体的なクラスは抽象クラスから多くの属性と関連を継承します 。図1（CIMモデルの抜粋）に示すように、具体的なクラスは抽象クラスに依存しています 。図1において、`Equipment Container` と `Equipment` は抽象クラスを表し、`Substation`、`Voltage Level`、および `Base Voltage` は具体的なクラスを表します 。ここでは、これらのクラスの関係にのみ関心があるため、クラスの意味については議論しません 。

モデルインスタンスに加えられた変更は、更新されたもの、新しいもの、および削除されたものの情報のみを含む差分ファイル（difference files）によって交換されます 。差分ファイルが受信されると、それらはモデルインスタンスに適用されます 。CIMの主な利点の1つは、モデルインスタンス全体を交換することなくデータを維持できる点にあります 。1つの会社によって行われた1つのモデルインスタンスへの変更は差分ファイルにエクスポートされ、同じネットワークのモデルインスタンスを維持する必要がある他の関心のある当事者に送信されます 。差分ファイルはXML形式のファイルです 。

セクション4では、CIMの階層構造に依存する、運用データベースのモデリングプロセスを提示します 。また、差分ファイルの使用に基づくCIM交換プロセスは、セクション5で説明する履歴モデルのための方法論的アプローチを開発するための基礎となります 。

## 4. アクティブモデル (Active model)

このセクションでは、方法論的アプローチの第1フェーズを提示します 。CIMインスタンスを保存することを目的としたCIM指向データベースをモデル化する、アクティブモデル（図2）について説明します 。アクティブモデルはCIMモデルの表現であり、CIMの各クラスがアクティブモデル表現を持っています 。CIMインスタンスを保存するために関関係データモデルパラダイムを選択したため、当社のアクティブモデルは関係DBMSの下で実装されます 。このデータベースをアクティブデータベース（Active Database）と呼びます 。

このフェーズにおける主な目標は、CIMインスタンスの保存と、それらへの容易かつ高速なアクセスを提供することです 。目標を達成するために、このフェーズは3つのステップに分かれています 。

1. CIMモデルと比較したアクティブモデルの分析、および典型的なアプローチが目標を満たさない理由の議論 


2. アクティブモデルを作成するための手順の策定 


3. アクティブデータベースの実装 



### 第1ステップ: アクティブモデルの分析

CIMの用語において、抽象クラスはいわゆる「抽象テーブル」にマッピングされ、具体的なクラスは「具体的なテーブル」にマッピングされます 。アクティブモデルでは、CIMの一部ではないBase Objectクラスを表す `BASE_OBJECT` テーブルを導入します 。これを導入するのは、すべてのテーブルがサロゲート主キー（`BASE_OBJECT_ID` 属性）を持つようにするためであり、これはBase Objectクラスを表すテーブルからの外部キーになります 。

`Identified Object`、`Equipment Container`、および `Equipment` クラスを表す抽象テーブルは、属性（列）や参照（外部キー）を含めずに作成されます 。これらの属性は、`Substation`、`Voltage Level`、および `Base Voltage` クラスを表す子である具体的なテーブルに含める方が都合が良いからです 。したがって、これらの具体的なテーブルには、それらの親テーブルからの属性が含まれます 。

概念的に類似したモデルを作成するための2つの典型的なアプローチ（Enterprise ArchitectによるSQL生成、または一般的なORMフレームワークによるテーブル・フォー・クラス（クラスごとのテーブル作成））について議論します 。しかし、多くの階層レベルを持つCIMのように複雑なモデルでは、CIMが比較的多数の抽象エンティティを持っているという潜在的な問題があります 。単にクラスごとにテーブルを作成した場合、いずれかのテーブルからデータを読み取るための単純なSELECTクエリを記述することが困難になります 。親クラスからマッピングされたデータを保持する各親テーブルに到達するために、**多くのJOIN句を使用しなければならなくなります** 。JOIN句が多くなればなるほど、クエリの速度は遅くなります 。しかし、当社の目標は、容易かつ高速なアクセスを提供することです 。

### 第2ステップ: 特定のORM手法の策定

当社のアプローチでは、特定の方法でORMを実行します 。

* 
**第一に、** クラスの属性を具体的なクラスに対してのみ、継承された属性を含めてテーブル代表にマッピングします 。


* 
**第二に、** 抽象クラスを表すテーブルは、列を含めずキーのみで作成されます 。抽象クラスは関係を適切に配置するために必要です（例: `Equipment` は抽象クラスである `Equipment Container` への関係を必要とする） 。


* 
**最後に、** 親の参照は具体的な子テーブルにのみ外部キーとしてマッピングされます 。



そうすることにより、**JOIN句を使用せずに、わずか1つのテーブルから必要なすべてのデータを取得することが可能になります** 。これにより、すべてのデータ属性が具体的なテーブルに押し下げられ（プッシュダウンされ）、抽象テーブルはモデルの骨組み（スケルトン）を形成します 。

### 第3ステップ: アクティブデータベースの実装

CIMモデルには約600のクラスがあり、そのうちの約200が具体的なクラスです 。ここで、CIM-XML構造化データを関係データベースにマッピングします 。手作業での実装作業（SQLコマンド、データベースプロシージャ、API通信レイヤーの記述）は非常に高くなる可能性があるため 、コードジェネレータ（Code Generator）の作成を提案します 。

当社のコードジェネレータはCIM UML仕様を読み込み、C#のCIMクラスで構成されるCIMオブジェクトモデルを生成します（開発にはCodeDomフレームワークを使用） 。次に、ORMを指定するXMLファイルが生成され、ORMフレームワークである **NHibernate** を使用してアクティブデータベースが作成されます 。

コードジェネレータは、選択されたDBMSの提供されたメカニズムを完全に活用する方法で、データベースストアドプロシージャを作成します 。

* 
**挿入（Insert）:** まず親テーブル（キーのみ）にデータを挿入し、その後、対応する具体的なテーブルに挿入します 。


* 
**更新（Update）:** 具体的なテーブルでのみデータを更新します 。


* 
**削除（Delete）:** 行はまず具体的なテーブルから削除され、次にそのすべての親テーブルから削除されます 。



データベースのストアドプロシージャを使用することで、速度が向上し、通信が簡素化されます 。このアクティブデータベースの設計により、読み取りおよび更新に対してJOIN句のないクエリを記述することが可能になり、潮流計算（ロードフロー）のような電力計算における最新状態へのアクセスにおいて重要となります 。同様のアプローチが[10]で適用されており、そこでは時間性能が大幅に向上しています 。

モデルインスタンスの変更の追跡、モデルインスタンスの復元、分析、統計、またはその他の計算のための履歴データの使用を提供するために、アクティブモデルを拡張する必要があります 。この拡張について次のセクションで議論します 。

## 5. 履歴モデル (Historical model)

CIMインスタンスの状態が記録される履歴モデル（図4）を提示します 。履歴モデルはアクティブモデルの拡張であり、アクティブモデルの具体的なテーブルに対する変更を追跡します 。必要なデータはすべて具体的なテーブルにあるため、抽象テーブルに対する変更は追跡しません 。履歴モデルを用いて、履歴データベース（Historical Database）を実装します 。

このフェーズにおける主な目標は、CIMインスタンスの変更追跡を提供すること、および変更が実行される前の選択された状態にモデルインスタンスを復元する方法を提供することです 。このフェーズは4つのステップに分かれています 。

### 第1ステップ: 単一要素の変更追跡

アクティブモデルの各具体的なテーブルの変更を追跡するために、各具体的なクラスの以前の状態を保存する新しい履歴テーブルを作成します 。たとえば、`Substation` クラスに対しては `SUBSTATION_H` テーブルが作成されます 。すべての履歴テーブルは、`BASE_OBJECT_H` テーブル（Base Object Historyクラスを表す）からのサロゲート主キーを持ち、このテーブルは `BASE_OBJECT` テーブルを介してアクティブモデルと接続されています 。

`Base Object History` は、どのアクション（**Insert, Update, Delete**）が行われたかという情報を保存します 。アクティブデータベースの要素に対して何らかのアクションが実行される前に、対応する履歴テーブルに新しいレコード（**履歴要素: history elements**）を作成することによってその状態が記録されます 。

履歴テーブルのみを持つことで、単一の要素レベルのみで効率的に変更を追跡する可能性が提供されますが 、すべての履歴テーブルを日付と時間で比較して検索する必要があるため、特定の時点にモデルインスタンス全体を復元することは非常に困難（高負荷）になる可能性があります 。

### 第2ステップ: 複数要素の同時変更のグループ化（差分グループ）

複数の要素に対して同時に加えられた変更をグループ化する構造を差分グループ（difference group）と呼び、これは差分ファイルを代表するものです 。履歴テーブルは `BASE_OBJECT_H` を介して `DIFFERENCE` テーブルに接続されており、各行が1つの差分グループを表します 。

これにより、履歴要素が差分グループへとグループ化され（図5参照）、1つのトランザクション内で同時に加えられた変更を見つけやすくなります 。各差分グループとともに、モデルインスタンスを有効な状態（依存関係を壊さない状態）で復元できるチェックポイントも作成します 。これにより、1つの変更グループを元に戻すために履歴データベース全体を日付と時間で検索する必要がなくなります 。

しかし、差分の連鎖が長くなると（例: Diff1とDiff2の2つのグループを遡る場合、履歴要素の重複を避けるために大量のデータを比較する必要が生じるなど）、復元はより複雑になり、差分グループが多くなればなるほど復元に時間がかかります 。

### 第3ステップ: モデルインスタンス復元のための構造（スライス）

モデルインスタンスを高速に元に戻す（リバートする）ため、`Base Object History` テーブルに `is_first` と `is_last` フラグを追加します 。これにより、ある要素の履歴のうち「最初」と「最後」の履歴要素をそれぞれ追跡します 。

新しく導入する構造は以下の通りです：

* 
**変更前のグループ (before group of changes):** 図4の `BEFORE` テーブルで表されます 。新しい変更を適用する前に、`is_last` フラグを持つすべての履歴要素がここに記録され、差分グループに接続されます 。


* 
**変更後のグループ (after group of changes):** 変更前グループが形成された後に作成された履歴要素で構成されます 。これは独立したテーブル構造ではなく、`is_first` フラグと変更前グループによって定義されます 。



このステップの最後に、対応する変更前と変更後のグループをスライス（slice）へと結合します 。1つのスライスは、いずれかのチェックポイントの前にモデルインスタンスを復元するために元に戻さなければならない、必要なすべての変更を含んでいます 。各差分グループには、有効なモデルインスタンスを復元するためにアンドゥするための独自のスライスがあります 。

図8に示すように、初期の状態に復元するには最も多くのデータを元に戻す必要がありますが、スライスを適用すれば、最新の変更を元に戻すために必要なデータは少なくなります 。

> 
> 表1: 単一履歴要素の復元（リバート）アルゴリズムの動作要約 * **Insertアクション状態:** `is_first` がtrueでアクティブモデルに存在する場合は「削除（remove）」を実行、存在しない場合は「何もしない（do nothing）」を実行 。`is_first` がfalseで存在する場合は「復元（revert）」、存在しない場合は「追加（add）」を実行 。
> * **Updateアクション状態:** アクティブモデルに存在する場合は「復元（revert）」、存在しない場合は「追加（add）」を実行 。
> * **Deleteアクション状態:** `is_first` がtrueで存在する場合は「復元（revert）」、存在しない場合は「追加（add）」を実行 。`is_first` がfalse（テキスト中一部フラグ表記揺れあり）で存在する場合は「削除（remove）」、存在しない場合は「何もしない」を実行 。
> 
> 

### 第4ステップ: 履歴データベースの実装

200の具体的なクラスすべてについて履歴クラスを作成し、テーブルにマッピングし、ストアドプロシージャとAPI通信レイヤーを作成する作業は非常に高負荷です 。そのため、コードジェネレータを拡張して履歴データベースの作成にも対応させました 。

コードジェネレータは、アクティブデータベースに変更が適用される前に、履歴データベースに履歴要素を作成するプロシージャ（アクティブ側プロシージャへの呼び出しを含む）を生成します 。これにより、CIMインスタンスに対するすべての変更が自動的に追跡され、要求に応じて任意の状態に復元可能となります 。これは、モデルインスタンスの保存、追跡、復元を最適化する新しいアプローチです 。

## 6. 評価 (Evaluation)

テストはPC環境（CPU: Intel Core 2 Duo E7500 2.93GHz, RAM: 8GB, DBMS: Oracle Database 11g Express Edition）で実行されました 。

### 性能測定結果の要約

* 
**アクティブモデルの読み取り（図9）:** XMLファイルからの読み取り時間とデータベースからの読み取り時間の双方とも、要素数に対して**線形（リニア）に依存**します 。また、読み取り速度は履歴データの量によって影響を受けません 。


* 
**モデルの挿入（図10）:** データベースへの挿入時間も線形に依存します（要素数500〜240,000に対し、所要時間は1.7秒から620秒） 。ただし、シリアル化を用いるXMLファイル保存（1.2秒〜2.5秒）と比較すると、複雑なテーブル構造に従うためデータベースへの挿入は著しく遅くなります 。


* 
**履歴追跡を伴う変更の保存（図11）:** すべての操作で変更前状態の記録が発生するため、処理負荷は上がりますが、平均して**履歴追跡を伴う変更には65%多い時間しか必要としません** 。要素数170〜86,000に対し、履歴ありのデータベース保存は2.1秒〜740秒（履歴なしは1秒〜475秒、XML保存は1.2秒〜4.2秒）です 。これは関係DBMSの全機能を活用した生成ストアドプロシージャの効果です 。なお、実験では全要素の約45%に変更が加えられました 。


* 
**モデルの復元（図12）:** 現在のモデルインスタンスを読み取った後、スライスを適用して復元を完了するまでには、平均して**75%多い時間が必要**となります 。これは、復元すべき変更を日付等から都度検索するのではなく、チェックポイントを表すスライスから単純に読み取るために高速化されています 。



### 生成されたコード行数

一般的な目的のソリューションでは全コード行数の48%〜75%の自動生成にとどまる例が多い中、当社はAPI通信レイヤーとデータベース関数に焦点を絞ることで、**全コード行数の約95%を自動生成**することに成功しました 。これは複雑な方法論的アプローチを支える上で優れた結果であると考えています 。
