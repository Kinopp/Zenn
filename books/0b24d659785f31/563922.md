# 問題10-1：内部結合（複数テーブルの結合）

### 難易度：★★☆☆☆ (Lv.2)

## 問題
OEスキーマの各テーブルを使用して、注文ID（`ORDER_ID`）が「2454」である注文の詳細データを取得してください。
この問題では、注文、顧客、注文明細、商品の計4つのテーブルを適切に結合する必要があります。なお、結果の表示順は問いません。

**【取得項目と編集ルール】**

* **ORDER_DATE**：`ORDERS`テーブルより取得。「YYYY-MM-DD HH24:MI:SS」形式の文字列に変換してください。
* **CUSTOMER_NAME**：`CUSTOMERS`テーブルの`CUST_FIRST_NAME`と`CUST_LAST_NAME`を半角スペースで結合してください。
* **PRODUCT_NAME**：`PRODUCT_INFORMATION`テーブルより取得してください。
* **QUANTITY**：`ORDER_ITEMS`テーブルより取得してください。


## 期待する結果
| ORDER_DATE          | CUSTOMER_NAME  | PRODUCT_NAME    | QUANTITY | 
| ------------------- | -------------- | --------------- | -------- | 
| 2007-10-02 16:49:34 | Manisha Taylor | PS 12V /P       | 3        | 
| 2007-10-02 16:49:34 | Manisha Taylor | MB - S600       | 0        | 
| 2007-10-02 16:49:34 | Manisha Taylor | Video Card /E32 | 12       | 
| 2007-10-02 16:49:34 | Manisha Taylor | KB 101/ES       | 120      | 
| 2007-10-02 16:49:34 | Manisha Taylor | Resin           | 18       | 
| 2007-10-02 16:49:34 | Manisha Taylor | Screws <B.32.P> | 16       | 
| 2007-10-02 16:49:34 | Manisha Taylor | Screws <S.32.S> | 13       | 


## 解答例
```sql:例1：INNER JOINを使用
SELECT
    TO_CHAR(o.order_date, 'YYYY-MM-DD HH24:MI:SS')  AS "ORDER_DATE",
    c.cust_first_name || ' ' || c.cust_last_name  AS "CUSTOMER_NAME",
    p.product_name,
    oi.quantity
FROM
    oe.order_items                   oi
    INNER JOIN oe.orders              o 
       ON oi.order_id = o.order_id
    INNER JOIN oe.customers           c 
       ON o.customer_id = c.customer_id
    INNER JOIN oe.product_information p 
       ON oi.product_id = p.product_id
WHERE o.order_id = 2454
```
```sql:例2：使用するテーブルをカンマで区切る方法
SELECT
    TO_CHAR(o.order_date, 'YYYY-MM-DD HH24:MI:SS')  AS "ORDER_DATE",
    c.cust_first_name || ' ' || c.cust_last_name  AS "CUSTOMER_NAME",
    p.product_name,
    oi.quantity
FROM
    oe.order_items         oi,
    oe.orders              o,
    oe.customers           c,
    oe.product_information p
WHERE
        o.order_id = 2454
    AND oi.order_id = o.order_id
    AND o.customer_id = c.customer_id
    AND oi.product_id = p.product_id
```
```sql:例3：USINGを使用（例1の派生）
SELECT
    TO_CHAR(order_date, 'YYYY-MM-DD HH24:MI:SS')  AS "ORDER_DATE",
    c.cust_first_name || ' ' || c.cust_last_name  AS "CUSTOMER_NAME",
    p.product_name,
    oi.quantity
FROM
    oe.order_items                   oi
    INNER JOIN oe.orders              o 
       USING(order_id)
    INNER JOIN oe.customers           c 
       USING(customer_id)
    INNER JOIN oe.product_information p 
       USING(product_id)
WHERE order_id = 2454
```

## 解説
複数のテーブルからバラバラになった情報をパズルのように組み合わせる「結合（JOIN）」は、SQLの醍醐味であり、最も実力を試される部分です。今回は「注文内容」を中心に、顧客情報と商品情報を紐づける実践的なクエリです。

### 1. 内部結合
内部結合（INNER JOIN）は、SQLで最も頻繁に使われる結合方法です。一言でいうと、**「複数のテーブル間で、指定した条件が両方に存在するデータのみを結びつける」**　という仕組みです。
![](https://storage.googleapis.com/zenn-user-upload/1252567be480-20260320.png)


#### ① 内部結合の仕組み
内部結合は、ベン図でいうところの「重なり合った部分（積集合）」を取り出します。
![](https://storage.googleapis.com/zenn-user-upload/ed0661145cce-20260320.png =180x)


#### ② 条件に合わないデータは「消滅」する
例として、下記２つのテーブルがあるとします。
* **社員テーブル**: 社員全員の情報が網羅されています。
* **資格テーブル**: 資格を保有している社員がどのような資格を持つかの情報が存在します（**資格がない社員のデータはありません**）。

これらを「社員ID」などで内部結合すると、**資格を持っていない社員の情報は、検索結果から消えてしまいます。**

内部結合は、**「結合する両方のテーブルに存在するデータのみ」** を抽出する仕組みです。そのため、片方の「資格テーブル」にデータが存在しない社員は、結合の条件から漏れてしまい、出力対象外となってしまうのです。


### 2. 結合の全体像：データの「ハブ」を見極める
今回のクエリでは、4つのテーブルが以下のような関係で繋がっています。

1.  **`ORDERS`（注文）**: 全体の中心。誰が（`customer_id`）いつ注文したかを管理。
2.  **`CUSTOMERS`（顧客）**: 顧客の名前情報を保持。`ORDERS` と `customer_id` で結合。
3.  **`ORDER_ITEMS`（注文明細）**: 注文の「中身（どの商品を何個か）」を保持。`ORDERS` と `order_id` で結合。
4.  **`PRODUCT_INFORMATION`（商品情報）**: 商品の名前を保持。`ORDER_ITEMS` と `product_id` で結合。


### 3. 3つの書き方の違いと実務での評価
解答例には3つのパターンがありますが、現場での使われ方は大きく異なります。

#### ① INNER JOIN ... ON（例1）：王道の書き方
最も標準的で、現在主流の書き方です。
* **メリット**: 「どのテーブルとどのテーブルを、何の条件でくっつけるか」が1セットで書けるため、非常に読みやすいです。
* **実務**: ほとんどのプロジェクトでこの書き方が推奨されます。

#### ② カンマ区切りと WHERE 句（例2）：古き良き（？）Oracleスタイル
Oracleの古いバージョンでよく使われていた書き方です。
* **注意点**: 結合条件（JOIN）と抽出条件（WHERE）が混ざり合うため、テーブルが増えると「結合し忘れ（デカルト積）」という大惨事を招きやすいです。
* **実務**: 既存の古いシステムの保守などで見かけることがありますが、新規作成時は例1を使うのがプロの証です。

#### ③ USING 句（例3）：名前が同じなら使える「時短」テクニック
結合するカラム名が両方のテーブルで全く同じ（例：両方とも `order_id`）場合に使える書き方です。
* **メリット**: `oi.order_id = o.order_id` と書く手間が省け、コードがスッキリします。
* **実務**: 便利な一方で、テーブル設計によってはカラム名が違うこともあるため、汎用性は `ON` の方が高いです。


### 3. その他の重要テクニック

#### フォーマットと加工
* **`TO_CHAR`**: 日時を秒まで指定された形式に整えています。
* **`|| ' ' ||`**: 名字と名前を繋げ、さらに間にスペースを挟むことで「フルネーム」という新しい項目を作り出しています。

#### 実行順序のヒント
データベースは、4つのテーブルをすべてくっつけて「巨大な1つの表」を作ってから、最後に `WHERE o.order_id = 2454` で必要な行だけをシュッと抜き出します。


### 4. 期待する結果の確認
結果を見ると、Manisha Taylorさんが1回の注文（2454番）で、ネジ（Screws）やビデオカードなど、複数の商品をまとめて購入している様子が分かります。
「1つの注文に複数の明細（商品）がぶら下がっている」という、**1対多（One-to-Many）** の関係が結合によって1つのリストとして可視化されました。

### **ORA-00918: 列の定義が未確定です（column ambiguously defined）**

SQL初心者が必ずといっていいほど遭遇する「ORA-00918」エラーについて説明します。
<br>

### 1. エラーの本質：何が起きているのか？
複数のテーブルを結合（JOIN）して検索する際、それぞれのテーブルに同名の列が存在することがあります（例：`ID`、`NAME`、`CREATED_AT` など）。
SQLの中でその列名を単独で書くと、Oracleは「どのテーブルのデータを取り出せばいいのか」を判断できず、処理をストップさせます。
<br>
### 2. 具体的な発生パターンと修正例

#### ダメな例（NG）

`EMPLOYEES`テーブルと`DEPARTMENTS`テーブルの両方に `DEPT_ID` という列がある場合：

```sql
SELECT DEPT_ID, EMP_NAME, DEPT_NAME
FROM EMPLOYEES E
JOIN DEPARTMENTS D ON E.DEPT_ID = D.DEPT_ID;
```

> **エラーの理由:** `SELECT`句にある `DEPT_ID` が、`EMPLOYEES`のものか `DEPARTMENTS`のものか区別がつきません。

<br>
#### 修正案：テーブル名（または別名）で修飾する

どのテーブルの列かを明示します。通常は、短く書くために**テーブル別名（エイリアス）**を使います。

```sql
SELECT E.DEPT_ID, E.EMP_NAME, D.DEPT_NAME
FROM EMPLOYEES E
JOIN DEPARTMENTS D ON E.DEPT_ID = D.DEPT_ID;
```

<br>

### 3. 注意点と陥りやすいポイント

#### ① WHERE句やORDER BY句での漏れ

`SELECT`句だけ直しても、他の場所で指定が漏れているとエラーになります。

* `WHERE DEPT_ID = 10` → `WHERE E.DEPT_ID = 10`
* `ORDER BY DEPT_ID` → `ORDER BY E.DEPT_ID`

<br>

#### ② USING句を使用する場合の特殊ルール

`JOIN`で `ON` ではなく `USING` を使う場合、**逆にテーブル修飾をしてはいけない**という特殊なルールがあります。

* **NG:** `SELECT E.DEPT_ID FROM EMPLOYEES E JOIN DEPARTMENTS D USING (DEPT_ID);`
* **OK:** `SELECT DEPT_ID FROM EMPLOYEES E JOIN DEPARTMENTS D USING (DEPT_ID);`

> `USING` を使うと、Oracle内部でその列が「結合キー」として1つに統合されるため、修飾すると逆に「未確定（あるいは不適切）」とみなされることがあります。

<br>

#### ③ インラインビュー（サブクエリ）での列名重複

サブクエリの中で同名の列を複数SELECTしていると、外側のクエリでそのサブクエリを呼んだ時に ORA-00918 が発生します。

```sql
-- サブクエリ内で名前が重複している例
SELECT * FROM (
    SELECT E.ID, D.ID FROM EMPLOYEES E, DEPARTMENTS D
) -- ここで「ID」という名前の列が2つできてしまう

```

この場合は、サブクエリ内で `D.ID AS DEPT_ID` のように別名をつけて重複を回避する必要があります。

<br>

### 4. トラブルを防ぐためのベストプラクティス

1. **常にエイリアス（別名）を使う**：
単一テーブルのクエリであっても、将来的にJOINが増える可能性があるため、最初から `T1.COLUMN` のようにテーブル別名をつけて書く癖をつけると安全です。
2. **SELECT * を避ける**：
`SELECT *` を使うと、意図せず同名の列を複数取得してしまい、後の処理（特にビューの作成時など）で混乱を招きます。
3. **共通列の命名規則**：
可能であれば、システム設計時に「どのテーブルのIDか」がすぐわかる名前（`EMP_ID` と `DEPT_ID` など）にするのが理想的です。
:::

# 問題10-2：外部結合１（LEFT OUTER JOIN）

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`COUNTRIES`テーブルにあるすべての国ID（`COUNTRY_ID`）を取得してください。あわせて、SHスキーマの`COUNTRIES`テーブルから対応する「国名（`COUNTRY_NAME`）」も取得してください。

**【抽出・編集ルール】**

* **結合条件**：HRスキーマの `COUNTRY_ID` と、SHスキーマの `COUNTRY_ISO_CODE` を比較して結合してください。
* **外部結合の利用**：HRスキーマ側にある国はすべて表示し、SHスキーマ側にデータが存在しない場合でも結果に含めてください。
* **NULLの扱い**：SHスキーマに該当する国名が存在しない場合は、「SHに存在しない」という文字列を表示してください。

## 期待する結果
| COUNTRY_ID | COUNTRY_NAME             | 
| ---------- | ------------------------ | 
| US         | United States of America | 
| DE         | Germany                  | 
| GB         | United Kingdom           | 
| NL         | Netherlands              | 
| DK         | Denmark                  | 
| FR         | France                   | 
| BR         | Brazil                   | 
| AR         | Argentina                | 
| JP         | Japan                    | 
| IN         | India                    | 
| AU         | Australia                | 
| CA         | Canada                   | 
| CN         | China                    | 
| SG         | Singapore                | 
| IT         | Italy                    | 
| MX         | Mexico                   | 
| CH         | Switzerland              | 
| NG         | Nigeria                  | 
| EG         | Egypt                    | 
| ZW         | Zimbabwe                 | 
| KW         | Kuwait                   | 
| IL         | Israel                   |

| ML         | SHに存在しない           | 
| BE         | SHに存在しない           | 


## 解答例
```sql:例1：LEFT JOINを使用
SELECT
    h.country_id,
    COALESCE(s.country_name, 'SHに存在しない') AS "COUNTRY_NAME"
FROM
    hr.countries h
    LEFT OUTER JOIN sh.countries s 
      ON h.country_id = s.country_iso_code
```
```sql:例2：使用するテーブルをカンマで区切る方法
SELECT
    h.country_id,
    COALESCE(s.country_name, 'SHに存在しない') AS "COUNTRY_NAME"
FROM
    hr.countries h,
    sh.countries s
WHERE
    h.country_id = s.country_iso_code (+)
```

## 解説
今回は、**「外部結合（OUTER JOIN）」** です。
これまでの内部結合（INNER JOIN）は「両方のテーブルに存在するデータ」のみを表示していましたが、今回は **「片方のテーブルにしかなくても、基準となるテーブルのデータはすべて表示する」** という、実務のデータ整合性チェックなどで欠かせないテクニックを学びます。

### 1. ３つの外部結合
外部結合（OUTER JOIN）には、**「どのテーブルを主役（全件表示）にするか」** によって3つの種類があります。

#### ① 左外部結合 (LEFT OUTER JOIN)　　※当問題
実務で最もよく使われる、いわば「王道」の結合です。**左側に書いたテーブルのデータはすべて表示** し、右側のテーブルに一致するデータがあればくっつけます。
**※先に登場したテーブルを「左」、後に登場したテーブルを「右」と表現します。**
![](https://storage.googleapis.com/zenn-user-upload/04905b5770ed-20260320.png)
![](https://storage.googleapis.com/zenn-user-upload/fb2f5f198011-20260321.png =180x)

#### ② 右外部結合 (RIGHT OUTER JOIN)
LEFT JOINの逆で、**右側に書いたテーブルのデータをすべて表示**します。
![](https://storage.googleapis.com/zenn-user-upload/42c0a9755b69-20260321.png)
![](https://storage.googleapis.com/zenn-user-upload/a8e03dd27c4a-20260321.png =180x)

#### ③ 完全外部結合 (FULL OUTER JOIN)
左と右、**両方のテーブルのデータをすべて表示**します。
![](https://storage.googleapis.com/zenn-user-upload/e422a1ec896c-20260321.png)
![](https://storage.googleapis.com/zenn-user-upload/f2a7bf46cf82-20260321.png =180x)


### 2. 文法解説：左外部結合（LEFT OUTER JOIN）
今回のように、実務ではほとんどの場合、基準を左に置く **`LEFT OUTER JOIN`** が使われます。

#### ① 動作の仕組み
1.  **左側（FROM句）**: `hr.countries` を基準にします。ここにある25ヶ国は、右側にデータがあろうとなかろうと、**すべて表示**されます。
2.  **右側（JOIN句）**: `sh.countries` から名前を探しに行きます。
3.  **不一致の場合**: 該当するコードがない場合、右側のテーブル由来のカラムはすべて **`NULL`** として出力されます。

### 3. NULLを回避する「COALESCE」関数
外部結合をすると、どうしても「SHにデータがない国」で `NULL` が発生します。これを「SHに存在しない」という分かりやすい文字に置き換えているのが **`COALESCE`（コアレス）** 関数です。

```sql
COALESCE(s.country_name, 'SHに存在しない')
```
* **仕組み**: 引数を左から順番に見ていき、**「最初にNULLではない値」**を返します。
* `country_name` があればそれを表示し、もし `NULL`（＝結合に失敗）なら `'SHに存在しない'` を表示するというロジックです。
※Oracleでは `NVL(s.country_name, 'SHに存在しない')` と書いても同じ結果が得られます。

### 4. Oracle独自の結合記法 `(+)`
解答例2にある `(+)` は、Oracleデータベース特有の古い書き方です。

```sql
WHERE h.country_id = s.country_iso_code (+)
```
* **意味**: `(+)` が付いている方のテーブルを「不足している可能性がある側（外部テーブル）」として扱います。
* **注意**: 現在のシステム開発では、解答例1のような**標準SQL（ANSI形式）**の `LEFT OUTER JOIN` を使うのが一般的です。理由は、他のデータベース（MySQLやPostgreSQLなど）でもそのまま動くことと、結合条件が `ON` 句にまとまって読みやすいからです。

### 5. 実務での活用シーン：マスタの不整合チェック
今回の問題は、まさに実務でよくある **「マスタデータの不備」を探す** シミュレーションになっています。
* HR（人事）マスタにはあるのに、SH（売上）マスタには登録されていない国が「BE（ベルギー）」「ML（マリ）」「ZM（ザンビア）」の3つあることが判明しました。

このように、**「あるはずのデータが、もう片方のテーブルから漏れていないか？」** を確認するために、外部結合は最強の武器になります。

<br>

:::message
### 右外部結合(RIGHT JOIN)って必要？
数学的・論理的には、**`RIGHT JOIN` でできることはすべて `LEFT JOIN` で書けます。** テーブル A と B があるとき、`A RIGHT JOIN B` は `B LEFT JOIN A` と全く同じ結果を返します。そのため、多くのエンジニアは「常に `LEFT JOIN` を使う」というマイルールを持っており、`RIGHT JOIN` を一生書かない人も珍しくありません。私もまだ実践では一度も使ったことはありません。

では、なぜわざわざ `RIGHT JOIN` が存在するのか、あえて使うとしたらどんな時でしょうか？

<br>
### 1. 複雑な「結合の連鎖」を壊したくない時
これが唯一と言ってもいい、実戦的な使い道です。

例えば、すでに 3 つのテーブルを結合しているクエリに、さらにもう 1 つテーブルを足したい場面を想像してください。

```sql
SELECT *
FROM customers c
JOIN orders o ON c.id = o.customer_id
JOIN details d ON o.id = d.order_id
-- ここで「商品マスター(products)」を足したい。
-- ただし、注文されていない商品も含めてすべて表示したい。
```

ここで `LEFT JOIN` にこだわると、`products` を一番左（`FROM` の直後）に持ってくるために、**クエリ全体を書き換える**必要が出てきます。

しかし、`RIGHT JOIN` を使えば、今の流れを維持したまま最後に「右側（新しく足す方）を優先してね」と付け加えるだけで済みます。

```sql
...
RIGHT JOIN products p ON d.product_id = p.id;
```
このように、**「左から右へ流れるロジックの組み立てを崩したくない」** という時に役立ちます。（それでも個人的には `LEFT JOIN` で書き直しちゃうと思います…）
<br>

### 2. 言語としての「対称性（シンメトリー）」

SQL は「自然言語（英語）」に近い形を目指して作られた言語です。
「左があるなら、右があってもいいじゃないか」という、いわばデザイン上の**対称性**のために用意されています。数学のプラスとマイナス、右足と左足のような関係ですね。
<br>

### 3. 分析の視点を変えた時
「注文(A)に紐づく顧客(B)」という視点でクエリを書いていたけれど、途中で「いや、主役は顧客(B)全員だ」と思い直した時、テーブルの順序を入れ替える手間を省いて `RIGHT` に書き換える…という「手抜きのショートカット」として使われることもあります。

<br>
### なぜ `RIGHT JOIN`でなく、`LEFT JOIN` が推奨されるのか？
それでもなお、世の中の解説や現場のコーディング規約で `LEFT JOIN` が推奨されるのには理由があります。

* **人間の認知特性**: 私たちは（特に横書き文化では）左から右へ情報を処理します。「メインのテーブルが左にあり、そこに情報を付け足していく」という `LEFT JOIN` の流れの方が、直感的に理解しやすいのです。
* **読みやすさの統一**: `LEFT` と `RIGHT` が 1 つのクエリに混在すると、どちらのテーブルが主軸なのか一瞬で判断できなくなり、バグ（結合漏れ）の原因になります。
:::


:::message
### とりあえず「外部結合」
SQL初心者に内部結合、外部結合の概念を教えた後、非常に多いのが、内部結合で済むところ、**全て外部結合を使用する**パターンです。
「とりあえず LEFT JOIN にしておけばデータが消えないから安心」というのは、SQL初心者が必ず通る道なのかもしれません。

### 1. なぜ「とりあえず外部結合」にしてしまうのか？（心理的背景）

初心者が外部結合を選んでしまう最大の理由は **「データの消失への恐怖」** です。

* **「消えるのが怖い」:** 内部結合（INNER JOIN）を使うと、結合相手がいない行が結果から消えてしまいます。これを見て「計算が合わなくなるのでは？」と不安になります。
* **「仕様が不明確」:** テーブル間の関係性（親に対して子が必ず存在するかどうか）を把握しきれていないため、「念のため」すべて残そうとします。
* **「左側が主役という直感」:** 「このテーブルのデータを全部見たい」という直感に、LEFT JOIN の挙動がマッチしすぎてしまうのです。
<br>
### 2. 外部結合を多用することによる 3 つのデメリット

「とりあえず」で外部結合を使うと、以下のような実害が発生します。

| デメリット | 内容 |
| :--- | :--- |
| **品質の隠蔽** | 本来「結合相手が必ずいるはず」のデータに不備（ゴミデータ）があっても、NULLとして表示されるため**異常に気づけません**。 |
| **集計ミス** | `COUNT` や `AVG` を使う際、意図しない NULL が混じることで**計算結果が狂う**原因になります。 |
| **パフォーマンス低下** | オプティマイザ（Oracleの実行計画を立てる司令塔）の選択肢を狭めてしまい、大規模データでは**処理が劇的に遅くなる**ことがあります。 

<br>

### 3. 【対策】INNER か OUTER かを見極める「魔法の質問」

資料には、判断基準として以下のフローチャートのようなチェックリストを載せると親切です。

> **Q. 結合相手がいないレコードは「表示されないのが正しい」ですか？**
> * **はい（いないなら無価値）** $\rightarrow$ **INNER JOIN**
>     * 例：注文詳細のない注文、社員のいない部署など。
> * **いいえ（いなくても存在自体を表示したい）** $\rightarrow$ **OUTER JOIN**
>     * 例：売上が0円の商品一覧、まだ配属先が決まっていない新入社員など。

<br>

### 5. まとめ
 **「外部結合は『優しさ』ではなく『例外処理』である」**
 すべてを救おうとするのではなく、データの意味（ビジネスルール）に従って、潔く切り捨てる INNER JOIN を使いこなせるようになりましょう。
:::

# 問題10-3：外部結合２（FULL OUTER JOIN と 差分抽出）

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`COUNTRIES`テーブルと、SHスキーマの`COUNTRIES`テーブルを比較し、**どちらか一方のテーブルにしか存在しない国**を特定してください。

**【抽出・編集ルール】**

* **結合条件**：HRスキーマの `COUNTRY_ID` と、SHスキーマの `COUNTRY_ISO_CODE` を比較します。
* **表示内容**：
* HRスキーマに存在しない（SHにのみ存在する）場合：国コードを表示し、ステータスに「HRになし」と表示。
* SHスキーマに存在しない（HRにのみ存在する）場合：国コードを表示し、ステータスに「SHになし」と表示。


## 期待する結果
| COUNTRY | STATUS   | 
| ------- | -------- | 
| BE      | SHになし | 
| ML      | SHになし | 
| ZM      | SHになし | 
| CL      | HRになし | 
| ES      | HRになし | 
| HU      | HRになし | 
| IE      | HRになし | 
| MY      | HRになし | 
| NZ      | HRになし | 
| PL      | HRになし | 
| RO      | HRになし | 
| SA      | HRになし | 
| SE      | HRになし | 
| TH      | HRになし | 
| TR      | HRになし | 
| ZA      | HRになし | 


## 解答例
```sql:例1：UNION ALLを使用
WITH unmatch_data AS (
    SELECT
        h.country_id       AS "HR",
        s.country_iso_code AS "SH"
    FROM
        hr.countries h
        FULL OUTER JOIN sh.countries s 
          ON h.country_id = s.country_iso_code
    ORDER BY
        h.country_id,
        s.country_iso_code
)
SELECT
    hr        AS "COUNTRY",
    'SHになし' AS "STATUS"
FROM
    unmatch_data
WHERE
    sh IS NULL
UNION ALL
SELECT
    sh        AS "COUNTRY",
    'HRになし' AS "STATUS"
FROM
    unmatch_data
WHERE
    hr IS NULL
```
```sql:例2：CASE文を使用
WITH unmatch_data AS (
    SELECT
        h.country_id       AS "HR",
        s.country_iso_code AS "SH"
    FROM
        hr.countries h
        FULL OUTER JOIN sh.countries s 
          ON h.country_id = s.country_iso_code
    ORDER BY
        h.country_id,
        s.country_iso_code
)
SELECT
    CASE
        WHEN hr IS NULL THEN sh 
        ELSE hr END AS "COUNTRY",
    CASE
        WHEN hr IS NULL THEN 'HRになし' 
        ELSE 'SHになし' END AS "STATUS"
FROM
    unmatch_data ud
WHERE
     hr IS NULL
  OR sh IS NULL
```

## 解説
前問（10-2）は「左側を基準にする」外部結合でしたが、今回は **「両方のテーブルを対等に比較し、仲間はずれを探す」** という、さらに高度な **完全外部結合（FULL OUTER JOIN）** のテクニックを駆使します。


### 1. 文法解説：完全外部結合（FULL OUTER JOIN）
`FULL OUTER JOIN` は、左右両方のテーブルにあるデータを**1つも漏らさずに**すべて結合します。

#### ① 動作の仕組み
1.  **一致するデータ**: 両方のテーブルにある国（例：JP, USなど）は、1行にまとまって表示されます。
2.  **左にしかないデータ**: `HR` にはあるが `SH` にない国は、`SH` 側の列が `NULL` になります。
3.  **右にしかないデータ**: `SH` にはあるが `HR` にない国は、`HR` 側の列が `NULL` になります。

今回の目的は、このうち「2」と「3」の **不一致データ（対称差）** だけを抜き出すことです。

### 2. 解答例のロジック比較

#### ① UNION ALL を使う方法（例1）
「SHにないリスト」と「HRにないリスト」を別々に作って、最後に縦にガッチャンコ（結合）する方法です。
* **メリット**: ロジックが非常に明快です。「上半分はSHなし担当、下半分はHRなし担当」と役割が分かれているため、後から修正しやすいのが特徴です。

#### ② CASE 式を使う方法（例2）
1つの `SELECT` 文の中で、条件分岐を使って表示を切り替える方法です。
* **メリット**: クエリがコンパクトにまとまります。
* **ロジック**: 
    * `hr IS NULL` なら、その国は `sh` 側から来たデータなので、ステータスを `'HRになし'` にする。
    * そうでなければ（＝`sh IS NULL` なら）、ステータスを `'SHになし'` にする。

### 3. 実務での活用シーン：システム間の同期チェック

この「どちらかにしか存在しないデータの抽出」は、エンジニアが最も神経を使う **「システム移行」や「データ同期」** の場面で、命綱となるテクニックです。

> **「不一致ゼロ」を目指す仕事**
> 例えば、「人事システム(HR)」と「販売システム(SH)」で国マスタがズレていると、売上集計時にエラーが出たり、存在しない国への配送指示が出てしまったりします。
> このSQLを定期的に実行することで、マスタの不整合をいち早く察知し、修正することができます。

### 4. 期待する結果のポイント
結果を見ると、ベルギー（BE）などは「SHになし」、逆にチリ（CL）やハンガリー（HU）などは「HRになし」と、両方のテーブルから漏れている国がすべて網羅されています。

論理的に表現すると、以下の条件のデータを抽出していることになります。
$$(HR \text{ is NULL}) \lor (SH \text{ is NULL})$$
※両方がNULLになることは（外部結合の性質上）ないので、実質的に「片方だけがNULL」の行を抽出しています。

# 問題10-4：自己結合（Self Join）

### 難易度：★★☆☆☆ (Lv.2)

## 問題
HRスキーマの`EMPLOYEES`テーブルを使用して、各従業員の氏名と、その従業員の直属の上司の氏名を並べて取得してください。

**【条件および編集ルール】**

* 1つの`EMPLOYEES`テーブルに対して、一方を「従業員用（`emp`）」、もう一方を「上司用（`mng`）」として別名を定義し、自己結合を行ってください。
* **結合キー**：従業員側の`MANAGER_ID`と、上司側の`EMPLOYEE_ID`を紐付けます。
* **外部結合の利用**：最上位の管理者（上司がいない従業員）も結果に含まれるよう、`LEFT OUTER JOIN`を使用してください。
* 今回は結果を絞り込むため、`EMPLOYEE_ID`が110以下のデータを対象とします。
* 氏名は`FIRST_NAME`と`LAST_NAME`を半角スペースで結合してください。

## 期待する結果
| EMPLOYEE_ID | EMPLOYEE_NAME   | MANAGER_ID | MANAGER_NAME    | 
| ----------- | --------------- | ---------- | --------------- | 
| 100         | Steven King     |            |                 | 
| 101         | Neena Yang      | 100        | Steven King     | 
| 102         | Lex Garcia      | 100        | Steven King     | 
| 103         | Alexander James | 102        | Lex Garcia      | 
| 104         | Bruce Miller    | 103        | Alexander James | 
| 105         | David Williams  | 103        | Alexander James | 
| 106         | Valli Jackson   | 103        | Alexander James | 
| 107         | Diana Nguyen    | 103        | Alexander James | 
| 108         | Nancy Gruenberg | 101        | Neena Yang      | 
| 109         | Daniel Faviet   | 108        | Nancy Gruenberg | 
| 110         | John Chen       | 108        | Nancy Gruenberg | 


## 解答例
```sql
SELECT
    emp.employee_id,
    emp.first_name || ' ' || emp.last_name AS employee_name,
    emp.manager_id,
    mng.first_name || ' ' || mng.last_name AS manager_name
FROM
    hr.employees emp
    LEFT JOIN hr.employees mng 
      ON emp.manager_id = mng.employee_id
WHERE
    emp.employee_id <= 110
ORDER BY
    emp.employee_id
```

## 解説
今回は、非常に面白い、そして避けては通れないテクニック**「自己結合（Self Join）」** です。
これまでは「AテーブルとBテーブル」という異なる表をくっつけてきましたが、今回は **「自分自身のコピーと自分自身をくっつける」** という、鏡合わせのような手法を学びます。組織図や部品の構成表（BOM）など、階層構造を持つデータを扱う際の必須スキルです。

### 1. 文法解説：自己結合（Self Join）とは？
同じテーブルに対して、それぞれ別の役割（名前）を与えて結合することです。

#### ① 別名（Alias）が命
同じ `EMPLOYEES` テーブルを2回登場させるため、データベースが混乱しないように必ず別名を付けます。
* **`emp`**: 「部下（従業員）」としての役割
* **`mng`**: 「上司（マネージャー）」としての役割

#### ② 結合のロジック
「部下の持っている『上司のID（`manager_id`）』」と、「上司が持っている『自分のID（`employee_id`）』」を紐づけます。
```sql
ON emp.manager_id = mng.employee_id
```

### 2. なぜ LEFT JOIN（外部結合）なのか？
ここがこの問題の最大のポイントです。期待する結果の1行目（Steven Kingさん）を見てください。

* Steven Kingさんは社長（トップ）なので、彼には上司がいません（`manager_id` が NULL です）。
* もしここで **`INNER JOIN`** を使ってしまうと、上司がいないSteven Kingさんは**結果から消えてしまいます。**

> **「欠け」を許さない組織図**
> 「上司がいない人（社長）」も含めて、全従業員をリストアップしたい場合は、必ず **`LEFT JOIN`** を使って、左側（部下側）のデータをすべて守る必要があります。

### 3. 実務での活用シーン：親子関係の紐解き
自己結合は、一つのテーブルの中に「親子関係」が隠れているデータ構造で威力を発揮します。

* **組織管理**: 「社員」と「その上司」
* **カテゴリ管理**: 「小カテゴリ（例：スニーカー）」と「その親カテゴリ（例：靴・シューズ）」
* **製造業**: 「製品」と「それを構成する部品」


### 4. 期待する結果の確認
結果を見ると、Alexander Jamesさん（103番）の上司はLex Garciaさん（102番）であることが一目で分かりますね。
さらに、Alexander Jamesさん自身も、Bruce Millerさん（104番）たちの「上司」として右側に登場しています。

このように、**「ある行では部下として、別の行では上司として」** 振る舞うデータを1行に並べて表示できるのが、自己結合の魔法です。

# 【完全版】問題10-5：自己結合２（同一年月の複数回注文）

### 難易度：★★★☆☆ (Lv.3)

## 問題

OEスキーマの`ORDERS`テーブルを使用して、**同じ年月の間に2回以上の注文を行った顧客**とその注文詳細を特定してください。

**【抽出・編集ルール】**

* **抽出条件**：
* 同一の顧客（`CUSTOMER_ID`）であること。
* 注文日（`ORDER_DATE`）の「年」と「月」が一致していること。
* 注文ID（`ORDER_ID`）が異なること（自分自身と一致するのを防ぐため）。

<br>
* **表示項目**：
* `CUSTOMER_ID`
* `CUST_NAME`：`CUSTOMERS`テーブルの`CUST_FIRST_NAME`と`CUST_LAST_NAME`を半角スペースで結合。
* `ORDER_ID`
* `ORDER_DATE`


* 結果の表示順は問いません。

## 期待する結果
| CUSTOMER_ID | CUST_NAME          | ORDER_ID | ORDER_DATE                  | 
| ----------- | ------------------ | -------- | --------------------------- | 
| 105         | Matthias MacGraw   | 2358     | 2008-01-08T17:03:12.654278Z | 
| 105         | Matthias MacGraw   | 2356     | 2008-01-26T09:22:41.934562Z | 
| 148         | Gustav Steenburgen | 2451     | 2007-12-17T17:03:52.562632Z | 
| 148         | Gustav Steenburgen | 2386     | 2007-12-06T12:22:34.225609Z | 


## 解答例
```sql:例1：同一年月で注文が一致しない→複数
SELECT
    o1.customer_id,
    c.cust_first_name || ' ' || c.cust_last_name AS cust_name ,
    o1.order_id,
    o1.order_date
FROM
         oe.orders o1
    INNER JOIN oe.orders o2 
       ON o1.customer_id = o2.customer_id
      AND o1.order_id <> o2.order_id
      AND extract(YEAR FROM o1.order_date) = extract(YEAR FROM o2.order_date)
      AND extract(MONTH FROM o1.order_date) = extract(MONTH FROM o2.order_date)
    INNER JOIN oe.customers c 
       ON o1.customer_id = c.customer_id
```
```sql:例2：COUNTして2以上→複数
WITH o1 AS (
    SELECT
        customer_id,
        extract(YEAR FROM order_date)  AS yr,
        extract(MONTH FROM order_date) AS mt,
        COUNT(*)
    FROM
        oe.orders
    GROUP BY
        customer_id,
        extract(YEAR FROM order_date),
        extract(MONTH FROM order_date)
    HAVING
        COUNT(*) > 1
)
SELECT
    o2.customer_id,
    c.cust_first_name || ' ' || c.cust_last_name AS cust_name,
    o2.order_id,
    o2.order_date
FROM
         o1
    INNER JOIN oe.orders    o2 
       ON o1.customer_id = o2.customer_id
      AND o1.yr = extract(YEAR FROM o2.order_date)
      AND o1.mt = extract(MONTH FROM o2.order_date)
    INNER JOIN oe.customers c 
       ON o2.customer_id = c.customer_id
```


## 解説
今回は、**「自己結合」**　応用編です。
この問題は、単にデータを繋げるだけでなく、**「同じテーブル内のデータ同士を比較して、重複や特定のパターンを見つけ出す」** という、非常に高度なロジックが求められます。
実務では「同じ日に2回以上来店した客」や「二重登録されている可能性のあるデータ」の抽出など、データクレンジングや不正検知で非常によく使われるパターンです。

### 1. ロジックの核心：自己結合による「比較」
解答例1では、`ORDERS`テーブルを2回登場させ（`o1`と`o2`）、それらをぶつけることで「自分以外の同じ条件のデータ」を探しています。

#### ① `o1.order_id <> o2.order_id` の重要性
自己結合で重複を探す際、最も重要なのがこの **「不一致条件」** です。
これがないと、すべての注文が「自分自身」と一致してしまい、すべての行が結果に出てきてしまいます。
「顧客IDと年月は同じだが、**注文IDは違う**」という条件を加えることで、初めて「他にも注文がある（＝複数注文している）」ことを証明できるのです。

### 2. 解答例の解説：2つのアプローチ

#### 例1：自己結合（Self-Join）による抽出
直感的で「これぞSQL」という書き方です。
* **仕組み**: 1つの注文に対し、同じ人の同じ年月の「別の注文」を横に並べようと試みます。
* **メリット**: 副問い合わせを使わないため、1つのクエリの流れで完結します。
* **注意点**: 同じ月に3回注文した人がいる場合、A-B、A-Cのように、1つの注文IDが複数回ヒットして重複表示される可能性があるため、実務では `DISTINCT` を併用することもあります。

#### 例2：集計（GROUP BY）＋ 結合（おすすめ）
現代のシステム開発で、より「確実」かつ「読みやすい」とされるアプローチです。

1.  **WITH句（o1）**: まず、注文テーブルを「顧客・年・月」で集計し、**`HAVING COUNT(*) > 1`** を使って「2回以上注文した人」という **「ターゲットリスト」** を先に作ります。
2.  **メインクエリ**: そのターゲットリストを元の注文テーブル（`o2`）と結合します。
* **メリット**: 最初に「どの月のどの客か」を確定させてから詳細（注文ID）を取りに行くため、ロジックが非常に堅牢です。大量データを扱う場合は、こちらの方がパフォーマンスが安定しやすい傾向にあります。

### 3. 文法ポイント：EXTRACT関数
年月を比較するために使われている `EXTRACT` 関数は、前章の日付セクションで学びましたね。

```sql
extract(YEAR FROM o1.order_date) = extract(YEAR FROM o2.order_date)
```

これを `TO_CHAR(order_date, 'YYYYMM')` で比較しても正解ですが、`EXTRACT` を使うと「数値」として比較されるため、データベース内部の処理効率が良くなる場合があります。

### 4. 期待する結果の確認
Matthias MacGrawさん（105番）を見てください。
* 2008年1月8日の注文（2358）
* 2008年1月26日の注文（2356）
同じ「2008年1月」の中に、異なる注文IDが2つ存在していることが分かります。

> **実務での一工夫**
> このようなリストは、マーケティング部門から「同じ月に何度も買ってくれるロイヤルカスタマーにクーポンを送りたい」といった要望でよく作成されます。その際、さらに `SUM(order_total)` などを加えて「月間合計額」も出すと、より喜ばれるレポートになります。

# 問題10-6：クロス結合（Cross Join）

### 難易度：★★★☆☆ (Lv.3)

## 問題
HRスキーマの`COUNTRIES`テーブルより、`REGION_ID`が「20」の国々を対象として、**2020年と2021年の2年分**のデータを記録するためのベースとなるデータを作成してください。

**【抽出・編集ルール】**

* **YEAR**：2020と2021の2つの行を持つ仮想的なデータを作成してください。
* **NAME**：`COUNTRIES`テーブルから、`REGION_ID = 20` に該当する国の名前を取得してください。
* **DATA**：将来的に値を入れるための空の列（NULL）を用意してください。
* **結合方法**：年データと国データをクロス結合（CROSS JOIN）させ、すべての組み合わせ（年×国）を生成してください。
* 結果の表示順は問いません。

## 期待する結果
| YEAR | NAME                     | DATA | 
| ---- | ------------------------ | ---- | 
| 2020 | Argentina                |      | 
| 2020 | Brazil                   |      | 
| 2020 | Canada                   |      | 
| 2020 | Mexico                   |      | 
| 2020 | United States of America |      | 
| 2021 | Argentina                |      | 
| 2021 | Brazil                   |      | 
| 2021 | Canada                   |      | 
| 2021 | Mexico                   |      | 
| 2021 | United States of America |      | 

## 解答例
```sql
WITH t_year AS (
    SELECT 2020 AS "YEAR" FROM dual
    UNION ALL
    SELECT 2021 AS "YEAR" FROM dual
)
SELECT
    t."YEAR",
    c.country_name AS "NAME",
    null           AS "DATA"
FROM
    hr.countries c
    CROSS JOIN t_year t
WHERE
    region_id = 20
```

## 解説
今回は、これまでの結合とは一線を画す **「クロス結合（CROSS JOIN）」** の登場ですね。
通常の結合は「共通点（IDなど）」を探して紐づけますが、クロス結合は **「共通点なんて関係ない、とにかく全通りの組み合わせ（総当たり）を作る！」** という、特殊かつ非常に強力な手法です。


### 1. 文法解説：クロス結合（CROSS JOIN）
別名「デカルト積」とも呼ばれます。Aテーブルのすべての行に対し、Bテーブルのすべての行を掛け合わせます。
![](https://storage.googleapis.com/zenn-user-upload/7ae6f5777a1e-20260324.png =300x)


#### ① 動作の仕組み
1. **左側**: `hr.countries` から地域20の国（5件）を取得。
2. **右側**: `WITH` 句で作った `t_year`（2件：2020年と2021年）を用意。
3. **掛け算**: 5カ国 × 2年 ＝ **10行** の結果が生成されます。

もし地域20に100カ国あれば、200行になります。このように、データを「爆発」させて網羅的な表を作るのがクロス結合の特徴です。

![](https://storage.googleapis.com/zenn-user-upload/aee281e869d7-20260324.png =200x)


### 2. 仮想テーブルの即時作成（WITH 句）

解答例の冒頭にある `WITH t_year AS ...` の部分は、テーブルがデータベースに存在しなくても、その場で「年リスト」という名の**使い捨てテーブル**を定義しています。

```sql
SELECT 2020 AS "YEAR" FROM dual
UNION ALL
SELECT 2021 AS "YEAR" FROM dual
```
このように `DUAL` と `UNION ALL` を組み合わせることで、「2020」と「2021」という2つの値を持つ即席のマスターデータを作っています。


### 3. 実務での活用シーン：データの「受け皿」作り
「全組み合わせを作るなんて、いつ使うの？」と思うかもしれませんが、実は **「穴のないレポート」** を作る際に必須のテクニックです。

* **実績ゼロの表示**: 「売上があった月」だけを集計すると、売上がなかった月はリストから消えてしまいます。まず「全店舗 × 全月」をクロス結合で作り、そこに実績をぶつけることで、「売上0円」の月も漏れなく表示できる綺麗なレポートが作れます。
* **今回のようなテンプレート作成**: 新しい年度の予算入力用テーブルを作る際、すべての国に対してあらかじめ「2020年の行」と「2021年の行」を空っぽの状態で用意しておく必要があります。

### 4. 期待する結果のポイント

結果を見ると、Argentina（アルゼンチン）に対して2020年の行と2021年の行が1つずつ作られていますね。他の国も同様です。
最後に `null AS "DATA"` としているのは、これからここに実績や予算を書き込むための **「空欄（受け皿）」** をあらかじめ用意している、という設計思想です。

> **クロス結合の注意点**
> 1,000行のテーブルと1,000行のテーブルをクロス結合すると、一気に**100万行**に膨れ上がります。条件を指定せずに巨大なテーブル同士をクロス結合すると、データベースがフリーズする原因（事故）になるため、実務では「何と何を掛け合わせるか」を慎重に制御しましょう。

「自己結合」の真髄、**「重複データのあぶり出し」** です。
今回の問題は、1つのテーブルを「2枚のカード」に見立てて重ね合わせ、同じ名前を持つペアを抽出するテクニックです。

### 1. 核心：なぜ自己結合が必要なのか？
通常、`GROUP BY` を使えば「同じ名前が何人いるか」は分かりますが、今回の期待する結果のように **「誰と誰が同じ名前なのか」という具体的な内訳（レコード同士の比較）** を出したい場合は、自己結合が必須となります。

#### ① 結合条件の読み解き
```sql
ON e1.first_name = e2.first_name
```
この一行で、データベースは「左側のテーブルの `FIRST_NAME`」と「右側のテーブルの `FIRST_NAME`」を総当たりで比較し、一致するものだけを繋ぎます。

### 2. ここがプロの技：`e1.employee_id < e2.employee_id`
この条件には、2つの非常に重要な役割があります。

#### 役割１：自分自身との一致を除外する
もしこの条件がないと、すべての行が「自分自身（`e1.ID` = `e2.ID`）」と結合してしまい、全員が結果に出てきてしまいます。

#### 役割２：重複ペアの「裏返し」をカットする
ここがLv3のポイントです！
例えば、ID:103のAlexanderとID:115のAlexanderがいる場合、もし条件を `e1.ID <> e2.ID`（等しくない）だけにすると、以下の2行が出てしまいます。

1. `ID:103 (e1)` と `ID:115 (e2)`
2. `ID:115 (e1)` と `ID:103 (e2)`

これでは結果が2倍に増えて見づらくなってしまいますよね。**「片方のIDがもう片方より小さい」**という不等号（`<`）を使うことで、ペアを1つに固定し、スッキリとしたリストにしているのです。


### 3. 実務での活用シーン：名寄せ（Data Cleansing）
実務において、このクエリは**「名寄せ」**や**「データの不備チェック」**で絶大な威力を発揮します。

* **顧客マスタの重複排除**: 同じ電話番号やメールアドレスで二重登録されているユーザーを見つけ出す。
* **注文エラーの特定**: 同じタイミングで全く同じ内容の注文が2回飛んでいないか（二重決済）を調査する。

### 4. 期待する結果の確認
期待する結果を見ると、110番のJohn Chenさんに対して、DUP_IDとして139番と145番のJohnさんが並んでいますね。
110番（Chen） < 139番（Seo）
110番（Chen） < 145番（Seo）
139番（Seo） < 145番（Singh）

このように、**「3人以上が同じ名前」** の場合でも、この不等号ロジックならすべての組み合わせを漏れなく、かつ重複なくリストアップできます。

# 【完全版】問題10-8：外部結合と自己結合（重複データのカウント）

問題10-8、Lv3の「完全版」クリア、本当におめでとうございます！
これは実務で行う **「名寄せ」や「データ品質調査」の集大成** とも言える問題です。

「重複がある人だけ」を出すのはLv2でしたが、今回は「重複がない人（ユニークな人）」も含めて全員をリストアップし、それぞれの状態をラベル付けするという、非常に難易度の高いロジックが求められています。

### 1. 例1の解説：自己結合 × 外部結合のコンビネーション
なぜ単純な `INNER JOIN` ではなく `LEFT OUTER JOIN` が必要なのか、その理由がこの問題の肝です。

#### ① 「ぼっち」を救う LEFT JOIN
もし `INNER JOIN` を使ってしまうと、名前が誰とも被っていない「ユニーク」な従業員は、結合相手が見つからず**結果から消滅**してしまいます。
`LEFT OUTER JOIN` を使うことで、右側（e2）に一致する人がいなくても、左側（e1）の全メンバーを確実に残すことができます。

#### ② COUNT(e2.employee_id) の魔法
`COUNT(*)` ではなく、結合相手の列名 `e2.employee_id` を指定してカウントしているのがポイントです。
* **重複あり**: e2にデータがあるので、その人数がカウントされる。
* **ユニーク**: e2側はすべてNULLなので、`COUNT` は **0** になる。
これによって、「0 ＝ ユニーク」という判定が可能になります。

### 2. 例2の解説：分析関数（Window関数）という「現代の武器」
解答例2で使用されている `COUNT(*) OVER(PARTITION BY ...)` は、現代のSQLにおいて最も強力な機能の一つです。

#### ① データを「畳まない」集計
通常の `GROUP BY` は行を一つにまとめてしまいますが、分析関数は**「行の数はそのままに、集計結果だけを横に添える」**ことができます。

#### ② PARTITION BY first_name
「名前ごとにグループ（パーティション）を作って、その中で数を数えてね」という指示です。
* `COUNT(*) OVER(...)` で「自分を含めた同じ名前の総数」が出ます。
* そこから **`- 1`** をすることで、「自分以外の重複者数」を導き出しています。非常にスマートですよね。

### 3. 実務での使い分け：どっちが「正解」？

| 特徴 | 自己結合（例1） | 分析関数（例2） |
| :--- | :--- | :--- |
| **可読性** | 少し複雑。結合と集計が入り混じる。 | **◎ スッキリ。** ロジックが直感的。 |
| **処理速度** | △ テーブルを2回読むため重くなりやすい。 | **◎ 高速。** 1回のスキャンで済むことが多い。 |
| **汎用性** | 古いDBでも動く。 | 近代的なDB（Oracle 8i以降など）ならOK。 |

**プロの視点**: 現代の実務では、例2の**分析関数**を使いこなせることが「上級者」の証とされます。自己結合で四苦八苦していた処理が、たった一行で解決する快感は一度味わうと病みつきになりますよ！

### 4. 期待する結果の確認
結果を見ると、Davidさんが「2人重複（＝合計3人）」、Peterさんが「1人重複（＝合計2人）」、そして他のメンバーがしっかり「ユニーク」として抽出されています。

> **「自分以外」をどう定義するか**
> 例1では `e1.ID <> e2.ID`、例2では `全体数 - 1` と、アプローチは違えど **「自分自身をカウントから外す」** という一貫したロジックが貫かれています。これがデータの正確性を支える重要なポイントです。

# 問題10-9：部分外部結合（Partitioned Outer Join）

### 難易度：★★★☆☆ (Lv.3)

## 問題

COスキーマの`ORDERS`テーブルと`ORDER_ITEMS`テーブルを使用して、商品ごとの月別注文合計数を取得してください。
通常、注文がない月はその行自体が表示されませんが、今回は「注文がない月も0件として表示」させる必要があります。

**【条件およびルール】**

* 抽出対象の商品ID（`PRODUCT_ID`）は **8** および **37** とします。
* 注文年月（`OT`）は「YYYYMM」形式（数値型）で表示してください。
* その月に該当商品の注文がなかった場合は、注文数（`SM`）に **0** を表示してください。
* 結果は、商品IDの昇順、および年月の昇順で表示してください。

| 202103 | 8          | 15  | 
| 202104 | 8          | 4   | 
| 202105 | 8          | 10  | 
| 202106 | 8          | 21  |

| 202108 | 8          | 39  | 
| 202109 | 8          | 15  | 
| 202110 | 8          | 19  | 
| 202111 | 8          | 13  | 
| 202112 | 8          | 38  | 
| 202201 | 8          | 15  | 
| 202202 | 8          | 10  | 
| 202203 | 8          | 14  | 
| 202204 | 8          | 0   | 
| 202102 | 37         | 0   | 
| 202103 | 37         | 9   | 
| 202104 | 37         | 0   | 
| 202105 | 37         | 17  | 
| 202106 | 37         | 17  | 
| 202107 | 37         | 25  |

| 202109 | 37         | 16  | 
| 202110 | 37         | 12  |

## 解答例
```sql
WITH full_year_month AS ( -- ORDERSテーブルに存在するすべての年月
    SELECT DISTINCT
        TO_NUMBER(TO_CHAR(
            TRUNC(o.order_tms, 'MM'),
            'YYYYMM'
        )) ot
    FROM
        co.orders o
), order_pr AS ( -- 年月、商品ごとの注文数を取得
    SELECT
        TO_NUMBER(TO_CHAR(
            TRUNC(o.order_tms, 'MM'),
            'YYYYMM'
        ))               ot,
        oi.product_id,
        SUM(oi.quantity) sm
    FROM
             co.orders o
        INNER JOIN co.order_items oi 
           ON o.order_id = oi.order_id
    GROUP BY
        trunc(o.order_tms, 'mm'),
        oi.product_id
)
SELECT
    f.ot,
    o.product_id,
    COALESCE(o.sm, 0) AS sm
FROM
    full_year_month f
    LEFT JOIN order_pr        o 
    PARTITION BY ( o.product_id )  -- 注文が存在しない場合、0件と表示するためのレコード作成
      ON f.ot = o.ot
WHERE o.product_id IN (8, 37)
ORDER BY
    o.product_id,
    f.ot
```

## 解説
今回は、実務の「集計・レポート作成」において、最も難易度が高く、かつ「プロとアマを分ける」と言われる **パーティション外部結合（Partitioned Outer Join）** の奥義です。
「データがない月も0件として表示する」というのは、Excelなら簡単ですが、SQLで実現しようとすると一気にパズルが複雑になります。

### 1. 核心：「歯抜け」のデータをどう埋めるか？
通常の `LEFT JOIN` では、基準となるテーブル（カレンダー）に全ての月があっても、結合先のデータに「特定の商品」の記録が全くなければ、その商品の行は消えてしまいます。

例えば、商品37番が2021年2月に1個も売れていなかった場合、普通の結合では「202102」という行自体が、商品37番のリストから消滅してしまうのです。



#### ① パーティション外部結合の魔法
```sql
LEFT JOIN order_pr o PARTITION BY ( o.product_id ) ON f.ot = o.ot
```
この `PARTITION BY ( o.product_id )` という記述が、魔法の正体です。
* **意味**: 「商品IDごとに、独立したカレンダー（外部結合）を適用してね」という命令です。
* **動作**: データベースは内部的に、商品8番用のカレンダーと、商品37番用のカレンダーを別々に用意し、それぞれに対して「歯抜け」がないかチェックして埋めてくれます。

### 2. クエリの構造解剖（3段階のステップ）

このクエリは、非常に論理的な3つの部品で構成されています。

#### ステップ1：時間軸の作成 (`full_year_month`)
まず、データの有無に関わらず「存在するべき年月のリスト」を抽出します。これがレポートの**縦軸**になります。

#### ステップ2：実績の集計 (`order_pr`)
次に、実際に売れたデータだけを「年月×商品」で集計します。ここではまだ「売れた時」のデータしかありません。

#### ステップ3：総当たり結合 (`SELECT` 句)
ここでパーティション外部結合の出番です。
「全ての年月（f）」に対して、「商品ごとの枠組み（PARTITION BY）」を作り、そこに「実績（o）」を流し込みます。実績がなければ `NULL` になるので、最後に **`COALESCE(o.sm, 0)`** で 0 に変換して完成です。

### 3. 実務での活用シーン：美しいレポート作成

このテクニックを知らないと、BIツールやレポート画面で「売上がない月だけグラフが飛んでしまう」という格好悪いことになります。

* **在庫管理**: 入出荷がない日も「在庫0」として表示し続ける。
* **KPIダッシュボード**: ログインがない日も「ユーザー数0」として折れ線グラフを繋げる。

> **「データがない」という情報を「0」として可視化する**
> 現場では、データが存在することと同じくらい、「データが存在しない（0である）」ことを示すのが重要な場合があります。パーティション外部結合は、そのための最強のツールです。

## 解答例
```sql:例１：CROSS JOINを使用
WITH target_months AS (
    -- 2015年の1月〜12月のカレンダー（12行）を動的に生成
    SELECT ADD_MONTHS(DATE '2015-01-01', LEVEL - 1) AS month_start
    FROM dual
    CONNECT BY LEVEL <= 12
),
emp_counts AS (
    -- 実際の採用データを月別・部門別に集計（データがある月のみ）
    SELECT
        department_id,
        TRUNC(hire_date, 'MM') AS hire_month,
        COUNT(*) AS cnt
    FROM
        hr.employees
    WHERE
        hire_date BETWEEN DATE '2015-01-01' AND DATE '2015-12-31'
        AND department_id IN (30, 50)
    GROUP BY
        department_id, TRUNC(hire_date, 'MM')
)
SELECT
    TO_CHAR(m.month_start, 'YYYY-MM') AS hire_month,
    d.department_id,
    NVL(e.cnt, 0) AS hire_count
FROM
    target_months m
CROSS JOIN 
    (SELECT DISTINCT department_id FROM hr.employees WHERE department_id IN (30, 50)) d
LEFT OUTER JOIN 
    emp_counts e ON (e.hire_month = m.month_start AND e.department_id = d.department_id)
ORDER BY
    d.department_id, m.month_start
```
```sql:例２：Oracle特有のパーティション・アウター結合を使用
WITH target_months AS (
    SELECT ADD_MONTHS(DATE '2015-01-01', LEVEL - 1) AS month_start
    FROM dual
    CONNECT BY LEVEL <= 12
),
emp_counts AS (
    SELECT department_id, TRUNC(hire_date, 'MM') AS hire_month, COUNT(*) AS cnt
    FROM hr.employees
    WHERE hire_date BETWEEN DATE '2015-01-01' AND DATE '2015-12-31'
      AND department_id IN (30, 50)
    GROUP BY department_id, TRUNC(hire_date, 'MM')
)
SELECT
    TO_CHAR(m.month_start, 'YYYY-MM') AS hire_month,
    e.department_id,
    NVL(e.cnt, 0) AS hire_count
FROM
    target_months m
LEFT OUTER JOIN emp_counts e PARTITION BY (e.department_id)
    ON (m.month_start = e.hire_month)
ORDER BY
    e.department_id, m.month_start;
```

## 解説
実務で売上や採用の「月次推移グラフ」をBIツール（TableauやExcelなど）で作成するとき、データが0の月が行ごとスキップされてしまい、「折れ線グラフが途切れる」「あるはずの月が軸から消える」というバグに直面したことのあるエンジニアは非常に多いです。
今回は、標準的なアプローチ（例1）と、Oracleが誇る超強力な独自構文（例2）の2つのアプローチが提示されています。それぞれの仕組みと、実務での圧倒的な優位性を解説します。

### 1. スクリプトの解説：なぜデータが消えるのか？
通常の `GROUP BY` は、「テーブルに存在する行」**しか集計できません。2015年5月に部門50の採用者が0人だった場合、テーブルにはレコード自体が存在しないため、SQLは「0人」という結果ではなく、**「5月の行そのものを出力しない」という挙動になります。

これを解決するために、解答例ではまず **`target_months`（12ヶ月分のカレンダーの土台）** を動的に生成しています。

#### 例1：CROSS JOIN（掛け算）によるアプローチ
もっとも直感的で、他システム（MySQLやPostgreSQLなど）でも応用できる汎用的な方法です。

1. `target_months`（12行）と、対象の部門ID（2行）を **`CROSS JOIN`** して、あらかじめ「全24行（12ヶ月 × 2部門）」の空の器（マスター表）を作ります。
2. その器に対して、実際の集計データ（`emp_counts`）を **`LEFT OUTER JOIN`** で紐付け、データがない場所を `NVL(cnt, 0)` でゼロ埋めします。

#### 例2：パーティション・アウター結合（Oracle特有）
こちらが今回の本命、Oracle特有の美技です。器をわざわざCROSS JOINで作る必要がありません。

```sql
FROM
    target_months m
LEFT OUTER JOIN emp_counts e PARTITION BY (e.department_id)
    ON (m.month_start = e.hire_month)
```

この **`PARTITION BY (e.department_id)`** が魔法のフレーズです。
「外部結合（`LEFT OUTER JOIN`）を実行するとき、**部門IDごとにグループを小分けにして、それぞれのグループに対してカレンダー（`target_months`）を丸ごと1枚ずつ適用してね**」という命令になります。

### 2. 文法・テクニックのポイント
#### パーティション・アウター結合の凄み

通常の外部結合（`LEFT JOIN`）では、結合元（左側）の行数は維持されますが、結合先（右側）にある「部門ID」のバリエーションをすべて網羅して複製することはできません。

| 結合の種類 | 挙動 |
| --- | --- |
| **通常の `LEFT JOIN`** | カレンダーの12行は維持されるが、データのない月は `DEPARTMENT_ID` も `NULL` になってしまい、部門ごとの12ヶ月は作れない。 |
| **`PARTITION BY` 付き `LEFT JOIN`** | 指定した列（部門ID）の**値の種類ごとにカレンダーを内部で複製**し、それぞれに対して結合を試みる。 |

結果として、実データがどれだけスカスカ（疎データ）であっても、指定した軸の数だけ綺麗にデータが引き伸ばされ、高密度な（密データ）表が完成します。


### 3. 実務でのアドバイス：レポーティングの品質向上
実務でこの「データの穴埋め」を行う際は、以下の2点に注意するとさらにクオリティが上がります。

#### ① 軸（パーティション）の絞り込み位置
例2の `emp_counts` 内で、あらかじめ `WHERE department_id IN (30, 50)` と絞り込んでいるのがポイントです。
もしここで絞り込まないと、テーブル内に存在する**すべての部門ID（10〜110など）に対して12ヶ月分のカレンダーが複製されてしまう**ため、巨大な結果セットが生成されてパフォーマンスが低下します。

#### ② NVL関数の適用
穴埋めされた行の集計値は `NULL` になっています。画面表示やCSV出力の際、空欄ではなくしっかりと `0` を見せるために `NVL(e.cnt, 0)` を忘れないようにしましょう。
