# 問題9-1（副問い合わせの基本） *Lv2*
### SHスキーマ`SALES`テーブルより、2019年1月1日から2019年3月31日までの合計売上個数（`QUANTITY_SOLD`の合計）と合計売上金額（`AMOUNT_SOLD`の合計）を取得してください。（順不同）


## 期待する結果
| CUST_ID | NAME            | SUM_QUANTITY_SOLD | SUM_AMOUNT_SOLD | 
| ------- | --------------- | ----------------- | --------------- | 
| 12783   | Rose Lehman     | 80                | 33676.07        | 
| 12539   | Lucas Gilboy    | 72                | 9647.59         | 
| 25244   | Rufus Rokus     | 74                | 9710.03         | 
| 2760    | Luana Crisp     | 72                | 9652.08         | 
| 5696    | Sabrina Pack    | 71                | 9595.62         | 
| 2791    | Madra Leary     | 74                | 5194.77         | 
| 9038    | Marvel Bakerman | 72                | 45103.24        | 
| 3720    | Michael Lincoln | 73                | 9675.79         | 
| 1255    | Sally Filbert   | 74                | 9710.03         | 

## 解答例
```sql:例1：インラインビューを使用
SELECT
    c.cust_id,
    c.cust_first_name || ' ' || cust_last_name AS name,
    sa.sum_quantity_sold,
    sa.sum_amount_sold
FROM
    sh.customers c
    INNER JOIN (
        SELECT
            cust_id,
            SUM(quantity_sold) AS sum_quantity_sold,
            SUM(amount_sold)   AS sum_amount_sold
        FROM
            sh.sales
        WHERE
            time_id BETWEEN DATE '2019-01-01' 
                        AND DATE '2019-03-31'
        GROUP BY
            cust_id
    ) sa ON c.cust_id = sa.cust_id
WHERE
    sa.sum_quantity_sold > 70
```
```sql:例2：WITH句を使用
WITH sa AS (
    SELECT
        cust_id,
        SUM(quantity_sold) AS sum_quantity_sold,
        SUM(amount_sold)   AS sum_amount_sold
    FROM
        sh.sales
    WHERE
        time_id BETWEEN DATE '2019-01-01' 
                    AND DATE '2019-03-31'
    GROUP BY
        cust_id
)
SELECT
    c.cust_id,
    c.cust_first_name || ' ' || cust_last_name AS name,
    sa.sum_quantity_sold,
    sa.sum_amount_sold
FROM
    sh.customers c
    INNER JOIN sa 
       ON c.cust_id = sa.cust_id
WHERE
    sa.sum_quantity_sold > 70
```

## 解説
SQLの「入れ子構造」、**副問い合わせ（サブクエリ）** の領域になります。
これまでは1つのテーブル、あるいは単純な結合を扱ってきましたが、ここからは **「クエリの結果を、あたかも1つのテーブルのように扱う」** という一段上のテクニックが必要になります。これができるようになると、SQLで表現できる世界が爆発的に広がります！

### 1. 文法解説：クエリの中の「仮想テーブル」

今回の問題のポイントは、**「売上の集計（合計）」と「顧客名の結合」をどのタイミングで行うか**、という点にあります。

#### ① インラインビュー（例1）
`FROM` 句の中に直接 `SELECT` 文を書く手法です。

```sql
FROM sh.customers c INNER JOIN ( SELECT ... FROM sh.sales ... ) sa
```


* **仕組み**: データベース内部で、まずカッコの中の集計処理（2019年1Qの売上計算）を行い、その結果を `sa` という名前の**一時的な仮想テーブル**としてメモリ上に展開します。その後、その仮想テーブルと顧客テーブルを結合します。
* **メリット**: その場限りの使い捨ての集計に向いており、クエリの流れが上から下へと直感的です。

#### ② WITH句（CTE：共通テーブル式）（例2）
クエリの冒頭で仮想テーブルを定義してしまう手法です。

```sql
WITH sa AS ( SELECT ... FROM sh.sales ... ) SELECT ... FROM sh.customers c INNER JOIN sa ...
```


* **仕組み**: 最初に `sa` という「部品」を作っておき、後続のメインクエリでその部品を呼び出します。
* **メリット**: **「圧倒的に読みやすい」** のが最大の特徴です。複雑なクエリになればなるほど、インラインビューよりも `WITH` 句の方が構造を把握しやすくなります。また、同じ部品をクエリ内で何度も再利用できるのも強みです。


### 2. なぜ「副問い合わせ」が必要なのか？
「最初から `SALES` と `CUSTOMERS` を結合して、最後に `GROUP BY` すればいいのでは？」と思うかもしれません。もちろんそれも可能ですが、今回の解答例のように **「先に集計してから結合する」** ことには大きなメリットがあります。

> **パフォーマンスの黄金律：先に絞って、先にまとめる**
> `SALES` テーブルのような巨大なデータ（ファクトテーブル）を扱う場合、先に結合してしまうと「大量の行 × 大量の行」の重い処理が発生します。
> カッコの中で先に**「2019年の3ヶ月分だけ」に絞り込み、かつ「顧客IDごとに1行」に集約**してから結合することで、データベースの作業量を劇的に減らすことができるのです。

### 3. 実務での使い分け：インラインビュー vs WITH句
現代の現場では、**`WITH` 句（例2）が好まれる傾向**にあります。

* **コードの再利用性**: 複数の場所で同じ集計結果を使いたい時、`WITH` 句なら一度書くだけで済みます。
* **デバッグのしやすさ**: カッコが何重にもなるインラインビューは、「どのカッコがどこで閉じているか」を見失いやすいですが、`WITH` 句は「部品」ごとに独立しているため、テストが非常に楽です。

# 問題9-2（単一行サブクエリ） *Lv2*
### HRスキーマ`EMPLOYEES`テーブルより、給与（`salary`）の平均値よりも大きい人を取得してください。取得対象は入社日（`HIRE_DATE`）が2018年1月1日以降の人。（給与額の降順）

## 期待する結果
| EMPLOYEE_NAME  | SALARY | 
| -------------- | ------ | 
| Eleni Zlotkey  | 10500  | 
| Mattea Marvins | 7200   | 
| David Lee      | 6800   | 

## 解答例
```sql
SELECT
    first_name  || ' ' || last_name AS employee_name,
    salary
FROM
    hr.employees
WHERE
    salary > (
        SELECT
            AVG(salary)
        FROM
            hr.employees
        )
    AND hire_date >= DATE'2018-01-01'
ORDER BY
    salary DESC;
```

## 解説
今回は、サブクエリの中でも最も基本的で、かつ強力な **「単一行サブクエリ（Single-row Subquery）」** の解説です。
「平均より売上が高い商品」「最も高い給与の社員」など、**「動的に決まる基準値」** を使ってデータを絞り込みたいときに欠かせないテクニックです。

### 1. 文法解説：単一行サブクエリとは？
その名の通り、カッコ内のクエリ（内側のクエリ）が **「たった1つの値（1行1列）」だけを返す** サブクエリのことです。

```sql
WHERE salary > ( SELECT AVG(salary) FROM employees )
```

#### ① 動作の仕組み：バケツリレー
データベースは、以下の順番で処理を行います。

1.  **内側（サブクエリ）を実行**: `hr.employees` 全体の平均給与を計算します（例：6461.8...）。
2.  **値を手渡す**: その結果を外側のクエリに渡します。
3.  **外側を実行**: 渡された値を元に、「`salary > 6461.8...`」という条件で最終的な絞り込みを行います。

### 2. なぜ「サブクエリ」を使わなければならないのか？
初心者が一番やってしまいがちなミスがこちらです。
❌ `WHERE salary > AVG(salary)`

これはエラーになります。なぜなら、**`WHERE` 句の中で直接「集計関数（`AVG` や `SUM`）」を使うことはできない**というルールがあるからです。

* **`WHERE` 句**: 1行ずつチェックするための場所。
* **`AVG` 関数**: 全行を計算しないと結果が出ないもの。

「全行計算し終わった結果」を「1行ずつのチェック」に持ち込むために、サブクエリというワンクッションが必要になるわけですね。

### 3. 実務でのポイント：比較演算子
単一行サブクエリは「1つの値」として扱われるため、通常の比較演算子がすべて使えます。

* **`>`**, **`<`**: ～より大きい、小さい。
* **`=`**, **`<>`**: ぴったり一致、一致しない。
* **`>=`**, **`<=`**: 以上、以下。

> **もしサブクエリが「2行以上」返してしまったら？**
> もし内側のクエリが「部署ごとの平均」などで複数行を返してしまった場合、単一行比較演算子（`>` や `=`）はエラーを出して停止します。その場合は、次回のテーマとなる「複数行サブクエリ（`IN` や `ANY`）」の出番です！

### 4. 期待する結果の確認
結果を見ると、平均（約6,461円）を超えており、かつ2018年以降に入社した3名がしっかり抽出されていますね。
Eleni Zlotkeyさんの10,500円など、平均値を大幅に上回る「高給与かつ新しい世代」のメンバーが特定できました。

# 問題9-3（複数行サブクエリ） 　*Lv2*
### HRスキーマ`EMPLOYEES`テーブルより、社員を取得してください。取得対象は`DEPARTMENTS`テーブル`DEPARTMENT_NAME`が「IT」である部門に所属する人。（順不同）

## 期待する結果
| EMPLOYEE_NAME   | JOB_ID  | DEPARTMENT_ID | 
| --------------- | ------- | ------------- | 
| Alexander James | IT_PROG | 60            | 
| Bruce Miller    | IT_PROG | 60            | 
| David Williams  | IT_PROG | 60            | 
| Valli Jackson   | IT_PROG | 60            | 
| Diana Nguyen    | IT_PROG | 60            | 

## 解答例
```sql:例1：INを使用
SELECT
    first_name || ' ' || last_name AS employee_name,
    job_id,
    department_id
FROM
    hr.employees
WHERE
    department_id IN (
        SELECT
            department_id
        FROM
            hr.departments
        WHERE
            department_name = 'IT'
    )
```
```sql:例2：EXISTSを使用
SELECT
    first_name || ' ' || last_name AS employee_name,
    job_id,
    department_id
FROM
    hr.employees e
WHERE
    EXISTS (
        SELECT
            'X'
        FROM
            hr.departments d
        WHERE
            e.department_id = d.department_id
            AND department_name = 'IT'
    )
```

## 解説
今回は、 **「複数行サブクエリ」** です。前問は結果が1つだけ（平均値など）でしたが、今回は「IT部門のID」という、**複数返ってくる可能性があるリスト**を相手にする方法です。
SQLにおいて、別々のテーブルにある情報を組み合わせて絞り込む際、もっとも頻繁に使う「実弾」のようなテクニックです。

### 1. 文法解説：IN 演算子（例1）
サブクエリが複数の値を返す場合、通常の `=` ではなく **`IN`** を使います。

```sql
WHERE department_id IN ( SELECT department_id FROM ... )
```

#### ① 動作の仕組み：リスト照合
イメージとしては、内側のクエリが「IT部門のIDは 60 です」という **リスト（名簿）** を作成し、外側のクエリが「この従業員のIDは、名簿の中に載っているかな？」と一人ずつ照合していく動きです。
![](https://storage.googleapis.com/zenn-user-upload/11fde255334b-20260319.png)


### 2. 文法解説：EXISTS 演算子と相関サブクエリ（例2）
こちらは少し中級者向けの、非常に強力な書き方です。

```sql
WHERE EXISTS ( SELECT 'X' FROM ... WHERE e.dept_id = d.dept_id )
```

#### ① 相関サブクエリ（Correlated Subquery）
内側のクエリの中に `e.department_id`（外側のテーブルの列）が登場していますよね。このように**「外側と内側がリンクしている」**状態を相関サブクエリと呼びます。

#### ② 動作の仕組み：存在チェック
`EXISTS` は「条件に合うデータが**1件でも存在するかどうか**」だけを判定します。
1. 外側の `EMPLOYEES` を1行読み込む。
2. その人の `department_id` を内側に持ち込み、`DEPARTMENTS` テーブルに「IT部門で、かつこのIDのデータはある？」と聞きに行く。
3. **1件でも見つかった瞬間**に「合格（TRUE）」として、その従業員を表示します。

![](https://storage.googleapis.com/zenn-user-upload/73e82724564f-20260319.png)


> **なぜ `SELECT 'X'` なのか？**
> `EXISTS` は中身の内容（値）には興味がなく、単に「行があるかないか」だけを見ます。そのため、列名を書く代わりに `'X'` や `1` などの適当な文字を書くのがSQLエンジニアの慣習です。

### 3. 実務での使い分け：IN vs EXISTS
「結局どっちがいいの？」という疑問に対する、現場の判断基準は以下の通りです。

| 特徴 | `IN` | `EXISTS` |
| :--- | :--- | :--- |
| **可読性** | 直感的で読みやすい。 | 少し複雑に見える。 |
| **得意なケース** | 内側（サブクエリ）の結果が**少ない**とき。 | 外側が巨大で、内側で**インデックスが効く**とき。 |
| **NULLの扱い** | サブクエリにNULLが含まれると結果が空になる危険がある。 | NULLの影響を受けにくく、安全。 |

# 問題9-4（差分の抽出）
### SHスキーマ`CUSTOMERS`テーブルより、2021年に一度も購入しなかった顧客（完全離脱者）を特定してください。具体的には`SALES`テーブル`time_id`に2021年のデータを持たない人が対象となります。出力対象は`CUST_YEAR_OF_BIRTH`が1924の人。（順不同）

## 期待する結果
| CUST_ID | CUST_GENDER | CUST_YEAR_OF_BIRTH | 
| ------- | ----------- | ------------------ | 
| 102011  | M           | 1924               | 
| 102258  | F           | 1924               | 
| 103921  | M           | 1924               | 
| 102555  | M           | 1924               | 
| 101256  | M           | 1924               |  

## 解答例
```sql:例1：INを使用
SELECT
    cust_id,
    cust_gender,
    cust_year_of_birth
FROM
    sh.customers
WHERE
    cust_id NOT IN (
        SELECT
            cust_id
        FROM
            sh.sales
        WHERE
            time_id BETWEEN DATE'2021-01-01' AND DATE'2021-12-31'
    )
    AND cust_year_of_birth = 1924;
```
```sql:例2：EXISTSを使用
SELECT
    cust_id,
    cust_gender,
    cust_year_of_birth
FROM
    sh.customers
WHERE
    NOT EXISTS (
        SELECT
            'X'
        FROM
            sh.sales
        WHERE
                sh.sales.cust_id = sh.customers.cust_id
            AND time_id BETWEEN DATE'2021-01-01' AND DATE'2021-12-31'
    )
        AND cust_year_of_birth = 1924;
```

## 解説
今回は「何かが**ない**こと」を条件にする、実務でも非常に重要度の高い **「差分の抽出（アンチジョイン）」** のテクニックですね。
「昨日は買ったのに今日は買っていない人」「キャンペーン対象外の人」など、マーケティング分析ではこの「引き算」の考え方が欠かせません。


### 1. 文法解説：NOT IN と NOT EXISTS
どちらも「サブクエリの結果に含まれないもの」を抽出しますが、アプローチが異なります。

#### ① NOT IN（例1）
「リストの中に存在しないこと」を確認します。
1. サブクエリが「2021年に購入した人のIDリスト」をドサッと作ります。
2. 外側のクエリが、自分の `cust_id` がその**リストに載っていないこと**をチェックします。

#### ② NOT EXISTS（例2）
「条件に合う行が1行も見つからないこと」を確認します。
1. 外側の顧客を1人ずつ見て、その人のIDをサブクエリに持ち込みます。
2. `SALES` テーブルに「この人の2021年の購入履歴」を探しに行き、**「見つからなかった（空だった）」場合のみ**合格とします。

### 2. 実務での超重要注意点：NULLの罠
初級者を超えてプロを目指すなら、必ず知っておかなければならない **「NOT IN の落とし穴」** があります。

> **サブクエリの結果に NULL が混ざると...**
> もしサブクエリ（`SALES`テーブル）の `cust_id` に1つでも **NULL** が含まれていた場合、`NOT IN` は**1行も結果を返さなくなります**。
> これは、SQLの論理で `NOT IN (1, 2, NULL)` が「1でも2でもNULLでもない」となり、NULLとの比較が「不明（UNKNOWN）」になってしまうためです。
一方、`NOT EXISTS` はNULLが含まれていても正しく動作します。そのため、実務では**より安全な `NOT EXISTS` が好まれる**傾向にあります。

### 3. パフォーマンスと使い分け

| 特徴 | `NOT IN` | `NOT EXISTS` |
| :--- | :--- | :--- |
| **直感的な理解** | ◎ わかりやすい | △ 少し複雑 |
| **NULLへの耐性** | ❌ 非常に弱い（結果が消える） | ✅ 強い（安全） |
| **実行速度** | 小規模なら高速 | **大規模データで真価を発揮** |

現代のOracleであれば、どちらで書いても内部的に最適な実行計画に変換されることが多いですが、**「迷ったら `NOT EXISTS`」** と覚えておくと、バグの少ない堅牢なコードが書けますよ。

### 4. 期待する結果の確認
1924年生まれ（現在102歳！）の非常にご高齢な顧客の中で、2021年に一度も購入がなかった方々がリストアップされています。
こうしたデータは、「この年代のお客様向けのサービスが最近利用されていないのでは？」といったビジネス上の気づきに繋がります。

# 【完全版】問題9-5（特定データの取得） *Lv3*
### SHスキーマ`SALES`テーブルより、過去に比べて購入額が減少している顧客を特定してください。具体的には下記の条件で取得してください。（順不同）
* **2021年の購入額が2020年の購入額よりも下回っている**
* **2021年の購入額が0より大きい（まだ離脱していない）**
* **`cust_id`が50よりも小さい**


## 期待する結果
| CUST_ID | SALES_2020 | SALES_2021 | 
| ------- | ---------- | ---------- | 
| 7       | 555.93     | 117.5      | 
| 27      | 29541.89   | 2849.03    | 
| 32      | 15877.21   | 112.89     | 
| 33      | 997.57     | 102.62     | 
| 49      | 705.37     | 302.56     | 
| 19      | 662.74     | 18.9       | 
| 20      | 7263.94    | 77.98      | 

## 解答例
```sql:例1：インラインビューを使用
SELECT 
    v.cust_id,
    v.sales_2020,
    v.sales_2021
FROM (
    -- 顧客ごとに年別の売上を横持ちにする集計用ビュー（副問合せ）
    SELECT 
        cust_id,
        SUM(CASE WHEN to_char(time_id, 'YYYY') = '2020' 
                    THEN amount_sold ELSE 0 END) as sales_2020,
        SUM(CASE WHEN to_char(time_id, 'YYYY') = '2021' 
                    THEN amount_sold ELSE 0 END) as sales_2021
    FROM sh.sales
    GROUP BY cust_id
) v
WHERE v.sales_2020 > v.sales_2021
  AND v.sales_2021 > 0
  AND v.cust_id < 50
```

```sql:例2：WITH句を使用
WITH v AS (
    SELECT 
        cust_id,
        SUM(CASE WHEN to_char(time_id, 'YYYY') = '2020' 
                    THEN amount_sold ELSE 0 END) AS sales_2020,
        SUM(CASE WHEN to_char(time_id, 'YYYY') = '2021' 
                    THEN amount_sold ELSE 0 END) AS sales_2021
    FROM sh.sales
    GROUP BY cust_id
)
SELECT 
    v.cust_id,
    v.sales_2020,
    v.sales_2021
FROM v
WHERE v.sales_2020 > v.sales_2021
  AND v.sales_2021 > 0
  AND v.cust_id < 50
```



## 解説
この問題は、実務における「データ分析」の現場で最も頻繁に遭遇するパターンの1つです。
単にデータを出すだけでなく、**「2020年と2021年の数値を比較して、その差に意味を見出す」** という、ビジネスインテリジェンス（BI）の基礎が詰まっています。

### 1. 核心テクニック：条件付き集計（Conditional Aggregation）
このクエリの最も美しい部分は、サブクエリ（仮想テーブル `v`）の中にある `SUM(CASE ...)` です。

通常、売上データは「1行1伝票」の縦長（ロング型）データですが、比較を行うためには「2020年の列」と「2021年の列」を持つ**横長（ワイド型）データ**に変換する必要があります。


### ① SUM(CASE WHEN ... ) の仕組み
```sql
SUM(CASE WHEN to_char(time_id, 'YYYY') = '2020' THEN amount_sold ELSE 0 END)
```
1.  **判定**: 1行ずつ「これは2020年のデータか？」をチェックします。
2.  **抽出**: 2020年なら金額を、そうでなければ `0` を出します。
3.  **集計**: それらを顧客ごとに合計します。

これにより、本来は別々の行にある「去年の数字」と「今年の数字」を、**同じ行の隣同士**に並べることができるのです。これを専門用語で「ピボット（旋回）」と呼びます。


### 2. なぜ「サブクエリ」が必要なのか？
「サブクエリを使わずに `HAVING` 句で書けないの？」と思うかもしれません。

実は、`HAVING` 句でも書けないことはないのですが、今回のように **「計算した結果同士をさらに比較する（`sales_2020 > sales_2021`）」** 場合、一度サブクエリで「確定した値」としてテーブル化してしまった方が、圧倒的にSQLが読みやすく、ミスも少なくなります。

* **内側（仮想テーブル `v`）**: 複雑な条件で「去年の売上」と「今年の売上」というシンプルな表を作る。
* **外側**: 出来上がったシンプルな表に対して、普通の `WHERE` 句で条件をかける。

この **「複雑なことは内側でやり、外側はシンプルに保つ」** のが、上級レベルの設計思想です。


### 3. ビジネス視点での絞り込み条件
ここがマーケティング分析として面白いポイントです。

* **`v.sales_2021 > 0`**: 2021年に「0より大きい」という条件を入れることで、**「完全に辞めてしまった人（離脱客）」を除外し、「まだ買ってくれているが、勢いが落ちている人（要注意客）」** だけを特定しています。
* **`v.sales_2020 > v.sales_2021`**: 減少の度合いをチェックしています。

### 4. 期待する結果の確認
CUST_ID = 27 の顧客を見てください。
2020年は「29,541」も買っていた超優良客なのに、2021年は「2,849」まで激減しています。もしあなたがこのショップの店長なら、このデータを見た瞬間に「何か不満があったのか？」「競合他社に流れたのか？」と、すぐに個別のフォローを入れるべきだと判断できますよね。

> **WITH句（例2）のすすめ**
> 実務では、この後に「減少率」を計算したり、顧客名と結合したりと、さらに処理が続くことが多いです。そのため、ロジックを独立させて管理できる **`WITH` 句** を好んで使うプロが多いですよ。

# 問題9-6（最新の履歴取得） *Lv2*
### SHスキーマ`SALES`テーブルより、`cust_id`=2の顧客が最後に購入した日の、販売詳細を特定してください。（順不同）


## 期待する結果
| CUST_ID | TIME_ID              | PROD_ID | AMOUNT_SOLD | 
| ------- | -------------------- | ------- | ----------- | 
| 2       | 2022-09-05T00:00:00Z | 18      | 1499.06     | 
| 2       | 2022-09-05T00:00:00Z | 18      | 1491.56     | 
| 2       | 2022-09-05T00:00:00Z | 18      | 1204.26     | 


## 解答例
```sql:例1：MAXを使用
SELECT 
    s.cust_id, 
    s.time_id, 
    s.prod_id, 
    s.amount_sold
FROM sh.sales s
WHERE 1=1
  AND s.time_id = (
    SELECT MAX(time_id) 
      FROM sh.sales sub 
     WHERE sub.cust_id = s.cust_id
  )
AND s.cust_id = 2;
```
```sql:例2：ALLを使用
SELECT 
    s.cust_id, 
    s.time_id, 
    s.prod_id, 
    s.amount_sold
FROM sh.sales s
WHERE 1=1
  AND s.time_id >= ALL(
    SELECT time_id 
      FROM sh.sales sub 
     WHERE sub.cust_id = s.cust_id
  )
  AND s.cust_id = 2;
```

## 解説
実務では「最新の住所を取得したい」「最後に発注した時の単価を知りたい」といった場面が多々あり、この **「最新履歴の特定」** はSQLの中でも定番中の定番と言えるテクニックです。
今回のポイントは、サブクエリを使って「最新の日付」という基準を動的に作り出している点です。


### 1. 文法解説：相関サブクエリによる「最新」の特定
解答例のどちらにも共通しているのは、内側のクエリが外側のクエリと連動している **「相関サブクエリ」** であることです。


#### ① MAX関数を使う方法（例1）
```sql
WHERE s.time_id = (SELECT MAX(time_id) FROM ... WHERE sub.cust_id = s.cust_id)
```
1.  **内側**: 顧客ごとに「一番大きい（新しい）日付」を1つだけ探し出します。
2.  **外側**: その日付にぴったり一致する行だけを表示します。

もっとも直感的で、多くのエンジニアが好んで使う「王道」の書き方です。

#### ② ALL演算子を使う方法（例2）
```sql
WHERE s.time_id >= ALL (SELECT time_id FROM ... WHERE sub.cust_id = s.cust_id)
```
* **`>= ALL` の意味**: サブクエリが返す「すべての値」以上であること。
* **仕組み**: 「自分自身の日付が、その顧客の全購入日の中で、誰よりも大きい（あるいは等しい）」＝「一番新しい」という論理になります。

### 2. 知っておくと得する「1=1」の意味
解答例の `WHERE 1=1` という記述。一見、意味がないように見えますが、これは現場でよく使われる **「開発の効率化」** のためのテクニックです。

* **理由1：プログラムでの生成**: プログラム（JavaやPythonなど）で動的にSQLを組み立てる際、条件がいくつあっても「必ず `AND` でつなげられる」のでコードが書きやすくなります。
* **理由2：デバッグのしやすさ**: 条件をコメントアウト（`--`）して一時的に無効化する際、どこを消してもエラーになりにくいという利点があります。

### 3. 実行結果の読み解き
期待する結果を見ると、2022年9月5日のデータが3行並んでいます。
「最新の1日」を特定しても、その日に複数の商品（`prod_id`=18 が3つ）を購入している場合、このように **「その日の詳細すべて」** が正しく取得されるのが、このクエリの優れた点です。

> **近代的な別解：分析関数（ウィンドウ関数）**
> 今回のサブクエリ以外にも、`RANK()` や `ROW_NUMBER()` といった分析関数を使って、「日付の新しい順に1, 2, 3...と番号を振り、1番だけを取る」という書き方もあります。Oracle 12c以降ではこちらの方がパフォーマンスが良い場合も多いです。

# 問題9-7（スカラ・サブクエリ） *Lv2*
### HRスキーマ`EMPLOYEES`テーブルより`NAME`、`SALARY`を取得し、さらに`DEPARTMENTS`テーブルより、該当する`DEPARTMENT_NAME`を取得してください。対象は`EMPLOYEE_ID`が110より小さいデータとしてください。（順不同）

## 期待する結果
| EMPLOYEE_ID | NAME            | SALARY | DEPT_NAME | 
| ----------- | --------------- | ------ | --------- | 
| 100         | Steven King     | 24000  | Executive | 
| 101         | Neena Yang      | 17000  | Executive | 
| 102         | Lex Garcia      | 17000  | Executive | 
| 103         | Alexander James | 9000   | IT        | 
| 104         | Bruce Miller    | 6000   | IT        | 
| 105         | David Williams  | 4800   | IT        | 
| 106         | Valli Jackson   | 4800   | IT        | 
| 107         | Diana Nguyen    | 4200   | IT        | 
| 108         | Nancy Gruenberg | 12008  | Finance   | 
| 109         | Daniel Faviet   | 9000   | Finance   | 

## 解答例
```sql:例1：スカラ・サブクエリを使用
SELECT
    e.employee_id,
    e.first_name || ' ' || e.last_name AS name,
    e.salary,
    -- ここで部署テーブル(departments)から部署名を1つだけSELECTする
    (SELECT d.department_name 
     FROM hr.departments d 
     WHERE d.department_id = e.department_id) AS dept_name
FROM
    hr.employees e
WHERE
    e.employee_id < 110
```
```sql:例2：結合を使用
SELECT
    e.employee_id,
    e.first_name || ' ' || e.last_name AS name,
    e.salary,
    d.department_name AS dept_name
FROM
    hr.employees e
    INNER JOIN hr.departments d
       ON d.department_id = e.department_id
WHERE
    e.employee_id < 110
```

## 解説
今回は、非常にユニークな **「スカラ・サブクエリ（Scalar Subquery）」** の解説です。
これまでのサブクエリは `FROM` 句や `WHERE` 句で使ってきましたが、今回は **`SELECT` 句の中で「1つの列」として扱う**という手法です。

### 1. 文法解説：スカラ・サブクエリとは？
`SELECT` 句の中にカッコ書きでクエリを埋め込む手法です。
このサブクエリは、**「1行1列（1つの値）」** だけを返さなければならないという厳格なルールがあるため、「スカラ（単一値）」と呼ばれます。

#### ① 動作の仕組み：行ごとの lookup（検索）
データベースは、メインの `EMPLOYEES` テーブルを1行読み込むたびに、その人の `department_id` を使って **「部署名は何？」と内側のクエリ（DEPARTMENTSテーブル）へ一瞬だけ聞きに行きます。**

1. 従業員100番（Steven）を読み込む
2. その人の `department_id = 90` を内側に渡す
3. 内側が `90` 番に対応する `Executive` を探し出してきて、列に埋める
4. 次の行へ進む...

### 2. 結合（JOIN）との違い
解答例2のように、同じ結果は `INNER JOIN` でも得られます。実務での使い分けがポイントです。

| 特徴 | スカラ・サブクエリ | JOIN（結合） |
| :--- | :--- | :--- |
| **可読性** | **「1つだけ情報を足したい」**時に直感的に書ける。 | 複数の列を足す時に適している。 |
| **行数の変化** | メインのテーブルの行数は絶対に変わらない。 | 結合条件によっては行数が増減する可能性がある。 |
| **パフォーマンス** | 大量データでは「行ごとに検索」するため遅くなりがち。 | 大量データを一気に処理するのに向いている。 |

### 3. 実務での「スカラ・サブクエリ」の使い所
「わざわざ JOIN でテーブルを繋げるほどでもないけど、ちょっとだけ別のテーブルから値を持ってきたい」という時に非常に重宝します。

* **マスタ名称の表示**: 今回のようにIDに対応する名前（部署名や商品名）を添えるだけの場合。
* **計算値の表示**: 各従業員の横に「全社の平均給与」を表示して比較したい場合。
    ```sql
    SELECT name, salary, (SELECT AVG(salary) FROM employees) as avg_sal FROM employees
    ```


### 4. 陥りやすいエラー：2行以上返すと爆発する

スカラ・サブクエリには「値は1つ（スカラ）」という鉄の掟があります。

> **複数行エラー (ORA-01427)**
> もし、内側の `SELECT d.department_name` の結果が、ある `department_id` に対して**2件以上**ヒットしてしまった場合、Oracleは「列の箱に1つの値を入れたいのに、2つ来た！」とパニックになり、実行エラーで停止します。
> これを防ぐためには、必ず `WHERE` 句で**主キー（ID）などを指定して、1件に絞り込む**必要があります。

### 5. 期待する結果の確認
Steven Kingさんは `Executive`、Alexander Jamesさんは `IT` と、各従業員の横に所属部署名が美しく添えられています。
`EMPLOYEES` テーブルには部署IDしかありませんが、スカラ・サブクエリという「窓」から別のテーブルを覗き見ることで、豊かな情報を表示できています。
