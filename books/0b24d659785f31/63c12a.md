# 問題13-1：列から行への変換（UNPIVOT）

### 難易度：★★★☆☆ (Lv.3)

## 問題
SHスキーマの`SUPPLEMENTARY_DEMOGRAPHICS`テーブルを使用して、顧客ごとの属性データ（居住年数、興味のあるスポーツなど）を縦持ち（行形式）に変換してください。

**【条件およびルール】**

* 変換後の列名は、項目名を **`ITEM`**、その内容を **`VALUE`** としてください。
* 対象項目：`YRS_RESIDENCE`, `AFFINITY_CARD`, `CRICKET`, `BASEBALL`, `TENNIS`, `SOCCER`, `GOLF`, `UNKNOWN`, `MISC`, `EDUCATION`, `OCCUPATION`, `HOUSEHOLD_SIZE`, `COMMENTS`
* 今回は `CUST_ID = 100005` のデータのみを取得対象とします。


## 期待する結果
| CUST_ID | ITEM           | VALUE                                                                                                     | 
| ------- | -------------- | --------------------------------------------------------------------------------------------------------- | 
| 100005  | AFFINITY_CARD  | 1                                                                                                         | 
| 100005  | BASEBALL       | 0                                                                                                         | 
| 100005  | COMMENTS       | Affinity card is a great idea. But your store is still too expensive. I am tired of your lousy junk mail. | 
| 100005  | CRICKET        | 0                                                                                                         | 
| 100005  | EDUCATION      | Assoc-A                                                                                                   | 
| 100005  | GOLF           | 1                                                                                                         | 
| 100005  | HOUSEHOLD_SIZE | 3                                                                                                         | 
| 100005  | MISC           | 0                                                                                                         | 
| 100005  | OCCUPATION     | Crafts                                                                                                    | 
| 100005  | SOCCER         | 1                                                                                                         | 
| 100005  | TENNIS         | 1                                                                                                         | 
| 100005  | UNKNOWN        | 0                                                                                                         | 
| 100005  | YRS_RESIDENCE  | 5                                                                                                         | 

## 解答例
```sql
WITH sd AS ( -- unpivotするためにこのwith句で型を統一する
    SELECT
        cust_id,
        education,
        occupation,
        household_size,
        to_char(yrs_residence) AS yrs_residence,
        to_char(affinity_card) AS affinity_card,
        to_char(cricket)       AS cricket,
        to_char(baseball)      AS baseball,
        to_char(tennis)        AS tennis,
        to_char(soccer)        AS soccer,
        to_char(golf)          AS golf,
        to_char(unknown)       AS unknown,
        to_char(misc)          AS misc,
        comments
    FROM
        sh.supplementary_demographics
    WHERE
        cust_id = 100005
)
SELECT
    cust_id,
    item,
    value
FROM
    sd UNPIVOT ( value
        FOR item
    IN ( education AS 'EDUCATION',
         occupation AS 'OCCUPATION',
         household_size AS 'HOUSEHOLD_SIZE',
         yrs_residence AS 'YRS_RESIDENCE',
         affinity_card AS 'AFFINITY_CARD',
         cricket AS 'CRICKET',
         baseball AS 'BASEBALL',
         tennis AS 'TENNIS',
         soccer AS 'SOCCER',
         golf AS 'GOLF',
         unknown AS 'UNKNOWN',
         misc AS 'MISC',
         comments AS 'COMMENTS' ) )
ORDER BY
    cust_id,
    item
```

## 解説
今回は、テーブルの形を根本から変える **「UNPIVOT（列から行への変換）」** という非常に強力なテクニックです。
通常のテーブルは「1レコード＝1つの対象（顧客など）」ですが、分析の現場では「1レコード＝1つの属性」という形に変換したい場面が多々あります。これを「横持ち（ワイド型）」から「縦持ち（ロング型）」への変換と呼びます。


### 1. 核心：なぜ型を統一（TO_CHAR）するのか？
このクエリの最大のポイントは、`UNPIVOT` を行う前段の **`WITH` 句（CTE）** にあります。

> **UNPIVOTの鉄則：データ型を揃えること**
> `UNPIVOT` で1つの列（今回の `VALUE` 列）にまとめられるデータは、すべて**同じデータ型**でなければなりません。
> * `YRS_RESIDENCE` は「数値型」
> * `EDUCATION` は「文字列型」
> * `COMMENTS` は「長大な文字列型」
> これらをそのまま混ぜようとすると、SQLは「型が違うものを同じ列に入れられない！」とエラーを吐いてしまいます。

そのため、解答例ではあえて **`TO_CHAR()`** を使い、すべての項目を一旦「文字列」という同じ器に移し替えています。この「下準備」ができるかどうかが、Lv3の分かれ道です。

### 2. 文法解説：UNPIVOT 句の構造
`UNPIVOT` 句の中身を分解してみましょう。

```sql
UNPIVOT (
    value        -- ❶ データそのものが入る列の名前
    FOR item     -- ❷ 元の「列名」が入る列の名前
    IN ( ... )   -- ❸ 行に変換したい「列」をリストアップ
)
```
### ① VALUE（値）
元々の各セルに入っていた中身（ Assoc-A, Crafts, 5 など）が格納される新しい列です。

### ② ITEM（項目名）
「この値は元々どの列のものだったか」を示すラベルが入る列です。`IN` 句で `education AS 'EDUCATION'` と書くことで、ラベル名を自由に指定できます。

### 3. 実務での活用シーン：属性の横断分析
この「縦持ち変換」は、以下のような場面で絶大な威力を発揮します。

* **アンケート結果の集計**: 「Q1, Q2, Q3...」と並んだ列を縦に並べ替えることで、「全設問を通して最も多い回答は何か？」を1つの `GROUP BY` で集計できるようになります。
* **EAVモデルの構築**: 属性が非常に多い（100列以上あるような）マスタを扱いやすくするために、ID・属性名・値という3列だけの形に変換して処理します。
* **BIツールへの流し込み**: 多くのモダンな分析ツール（TableauやPower BIなど）は、横に長い表よりも、縦に長い表の方が圧倒的に扱いやすい設計になっています。


### 4. 期待する結果の確認
CUST_ID = 100005 の顧客一人に対し、元々は1行しかなかったデータが、13行（13項目分）に増えていますね。
このように、**「列をデータの種類としてではなく、1つのレコードとして扱う」** ことで、SQLでのフィルタリングや並び替えの自由度が劇的に向上します。

# 問題13-2：行から列への変換（PIVOT）

### 難易度：★★★☆☆ (Lv.3)

## 問題
COスキーマの`ORDERS`テーブルと`ORDER_ITEMS`テーブルを使用して、年度別の注文総額を算出してください。

**【条件および算出ルール】**

* **売上計算**：1注文あたりの金額は、`ORDER_ITEMS`テーブルの **`UNIT_PRICE`（単価） × `QUANTITY`（数量）** の合計とします。
* **年度の特定**：`ORDERS`テーブルの `ORDER_TMS` から年を抽出してください。
* **横持ち変換**：算出した年度ごとの総額を、「2021年（`Y2021`）」と「2022年（`Y2022`）」の**2つの列**に振り分けて表示してください。

## 期待する結果
| Y2021     | Y2022    | 
| --------- | -------- | 
| 222438.11 | 86160.42 | 

## 解答例
```sql
SELECT
    *
FROM
    (
        WITH order_total AS (
            SELECT
                order_id,
                SUM(unit_price * quantity) AS total
            FROM
                co.order_items
            GROUP BY
                order_id
        )
        SELECT
            extract(YEAR FROM o.order_tms)  AS yr,
            SUM(ot.total)                   ttl
        FROM
            order_total ot
            LEFT JOIN co.orders   o ON ot.order_id = o.order_id
        GROUP BY
            extract(YEAR FROM o.order_tms)
    ) PIVOT (
        SUM(ttl)
        FOR yr
        IN ( 2021 AS y2021, 2022 AS y2022 )
    )
```

## 解説
前問（13-1）の `UNPIVOT` とは対照的に、今回は縦に並んだデータを横に広げる **`PIVOT`（ピボット）** のテクニックです。
実務において、年次報告書やダッシュボード用のデータを作成する際、「年」や「月」を横に並べて比較しやすくする処理は非常に頻出します。

### 1. 核心：PIVOT（行から列への入れ替え）の仕組み
`PIVOT` は、集計した結果（行）を新しい「列名」として再定義する操作です。

#### ① クエリの3段階構造
このクエリは、外側に向かって段階的にデータを作り上げています。

1.  **内側の `WITH` 句 (`order_total`)**: まずは明細単位の計算です。注文IDごとに「単価 × 個数」を合計し、注文ごとの総額を出します。
2.  **中間クエリ (`SELECT ... GROUP BY`)**: 注文テーブルと結合し、「2021年」と「2022年」それぞれの合計金額を算出します。この時点ではまだ、データは2行（縦）に並んでいます。
3.  **外側の `PIVOT` 句**: ここで魔法が起きます。縦に並んでいた年（2021, 2022）を横に倒して、列名に変換します。

### 2. 文法解説：PIVOT 句の内側

```sql
PIVOT (
    SUM(ttl)                               -- ❶ 列の交差点に置きたい「値」
    FOR yr                                 -- ❷ 列名に変換したい「元の列」
    IN ( 2021 AS y2021, 2022 AS y2022 )    -- ❸ どの値を列にするか、その名前は何か
)
```

* **`FOR yr`**: 「どの列の値を横に並べたいか」を指定します。今回は `yr`（年）の値を列名にしたいのでこれを指定します。
* **`IN (...)`**: ここで指定した値だけが列になります。`AS` を使うことで、期待する結果のような `Y2021` という見やすい列名に変更できます。

<br>


### 3. 実務での活用シーン：クロス集計レポート
`PIVOT` は、いわゆる「クロス集計表」を作成するための最強のツールです。

* **売上推移表**: 行に「商品カテゴリ」、列に「1月、2月、3月...」を並べて、月ごとの売上変化を見る。
* **在庫マトリックス**: 行に「倉庫名」、列に「サイズ（S, M, L）」を並べて、どこに何が何個あるかを見る。
* **比較分析**: 前問のように「居住年数」などの属性を列にして、セグメントごとの特徴を横並びで比較する。

### 4. プロの別解：CASE式を使ったピボット
実は、`PIVOT` 句が導入される前（あるいは他のDB）では、以下のように `SUM(CASE ...)` を使って手動でピボットするのが一般的でした。

```sql
SELECT
    SUM(CASE WHEN yr = 2021 THEN ttl ELSE 0 END) AS y2021,
    SUM(CASE WHEN yr = 2022 THEN ttl ELSE 0 END) AS y2022
FROM ...
```
この書き方も非常に汎用性が高いので、`PIVOT` 句とセットで覚えておくと、複雑な条件での列変換にも対応できるようになりますよ。

# 【完全版】問題13-3：行から列への変換（年度別の月次比較レポート）

### 難易度：★★★☆☆ (Lv.3)

## 問題

COスキーマの`ORDERS`テーブルと`ORDER_ITEMS`テーブルを使用して、月ごとの注文総額を「2021年」と「2022年」で並べて表示してください。

**【条件および算出ルール】**

* **売上計算**：1注文あたりの金額は、`ORDER_ITEMS`テーブルの **`UNIT_PRICE` × `QUANTITY`** の合計とします。
* **軸の定義**：
* **縦軸（行）**：注文月（`MT`）を 1〜12 の数値で表示します。
* **横軸（列）**：注文年（`YR`）を抽出し、2021年（`Y2021`）と2022年（`Y2022`）の列に変換します。


* **表示順**：月の昇順で並べてください。


## 期待する結果
| MT  | Y2021    | Y2022    | 
| --- | -------- | -------- | 
| 1   |          | 33323.64 | 
| 2   | 3256.22  | 24081.63 | 
| 3   | 11405.42 | 23269.17 | 
| 4   | 18317.39 | 5485.98  | 
| 5   | 18254.94 |          | 
| 6   | 20500.44 |          | 
| 7   | 19884.46 |          | 
| 8   | 23353.01 |          | 
| 9   | 26362.46 |          | 
| 10  | 25922.88 |          | 
| 11  | 25412.36 |          | 
| 12  | 29768.53 |          | 

## 解答例
```sql
SELECT
    *
FROM
    (
        WITH order_total AS (
            SELECT
                order_id,
                SUM(unit_price * quantity) AS total
            FROM
                co.order_items
            GROUP BY
                order_id
        )
        SELECT
            extract(YEAR FROM o.order_tms)  AS yr,
            extract(MONTH FROM o.order_tms) AS mt,
            SUM(ot.total)                   ttl
        FROM
            order_total ot
            LEFT JOIN co.orders   o ON ot.order_id = o.order_id
        GROUP BY
            extract(YEAR FROM o.order_tms),
            extract(MONTH FROM o.order_tms)
    ) PIVOT (
        SUM(ttl)
        FOR yr
        IN ( 2021 AS y2021, 2022 AS y2022 )
    )
ORDER BY
    mt
```

## 解説
前問（13-2）は「年」を横に並べるだけでしたが、今回は **「月」という時間軸を縦に残したまま、「年」を横に広げる** という、実務の月次報告書で最もよく使われる**前年比較（YoY: Year over Year）レポート**の形です。

### 1. 核心：「どの列を残し、どの列を回すか」
`PIVOT` 句を使う際、最も重要なのは「PIVOT句の中で**指定しなかった列**がどうなるか」という点です。

* **`FOR yr`**: 年（`yr`）は横に回転して「列」になります。
* **`SUM(ttl)`**: 合計金額は、新しい列の中身（値）になります。
* **`mt` (月)**: PIVOT句で指定されていないこの列は、**そのまま「行」の軸として残ります。**

これにより、1月〜12月という縦の並びを維持したまま、その横に2021年と2022年の数値を並べることができるわけです。


### 2. クエリの組み立てプロセス
このクエリは、複雑に見えて実は非常に綺麗な3階層構造になっています。

1.  **部品作成 (`WITH order_total`)**: 
    注文明細から「注文ごとの合計金額」を計算。
2.  **集計の下地 (サブクエリ内 `SELECT`)**: 
    「年（`yr`）」「月（`mt`）」「その年月の合計（`ttl`）」という、**縦長（ロング型）** の集計表を一度作ります。
3.  **仕上げ (`PIVOT`)**: 
    縦長の表から `yr` だけを横に倒して、**横長（ワイド型）** の比較表に変換します。


### 3. 実務での活用シーン：前年比・季節性分析
この形式のデータは、ビジネスの意思決定において非常に高い価値を持ちます。

> **ビジネス視点での読み解き**
> * **季節性の把握**: 「毎年12月はギフト需要で売上が伸びる」といったトレンドが、縦の推移で一目でわかります。
> * **成長の確認**: 同じ「3月」で横に比較したとき、2021年（11,405）から2022年（23,269）へと倍増していることが即座に把握できます。


### 4. 成功のポイント：ORDER BY の位置
`PIVOT` した直後の結果は、並び順が保証されません。レポートとして月がバラバラ（1月、10月、2月...）に出てくると非常に読みづらいため、最後にしっかりソートすることで、期待する結果通りの美しいカレンダー形式になります。

# 【完全版】問題13-4：2項目のクロス集計（PIVOT）

### 難易度：★★★☆☆ (Lv.3)

## 問題

SHスキーマの`SUPPLEMENTARY_DEMOGRAPHICS`テーブルをもとに、「学歴（`EDUCATION`）」を縦軸に、「世帯人数（`HOUSEHOLD_SIZE`）」を横軸に展開して、各セグメントごとの顧客数を算出してください。

**【条件およびルール】**

* **縦軸（行）**：`EDUCATION` を表示し、昇順で並べてください。
* **横軸（列）**：`HOUSEHOLD_SIZE` の各値（'1', '2', '3', '4-8', '9+'）を列として展開してください。
* **集計値**：各セグメントの顧客レコード数（`COUNT`）を表示してください。
* ※元のデータに馴染みがない場合でも、特定の「学歴」と「世帯人数」が交差するポイントの合計人数を出すイメージで作成してください。
  

## 期待する結果
| EDUCATION | SIZE_1 | SIZE_2 | SIZE_3 | SIZE_4_TO_8 | SIZE_9_PLUS | 
| --------- | ------ | ------ | ------ | ----------- | ----------- | 
| 10th      | 39     | 26     | 28     | 0           | 21          | 
| 11th      | 47     | 15     | 34     | 0           | 16          | 
| 12th      | 16     | 10     | 11     | 0           | 8           | 
| 1st-4th   | 2      | 2      | 11     | 0           | 2           | 
| 5th-6th   | 2      | 8      | 16     | 0           | 6           | 
| 7th-8th   | 3      | 23     | 44     | 0           | 12          | 
| 9th       | 5      | 17     | 33     | 0           | 9           | 
| < Bach.   | 247    | 266    | 331    | 0           | 125         | 
| Assoc-A   | 18     | 46     | 73     | 0           | 20          | 
| Assoc-V   | 14     | 58     | 77     | 0           | 32          | 
| Bach.     | 81     | 218    | 373    | 0           | 46          | 
| HS-grad   | 209    | 378    | 563    | 0           | 179         | 
| Masters   | 8      | 50     | 99     | 0           | 18          |

| Presch.   | 0      | 1      | 0      | 0           | 1           | 
| Profsc    | 0      | 23     | 61     | 0           | 5           | 

## 解答例
```sql
SELECT
    *
FROM
    (
        SELECT
            education,
            household_size
        FROM
            sh.supplementary_demographics
    ) PIVOT (
        COUNT(*)
        FOR household_size
        IN ( '1' AS size_1, '2' AS size_2, '3' AS size_3, '4-8' AS size_4_to_8, '9+' AS size_9_plus )
    )
ORDER BY
    education;
```

## 解説
今回は、**「2項目によるクロス集計（マトリックス表）」** ですね。
これまでの `PIVOT` は「年月」などの時系列がメインでしたが、今回は「学歴」と「世帯人数」という、完全に異なる2つの属性を掛け合わせています。これぞ、統計分析やマーケティングリサーチで使われるクロス集計の真髄です。

### 1. 核心：PIVOTが作る「データの地図」
今回のクエリは、膨大な顧客データを「学歴（縦軸）」と「世帯人数（横軸）」という2つの座標で整理し、その交差点に「何人いるか」をマッピングしています。

#### ① 縦軸を決めるのは「残り物」
`PIVOT` 句の面白い（そして少しトリッキーな）ルールは、**「PIVOT句の中で指定しなかった列が、自動的に縦軸（行）になる」** という点です。
* 今回、サブクエリで `education` と `household_size` の2つだけを抽出しました。
* `household_size` を横軸（`FOR` 句）に指定したため、**残った `education` が自動的に縦軸**として採用されます。

### ② データの集計方法
```sql
PIVOT ( COUNT(*) FOR household_size IN (...) )
```
交差点に置く値として `COUNT(*)` を指定しています。これにより、各セグメントの顧客数が算出されます。


### 2. 文法解説：IN句でのラベル指定

```sql
IN ( '1' AS size_1, '2' AS size_2, ... )
```
`IN` 句の中で `'1'` などの値をそのまま列名にすることもできますが、SQLの列名として扱いやすくするために `AS` で名前を付けています。
* 元のデータ：`'4-8'`（ハイフンが含まれる文字列）
* 変換後の列名：`SIZE_4_TO_8`（プログラムや他のツールで扱いやすい形式）
このように、**「人間が読みやすく、システムが扱いやすい」** 形に整えるのがプロのテクニックです。

### 3. 実務での視点：データの「偏り」を見抜く
このクロス集計表が完成すると、単なる平均値や合計値では見えなかった **「相関関係」** が浮き彫りになります。

* **HS-grad（高校卒）**: 世帯人数「3」が563人と非常に多く、ボリュームゾーンであることがわかります。
* **PhD（博士号）**: 世帯人数「1」はわずか1人に対し、「3」が33人と、高学歴層では一定規模の世帯を形成している傾向が見て取れます。


### 4. 現場でよくある悩み：NULLの扱い
Oracleの `PIVOT` 句では、該当する組み合わせがない場合、デフォルトでは **`NULL`** が入ります。
もし期待する結果のように「0」と表示させたい場合は、出力時に `NVL` 関数などを使って加工することもありますが、最近のBIツールでは「NULLは自動的に0として描画する」設定が多いため、まずはこのシンプルなPIVOTでデータを渡すのがスマートです。

# 【完全版】問題13-5：PIVOTによる昨対比分析（減少顧客の特定＜問題9-5の別解＞）

### 難易度：★★★☆☆ (Lv.3)

## 問題

SHスキーマの`SALES`テーブルを利用し、**2020年に比べて2021年の購入額が減少している顧客**を特定してください。

**【抽出・フィルタリング条件】**

* **PIVOTの活用**：2020年と2021年の売上をそれぞれ `SALES_2020`、`SALES_2021` という列に展開してください。
* **減少判定**：2021年の購入額が、2020年の購入額よりも低いこと。
* **生存判定**：2021年の購入額が 0 より大きい（完全に離脱はしていない）こと。
* **対象範囲**：`cust_id` が 50 未満の顧客。

## 期待する結果
| CUST_ID | SALES_2020 | SALES_2021 | 
| ------- | ---------- | ---------- | 
| 7       | 555.93     | 117.5      | 
| 27      | 29541.89   | 2849.03    | 
| 32      | 15877.21   | 112.89     | 
| 33      | 997.57     | 102.62     | 
| 49      | 705.37     | 302.56     | 
| 19      | 662.74     | 18.9       | 
| 20      | 7263.94    | 77.98      | 

## 解答例
```sql
SELECT
    cust_id,
    sales_2020,
    sales_2021
FROM
    (
        SELECT
            cust_id,
            TO_CHAR(time_id, 'YYYY') AS sales_year,
            amount_sold
        FROM
            sh.sales
        WHERE
            TO_CHAR(time_id, 'YYYY') IN ( '2020', '2021' )
    )
     PIVOT (
        SUM(amount_sold)
        FOR sales_year
        IN ( '2020' AS sales_2020, 
             '2021' AS sales_2021 )
    )
WHERE
    sales_2020 > sales_2021
    AND sales_2021 > 0
    AND cust_id < 50
```

## 解説
以前、問題9-5で「自己結合（SELF JOIN）」や「副問い合わせ」を駆使して解いたこの課題。今回は **`PIVOT`句** を使うことで、驚くほど直感的、かつシンプルに解決していますね。
実務において「去年の売上と今年の売上を比較して、調子が落ちている顧客を見つける」といった **傾向分析（トレンド分析）** は、マーケティング部門から最も頻繁に依頼されるタスクの一つです。

### 1. 核心：行の比較を「列の比較」に変える
SQLの基本は「行」単位の処理です。そのため、「2020年の行」と「2021年の行」を比較するのは本来少し手間がかかります。

#### ① 縦を横にするメリット
`PIVOT` を使う最大の利点は、**「別の行にあったデータを、同じ行の隣の列に持ってくる」** ことにあります。
* **変換前**: 2020年の売上行と2021年の売上行がバラバラに存在。
* **変換後**: 1人の顧客に対し、`SALES_2020` と `SALES_2021` という2つの列が横に並ぶ。

これにより、`WHERE sales_2020 > sales_2021` という**単純な引き算のような条件**で比較ができるようになります。これがPIVOTの魔法です。


### 2. クエリの3ステップ解剖
このクエリは、データが「絞られ、形を変え、さらに選別される」という綺麗な流れで構成されています。

1.  **データの準備（サブクエリ）**:
    `sh.sales` から必要な 2020年と2021年のデータだけを抜き出します。ここで `TO_CHAR` を使って「年」というラベル（`sales_year`）を作っているのがポイントです。
2.  **形状変換（PIVOT）**:
    縦に並んだ年度を横に倒します。`SUM(amount_sold)` を中身に入れ、`sales_2020` と `sales_2021` という新しい列を生成します。
3.  **最終選別（外側のWHERE）**:
    横並びになった数値を見て、「売上が減っているか（`2020 > 2021`）」、「まだ完全に離脱していないか（`2021 > 0`）」といった**ビジネスルール**を適用します。

### 3. ビジネス視点：離脱予備軍の特定
このクエリの結果に出てくる顧客（ID: 7, 27, 32...）は、いわば **「危険信号」** が灯っている顧客です。

* **分析の価値**: 全く買わなくなった「離脱客」を見つけるのは簡単ですが、このクエリのように「買っている金額が減ってきた客」を見つけることで、**完全に離脱する前に対策（クーポン配布やリマインドメールなど）を打つことが可能**になります。
* **実務での応用**: 今回は「年」で比較しましたが、これを「直近3ヶ月」と「その前の3ヶ月」に変えれば、よりリアルタイムな離脱予備軍リストになります。

### 4. プロの視点：自己結合版との違い
問題9-5で学んだ自己結合（テーブルを2回つなげる方法）と比べると、今回の `PIVOT` 版は以下の点が優れています。

* **読みやすさ**: 「2020年を列Aに、2021年を列Bに」という意図が明確。
* **拡張性**: もし「2019年も比較したい」となった場合、`IN` 句に一つ追加するだけで済みます。自己結合だとテーブルを3回繋げることになり、クエリがどんどん複雑になってしまいます。

# 【完全版】問題13-6：複数集計関数を同時に展開するマルチPIVOT

## 期待する結果

## 解説
今回は「複数の集計関数を同時に展開するマルチPIVOT」です。
実務のダッシュボードや経営報告資料を作る際、「売上金額だけ」「注文本数だけ」のレポートだと、「売上は増えているが、実は1件の超大口注文のおかげで、取引顧客数は激減している（危険な状態）」といったビジネスの異常に気づけません。金額（SUM）と件数（COUNT）を同時に横並びにするこのテクニックは、まさに**ビジネスの健康診断**に必須のスキルです。
Oracleの `PIVOT` 構文の真骨頂とも言えるこのクエリの仕組みを分かりやすく解説します。

### 1. スクリプトの解説：列が倍々に増える魔法
このクエリの核は、`PIVOT` 句の中で**2つの集計関数**を同時に指定している点にあります。

#### マルチPIVOTの展開ルール

```sql
PIVOT (
    SUM(item_amt) AS sales,
    COUNT(*)      AS count
    FOR yr IN ( 2021 AS y2021, 2022 AS y2022 )
)
```

通常のPIVOTは「展開する値（今回は2年分）」の数だけ列が増えますが、集計関数を2つにすると、「展開する値の数 × 集計関数の数」の分だけ列がダイナミックに増殖します。今回は $2 \times 2 = 4$ 列が自動生成されます。

Oracle内部では、以下のように列名が自動的にドッキング（結合）されます。

* `y2021`（年のエイリアス） ＋ `sales`（集計のエイリアス） ＝ **`Y2021_SALES`**
* `y2021`（年のエイリアス） ＋ `count`（集計のエイリアス） ＝ **`Y2021_COUNT`**
* `y2022` ＋ `sales` ＝ **`Y2022_SALES`**
* `y2022` ＋ `count` ＝ **`Y2022_COUNT`**

この規則性を知っておくと、最外周の `SELECT` で迷わず正しい列名を指定できるようになります。

### 2. 文法・テクニックのポイント

#### ① なぜサブクエリ（インラインビュー）で囲むのか？
`PIVOT` を使うときの一番の約束事は、「PIVOT句に渡す前に、データを必要な列だけに絞り込んでおくこと」です。

もし、サブクエリを使わずにテーブルを丸ごと `PIVOT` に放り込むと、テーブルに含まれる `ORDER_STATUS` や `CUSTOMER_ID` など、**集計に関係のないすべての列が自動的に「グループ化（GROUP BY）の軸」として扱われてしまいます。**
結果として、月（`MT`）ごとに1行にまとまらず、データが細切れになってレポートが崩壊してしまいます。

> 「横軸にしたい列（`yr`）」「縦軸にしたい列（`mt`）」「集計したい列（`item_amt`）」の**3種類だけをサブクエリで正確に切り出してから PIVOT に渡す**のが、失敗しない鉄則です。

#### ② EXTRACT 関数のスマートさ

日付（`TIMESTAMP`型など）から「年」や「月」を数値として取り出すために、`EXTRACT(YEAR FROM ...)` や `EXTRACT(MONTH FROM ...)` を使用しています。
`TO_CHAR(..., 'MM')` でも同じように月を抽出できますが、文字列（'01', '02'...）ではなく**純粋な数値（1, 2...）として取り出せる**ため、レポートのソートや比較が非常に扱いやすくなります。

### 3. 実務でのアドバイス：客単価の可視化
今回の出力結果（期待する結果）の2月と3月を見比べてみましょう。とても面白いビジネスの動きが見えてきます。

* **2021年2月**: 売上 約3,256 / 件数 35件 $\rightarrow$ 1件あたり**約93ドル**
* **2021年3月**: 売上 約11,405 / 件数 146件 $\rightarrow$ 1件あたり**約78ドル**

3月は売上が3倍以上に跳ね上がっていますが、1件あたりの購入額（客単価）は下がっており、「客単価は落ちたが、注文数が爆発的に増えたことで総売上が伸びた」という背景が見えてきます。
マルチPIVOTを使うと、こうした「数字の裏にあるストーリー」をクエリ一発で経営陣に提示できるようになります。

実務で即戦力になる重要テクニックを3つのポイントに絞って深掘り解説します。

### 1. スクリプトの解説：日付から四半期への美しい変換
このクエリが非常にスマートなのは、サブクエリ（インラインビュー）の中で四半期（Q1〜Q4）へのデータ整形を完結させている点です。

#### ① 秘密兵器 `TO_CHAR(..., 'Q')`

```sql
TO_CHAR(o.order_tms, 'Q') AS qtr
```

日付やタイムスタンプから四半期を切り出す際、`CASE` 式で「1月〜3月なら1、4月〜6月なら2……」と書くのは非常に面倒ですよね。
Oracleには、フォーマットマスクに **`'Q'`（Quarter）** を指定するだけで、自動的に `'1'` 〜 `'4'` の文字列を返してくれる素晴らしい機能が備わっています。これだけでコードの美しさが劇的に変わります。

#### ② パフォーマンスを意識した日付フィルタリング

```sql
WHERE o.order_tms >= TIMESTAMP '2021-01-01 00:00:00'
  AND o.order_tms < TIMESTAMP '2022-01-01 00:00:00'
```

「2021年のデータに絞る」というとき、つい `TO_CHAR(order_tms, 'YYYY') = '2021'` と書きたくなりますが、解答例の書き方は**100点満点のプロの記述**です。
列に直接関数（`TO_CHAR`など）を適用してしまうと、`order_tms` 列にインデックスが貼られていても機能しなくなります（インデックスの無効化）。上記のように生の日付のまま範囲指定（不等号）を行うことで、**インデックスをフル活用して高速に処理**できます。

### 2. 文法・テクニックのポイント
#### マルチPIVOTの命名規則（おさらい）
今回も「4つの四半期（値）」 $\times$ 「2つの集計関数」によって、右側に $4 \times 2 = 8$ 個の列がダイナミックに生成されます。

```sql
PIVOT (
    SUM(item_amt) AS sales,
    COUNT(*)      AS count
    FOR qtr IN ( '1' AS q1, '2' AS q2, '3' AS q3, '4' AS q4 )
)
```

列名のドッキング規則は **`[FOR句のエイリアス]_[集計関数のエイリアス]`** となるため、自動生成される列名は以下の通りになります。

## 解説
クロス集計の最終奥義とも言える **`PIVOT XML`** の登場です。
通常の `PIVOT` を実務で使い始めると、ほぼ100%のエンジニアが「`IN` 句の中にいちいち固定値を手動で並べるの面倒くさすぎる…自動で国や店舗のリストを拾ってきてくれないかな？」という壁にぶち当たります。

この「SQLの宿命（列名の事前確定）」を、出力をXMLにすることで力技で突破する、Oracle独自の超強力なテクニックを徹底解説します。

### 1. スクリプトの解説：ハードコードからの完全脱却
このクエリの最大の見どころは、`PIVOT XML` 句内の **`IN` 句に記述されたサブクエリ** です。

```sql
PIVOT XML (
    SUM(amount_sold) AS amount_sold
    FOR country_id
    -- ❷ 固定値ではなく、サブクエリで動的にリストを取得！
    IN ( SELECT country_id FROM sh.countries )
)
```

#### なぜこれが「革命的」なのか？

通常の `PIVOT` では、`IN ('US', 'CA', 'JP')` のように値をハードコーディングしなければなりません。そのため、新しい国（例：'FR'）が進出するたびに、本番稼働しているプログラムのSQLを書き換えて再リリースするという恐ろしい運用が発生します。

しかし、`PIVOT XML` を使って上記のようにマスターテーブル（`sh.countries`）から `SELECT` する形にしておけば、**テーブルに新しい国が追加された瞬間、クエリを1文字も修正することなく自動的に新しい国がクロス集計の横軸に組み込まれます。** まさにメンテナンス性100点満点の設計です。

### 2. 文法・テクニックのポイント

#### ① なぜ通常の `PIVOT` ではサブクエリが禁止されているのか？
関係データベース（RDB）の基本ルールとして、「SQLの実行前に、出力される列の数と列名がカチッと決まっていなければならない」という大原則があります。
サブクエリを使うと、データの増減によって列数が変わってしまう（動的スキーマ）ため、通常の `PIVOT` ではサブクエリが文法エラーになります。

#### ② 原則を突破するための「XML形式」
「列数を固定できないなら、**『1つの列（CLOB型）』の中に、すべての集計結果をXML形式のテキストとして詰め込んで返せばいいじゃない**」という逆転の発想から生まれたのが `PIVOT XML` です。

期待する結果を見ると、右側の列が **`COUNTRY_ID_XML`** という1つの列になっており、その中に以下のようなタグ形式で全データが内包されています。

```xml
<PivotSet>
    <item>
        <column name = "COUNTRY_ID">52769</column>
        <column name = "AMOUNT_SOLD">763603.28</column>
    </item>
    ...内容がどれだけ増えても、この1列の中にすべて横並びで入る...
</PivotSet>
```

* **列名の自動決定**: `[FOR句の列名]_XML` という名前の列が自動生成されます。


### 3. 実務でのアドバイス：XMLデータをどう活かすか？
「SQL一発で綺麗に横並びの表（Grid）が出ないなら、使いにくくない？」と思うかもしれません。しかし、実務のシステム開発（Java, Python, C# などの Webアプリケーション）において、この機能は**神機能**として崇められています。

#### 実務での王道ワークフロー
1. **SQL側**: `PIVOT XML` を使って、どんなに項目（国や商品）が増減してもエラーにならない堅牢なXMLデータを一撃で取得する。
2. **プログラム側（フロントエンド）**: 受け取ったXML（またはJsonに変換したもの）を画面表示ライブラリ（マトリックス形式のグリッドビューなど）に放り込む。
3. **画面上**: ライブラリがXMLを自動解析し、ユーザーの画面には綺麗な「動的クロス集計表」がレンダリングされる。

> **ExcelやBIツールとの連携**

# 【完全版】問題13-9：小計・合計行を完全網羅する立体クロス集計（PIVOT × CUBE）

### 難易度：★★★★☆ (Lv.4)

## 問題

単にデータをクロス集計するだけでなく、縦軸・横軸の各小計、および全体の総合計までをすべて網羅した、見栄えの良い立体クロス集計レポートを構築する必要があります。

* **全方位の集計**: `CUBE` 句を使用して、縦軸・横軸の各小計、および右下の総合計を含むすべての集計行・列を網羅してください。

完璧な「完全版」、ありがとうございます！問題の背景、使用テーブル、そして期待する結果が美しく一本の線で繋がりましたね。

このクエリは、多次元集計の王様である **`CUBE`** と、クロス集計の定番である **`PIVOT`** を極めて高いレベルで組み合わせた、まさに「BI（ビジネスインテリジェンス）レポートの模範解答」です。

システムが自動生成する集計の隙間（`NULL`）を完全にコントロールし、最終的な見栄えまでこだわり抜いたこのクエリの職人技を、4つのステップに分解して徹底解説します！


### 1. スクリプトの核心：4つの職人技

#### ① `CUBE` 句による「全方位集計」の自動生成

```sql
GROUP BY CUBE(education, household_size)
```

通常の `GROUP BY` は指定した組み合わせの明細しか出しません。しかし、`CUBE` を使うと、指定された列の「ありとあらゆる組み合わせ（縦の合計・横の合計・右下の総合計）」をバックグラウンドで一撃で計算してくれます。

* **明細**: 「10th」で「世帯人数1人」の件数
* **横の小計**: 「10th」の全世帯人数の合計
* **縦の小計**: 世帯人数「1人」の全学歴の合計
* **右下の総合計**: すべての学歴・すべての世帯人数の総計（斜め・全体の合計）

#### ② `GROUPING` 関数による「意味のあるNULL」の救済

`CUBE` が計算してくれた「小計」や「合計」の行には、システム上の目印として **`NULL`** が入ります。
しかし、そのまま `PIVOT` に流すと画面上でただの空欄になってしまうため、**`GROUPING` 関数** を使って `'TOTAL'` というラベルに翻訳しています。

```sql
CASE WHEN GROUPING(education) = 1 THEN 'TOTAL' ELSE education END
```

`GROUPING(列名)` は、その行が「CUBEによって生み出された合計行」である場合にのみ **`1`** を返します。これを利用して、純粋なデータ不備の `NULL` と、集計上の `NULL` を完璧に見分けて `'TOTAL'` に置換しているのが非常にスマートです。

#### ③ `PIVOT` 句での「TOTAL列」の動的回収

```sql
PIVOT (
    SUM(cnt)
    FOR household_size
    IN ( ..., 'TOTAL' AS total )
)
```

ステップ③で、世帯人数が空欄（合計）の場所に `'TOTAL'` という名前を付けました。
これを `PIVOT` の `IN` 句の末尾に滑り込ませることで、本来はデータとして存在しないはずの `'TOTAL'` が横軸の列として展開され、「右端の合計列（`TOTAL`）」が綺麗に誕生します。

#### ④ `ORDER BY` による「総合計行の最下部ピン留め」

```sql
ORDER BY 
    CASE WHEN education = 'TOTAL' THEN 1 ELSE 0 END, 
    education
```

普通に文字列（`education`）だけでソートすると、アルファベット順のルールによって `'TOTAL'` 行が表の途中に紛れ込んでしまいます（`HS-grad` と `Masters` の間など）。
そこで、「もし `'TOTAL'` なら `1`（後回し）、それ以外なら `0`（優先）」という重み付けをソート条件に挟むことで、**総合計行を確実に一番下に配置する**という、レポートとしての完璧な優しさが実装されています。


### 2. 実務での使い分け：CUBE と ROLLUP
`ROLLUP` と、実際に使った `CUBE` の違いは、実務のレポート設計で非常に重要になります。

* **`ROLLUP(A, B)` [階層的な小計]**
「会社 $\rightarrow$ 本部 $\rightarrow$ 課」のように、データに明確な上下関係（親子関係）がある場合に使います。右肩下がりに、組織ごとの小計を綺麗に積み上げます。
* **`CUBE(A, B)` [網羅的なマトリックス]**
