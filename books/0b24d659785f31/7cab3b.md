# 問題15-1：MODEL句の基礎（売上予測）

### 難易度：★★★☆☆ (Lv.3)

## 問題

SHスキーマの`SALES`テーブルを使用し、2022年10月〜12月の実績値をもとに、2023年1月〜3月の売上予測値を算出して表示してください。

**【予測ルール】**

* **2023年1月**：2022年10月の実績 $\times 1.1$
* **2023年2月**：2022年11月の実績 $\times 1.1$
* **2023年3月**：2022年12月の実績 $\times 1.1$
* ※算出結果はすべて小数点第3位を切り捨て（第2位まで表示）てください。



## 期待する結果
| TM     | SM         | 
| ------ | ---------- | 
| 202210 | 2449167.91 | 
| 202211 | 2474687.5  | 
| 202212 | 2547042.11 | 
| 202301 | 2694084.7  | 
| 202302 | 2722156.25 | 
| 202303 | 2801746.32 | 

## 解答例
```sql
SELECT
    tm,
    sm
FROM
    (
        SELECT
            TO_NUMBER(to_char(time_id, 'yyyymm')) AS tm,
            SUM(amount_sold)                      AS sm
        FROM
            sh.sales
        WHERE
            time_id BETWEEN DATE '2022-10-01' AND DATE '2022-12-31'
        GROUP BY
            tm
    )
MODEL
    DIMENSION BY ( tm )
    MEASURES ( sm )
    RULES (
        sm[202301]= TRUNC(sm[202210]* 1.1, 2),
        sm[202302]= TRUNC(sm[202211]* 1.1, 2),
        sm[202303]= TRUNC(sm[202212]* 1.1, 2)
    )
ORDER BY
    tm
```

## 解説
**`MODEL`句** は、一言で言えば「SQLの中にExcelを持ち込む」ような、非常に強力かつユニークな機能です。
通常、SQLは「すでにあるデータ」を取得・加工するものですが、`MODEL`句を使うと、存在しない未来のデータ（行）を計算によって**その場で生成**することができます。

### 1. 核心：MODEL句を「Excel」でイメージする
`MODEL`句を理解する一番の近道は、結果セットを「スプレッドシート（表計算）」として捉えることです。

#### ① DIMENSION BY（行の見出し）
Excelでいう「行番号」や「キー」です。今回は `tm`（年月）を軸にしています。

#### ② MEASURES（セルの値）
Excelの「セルの中身」です。計算対象となる数値（今回は売上額 `sm`）を指定します。

#### ③ RULES（数式）
これが`MODEL`句の本体です。Excelで `A4 = A1 * 1.1` と入力するように、特定の「座標」に対して計算式を割り当てます。

![](https://storage.googleapis.com/zenn-user-upload/a384639655bb-20260327.png)




### 2. ここが凄い：存在しない行の自動生成
今回のクエリの最大の特徴は、「元のデータには2023年の行が存在しない」のに、結果には表示されるという点です。

```sql
sm[202301] = TRUNC(sm[202210] * 1.1, 2)
```

この一文で、SQLは以下の処理を自動で行います：

1. `tm` が `202301` である行を探す。
2. もし**存在しなければ、新しい行を勝手に作る。**
3. その行の `sm` 列に、`202210` の値に 1.1 を掛けた結果を代入する。

通常、新しい行を作るには `UNION ALL` などで無理やり結合する必要がありますが、`MODEL`句なら数式を書くだけで「予実管理表」のようなデータが作れてしまいます。

### 3. 実務での活用シーン：高度なシミュレーション
`MODEL`句は、単なる予測以上の複雑な計算（再帰計算）が得意です。

* **在庫シミュレーション**: 「前日の在庫 － 今日の出荷予定 ＝ 今日の在庫」という、前の行の結果を使う計算。
* **住宅ローンの返済表**: 毎月の残高に対して利息を計算し、次の月の開始残高にする処理。
* **売上目標の自動生成**: 前年実績に一定の成長率を乗せて、全月分の目標値を一括作成。

> **柔軟なアクセス方法**
> 今回は `sm[202301]` と直接指定しましたが、`sm[ANY]`（すべての月）や `sm[tm > 202212]`（特定の範囲）といった指定も可能です。まさに「セルの範囲指定」に近い感覚でクエリを操れます。

### 4. 期待する結果の確認
2022年12月までの実績データの下に、計算された2023年の予測値が3ヶ月分きれいに並びましたね！
`TRUNC(..., 2)` によって、指定通り小数点第3位が切り捨てられ、美しい予測レポートが完成しています。

# 【完全版】問題15-2：未来の繰り返し予測（再帰と反復）

### 難易度：★★★★☆ (Lv.4)

## 問題

SHスキーマの`SALES`テーブルを使用し、2022年10月〜12月の実績をもとに、**2023年12月まで**の12ヶ月分をシミュレーションしてください。

**【シミュレーションルール】**

* **予測式**：対象月の**3ヶ月前**の売上額（実績または予測値）に対して **1.1倍** する。
* **端数処理**：小数点第3位を切り捨て。
* **計算の連鎖**：
* 2023年01月 = 2022年10月（実績） × 1.1
* ...
* 2023年04月 = **2023年01月（予測値）** × 1.1
* 2023年05月 = **2023年02月（予測値）** × 1.1


* つまり、一度出した予測値が次の計算のベースになります。


## 期待する結果
| TM     | SM         | 
| ------ | ---------- | 
| 202210 | 2449167.91 | 
| 202211 | 2474687.5  | 
| 202212 | 2547042.11 | 
| 202301 | 2694084.7  | 
| 202302 | 2722156.25 | 
| 202303 | 2801746.32 | 
| 202304 | 2963493.17 | 
| 202305 | 2994371.87 | 
| 202306 | 3081920.95 | 
| 202307 | 3259842.48 | 
| 202308 | 3293809.05 | 
| 202309 | 3390113.04 | 
| 202310 | 3585826.72 | 
| 202311 | 3623189.95 | 
| 202312 | 3729124.34 | 

## 解答例
```sql:例1：MODEL句を使用
SELECT
    TO_NUMBER(to_char(
        ADD_MONTHS(DATE '2022-10-01', seq - 1),
        'yyyymm'
    )) AS tm,
    sm
FROM
    (
        SELECT
            ROW_NUMBER()
            OVER(
                ORDER BY
                    TO_NUMBER(to_char(time_id, 'yyyymm'))
            )                                     AS seq,
            TO_NUMBER(TO_CHAR(time_id, 'yyyymm')) AS tm,
            SUM(amount_sold)                      AS sm
        FROM
            sh.sales
        WHERE
            time_id BETWEEN DATE '2022-10-01' AND DATE '2022-12-31'
        GROUP BY
            tm
    )
MODEL 
    DIMENSION BY ( seq )
    MEASURES ( sm,
               tm )
    RULES ITERATE(12) (
        sm[iteration_number + 4]= TRUNC(sm[iteration_number + 1]* 1.1, 2)
    )
ORDER BY
    seq
```
```sql:例2：再帰的WITH句を使用
WITH 
-- 1. 実績データを準備
 base_data AS (
    SELECT
        ROW_NUMBER()
        OVER(
            ORDER BY
                TO_NUMBER(to_char(time_id, 'yyyymm'))
        )                                     AS seq,
        TO_NUMBER(to_char(time_id, 'yyyymm')) AS tm,
        SUM(amount_sold)                      AS sm
    FROM
        sh.sales
    WHERE
        time_id BETWEEN DATE '2022-10-01' AND DATE '2022-12-31'
    GROUP BY
        TO_NUMBER(to_char(time_id, 'yyyymm'))
),
-- 2. 再帰計算（ここがループ本体）
 prediction (
    seq,
    tm,
    sm
) AS (
    -- 実績データ：最初の手順（実績3ヶ月分を入れる）
    SELECT
        seq,
        tm,
        sm
    FROM
        base_data
    UNION ALL
    -- 予測データ（再帰部）：一期前のデータを使って次を作る
    -- seq=1(202210) から seq=4(202301) を作る
    SELECT
        p.seq + 3,
        TO_NUMBER(to_char(
            add_months(TO_DATE(p.tm
                               || '01', 'yyyymmdd'), 3),
            'yyyymm'
        )),
        TRUNC(p.sm * 1.1, 2)
    FROM
        prediction p
    WHERE
        p.seq <= 12 -- 15回目（12ヶ月分）まで繰り返す
)
SELECT
    tm,
    sm
FROM
    prediction
ORDER BY
    seq;
```

## 解説
問題15-1では「特定の月をコピーする」だけでしたが、今回は「予測値を使ってさらに先の予測を出す」という、実務のシミュレーションで最も重要な再帰的ループの考え方が必要になります。
この問題が解ければ、SQLを使って数年先までのキャッシュフロー予測や、複利計算を伴う資産運用シミュレーションなどが自由自在に組めるようになります。

### 1. 核心：「フィードバック・ループ」の仕組み
この問題の面白さは、「2023年4月の予測を出すために、自分が計算した2023年1月の予測値を使う」という点にあります。

10月の実績 $\rightarrow$ 1月の予測
11月の実績 $\rightarrow$ 2月の予測
12月の実績 $\rightarrow$ 3月の予測
**1月の予測 $\rightarrow$ 4月の予測（ここでループが繋がる！）**

### 2. 例1：MODEL句の「ITERATE」による力技
`MODEL`句の真のパワーは、この `ITERATE`（繰り返し）命令にあります。

#### ① ITERATE(12) と iteration_number

```sql
RULES ITERATE(12) (
    sm[iteration_number + 4] = TRUNC(sm[iteration_number + 1] * 1.1, 2)
)
```

* **`ITERATE(12)`**: 「中の計算を12回繰り返せ」という命令です。
* **`iteration_number`**: ループの回数が入る変数です（0, 1, 2...と増えます）。

#### ② 計算の連鎖
* **1回目 (num=0)**: `sm[4]` (1月) を `sm[1]` (10月) から計算。
* **2回目 (num=1)**: `sm[5]` (2月) を `sm[2]` (11月) から計算。
* **4回目 (num=3)**: `sm[7]` (4月) を **`sm[4]` (さっき計算した1月)** から計算。

このように、一度計算した結果が即座に次の計算の材料（セル）として使えるのが、Excel的な `MODEL` 句の最大の特徴です。


### 3. 例2：再帰的WITH句による「自己増殖」
`WITH` 句（再帰CTE）は、数学の「漸化式（ぜんかしき）」のような考え方でデータを生成します。

#### ① 1行から1行を生み出す
再帰部分の `JOIN` はありませんが、自分自身の「3ヶ月前の行」を元にして「今の行」を1つずつ生み出し、それを縦に積み上げていきます。

#### ② 終了条件
`WHERE p.seq <= 12` によって、無限ループを防ぎ、必要な期間（12ヶ月分）でピタッと止めています。

### 4. 実務での使い分け：どっちが「強い」？

| 特徴 | MODEL句 (例1) | 再帰的WITH句 (例2) |
| --- | --- | --- |
| **得意分野** | **複雑なセル間の相関**。例えば「売上が増えたら在庫を減らす」など。 | **シンプルな時系列の連続**。前月の値を引き継ぐような処理。 |
| **可読性** | Excelに慣れている人には直感的。 | プログラマーや論理思考の人には直感的。 |
| **パフォーマンス** | 大量の計算（数万セル）でも安定して高速。 | 再帰が深すぎると重くなる場合がある。 |

> **ビジネスの現場では**
> 中期経営計画などで「去年比10%成長を3年間続けたらどうなるか？」といった**シミュレーション**を行う際、`MODEL` 句が書けると、他の人がExcelで数時間かけて作るシートを、SQL数行で、しかも最新のDBデータを使って一瞬で出力できるようになります。

# 【完全版】問題15-3：モデル句による離脱者分析（Churn Analysis）

### 難易度：★★★★☆ (Lv.4)

## 問題
SHスキーマの `SALES` テーブルを使用し、2021年の四半期（Quarter）ごとの売上推移から、顧客のステータスを判定してください。

**【判定ルール（Q4時点でのSTATUS）】**

* **CHURNED（完全離脱）**:
  * 売上が **Q1 > Q2 > Q3** と連続減少しており、かつ **Q4の売上が 0**（データなし）。


* **INACTIVE（休眠）**:
  * 上記には当てはまらないが、**Q4の売上が 0**（データなし）。


* **ACTIVE（活動中）**:
  * Q4に売上が存在する。

**【条件】**
* 表示対象：`CUST_ID` が 71, 100, 525。
* 売上のない四半期は行自体が存在しませんが、MODEL句でQ4の行を補完して判定結果を表示してください。
* 結果は、**顧客ID（CUST_ID）の昇順**、および**四半期（QTR）の昇順**で表示してください。

## 期待する結果
| CUST_ID | QTR | AMOUNT  | STATUS   | 
| ------- | --- | ------- | -------- | 
| 71      | 1   | 160.37  |          | 
| 71      | 2   | 39.9    |          | 
| 71      | 3   | 162.34  |          | 
| 71      | 4   | 12.58   | ACTIVE   | 
| 100     | 1   | 210.95  |          | 
| 100     | 2   | 81.35   |          | 
| 100     | 4   |         | INACTIVE | 
| 525     | 1   | 4849.34 |          | 
| 525     | 2   | 4405.46 |          | 
| 525     | 3   | 486.18  |          | 
| 525     | 4   |         | CHURNED  | 

## 解答例
```sql
WITH user_quarterly_sales AS (
    -- 顧客・四半期ごとの売上合計を算出
    SELECT
        cust_id,
        TO_CHAR(time_id, 'q') AS qtr,
        SUM(amount_sold)      AS amount
    FROM
        sh.sales
    WHERE
        time_id BETWEEN DATE '2021-01-01' AND DATE '2021-12-31'
        AND cust_id IN ( 71, 100, 525 )
    GROUP BY
        cust_id,
        TO_CHAR(time_id, 'q')
)
SELECT
    *
FROM
    user_quarterly_sales
MODEL
    PARTITION BY ( cust_id ) 
    DIMENSION BY ( qtr )
    MEASURES ( 
        amount, 
        CAST(null AS VARCHAR2(20)) AS status )
    RULES (
        -- Q4の時点で「減少→減少→0」のパターンを判定
        status['4']=
            CASE
                WHEN amount['1']> amount['2']  -- Q1 > Q2 (減少)
                     AND amount['2']> amount['3']  -- Q2 > Q3 (さらに減少)
                     AND amount['4']IS NULL        -- Q4で購入なし(データがない=NULL)
                      THEN
                    'CHURNED'
                WHEN amount['4']IS NULL THEN
                    'INACTIVE'
                ELSE
                    'ACTIVE'
            END
    )
ORDER BY
    cust_id,
    qtr;
```

## 解説
今回は「完全離脱者の特定」になります。`MODEL`句を使った分析の、まさに**真骨頂**といえる問題です。
これまでのSQLでは「一列前のデータ」を見るのに `LAG` 関数などを使いましたが、今回の条件（Q1 > Q2 > Q3 かつ Q4がゼロ）のように、**複数の離れた行の状態を組み合わせて判定を下す**場合、`MODEL`句はExcelのセルを参照するような感覚で非常に強力な武器になります。

### 1. 核心：`MODEL`句による「顧客カルテ」の作成
このクエリでは、各顧客をひとつの「表（セル集団）」として扱い、その中で特定のパターンを探しています。

#### ① `PARTITION BY (cust_id)`
これが非常に重要です！顧客ごとに計算の範囲を完全に切り離しています。これにより、ID 71番の計算が ID 100番のデータに干渉することなく、「顧客ごとのタイムライン」を独立して評価できます。

#### ② 存在しない行（Q4）の扱い
実務でよくあるのが、「売上がゼロ」のときはデータ自体がテーブルに存在しないというケースです。

```sql
WHEN ... AND amount['4'] IS NULL THEN 'CHURNED'
```

`MODEL`句では、ルールで指定された座標（`['4']`）にデータがない場合、そこを **`NULL`** として扱います。これを利用して「第4四半期に購入記録がない」という状態をスマートに判定しています。


### 2. 判定ロジックの深掘り：なぜ「CHURNED」なのか？
期待する結果の3人を例に、`RULES`の中身がどう動いているか見てみましょう。

| CUST_ID | 推移パターン | 判定結果 | 理由 |
| --- | --- | --- | --- |
| **525** | Q1(大) > Q2(中) > Q3(小) → Q4(無) | **CHURNED** | 理想的な（？）「徐々に減って最後に消えた」パターン。 |
| **100** | Q1 > Q2 → Q3(無) → Q4(無) | **INACTIVE** | Q3の時点で既にデータがないため、`amount['2'] > amount['3']` の比較ができず（UNKNOWNになり）、最初の条件を外れます。 |
| **71** | Q1 > Q2 < Q3 → Q4(有) | **ACTIVE** | Q4に売上があるため、離脱とはみなされません。 |

> **NULLとの比較に注意**
> SQLのルール上、`100 > NULL` は `TRUE` ではなく `UNKNOWN` になります。そのため、Q3が欠損しているID 100番は「連続減少」の条件を満たさないと判定されます。ここが厳密なデータ分析の面白いところです。


### 3. 実務での活用：Churn（離脱）分析
この手法は、SaaSビジネスやECサイトの「解約予兆分析」でそのまま使えます。

* **予兆の検知**: 「完全にいなくなる（Q4=0）」前に、「Q1 > Q2 > Q3」の時点でアラートを出すように改造すれば、離脱防止のキャンペーンを打つターゲットリストになります。
* **複雑なフラグ立て**: 1つの `CASE` 文で、過去の複数時点の傾向を「文字列のラベル」に変換できるため、そのままBIツールのフィルター用データとして活用可能です。

### 4. 卒業へのステップ：`MEASURES`の工夫

```sql
MEASURES ( amount, CAST(null AS VARCHAR2(20)) AS status )
```

`status` という列は元々のテーブルにはありませんが、ここで「空の器」として定義することで、`RULES` 内で自由に値を書き込めるようになります。
このように、「元データにない列をその場で作って、計算結果を格納する」のが、`MODEL`句を使いこなす上での重要なテクニックです。

# 【完全版】問題15-4：モデル句による在庫枯渇シミュレーション

### 難易度：★★★★☆ (Lv.4)

## 問題
COスキーマの注文データ（2021年2月〜2022年4月）と現在の在庫データを使用し、「現在の在庫から毎月の平均注文数を引き続けたら、いつ在庫がマイナスになるか」をシミュレーションしてください。

**【シミュレーション条件】**

* **対象商品**：`PRODUCT_ID` が 19 および 35。
* **平均注文数の算出**：2021年2月から2022年4月（計15ヶ月）の総注文数を15で割ったもの（四捨五入して整数）。
* **ループ処理**：
* 2022年4月を起点（現在の在庫）とします。
* 翌月以降、在庫から平均注文数を差し引いていきます。
* **在庫がマイナスになった時点で、その商品についての計算を終了**してください。

* **表示項目**：年月（`OT`）、商品ID（`PRODUCT_ID`）、シミュレーション在庫数（`SUM_IVT`）。
* **商品ID（PRODUCT_ID）の昇順**、および**年月（OT）の昇順**で表示してください。

  
## 期待する結果
| OT     | PRODUCT_ID | SUM_IVT | 
| ------ | ---------- | ------- | 
| 202204 | 19         | 70      | 
| 202205 | 19         | 50      | 
| 202206 | 19         | 30      | 
| 202207 | 19         | 10      | 
| 202208 | 19         | -10     | 
| 202209 | 19         | -30     | 
| 202204 | 35         | 36      | 
| 202205 | 35         | 19      | 
| 202206 | 35         | 2       | 
| 202207 | 35         | -15     | 
| 202208 | 35         | -32     | 

## 解答例
```sql
WITH order_sum AS ( -- 商品ごとの注文数合計
    SELECT
        oi.product_id,
        SUM(oi.quantity) sum_ord
    FROM
             co.orders o
        INNER JOIN co.order_items oi ON o.order_id = oi.order_id
    GROUP BY
        oi.product_id
), inv_sum AS ( -- 商品ごとの在庫数合計
    SELECT
        i.product_id,
        SUM(i.product_inventory) sum_ivt
    FROM
        co.inventory i
    GROUP BY
        i.product_id
), inv_data AS ( -- 現在の商品ごとの在庫数、１ヶ月の注文数
    SELECT
        1     nm,
        i.product_id,
        o.sum_ord,
        round(o.sum_ord / (MONTHS_BETWEEN(DATE '2022-04-01', DATE '2021-02-01') + 1)) AS avg_ord,
        i.sum_ivt
    FROM
             order_sum o
        INNER JOIN inv_sum i ON o.product_id = i.product_id
    WHERE
        o.product_id in (19, 35)
)
SELECT
    to_char(
                add_months(DATE '2022-04-01', nm - 1),
        'yyyymm'
   ) ot,
    product_id,
    sum_ivt
FROM
    inv_data
MODEL
    PARTITION BY ( product_id ) DIMENSION BY ( nm )
    MEASURES ( sum_ivt,
               avg_ord )
    RULES ITERATE(20) UNTIL(sum_ivt[iteration_number + 1]< 0) (
        -- 次月の在庫 = 今月の在庫 - 平均注文数
        sum_ivt[iteration_number + 2]= sum_ivt[iteration_number +1]- avg_ord[1]
    )
ORDER BY
    product_id,
    nm
```

## 解説
今回は、実務の「SCM（サプライチェーン・マネジメント）」や「需要予測」の現場でそのまま使える非常に高度なクエリです。
この問題のポイントは、単なる未来予測ではなく、**「在庫がマイナスになるまで」という動的な終了条件**を伴うシミュレーションをSQLだけで完結させている点にあります。

### 1. 核心：「動的ループ」と終了条件（UNTIL）
15-2の「繰り返し予測」との最大の違いは、`RULES` 句にある **`UNTIL`** 条件の活用です。

#### ① ITERATE(20) UNTIL(条件)

```sql
RULES ITERATE(20) UNTIL(sum_ivt[iteration_number + 1] < 0)
```

* **`ITERATE(20)`**: 最大で20ヶ月先までシミュレーションを行います。
* **`UNTIL(...) < 0`**: 計算結果がマイナスになった瞬間にループを停止します。
これにより、商品ごとに「いつ在庫が切れるか」が異なる場合でも、必要な行数だけを正確に生成することができます。

#### ② 漸化式による在庫の減算

```sql
sum_ivt[iteration_number + 2] = sum_ivt[iteration_number + 1] - avg_ord[1]
```

Excelで「上のセルの値（在庫）から固定値（平均注文数）を引く」という数式を下にドラッグする操作を、SQLが内部で再帰的に実行しています。


### 2. データの準備：平均値の算出
シミュレーションの精度を決めるのは、前段の `inv_data` CTEでの計算です。

* **`MONTHS_BETWEEN`**: 過去の全期間（2021年2月〜2022年4月）が「何ヶ月間か」を正確に算出します。
* **`avg_ord`**: 総注文数を期間で割り、月平均の消費ペースを導き出しています。

この「実績に基づいた定数」を `MODEL` 句に渡すことで、根拠のあるシミュレーションが可能になります。

### 3. 実務での活用：欠品リスクの可視化
このクエリが書けると、在庫管理システムにおいて以下のような高度な機能を提供できます。

* **発注勧告アラート**: 「現在のペースだと〇ヶ月後に在庫が切れるので、今すぐ補充が必要」というリストを自動生成。
* **安全在庫の策定**: 平均注文数に「変動係数」を掛け合わせ、よりシビアな条件下でのシミュレーション。
* **キャパシティ・プランニング**: 倉庫の容量と将来の在庫推移を照らし合わせた計画策定。

### 4. 期待する結果の分析
結果を見ると、商品IDによって在庫が切れるタイミングが異なることがわかります。

* **商品 19**: 2022年07月まではプラス（10）を維持していますが、08月にはマイナス（-10）に転落します。
* **商品 35**: 2022年06月でギリギリプラス（2）ですが、07月には大幅なマイナス（-15）になります。

このように、「商品ごとの特性（在庫量と消費スピード）」を `PARTITION BY` で切り分けて同時にシミュレーションできるのが `MODEL` 句の最大の強みです。

# 【完全版】問題15-5：MODEL句による移動平均の算出（トレンド平滑化）

### 難易度：★★★☆☆ (Lv.3)

## 問題
マーケティング分析において、日次や月次の売上データは変動（ノイズ）が激しく、真のトレンドが見えにくいことがあります。
SHスキーマの **`SALES`** テーブルを使用し、月ごとの売上合計を算出した上で、 **「直近3ヶ月の移動平均（Moving Average）」** を計算してください。

**【算出・編集ルール】**

1. **TM（年月）**: 2021年1月〜12月の実績値。
2. **SM（売上合計）**: 各月の `AMOUNT_SOLD` の合計。
3. **MOV_AVG（3ヶ月移動平均）**:
   * **「当月・1ヶ月前・2ヶ月前」** の3ヶ月分の売上の平均値を算出してください。
   * データが3ヶ月分揃わない月（1月、2月）は、存在する月のみの平均で構いません。
   * 小数点第3位を四捨五入し、第2位まで表示してください。
4. 表示順は **`TM`** の昇順とします。

## 期待する結果
| TM     | SM         | MOV_AVG    | 
| ------ | ---------- | ---------- | 
| 202101 | 2006378.46 | 2006378.46 | 
| 202102 | 2118618.97 | 2062498.72 | 
| 202103 | 1859892.06 | 1994963.16 | 
| 202104 | 1765510.12 | 1914673.72 | 
| 202105 | 1874492.85 | 1833298.34 | 
| 202106 | 1731727.95 | 1790576.97 | 
| 202107 | 1896762.82 | 1834327.87 | 
| 202108 | 2112255.79 | 1913582.19 | 
| 202109 | 2112220.68 | 2040413.1  | 
| 202110 | 2164612.21 | 2129696.23 | 
| 202111 | 2060343.77 | 2112392.22 | 
| 202112 | 2062690.94 | 2095882.31 | 

## 解答例

```sql
SELECT
    tm,
    sm,
    mov_avg
FROM
    (
        SELECT
            TO_NUMBER(TO_CHAR(time_id, 'yyyymm')) AS tm,
            SUM(amount_sold) AS sm
        FROM
            sh.sales
        WHERE
            time_id BETWEEN DATE '2021-01-01' AND DATE '2021-12-31'
        GROUP BY
            TO_NUMBER(TO_CHAR(time_id, 'yyyymm'))
    )
MODEL
    DIMENSION BY ( tm )
    MEASURES ( sm, 0 AS mov_avg )
    RULES (
        -- CV()関数を用いて、現在の月の値を基準に「2ヶ月前〜当月」の範囲を平均する
        mov_avg[ANY] = ROUND(
            AVG(sm)[tm BETWEEN cv() - 2 AND cv()],
            2
        )
    )
ORDER BY
    tm
```

## 解説
今回の問題は、Oracle SQLの強力な機能である**MODEL句**を用いて、スプレッドシート（Excel）のようなセル操作感覚で**移動平均**を算出する手法を学びます。
通常、移動平均は分析関数（`AVG() OVER...`）で書くのが一般的ですが、MODEL句を使うことでより複雑な数式や、行を跨いだ柔軟な参照が可能になります。

### 1. クエリの構造解説
このSQLは大きく分けて「集計を行うインラインビュー」と「計算を行うMODEL句」の2段階で構成されています。

#### ① インラインビュー（データの準備）
まず、`sh.sales` テーブルから2021年のデータを抽出し、月単位（YYYYMM形式）で売上合計を算出します。

* **`TO_NUMBER(TO_CHAR(time_id, 'yyyymm'))`**: 日付型を数値の「202101」といった形式に変換し、これを次元（住所）として使えるようにします。

#### ② MODEL句（スプレッドシート化）
ここが本問の核心です。抽出した結果セットを多次元配列（セルの集まり）として定義します。

* **`DIMENSION BY (tm)`**: `tm`（年月）を、各行を特定するための「行番号」や「キー」として定義します。
* **`MEASURES (sm, 0 AS mov_avg)`**: 操作対象となる値を定義します。ここでは既存の売上（`sm`）と、これから計算結果を格納する空の列（`mov_avg`）を用意しています。

### 2. RULESセクションとCV関数の詳細
`RULES` 内で行われている計算式を詳しく見ていきましょう。

```sql
mov_avg[ANY] = ROUND(
    AVG(sm)[tm BETWEEN cv() - 2 AND cv()],
    2
)
```

#### キーワード解説
1. **`ANY`**: 全ての `tm`（1月〜12月）に対してこのルールを適用することを意味します。
2. **`cv()` (Current Value)**: 現在処理している行の次元（`tm`）の値を参照します。
   * 例えば、3月（`202103`）を処理しているとき、`cv()` は `202103` を返します。

3. **`tm BETWEEN cv() - 2 AND cv()`**:
   * **現在の月（`cv()`）から2ヶ月前（`cv() - 2`）までの範囲**を指定しています。
   * 3月の場合：`tm BETWEEN 202101 AND 202103` となり、1月・2月・3月の3ヶ月分が抽出されます。

4. **`AVG(sm)[...]`**: 指定した範囲の `sm` 列に対して平均値を算出します。データが存在しない月（1月の計算時の-1ヶ月、-2ヶ月など）は無視して計算されるため、問題文の「存在する月のみの平均で構わない」という条件を自然に満たします。

### 3. 実践的なポイント
#### なぜ分析関数ではなくMODEL句なのか？

通常、移動平均は以下の分析関数でも書けます：

```sql
AVG(sm) OVER (ORDER BY tm ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
```

しかし、MODEL句には以下の利点があります。

* **複雑な条件分岐**: 「もし売上が前月より◯%低ければ、特別な係数を掛ける」といった処理が容易。
* **存在しないデータの補完**: 欠落している月のデータ（行）を計算の中で動的に作り出すことも可能です。
* **可読性**: 計算式がExcelの数式に近いため、複雑なビジネスロジックを記述する際に直感的になります。

#### 注意点：数値計算としての `cv() - 2`
このクエリでは `tm` を `202101` という「数値」として扱っているため、`cv() - 2` が成立しています。もし年を跨ぐ場合（例：`202201 - 2` は `202199` になり、`202111` にはならない）、単純な引き算ではうまくいきません。その場合は日付型のまま処理するか、適切な数値変換ロジックが必要になります。

# 【完全版】問題15-6：多次元階層における集計とシェア算出（クロスディメンション参照）

### 難易度：★★★★☆ (Lv.4)

## 問題
経営分析チームより、製品カテゴリ別の売上レポートの作成依頼がありました。
単にカテゴリごとの売上を出すだけでなく、 **「全カテゴリ合計（Total）」** の行を仮想的に生成し、さらにその合計値を用いて **「各カテゴリが全体の何％を占めているか（Share）」** を算出してください。

通常であれば `RATIO_TO_REPORT` 分析関数や `ROLLUP` を組み合わせる場面ですが、今回は **MODEL 句の多次元参照** を用いて、一つの数式内で「合計の算出」と「シェアの計算」を同時に行います。

2021年の売上データを対象に、以下の情報を取得する SQL を作成してください。

**【使用テーブル】**
* **`sh.sales`**（売上履歴）
* **`sh.products`**（商品マスタ）
* **`sh.times`**（時間マスタ）

<br>

**【抽出・集計ルール】**

1. **DIMENSION（次元）**: `PROD_CATEGORY`（製品カテゴリ）と `CALENDAR_YEAR`（年）の2次元を定義します。
2. **仮想行の生成**: 元データには存在しない **`Total`** という名前のカテゴリ行を生成し、その年の全カテゴリの合計売上を算出してください。
3. **SHARE（構成比）の算出**:
   * 各カテゴリの売上が、その年の `Total` 行の売上に対して何％にあたるかを計算してください。
   * 小数点第3位を四捨五入し、第2位まで表示してください。


4. 対象は 2021年のみとし、表示順はカテゴリの昇順（ただし `Total` は最後）とします。

## 期待する結果
| PROD_CATEGORY     | YEAR | SALES_AMOUNT | SHARE_PCT | 
| ----------------- | ---- | ------------ | --------- | 
| Baseball          | 2021 | 6464786.22   | 27.2      | 
| Cricket           | 2021 | 3434409.23   | 14.45     | 
| Golf              | 2021 | 4336456.4    | 18.25     | 
| Soccer / Football | 2021 | 4329248.89   | 18.22     | 
| Tennis            | 2021 | 5200605.88   | 21.88     | 
| Total             | 2021 | 23765506.62  | 100       | 

## 解答例

```sql
SELECT
    prod_category,
    year,
    sales_amount,
    share_pct
FROM
    (
        SELECT
            p.prod_category,
            t.calendar_year AS year,
            SUM(s.amount_sold) AS sales_amount
        FROM
            sh.sales s
            INNER JOIN sh.products p ON s.prod_id = p.prod_id
            INNER JOIN sh.times t ON s.time_id = t.time_id
        WHERE
            t.calendar_year = 2021
        GROUP BY
            p.prod_category,
            t.calendar_year
    )
MODEL
    -- カテゴリと年の2次元で管理
    DIMENSION BY ( prod_category, year )
    -- 売上とシェアの2つの器を用意
    MEASURES ( sales_amount, 0 AS share_pct )
    RULES (
        -- 1. 全カテゴリの合計を 'Total' という新しい座標に代入
        sales_amount['Total', 2021] = SUM(sales_amount)[prod_category <> 'Total', cv()],
     
        -- 2. 各カテゴリの売上を、同じ年の 'Total' 座標の売上で割ってシェアを算出
        share_pct[ANY, ANY] = ROUND(
            sales_amount[cv(), cv()] / sales_amount['Total', cv()] * 100, 
            2
        )
    )
ORDER BY
    CASE WHEN prod_category = 'Total' THEN 1 ELSE 0 END,
    prod_category
```

## 解説
今回の問題は、Oracle SQLの真骨頂とも言えるMODEL句による「仮想行の生成」と「多次元参照」を組み合わせた高度なレポート作成手法です。
通常、合計行を作るには `ROLLUP`、シェアを出すには `RATIO_TO_REPORT` を使いますが、MODEL句を使うとこれらを「セルとセルの計算式」として、より直感的に記述できます。

### 1. 構造の全体像：SQLの設計図
このクエリは、まず実データを集計し、その結果を「多次元配列（スプレッドシート）」のように扱って加工しています。

#### ① インラインビュー（下準備）
`sh.sales`、`sh.products`、`sh.times` を結合し、カテゴリ別・年別の売上合計（`sales_amount`）を算出します。この時点では、まだ「Total」行は存在しません。

#### ② MODEL句の定義
ここがスプレッドシートの「枠組み」を決める部分です。

* **`DIMENSION BY (prod_category, year)`**: 「製品カテゴリ」と「年」を、セルの住所（行と列のようなもの）として定義します。
* **`MEASURES (sales_amount, 0 AS share_pct)`**: 操作したい値です。`share_pct` は元データにないため、初期値 `0` で器だけ用意します。

### 2. RULESセクションの徹底解説
ここがこのクエリの「心臓部」です。

#### 仮想行「Total」の生成

```sql
sales_amount['Total', 2021] = SUM(sales_amount)[prod_category <> 'Total', cv()]
```

この一行が非常に強力です。

1. **左辺**: `prod_category` が `'Total'` という新しい住所を指定しています。元データにこのカテゴリがなくても、**MODEL句が自動的に新しい行をメモリ上に生成**します。
2. **右辺**: `SUM(sales_amount)[...]` で合計を計算します。
* `prod_category <> 'Total'`: 自分自身（Total）を合計に含めないようにフィルタリングします（循環参照の防止）。
* `cv()`: 2つ目の次元（年）について、「現在の値（2021）」を引き継ぎます。



#### シェア（構成比）の算出

```sql
share_pct[ANY, ANY] = ROUND(
    sales_amount[cv(), cv()] / sales_amount['Total', cv()] * 100, 
    2
)
```

1. **`ANY, ANY`**: すべてのカテゴリ、すべての年に対してこの計算を適用します。
2. **`sales_amount[cv(), cv()]`**: 「自分自身のカテゴリ、自分自身の年」の売上。
3. **`sales_amount['Total', cv()]`**: 「同じ年の 'Total' カテゴリ」の売上を参照。
* これが**クロスディメンション参照**です。特定の行（Total）の値を、他のすべての行の計算に利用しています。

### 3. 仕上げのテクニック：ORDER BY
期待される結果では、`Total` が一番下にくる必要があります。しかし、アルファベット順では `T` は途中にきてしまいます。

```sql
ORDER BY
    CASE WHEN prod_category = 'Total' THEN 1 ELSE 0 END,
    prod_category
```

* `CASE` 式を使って、`Total` なら `1`、それ以外なら `0` という重みを付けます。
* これにより、まず「0（一般カテゴリ）」が並び、その後に「1（Total）」が来るよう制御しています。

### 4. MODEL句を使うメリット（vs 分析関数）

| 機能 | 分析関数 (`ROLLUP`/`RATIO_TO_REPORT`) | MODEL句 |
| --- | --- | --- |
| **柔軟性** | 定型的な集計に強い | 任意のセル同士で複雑な数式が組める |
| **行の追加** | 階層的な合計のみ可能 | 全く新しいラベルの行を自由に追加可能 |
| **可読性** | SQLらしい宣言的な記述 | Excelの数式に近い直感的な記述 |
