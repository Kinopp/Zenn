# 問題16-1：行パターンマッチング初歩の初歩１

### 難易度：★★★☆☆ (Lv.3)

## 問題

MATCH_RECOGNIZE句を使用して、HRスキーマの`COUNTRIES`テーブルから、`REGION_ID`が「20」のデータを取得してください。
なお、レコードの表示順序は問いません。

**【学習のポイント】**
通常、特定のIDを抽出するだけなら `WHERE region_id = 20` で十分ですが、ここではあえて `MATCH_RECOGNIZE` の基本作法を使い、以下のキーワードの役割を理解してください。

* **`PATTERN`**: 探したいパターンの並び順（正規表現のような書き方）。
* **`DEFINE`**: パターン内で使う変数の条件定義。
* **`ALL ROWS PER MATCH`**: 見つかったパターンに含まれるすべての行を表示する指定。

## 期待する結果
| REGION_ID | COUNTRY_ID | COUNTRY_NAME             | 
| --------- | ---------- | ------------------------ | 
| 20        | CA         | Canada                   | 
| 20        | BR         | Brazil                   | 
| 20        | AR         | Argentina                | 
| 20        | US         | United States of America | 
| 20        | MX         | Mexico                   | 

## 解答例
```sql
SELECT
    *
FROM
    hr.countries 
    MATCH_RECOGNIZE (
        ORDER BY
            region_id
        ALL ROWS PER MATCH
        PATTERN ( 
            group20+ 
        )
        DEFINE
            group20 AS region_id = 20
    )
```

## 解説
Oracle SQLの最先端機能の一つ、`MATCH_RECOGNIZE`句（行パターンマッチング）についてです。
本来、この機能は株価の「V字回復」やログデータの「特定のエラーパターン」など、複数の行にまたがるシーケンス（連続性）を正規表現のように探すための非常に強力な武器です。
今回はその「初歩の初歩」として、単純なフィルタリングをこの構文でどう書くか、という問題です。

### 1. 核心：MATCH_RECOGNIZEは「行に対する正規表現」
通常の `WHERE` 句が「個々の行」を判定するのに対し、`MATCH_RECOGNIZE` は「並んだ行の中に、特定のパターンがあるか」を判定します。

#### ① PATTERN ( group20+ )
正規表現でおなじみの `+` が使われています。これは「`group20` という条件に合う行が **1回以上連続して出現するパターン**」を探せ、という意味になります。

#### ② DEFINE group20 AS region_id = 20
ここで「`group20` とは何か」を定義しています。今回は単純に `REGION_ID` が 20 であること、としています。

### 2. 構文の解剖：なぜこの設定が必要か？
解答例にある各オプションの意味を整理しておきましょう。

* **`ORDER BY region_id`**: パターンを探す前に、データをどの順番で並べるかを指定します。行パターンマッチングにおいて、並び順は命（いのち）です。
* **`ALL ROWS PER MATCH`**: パターンに一致した行を**すべて**出力します。
* これを指定しない（デフォルトの `ONE ROW PER MATCH`）と、一致した複数の行がギュッと1行に集約されてしまいます。今回は全データが見たいため、これが必要です。

### 3. 実務での視点：なぜあえてこれを使うのか？
正直なところ、この問題のような単純な抽出なら `WHERE region_id = 20` と書くのが一番早いですし、行パターンマッチングを使用する必要はありません。今回は行パターンマッチングの学習ということで、あえて問題にしております。

以下のような複雑な条件が出てきたときに、この構文が活きてきます。

* **「売上が3日連続で上がった直後に、1日だけ下がったパターン」**
* **「ログイン失敗が1分以内に5回連続したパターン」**

これらを従来のSQL（自己結合や分析関数）で書くとクエリが迷宮化しますが、`MATCH_RECOGNIZE` なら **`PATTERN (UP UP UP DOWN)`** のように、直感的に記述できるようになります。

### 4. 期待する結果の確認
結果には、アメリカ大陸（REGION_ID: 20）に属するカナダ、ブラジル、アルゼンチンなどの国々が正しく抽出されていますね。


:::message
### MATCH_RECOGNIZEの文法詳細
`MATCH_RECOGNIZE`は、Oracle 12cから導入された比較的新しい構文ですが、その強力さゆえに「SQLの最終兵器」の一つとも呼ばれます。

基本的な考え方は、「テーブル全体を1つの長い文字列のように見立てて、そこに正規表現で検索をかける」というイメージです。

全体の構文図をもとに、主要な5つのパーツを分解して解説します。

<br>

### 1. 前準備：データの整理

パターンを探す前に、データを「どの範囲で」「どの順番で」並べるかを決めます。

* **`PARTITION BY`** (任意): データをグループ化します（例：`cust_id` ごとにパターンを探す）。
* **`ORDER BY`** (必須): パターンを判定する「時間順」や「ID順」を指定します。

<br>

### 2. 出力の形：ONE ROW か ALL ROWS か

マッチした結果をどう表示するかを決めます。

* **`ONE ROW PER MATCH`** (デフォルト): 1つのパターンに一致した複数行を**1行にまとめて**出力します（集計に向いています）。
* **`ALL ROWS PER MATCH`**: マッチした行を**すべてそのまま**出力します（詳細を確認するのに向いています）。

<br>

### 3. MEASURES：出力したい値の定義

通常の `SELECT` 句のように、結果に含めたい値を定義します。ここで便利な「特殊関数」が使えます。

* **`MATCH_NUMBER()`**: 何番目のマッチかを表示。
* **`CLASSIFIER()`**: その行がどの変数（後述の `DEFINE` で決めた名前）に一致したかを表示。
* **`FINAL COUNT(A.id)`**: マッチした「A」という区間の件数を集計、といった計算が可能です。

<br>

### 4. PATTERN：探したい「形」のデザイン

ここが最もエキサイティングな部分です。正規表現の記号を使って、行の並び順を定義します。

* **`PATTERN (A B+ C)`**: Aが1回、その次にBが1回以上、最後にCが1回、という並びを探せ。
* **`PATTERN (UP{3,} DOWN)`**: 3回以上連続で上昇（UP）した後、下落（DOWN）したパターンを探せ。

<br>

### 5. DEFINE：変数の正体を決める

`PATTERN` で使ったアルファベット（変数）が、具体的にどういう条件なのかを定義します。

```sql
DEFINE
  UP AS price > PREV(price),    -- 「UP」とは、前の行より価格が高いこと
  DOWN AS price < PREV(price)   -- 「DOWN」とは、前の行より価格が低いこと

```

ここで **`PREV()`**（前の行を参照）や **`FIRST()`**（マッチ区間の最初の行を参照）といったナビゲーション関数を駆使して条件を作ります。

<br>

### まとめ
これだけは押さえておきたい主要なキーワードを整理します。

| キーワード | 役割 | イメージ |
| :--- | :--- | :--- |
| **PARTITION BY** | データをグループ分けする | どの「部署」や「ユーザー」ごとに探すか？ |
| **ORDER BY** | 行を並べる（必須） | 時系列順（日付など）に並べないと意味がない |
| **MEASURES** | 出力したい値を定義する | パターンの開始日や、変化率の計算結果など |
| **PATTERN** | 探したいパターンの形（必須） | 正規表現のように `(UP+ DOWN+)` と書く |
| **DEFINE** | パターンの各変数を定義する（必須） | 「UP」とは「前の行より価格が高いこと」と定義 |

<br>

# 問題16-2：行パターンマッチング初歩の初歩２

### 難易度：★★★☆☆ (Lv.3)

## 問題
MATCH_RECOGNIZE句を使用して、HRスキーマの`COUNTRIES`テーブルから、`REGION_ID`が「20」のデータの件数を取得してください。

## 期待する結果
| REGION_ID | CNT | 
| --------- | --- | 
| 20        | 5   | 

## 解答例
```sql
SELECT
    *
FROM
    hr.countries 
    MATCH_RECOGNIZE (
        ORDER BY
            region_id
        MEASURES
           region_id      AS region_id,
           COUNT(*)       AS cnt
        ONE ROW PER MATCH
        PATTERN ( 
            group20+ 
        )
        DEFINE
            group20 AS region_id = 20
    )
```

## 解説
前回（16-1）は「パターンに一致する行をすべて出す」という使い方でしたが、今回は「見つけたパターンをギュッと1行にまとめる」という、集計としての `MATCH_RECOGNIZE` です。
「`GROUP BY` でいいじゃないか」という声が聞こえてきそうですが、この構文で集計を行う仕組みを理解すると、複雑な集計を取り扱う際に非常に役立ちます。


### 1. 核心：`ONE ROW PER MATCH` による集約
今回の最大のポイントは、出力形式の切り替えです。

* **前回（ALL ROWS...）**: パターンに一致した行を、バラさずにそのまま表示。
* **今回（ONE ROW...）**: パターン（`group20` が1回以上連続する区間）を見つけたら、それを「1つの塊（マッチ）」として扱い、結果を1行に集約します。


### 2. MEASURES句：まとめ方の指定
`ONE ROW PER MATCH` を使う場合、その1行に「何を表示するか」を `MEASURES` で定義する必要があります。

* **`COUNT(*)`**: 従来の集計関数と同じですが、ここでは「そのマッチ（区間）の中に何行含まれていたか」を数えます。
* **`region_id`**: マッチした区間の代表値として `REGION_ID` を出力しています。

### 3. なぜ `GROUP BY` ではなくこれを使うのか？
例えば、株価データで「3日連続上昇」というパターンが**期間中に3回発生**したとしましょう。

* **`GROUP BY`**: 条件に合う日を全部まとめて数えてしまいます。
* **`MATCH_RECOGNIZE`**: 「1回目の3連騰（3日間）」、「2回目の3連騰（3日間）」……という風に、**連続性が途切れたら別のマッチとして分けて集計**できます。

今回の問題では `REGION_ID=20` が一箇所に固まっている（ORDER BYされている）ため、結果として1行になりますが、「連続性が切れたら別の行として出す」という挙動が、標準の集計関数との決定的な違いです。

### 4. 期待する結果の確認
狙い通り、`REGION_ID` が 20 の国々が1つの「パターン」として認識され、その中に含まれる 5 件という数字が `CNT` として算出されました。

# 【完全版】問題16-3：上昇・下降パターンの認識１

### 難易度：★★★★☆ (Lv.4)

## 問題
SHスキーマの`SALES`テーブルを使用し、月ごとの売上が「前月より高い」状態が3回以上続いた期間を特定してください。
なお、レコードはSTART_MONTHの昇順でソートしてください。

![](https://storage.googleapis.com/zenn-user-upload/8a0b20c7cfb9-20260319.png)

## 期待する結果
| START_MONTH | END_MONTH | DURATION | 
| ----------- | --------- | -------- | 
| 2019-06     | 2019-10   | 5        | 
| 2020-07     | 2020-09   | 3        | 
| 2020-12     | 2021-02   | 3        | 
| 2022-10     | 2022-12   | 3        | 

## 解答例
```sql
SELECT *
FROM (
    SELECT 
        TO_CHAR(time_id, 'YYYY-MM') AS month,
        SUM(amount_sold) AS total_rev
    FROM sh.sales
    GROUP BY TO_CHAR(time_id, 'YYYY-MM')
)
MATCH_RECOGNIZE (
    ORDER BY month
    MEASURES 
        FIRST(up.month) AS start_month,
        LAST(up.month) AS end_month,
        COUNT(up.month) AS duration
    ONE ROW PER MATCH
    AFTER MATCH SKIP TO LAST up
    -- パターン定義：最初の行(STRT)の後に、上昇(UP)が3回以上続く
    PATTERN (strt up{3,})
    DEFINE 
        up AS up.total_rev > prev(up.total_rev)
)
ORDER BY start_month;
```

## 解説
ここからが **`MATCH_RECOGNIZE`** の真骨頂。これまでのSQLでは「前月比」を出すだけでも一苦労でしたが、この構文を使えば「3ヶ月連続上昇」といった時系列のトレンド（波形）を、まるで言葉で説明するように記述できます。
データ分析の実務で「V字回復」や「右肩下がり」を特定する際に必須となるテクニックを解剖していきましょう。


### 1. 核心：パターンの「文法」を理解する
今回のクエリの心臓部は `PATTERN` と `DEFINE` の連携にあります。

#### ① PATTERN (strt up{3,})

ここには「何を探したいか」を正規表現で書きます。

* **`strt`**: 起点となる行です。条件が定義されていない（`DEFINE` にない）変数は、「どんな行でもOK」というワイルドカードとして機能します。
* **`up{3,}`**: `up` という条件に合う行が **3回以上連続** することを示します。

#### ② DEFINE up AS up.total_rev > prev(up.total_rev)
「何をもって上昇（up）とするか」を定義します。

* **`prev(...)`**: 直前の行（この場合は1ヶ月前）の値を参照します。
* つまり、「今月の売上が、先月の売上より大きいこと」が `up` の正体です。

### 2. MEASURES：マッチした区間の情報を抜き出す
パターンが見つかった際、その「塊」の中から必要な情報を抽出します。

* **`FIRST(up.month)`**: マッチした連続上昇区間の中で、**最初の `up` 行**の月を取得します。
* **`LAST(up.month)`**: 逆に、**最後の `up` 行**（上昇が止まる直前）の月を取得します。
* **`COUNT(up.month)`**: 何回上昇したかではなく、このパターンに含まれる `up` 行の総数、つまり「期間（DURATION）」を算出します。


### 3. 実務の重要ポイント：`AFTER MATCH SKIP`
この一文があるかどうかで、結果が大きく変わります。

```sql
AFTER MATCH SKIP TO LAST up
```

これは「マッチが見つかった後、次の探索をどこから始めるか」を指定するものです。
もしこれを書かないと、1ヶ月ずつずらしながら重複してマッチを探してしまい、「3ヶ月連続上昇」の中に「別の3ヶ月連続」が重なって出力されるなど、結果がノイズだらけになってしまいます。「一つの上昇トレンドを一つの塊として捉える」ために不可欠な設定です。


### 4. 期待する結果の分析（ビジネス視点）
結果を見ると、例えば **2019-06 から 2019-10** までの期間、なんと **5ヶ月連続** で売上が伸び続けていたことがわかります。

* **なぜ重要か？**: 単なる「前月比プラス」の月を探すのではなく、「勢いがついている期間」を特定することで、当時のキャンペーンの効果測定や、季節性の強いトレンドを客観的に証明できるようになります。

# 【完全版】問題16-4：上昇・下降パターンの認識２

### 難易度：★★★★☆ (Lv.4)

## 問題
HRスキーマの`EMPLOYEES`テーブルより、部門ごとに採用順（`HIRE_DATE`順）にデータを見たとき、「新しく入った従業員の給与が、直前に採用された従業員よりも高い状態が3回以上連続した期間」を特定してください。
なお、レコードは`CONSECUTIVE_INCREASES`の降順、次いで`START_HIRE_DATE`の昇順でソートしてください。

## 期待する結果
| DEPARTMENT_ID | START_HIRE_DATE | END_HIRE_DATE | CONSECUTIVE_INCREASES | START_SALARY | END_SALARY | 
| ------------- | --------------- | ------------- | --------------------- | ------------ | ---------- | 
| 50            | 2017-04-10      | 2017-11-16    | 4                     | 2100         | 5800       | 
| 50            | 2017-12-12      | 2018-02-03    | 4                     | 2400         | 2800       | 
| 80            | 2015-12-15      | 2016-03-23    | 3                     | 7500         | 10000      | 
| 80            | 2018-01-04      | 2018-01-29    | 3                     | 6200         | 10500      | 

## 解答例
```sql
SELECT
    department_id,
    start_hire_date,
    end_hire_date,
    consecutive_increases,
    start_salary,
    end_salary
FROM hr.EMPLOYEES
    MATCH_RECOGNIZE (
    PARTITION BY department_id
    ORDER BY hire_date
    MEASURES
        FIRST(hire_date) AS start_hire_date,
        LAST(hire_date) AS end_hire_date,
        COUNT(UP.employee_id) + 1 AS consecutive_increases,
        FIRST(salary) AS start_salary,
        LAST(salary) AS end_salary
    ONE ROW PER MATCH
    -- パターン定義：任意の開始点(STRT)から、給与が前回より高い状態(UP)が2回以上連続する
    PATTERN (STRT UP{2,}) 
    DEFINE
        UP AS salary > PREV(salary)
    )
ORDER BY consecutive_increases DESC, start_hire_date
```

## 解説
今回の問題は、前問の「売上トレンド」の応用ですが、「部署ごと（PARTITION BY）」の切り分けが加わり、より実務的な「組織内の給与インフレ分析」といった高度なデータ抽出になっています。
この `MATCH_RECOGNIZE` 句の集大成となるポイントを解説します。


### 1. 核心：`PARTITION BY` と `ORDER BY` の役割
階層問い合わせや分析関数でもおなじみですが、行パターンマッチングにおいてこのセットは「分析の舞台」を整えるために不可欠です。

* **`PARTITION BY department_id`**: 部署ごとに「別の世界」として扱います。部署Aの採用順が部署Bの給与推移に影響を与えないようにします。
* **`ORDER BY hire_date`**: 「採用された順」という時間の軸を作ります。この並び順が崩れると、パターンの意味がなくなってしまいます。


### 2. パターン定義の微調整：`{2,}` の意味
ここが少しトリッキーな部分です。

#### ① `PATTERN (STRT UP{2,})`
* **`STRT`**: 最初の1人目。特に条件がないので誰でも当てはまります。
* **`UP{2,}`**: 「前の人より給与が高い」という事象が **2回以上** 続くこと。
* **合計人数**: 「最初の1人」＋「上昇した2人以上」＝ **合計3人以上** の連続した期間を特定しています。

#### ② `COUNT(UP.employee_id) + 1`
`COUNT(UP)` は「上昇した回数（人数）」だけを数えるため、起点となった `STRT` の1人を足すことで、「その上昇トレンドに関わった全従業員数」を算出しています。


### 3. 実行結果の読み解き：組織の傾向が見える
期待する結果の **Department 50** を見てみましょう。

| START_HIRE_DATE | END_HIRE_DATE | INCREASES | START | END |
| --- | --- | --- | --- | --- |
| 2017-04-10 | 2017-11-16 | **4** | 2100 | 5800 |

これは、「2017年4月から11月にかけて採用された4名が、**一人も欠かさず前の新入社員より高い初任給で入社してきた**」という事実を物語っています。

* **ビジネス的なインサイト**: このデータから、「この時期、この部署では採用市場が過熱しており、初任給を引き上げ続けないと人が採れなかった」といった、当時の人事戦略や市場背景を推測することができます。

### 4. プロの視点：`PREV` 関数の凄さ

```sql
DEFINE UP AS salary > PREV(salary)
```

この `PREV` 関数が `MATCH_RECOGNIZE` 句の中で使えるのが最大の強みです。

通常、SQLで「一つ前の行」と比較するには `LAG` 関数を使い、さらにその結果を外側で判定する必要がありますが、`MATCH_RECOGNIZE` なら **「条件を定義する（DEFINE）」** 段階で、前の行を自由自在に参照できます。これにより、複雑な「波形」の定義が驚くほどスッキリ記述できます。

# 【完全版】問題16-5：階層構造のカウント

### 難易度：★★★★☆ (Lv.4)

## 問題

HRスキーマの`EMPLOYEES`テーブルを参照し、従業員と上司のリレーションをツリー構造で取得してください。また、各従業員の配下にいる全従業員（部下およびそのまた部下すべて）の数を取得してください。

出力にあたっては以下の条件を満たしてください。

* 最上位の従業員を「1」、その下位の従業員を「2」という形で、レベルに応じた番号を氏名に付与する。
* 階層が深くなるごとに、氏名の前に全角スペース2つ分（半角スペース4つ相当）のインデントを付与する。
（例）「1. Steven King」、「  2. Neena Kochhar」、「    3. Nancy Greenberg」
* なお、レコードは深さ優先探索順（兄弟間は氏名の昇順）で表示してください。


## 期待する結果
| ID  | NAME                                                                    | SUBS |

```sql:例2（行パターンマッチングで解決）
with hierarchy as (
   select
      lvl, EMPLOYEE_ID as id,  name, rownum as rn
   from (
      select
         level as lvl, e.EMPLOYEE_ID, e.FIRST_NAME || ' ' || e.LAST_NAME as name
      from hr.employees e
      start with e.MANAGER_ID is null
      connect by e.MANAGER_ID = prior e.EMPLOYEE_ID
      order siblings by name
   )
)
select
   id
 ,  lpad(' ', 2 *(lvl -1)) || lvl || '. ' || name as name
 , subs
from hierarchy
match_recognize (
   order by rn
   measures
      strt.rn           as rn
    , strt.lvl          as lvl
    , strt.id           as id
    , strt.name         as name
    , count(higher.lvl) as subs
   one row per match
   after match skip to next row
   pattern (
      strt higher*
   )
   define
      higher as higher.lvl > strt.lvl
)
order by rn;
```

## 解説
これまでの問題（14-3など）でも「配下人数の集計」を扱いましたが、今回の解答例には「スカラー副問合せによる力技」と、「行パターンマッチングによる技巧派」という、全く異なる2つの哲学が示されています。
特に例2の「DFS（深さ優先探索）順に並んだリストに対してパターンマッチングを行う」という発想は、Oracle SQLを極めた者にしか辿り着けない非常に高度なテクニックです。


### 1. 核心：なぜこの問題が高難易度なのか
階層構造のデータにおいて、「自分より下の階層（孫やひ孫まで含む）の数」を数えるのは、標準的な集計（`GROUP BY`）だけでは不可能です。

なぜなら、**「誰が誰の部下か」という情報はわかっても、「誰が誰の『配下全体』に含まれるか」は、ツリーを辿りきってみるまで確定しないから**です。

### 2. 解法1：階層の「入れ子」構造（伝統的アプローチ）
例1は、直感的で非常に分かりやすい「ループ的」な考え方です。

1. **メインクエリ**: まず普通に従業員のツリーを作ります（`CONNECT BY`）。
2. **スカラー副問合せ (`subs`)**: ここがポイントです。**1行表示するごとに、その人を「起点」とした新しいツリー探索を裏側で実行**し、その結果（行数）をカウントしています。

> **メリットとデメリット**
> * **メリット**: コードが読みやすく、直感的に「配下を数えている」ことがわかります。
> * **デメリット**: 107人いれば107回、1万いれば1万回、新しくツリーを探索するため、大規模な組織図ではパフォーマンスが劇的に低下する恐れがあります。
> 


### 3. 解法2：DFS順リストへのパターンマッチング（現代的アプローチ）
例2は、SQLの実行効率を極限まで高めた、非常に「賢い」解法です。

#### ① 仕組みのヒント：DFS（深さ優先探索）の性質
ツリーを「深さ優先」で並べると、ある人の「配下全員」は、必ずその人のすぐ下の行から、「自分と同じか、より浅いレベル」が現れる直前までに固まって出現します。

#### ② `MATCH_RECOGNIZE` のロジック
1. **`PATTERN (strt higher*)`**: 「起点となる人（`strt`）」と、その後に続く「自分よりレベルが深い（＝配下である）行（`higher`）」の連続を探します。
2. **`DEFINE higher AS higher.lvl > strt.lvl`**: 「自分のレベルより数字が大きい間は、すべて自分の部下（配下）である」と定義しています。
3. **`AFTER MATCH SKIP TO NEXT ROW`**: 全員に対してこの「配下探し」を行います。

> **なぜこれが「最強」なのか？**
> 例1のように何度もツリーを検索し直すのではなく、**「一列に並んだ名簿を上から下へ一度スキャンするだけ」** で全員の配下数を確定させています。計算量が劇的に少ない、実務において極めて優秀なクエリです。

* **Neena Yang** (ID 101) は **11人**、その下の **Nancy Gruenberg** は **5人** と、ツリーを下るにつれて「傘下」の人数が正しく減っていくのが確認できます。

### AFTER MATCH SKIP TO の種類と説明
SQLの行パターンマッチング（`MATCH_RECOGNIZE`句）において、**`AFTER MATCH SKIP TO`**は非常に重要な役割を果たします。これは「一つのマッチが見つかった後、次の検索をどこから再開するか」を制御するもので、これによって**マッチの重複を許すかどうか**が決まります。

以下に、主要な5つのオプションとその動作をまとめました。

| オプション | 説明 | 重複の有無 |
| --- | --- | --- |
| **`PAST LAST ROW`** | 現在のマッチの**最後の行の直後**から検索を再開します（デフォルト）。 | なし |
| **`TO NEXT ROW`** | 現在のマッチの**最初の行の次の行**から検索を再開します。 | あり（最大限） |
| **`TO FIRST variable`** | 指定した変数（`variable`）にマッチした**最初の行**から再開します。 | あり |
| **`TO LAST variable`** | 指定した変数（`variable`）にマッチした**最後の行**から再開します。 | あり |
| **`TO variable`** | `TO LAST variable` と同じ動作をします。 | あり |

<br>

### 動作のイメージ図
例えば、`A B C` というパターンを探している際、ある行セットでマッチが見つかった後の再開地点は以下のようになります。

<br>

### 各オプションの詳細解説

#### 1. PAST LAST ROW (デフォルト)
最も一般的な設定です。一度マッチした行は、次のマッチの開始点にはなり得ません。

* **用途:** 重複のない、独立したイベントを抽出したい場合。
* **挙動:** `[1, 2, 3]` がマッチしたら、次は `4` 行目から探し始めます。

<br>
#### 2. TO NEXT ROW
最も「欲張り」な検索です。

* **用途:** 重複を許容して、考えられるすべてのパターンを網羅したい場合（例：移動平均のようなスライディングウィンドウ処理）。
* **挙動:** `[1, 2, 3]` がマッチしたら、次は `2` 行目から探し始めます。

<br>
#### 3. TO FIRST / LAST variable

特定の条件に合致した地点まで「戻る」または「進む」ことができます。

* **用途:** 複雑なステートマシンを実装する場合。例えば、「急騰（UP）」の後に「調整（DOWN）」が来た際、次の検索を「調整の開始地点」からやり直したい場合などに有効です。
* **注意:** `TO FIRST variable` を使う際、再開地点が現在のマッチの開始点と同じだと、無限ループに陥る可能性があるため、実装（Oracle等）によっては「必ず1行は進む」などの制約があります。

<br>
### 具体的な使用例

```sql
SELECT *
FROM Ticker
MATCH_RECOGNIZE (
    PARTITION BY Symbol
    ORDER BY Tstamp
    MEASURES ...
    -- ここで再開地点を指定
    AFTER MATCH SKIP TO PAST LAST ROW 
    PATTERN (START_UP UP+ DOWN+)
    DEFINE
        UP AS Price > PREV(Price),
        DOWN AS Price < PREV(Price)
)
```

上級者レベルの分析では、**`TO LAST variable`** を使いこなせると、特定のイベントの「終点」を次のイベントの「起点」としてスムーズに繋げることができるようになります。

## 解答例
```sql
WITH monthly_sales AS (
    SELECT 
        p.prod_name,
        TO_CHAR(s.time_id, 'YYYY-MM') AS month,
        SUM(s.amount_sold) AS revenue
    FROM sh.sales s
    JOIN sh.products p ON s.prod_id = p.prod_id
    WHERE p.prod_id = 13 -- 特定の製品で分析
    GROUP BY p.prod_name, TO_CHAR(s.time_id, 'YYYY-MM')
)
SELECT *
FROM monthly_sales
MATCH_RECOGNIZE (
    ORDER BY month
    MEASURES 
        FIRST(down.month) AS start_month,
        LAST(down.month)  AS bottom_month,
        LAST(up.month)    AS end_month,
        LAST(down.revenue) AS bottom_revenue
    ONE ROW PER MATCH
    AFTER MATCH SKIP TO LAST up
    -- パターン：最初の1行の後、減少が1回以上、その後に増加が1回以上
    PATTERN (strt down+ up+)
    DEFINE 
        down AS revenue < PREV(revenue),
        up   AS revenue > PREV(revenue)
)
ORDER BY start_month
```

## 解説
通常の `GROUP BY` や分析関数を駆使しても、この「V字回復」のような「一連の流れ（シーケンス）」を特定しようとすると、クエリが何重にもなり非常に複雑になります。これを正規表現のような感覚でスマートに記述できるのが、行パターンマッチングの真骨頂です。

### 1. スクリプトの解説：正規表現でデータを捉える

このクエリの核心は、テーブルを「行の集まり」ではなく「**時間の流れ（シーケンス）**」として定義している点にあります。

#### パターンの定義：PATTERN 句

```sql
PATTERN (strt down+ up+)
```

ここでは、私たちが探したい「V字」の形を記号で定義しています。

* **`strt`**: パターンの開始地点。
* **`down+`**: `down` という条件を満たす行が **1回以上** 連続すること。
* **`up+`**: その後に `up` という条件を満たす行が **1回以上** 連続すること。

#### 変数の定義：DEFINE 句

パターンで使った `down` や `up` が具体的にどういう状態かを定義します。

```sql
DEFINE 
    down AS revenue < PREV(revenue),
    up   AS revenue > PREV(revenue)
```

* **`PREV(revenue)`**: 一つ前の行の売上と比較しています。前の行より下がれば `down`、上がれば `up` と判定されます。


### 2. 文法・テクニックのポイント

#### ① MEASURES 句での「ピンポイント抽出」

パターン全体の中から、特定の瞬間を抜き出すために `FIRST` や `LAST` 関数を使います。

* **`FIRST(down.month)`**: 下がり始めた最初の月（開始月）。
* **`LAST(down.month)`**: 下がりきった最後の月（つまり、**底**）。
* **`LAST(up.month)`**: 上がりきった最後の月（終了月）。

#### ② データのスキップ：AFTER MATCH SKIP 句

```sql
AFTER MATCH SKIP TO LAST up
```

一つのV字回復を見つけた後、「次、どこから探し始めるか」を指定します。
これがないと、大きなV字の中に含まれる小さな波を重複して拾ってしまうことがありますが、`LAST up`（上がりきったところ）まで飛ばすことで、一つの大きな回復トレンドとして綺麗に抽出できます。

#### ③ なぜ分析関数（Window関数）ではないのか？

`LAG` 関数などでも「前月比」は出せますが、**「いつまで下がり続け、いつから上がり始めたか」** という「状態の遷移」を管理するには、フラグ立てや複雑な結合が必要になります。`MATCH_RECOGNIZE` は、状態（State）を内部で保持しながらスキャンするため、圧倒的に高速で読みやすいコードになります。

### 3. 実務での活用シーン：高度なトレンド分析

この「行パターン一致」は、売上分析以外にも驚くほど広い分野で活用されています。

* **金融・株価**: 「ダブルボトム」や「ゴールデンクロス」といったテクニカル指標の検出。
* **製造・IoT**: センサーデータの「急激な電圧降下」の後に「一定時間不安定な挙動」が続く、といった故障予兆の検知。
* **不正検知**: 「深夜に少額の引き出しが3回連続」した直後に「多額の送金」が行われる、といった犯罪パターンの特定。

### まとめ

`MATCH_RECOGNIZE` は、SQLを **「データの抽出言語」から「イベントの解析言語」へと進化させる** 機能です。構文は独特ですが、一度 `PATTERN` と `DEFINE` の関係に慣れてしまえば、時系列データの分析において最強の武器になります。
今回の「V字」を少し応用して、売上が一定期間「横ばい（FLAT）」になった後に急上昇するパターンなども、この構文を少し変えるだけで簡単に作れます。

# 【完全版】問題16-7：W字型（ダブルボトム）パターンの検出

### 難易度：★★★★☆ (Lv.4)

## 問題
マーケティング部門から、「一時的なリバウンド（だまし）に終わらず、二度の底を打って力強く回復した製品の売上推移を特定したい」との依頼がありました。
いわゆる「ダブルボトム（W字型）」は、市場の底堅い需要を確認できた重要なサインとみなされます。

SHスキーマの売上データから、この「W字」の波形を描いている期間を抽出してください。
`SALES` テーブルおよび `PRODUCTS` テーブルを使用し、**製品ID：13** について、月ごとの売上合計が以下のパターンを描いている期間を特定してください。

* **パターン定義**:
1. 減少（`DOWN`）が1回以上
2. その後に上昇（`UP`）が1回以上（これが「だまし」の回復）
3. 再び減少（`DOWN`）が1回以上
4. 最後に上昇（`UP`）が1回以上（これが「真の回復」）

* **期待する出力**:
* パターンの「開始月」、「1度目の底の月」、「2度目の底の月」、「終了月」。
* レコードは開始月の昇順でソートしてください。


## 期待する結果
| START_MONTH | BOTTOM_1 | BOTTOM_2 | END_MONTH | 
| ----------- | -------- | -------- | --------- | 
| 2019-02     | 2019-04  | 2019-06  | 2019-07   | 
| 2019-08     | 2019-10  | 2020-04  | 2020-05   | 
| 2020-06     | 2020-06  | 2020-09  | 2020-10   | 
| 2020-12     | 2020-12  | 2021-03  | 2021-04   | 
| 2021-05     | 2021-06  | 2021-09  | 2021-10   | 
| 2021-11     | 2021-11  | 2022-01  | 2022-02   | 
| 2022-03     | 2022-03  | 2022-05  | 2022-07   | 
| 2022-08     | 2022-08  | 2022-11  | 2022-12   | 

## 解答例
```sql
WITH monthly_sales AS (
    SELECT 
        TO_CHAR(s.time_id, 'YYYY-MM') AS month,
        SUM(s.amount_sold) AS revenue
    FROM sh.sales s
    WHERE s.prod_id = 13
    GROUP BY TO_CHAR(s.time_id, 'YYYY-MM')
)
SELECT *
FROM monthly_sales
MATCH_RECOGNIZE (
    ORDER BY month
    MEASURES 
        FIRST(d1.month) AS start_month,
        LAST(d1.month)  AS bottom_1,
        LAST(d2.month)  AS bottom_2,
        LAST(u2.month)  AS end_month
    ONE ROW PER MATCH
    AFTER MATCH SKIP TO LAST u2
    -- W字パターンの定義： 下落1 -> 上昇1 -> 下落2 -> 上昇2
    PATTERN (strt d1+ u1+ d2+ u2+)
    DEFINE 
        d1 AS revenue < PREV(revenue),
        u1 AS revenue > PREV(revenue),
        d2 AS revenue < PREV(revenue),
        u2 AS revenue > PREV(revenue)
)
ORDER BY start_month
```

## 解説
前回の「V字型」に続き、今回はさらに複雑な「W字型（ダブルボトム）」の検出です。
これが書けるようになると「単なるデータの集計係」から「データからストーリーを読み解くアナリスト」へと完全にステージが変わります。`MATCH_RECOGNIZE` の真骨頂である「連続する状態の変化」をどう定義しているか、深く掘り下げて解説します。

### 1. スクリプトの解説：W字を記号で分解する

このクエリの魔法は、`PATTERN` 句の中にあります。

#### パターンの定義：W字の設計図

```sql
PATTERN (strt d1+ u1+ d2+ u2+)
```

ここでは「W」の形を、一筆書きの順序で定義しています。

* **`strt`**: 開始地点。
* **`d1+`**: 1度目の下落（Down 1）。
* **`u1+`**: 1度目のリバウンド（Up 1）。
* **`d2+`**: 2度目の押し目（Down 2）。
* **`u2+`**: 本格的な回復（Up 2）。

この `+` （1回以上の繰り返し）という正規表現でおなじみの量化子を使うことで、「3ヶ月かけて下がり、1ヶ月だけ上がり、また2ヶ月下がる……」といった**期間の変動を柔軟に吸収**してパターンを特定できるのが、この機能の凄みです。


### 2. 文法・テクニックのポイント

#### ① 状態の定義（DEFINE句）

```sql
DEFINE 
    d1 AS revenue < PREV(revenue),
    u1 AS revenue > PREV(revenue),
    ...
```

ここでは `d1` も `d2` も「前の行より売上が低い」という同じ条件ですが、あえて名前を分けています。これにより、`MEASURES` 句で「1つ目の底（`LAST(d1.month)`）」と「2つ目の底（`LAST(d2.month)`）」を**明確に区別して抽出**することが可能になります。

#### ② MEASURES 句での位置特定

この句は、見つけたパターンの中から「どの瞬間の値をレポートに載せるか」を決めるカメラのレンズのような役割です。

* **`FIRST(d1.month)`**: 下落が始まった瞬間（パターンの入り口）。
* **`LAST(d1.month)`**: 1つ目の下落が終わった瞬間（1つ目の底）。
* **`LAST(d2.month)`**: 2つ目の下落が終わった瞬間（2つ目の底）。

#### ③ 重複を避ける「SKIP TO」の戦略

```sql
AFTER MATCH SKIP TO LAST u2
```

W字のような複雑なパターンでは、「大きなW字の中に小さなV字」が隠れていることがあります。
`SKIP TO LAST u2` と指定することで、「完全にW字が完成した（`u2` が終わった）ところまでスキップして、次を探す」という挙動になります。これにより、データの二重計上を防ぎ、最も大きなトレンドだけを拾い出すことができます。

### 3. 実務での活用：テクニカル分析としてのSQL
「ダブルボトム」は投資の世界でも「底入れのサイン」として非常に有名ですが、ビジネス分析でも以下のように応用されます。

* **販促効果の検証**: キャンペーンで一時的に売上が戻った（`u1`）が、終了後にまた落ち込み（`d2`）、その後口コミで再燃（`u2`）した、といった**長期的な定着プロセス**の可視化。
* **システム負荷監視**: サーバーのレスポンス遅延が一度回復したように見えて再発し、最終的にパッチ適用で安定した、という一連の障害パターンの特定。

### まとめ

`MATCH_RECOGNIZE` は一見難解ですが、「探したい波形をアルファベットで定義し、そのアルファベットの動きを `DEFINE` で決める」というパズルだと考えれば、非常に強力なツールになります。

# 【完全版】問題16-8：給与の停滞（プラトー）期間の特定

### 難易度：★★★★☆ (Lv.4)

## 問題
人事部門から、「部門内において、採用順に見たときに初任給が前任者と全く同じ額で据え置かれている期間（プラトー）を特定したい」との依頼がありました。
同一の給与で複数名が連続して採用されている期間を抽出することで、当時の給与規定の硬直性や、採用市場の安定度を分析する材料とします。

HRスキーマの`employees` テーブルを使用し、部門（`department_id`）ごとに採用日（`hire_date`）の昇順でデータを見たとき、**「給与（`salary`）が直前に採用された従業員と同一である状態」が1回以上続いた期間**を特定してください。

出力には以下の情報を含めてください：

1. 部門ID
2. その停滞期間の開始採用日（1人目の採用日）
3. その停滞期間の終了採用日（最後の人の採用日）
4. その期間に採用された人数（据え置きが始まった1人目を含む）
5. その期間の給与額

なお、結果は `department_id` の昇順、次いで `start_date` の昇順でソートしてください。


## 期待する結果
| DEPARTMENT_ID | START_DATE           | END_DATE             | PLATEAU_COUNT | SALARY | 
| ------------- | -------------------- | -------------------- | ------------- | ------ | 
| 50            | 2016-07-11T00:00:00Z | 2016-08-26T00:00:00Z | 2             | 2900   | 
| 50            | 2018-02-06T00:00:00Z | 2018-03-08T00:00:00Z | 2             | 2200   | 

## 解答例
```sql
SELECT
    department_id,
    start_date,
    end_date,
    plateau_count,
    salary
FROM hr.employees
    MATCH_RECOGNIZE (
        PARTITION BY department_id
        ORDER BY hire_date
        MEASURES
            FIRST(hire_date) AS start_date,
            LAST(hire_date)  AS end_date,
            COUNT(*)         AS plateau_count,
            FIRST(salary)    AS salary
        ONE ROW PER MATCH
        AFTER MATCH SKIP TO LAST same
        -- パターン：最初の1行(STRT)の後に、同じ給与の行(SAME)が1回以上続く
        PATTERN (strt same+)
        DEFINE
            same AS salary = PREV(salary)
    )
ORDER BY department_id, start_date
```

## 解説
今回は、`MATCH_RECOGNIZE` を使った「連続する同一値（停滞）の検出」ですね。

前回の「V字」「W字」は「増減の変化」を捉えるものでしたが、今回は「変化しないこと」を捉えるパターンです。実務では「株価の横ばい」や「センサーデータの固着」などの異常検知にも使われる非常に汎用性の高いテクニックです。

### 1. スクリプトの解説：停滞を「一筆書き」で定義する
このクエリは、各部門のタイムラインをスキャンし、給与が動かなくなった区間を「一つのイベント」として抽出しています。

#### パターンの定義：PATTERN 句

```sql
PATTERN (strt same+)
```

* **`strt`**: 停滞が始まる「起点」となる1行目です。特に条件（DEFINE）がないため、どんな行でも起点になり得ます。
* **`same+`**: 起点（または直前の行）と同じ給与を持つ行が **1回以上** 続くことを意味します。
* 2人以上のグループにならないと「停滞」とは呼べないため、量化子 `+`（1回以上）を使っています。

#### 条件の定義：DEFINE 句

```sql
DEFINE same AS salary = PREV(salary)
```

* **`PREV(salary)`**: 「自分自身の1行前」の値を参照します。
* これにより、「前の人と給与が同じである」という状態が続いている間、ひとまとめのグループ（`same`）としてカウントされ続けます。

### 2. 文法・テクニックのポイント

#### ① MEASURES 句での集計

`ONE ROW PER MATCH`（一致したパターンを1行にまとめる）を指定しているため、`MEASURES` 句でその期間の統計情報を定義します。

* **`FIRST(hire_date)`**: パターン全体の最初の行（`strt`）の日付。
* **`LAST(hire_date)`**: パターン全体の最後の行（最後の `same`）の日付。
* **`COUNT(*)`**: `strt` とすべての `same` を合わせた合計人数。

#### ② AFTER MATCH SKIP の重要性

```sql
AFTER MATCH SKIP TO LAST same
```

この一文は、「一つの停滞期間を見つけたら、その期間の**最後の人**まで読み飛ばして、次の探索を始めてね」という指示です。
これがないと、2人目、3人目をそれぞれ「起点」とした重複した結果が出てしまうため、期間を特定する問題では必須の設定です。

#### ③ PARTITION BY と ORDER BY

`MATCH_RECOGNIZE` 内のこれらは、Window関数（分析関数）と同じ役割を果たします。

* **`PARTITION BY department_id`**: 部門が変わったら、給与が同じでも「別のイベント」として扱います。
* **`ORDER BY hire_date`**: 採用順という「時間の軸」を確定させます。

### 3. 実務での活用シーン：データの「静止」を捉える

このパターンマッチングは、以下のようなビジネス要件で威力を発揮します。

* **在庫管理**: 「在庫数が1週間以上、1個も変動していない商品」の特定（死蔵在庫の検出）。
* **システム監視**: 「CPU使用率が10分間、全く同じ数値で張り付いている」状態の特定（プロセスのフリーズ検知）。
* **不正検知**: 「同一のIPアドレスから、1秒以内に連続してアクセスが来ている」パターンの抽出。


> **「遊び」を持たせる応用**
> 今回は `salary = PREV(salary)` と完全一致を見ましたが、実務では `ABS(salary - PREV(salary)) < 100` のように記述することで、「ほぼ横ばい（誤差の範囲）」という柔軟な停滞パターンを定義することも可能です。

### まとめ

「起点（`strt`）を決め、その後の行が条件（`PREV`との比較）を満たし続ける間を一つの塊にする」というのが、`MATCH_RECOGNIZE` による期間抽出の基本形です。

この構文をマスターすれば、複雑な自己結合や分析関数の組み合わせから解放され、宣言的に「どんな形を探したいか」を記述できるようになります。

# 【完全版】問題16-9：移動平均を超え続ける「確変」期間の抽出

### 難易度：★★★★☆ (Lv.4)

## 問題
経営層から「単なる一過性の売上増ではなく、過去のトレンド（直近3ヶ月の平均）を継続的に上回り続けている、真の『好調期間（確変モード）』を特定してほしい」との高度な分析依頼がありました。
移動平均を基準とすることで、季節変動や一時的なスパイクに惑わされない、真に勢いのある期間を炙り出します。

SHスキーマの`sales` テーブルのデータを使用し、月ごとの合計売上高を算出してください。その結果に対して `MATCH_RECOGNIZE` 句を適用し、以下の条件を満たす期間を抽出してください。

1. **好調行（`HIGH_PERF`）の定義**:
その月の売上が、**「直近3ヶ月の売上平均」を上回っている**こと。
平均の算出式は以下の通りとする。

$$\text{Average} = \frac{\text{Revenue}_{t-1} + \text{Revenue}_{t-2} + \text{Revenue}_{t-3}}{3}$$


2. **パターンの定義**:
「好調行」が **3ヶ月以上連続** している期間を特定する。
3. **出力項目**:
* 好調期間の開始月（`START_MONTH`）
* 好調期間の終了月（`END_MONTH`）
* その期間内の最大月間売上（`MAX_REV`）
* その期間の継続月数（`DURATION`）

なお、集計対象は全製品の合計とし、結果は `START_MONTH` の昇順でソートしてください。

## 期待する結果
| START_MONTH | END_MONTH | MAX_REV    | DURATION | 
| ----------- | --------- | ---------- | -------- | 
| 2019-06     | 2019-10   | 2236464.53 | 5        | 
| 2020-07     | 2020-09   | 2030917.97 | 3        | 
| 2020-12     | 2021-02   | 2118618.97 | 3        | 
| 2021-07     | 2021-10   | 2164612.21 | 4        | 
| 2022-01     | 2022-04   | 2379957.23 | 4        | 
| 2022-06     | 2022-12   | 2547042.11 | 7        | 

## 解答例
```sql
WITH monthly_sales AS (
    -- 月ごとの売上合計を算出
    SELECT 
        TO_CHAR(time_id, 'YYYY-MM') AS month,
        SUM(amount_sold) AS revenue
    FROM sh.sales
    GROUP BY TO_CHAR(time_id, 'YYYY-MM')
)
SELECT *
FROM monthly_sales
MATCH_RECOGNIZE (
    ORDER BY month
    MEASURES 
        FIRST(high.month)   AS start_month,
        LAST(high.month)    AS end_month,
        MAX(high.revenue)   AS max_rev,
        COUNT(high.month)   AS duration
    ONE ROW PER MATCH
    AFTER MATCH SKIP TO LAST high
    -- パターン：HIGH_PERFが3回以上連続
    PATTERN (high{3,})
    DEFINE 
        -- 直近3ヶ月の売上平均をPREV関数で計算し、それと比較する
        high AS revenue > (
            PREV(revenue, 1) + 
            PREV(revenue, 2) + 
            PREV(revenue, 3)
        ) / 3
)
ORDER BY start_month
```

## 解説
単に「先月より高い」ではなく、「過去3ヶ月のトレンドを上回り続けている」という動的な基準値をSQLだけで処理する、非常にプロフェッショナルな解法です。ポイントを絞って解説します。

### 1. スクリプトの解説：動的な「壁」との戦い

このクエリの凄みは、「基準値が毎月変化する」中で、その壁を越え続けている区間を特定している点にあります。

#### パターンの定義：正規表現の量化子

```sql
PATTERN (high{3,})
```

ここでは、条件を満たす行 `high` が **「3回以上（`{3,}`）連続する」** ことを定義しています。

* `{3}` なら「ちょうど3回」
* `{3,5}` なら「3〜5回」
* `{3,}` なら「3回以上ならいくらでも」という意味になり、長期的なトレンドを漏らさずキャッチできます。

#### 条件の定義：PREV関数の多段活用

```sql
DEFINE high AS revenue > (
    PREV(revenue, 1) + PREV(revenue, 2) + PREV(revenue, 3)
) / 3
```

ここが最もテクニカルな部分です。
通常、移動平均を出すには `AVG(...) OVER(...)` を使いますが、`MATCH_RECOGNIZE` 内では **`PREV` 関数** を使って直接過去の値を指定できます。

* **`PREV(revenue, 1)`**: 1ヶ月前の売上
* **`PREV(revenue, 2)`**: 2ヶ月前の売上
* **`PREV(revenue, 3)`**: 3ヶ月前の売上

これらを足して3で割ることで、Window関数を使わずにその場での「基準値」を作り出しています。

### 2. 文法・テクニックのポイント

#### ① 集計済みデータへの適用

`MATCH_RECOGNIZE` は非常に強力ですが、複雑な集計（`SUM` や `GROUP BY`）を同時に行うことはできません。
そのため、解答例のように **`WITH` 句で「1月1行」の綺麗なデータを作ってから** パターンマッチをかけるのが、実務における鉄則のワークフローです。

#### ② MEASURES 句での集計機能

```sql
MEASURES 
    MAX(high.revenue) AS max_rev,
    COUNT(high.month) AS duration
```

`MATCH_RECOGNIZE` 内の `MEASURES` では、**そのパターンに一致した区間だけ**を対象とした集計が可能です。
これにより、「好調期間の中で、一番売れたのはいくらか？」「結局、何ヶ月続いたのか？」というサマリーを、サブクエリなしで一行に集約できます。

#### ③ データの連続性と「窓」

このロジックで注意が必要なのは、データの最初の3ヶ月間です。
1ヶ月目のデータには「3ヶ月前」が存在しないため、`PREV` は `NULL` を返します。その結果、条件式全体が `NULL` となり、最初の3ヶ月間は絶対に `high` と判定されません。
実務では、この「ウォームアップ期間」を考慮して分析対象期間を設定することが重要です。

### 3. 実務でのアドバイス：ビジネスインテリジェンスへの応用

今回の「確変期間」の抽出は、以下のような高度なマーケティング分析に応用可能です。

* **広告効果の持続性**: キャンペーン終了後もトレンドを上回り続けている場合、一過性ではなく「ブランドの底上げ」に成功したと判断できます。
* **異常なバズの検知**: SNS等で急激に注目を集め、通常ではありえない期間成長し続けている商品を早期発見し、在庫補充の判断に繋げます。
* **退職予兆の検知**: 給与や残業時間が「過去の個人平均」を一定期間外れ続けているパターンを検出し、ケアが必要なメンバーを特定します。
