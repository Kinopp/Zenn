# 問題18-1（おおよその数）  *Lv2*
### SHスキーマ`SALES`テーブルに存在する`cust_id`のおおよその件数を取得してください（重複は排除してください）。

## 期待する結果
| APPROX_CUSTOMER_COUNT | 
| --------------------- | 
| 7014                  | 

※ この値でない可能性あり

## 解答例
```sql
SELECT 
    APPROX_COUNT_DISTINCT(cust_id) AS approx_customer_count
FROM 
    sh.sales;
```

## 解説
今回は、標準的なSQLの枠を超えた、Oracle Databaseの「ビッグデータ処理」に関するテクニックが登場します。今回のテーマは **「近似関数」** です。

### 1. 文法解説：APPROX_COUNT_DISTINCT関数
膨大なデータの中から「重複を除いた件数」を**高速かつおおよそ**で算出するための関数です。

```sql
SELECT 
    APPROX_COUNT_DISTINCT([カラム名])
FROM 
    [テーブル名];
```

### ① なぜ「おおよそ」なのか？
通常、重複を排除した件数を数えるには `COUNT(DISTINCT cust_id)` を使います。しかし、数百万〜数億行という巨大なテーブル（今回の `SH.SALES` など）でこれを実行すると、コンピュータは「すべての値を並び替えて重複をチェックする」という非常に重い作業を強いられます。

そこで登場したのがこの関数です。厳密な1件単位の正確さを犠牲にする代わりに、**メモリ消費を劇的に抑え、爆速で結果を返します。**
![](https://storage.googleapis.com/zenn-user-upload/47a0078a8601-20260320.png)

### ② 精度とパフォーマンス
* **精度**: 一般的に97%以上の精度が保証されています。
* **用途**: 「正確な1円単位の決算」には向きませんが、「昨日の利用者はだいたい何万人くらいだったか？」という**傾向把握やダッシュボード表示**には最適です。

### 2. 比較：正確なカウント vs おおよそのカウント
実務でどちらを使うべきか迷った時の判断基準を整理しました。

| 特徴 | `COUNT(DISTINCT ...)` | `APPROX_COUNT_DISTINCT(...)` |
| :--- | :--- | :--- |
| **正確性** | 100% 正確 | 近似値（わずかな誤差あり） |
| **実行速度** | データ量に比例して遅くなる | **非常に高速** |
| **リソース消費** | 大量のメモリと一時領域を消費 | 非常に少ない |
| **主な用途** | 請求、監査、決算報告 | 統計分析、リアルタイム監視 |


### 3. 知っておくと得する豆知識

#### SHスキーマの背景
今回使用している `SH`（Sales History）スキーマは、Oracleがデータウェアハウス（大量の蓄積データ分析）の練習用に提供しているものです。`SALES` テーブルは特にレコード数が多いため、こうした近似関数を試すのにうってつけの場所です。

#### 自動切り替え設定
実はOracleの設定（`OPTIMIZER_USE_PENDING_STATISTICS`等）によっては、普通の `COUNT(DISTINCT)` と書いても、内部で自動的に `APPROX_...` に書き換えて実行してくれるマジックのような機能も存在します。

# 【完全版】問題18-2（おおよそのランキング）　　*Lv3*
### SHスキーマ`SALES`テーブルにより、`AMOUNT_SOLD`のおおよその合計値と、おおよそのランキングTOP10を取得してください。（順位の大きい順に表示）。

## 期待する結果
| PROD_ID | TOTAL_SALES      | RANKING | 
| ------- | ---------------- | ------- | 
| 26      | 2572944.13000026 | 10      | 
| 28      | 3543725.89000017 | 9       | 
| 29      | 3845387.37999989 | 8       | 
| 21      | 5498727.80999996 | 7       | 
| 15      | 5635963.08000012 | 6       | 
| 13      | 6312268.40000003 | 5       | 
| 20      | 6691996.80999932 | 4       | 
| 14      | 7189171.77000041 | 3       | 
| 17      | 8314815.40000011 | 2       | 
| 18      | 15011642.5200011 | 1       | 

## 解答例
```sql
SELECT
    PROD_ID,
    APPROX_SUM(AMOUNT_SOLD) AS TOTAL_SALES,
    APPROX_RANK(
        ORDER BY
            APPROX_SUM(AMOUNT_SOLD) DESC
    )                       AS RANKING
FROM
    SH.SALES
GROUP BY
    PROD_ID
HAVING
    APPROX_RANK(
        ORDER BY
            APPROX_SUM(AMOUNT_SOLD) DESC
    ) <= 10;
```


## 解説
この問題は、Oracle Database 12c R2以降で導入された **「近似集計（Approximate Aggregation）」** の真髄に触れる内容です。
数千万、数億といった「ビッグデータ」を相手にする際、1円単位の正確さよりも **「上位10位を爆速で知りたい」** というビジネスニーズに応えるための高度なテクニックを解説します。

### 1. 文法解説：近似ランキングの仕組み
今回のクエリでは、2つの強力な近似関数が使われています。

#### ① APPROX_SUM
`SUM` 関数の近似版です。巨大なデータセットにおいて、正確な合計を出すためのメモリ消費を抑え、高速に合計の「目安」を算出します。
* 結果に `2572944.13000026` のような細かい端数が出ているのは、内部で浮動小数点を用いた近似計算が行われているためです。

#### ② APPROX_RANK
「～の中で何位か」という順位を近似的に算出します。

```sql
APPROX_RANK(
    ORDER BY [集計関数] DESC
)
```
* 通常の `RANK()` 関数は一度全てのデータをソート（並び替え）する必要があるため非常に重い処理ですが、`APPROX_RANK` はソートを最小限に抑えて「上位層」を特定します。

### 2. なぜ WHERE ではなく HAVING なのか？
通常、`RANK()` などの分析関数（ウィンドウ関数）の結果で絞り込みたい場合、SQLの実行順序の関係で **「インラインビュー（サブクエリ）」** を使わなければなりませんでした。

> **通常の書き方（重い）**
> `SELECT * FROM (SELECT ..., RANK() OVER(...) as rnk ...) WHERE rnk <= 10`

しかし、Oracleの近似関数では **`HAVING` 句の中に直接ランキング条件を書くことができます。**
これにより、Oracleのオプティマイザは「あ、上位10個だけサッと出せばいいんだな」と判断し、無駄な計算を極限まで省いた実行計画を立てることができます。

### 3. 実務での活用シーン：ビッグデータ分析
このクエリが本領を発揮するのは、以下のようなケースです。

* **ECサイトのリアルタイムランキング**: 数億件の販売ログから、「今、売れている商品TOP10」を数秒で表示したい。
* **不正検知**: 膨大なログの中から、異常なアクセス数の上位を即座にリストアップしたい。

| 関数 | 役割 | メリット |
| :--- | :--- | :--- |
| **`APPROX_SUM`** | おおよその合計 | メモリ消費を抑え、ディスクI/Oを激減させる。 |
| **`APPROX_RANK`** | おおよその順位 | 巨大なソート処理を回避し、Top-N抽出を高速化する。 |
