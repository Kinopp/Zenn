# 問題4-1（NULL）  *Lv1*
### **HRスキーマ`DEPARTMENTS表`より、`MANAGER`が存在する（`MANAGER_ID`が`NULL`でない）データを取得してください。（順不同）**

## 期待する結果
| 	DEPARTMENT_ID	| 	DEPARTMENT_NAME	| 	MANAGER_ID	| 	LOCATION_ID	| 
| 	----	| 	----	| 	----	| 	----	| 
| 	10	| 	Administration	| 	200	| 	1700	| 
| 	20	| 	Marketing	| 	201	| 	1800	| 
| 	30	| 	Purchasing	| 	114	| 	1700	| 
| 	40	| 	Human Resources	| 	203	| 	2400	| 
| 	50	| 	Shipping	| 	121	| 	1500	| 
| 	60	| 	IT	| 	103	| 	1400	| 
| 	70	| 	Public Relations	| 	204	| 	2700	| 
| 	80	| 	Sales	| 	145	| 	2500	| 
| 	90	| 	Executive	| 	100	| 	1700	| 
| 	100	| 	Finance	| 	108	| 	1700	| 
| 	110	| 	Accounting	| 	205	| 	1700	|

## 解答例
```sql
SELECT
    *
FROM
    hr.departments
WHERE
    manager_id IS NOT NULL
```

## 解説
今回は、SQLの難所の一つである **「NULL（ヌル）」** の扱いです。「値がない」という状態をどう扱うかは、SQLにおいて非常に重要なポイントです。

### 1. 文法解説：IS NOT NULL 演算子
データが「空（NULL）ではない」ことを条件にするには、専用の演算子を使用します。

```sql
WHERE [カラム名] IS NOT NULL
```

#### ① 「NULL」とは何か？
NULLは「0」でも「空文字（""）」でもありません。**「値が未定義」「不明」「まだ決まっていない」** という状態を指します。
今回の問題では、「マネージャーが誰だか決まっている部署」を探すために、この条件を使っています。

#### ② なぜ「!= NULL」と書いてはいけないのか？
ここが最大の注意点です！
SQLにおいて、NULLは比較演算子（`=` や `!=`）で判定することができません。
* `manager_id != NULL` と書いても、結果は「真」にも「偽」にもならず、**「不明 (UNKNOWN)」** となり、1行も取得できません。
* NULLを扱うときは、必ず **`IS NULL`** または **`IS NOT NULL`** を使うというルールを覚えておきましょう。
* 詳細は下記に記載しています。


### 2. 実務での活用シーン
`IS NOT NULL` は、データの品質チェックや絞り込みで頻繁に使われます。

* **必須項目の確認**: 「メールアドレスを登録済みの顧客だけを抽出したい」とき（`WHERE email IS NOT NULL`）。
* **処理済みデータの除外**: 「完了日が入力されていない（＝まだ終わっていない）タスクだけを見たい」とき（`WHERE completion_date IS NULL`）。


### 3. ちょっとしたコツ：NULLと論理否定
「NULLではない」の反対は、当然「NULLである」です。

| 条件 | 意味 |
| :--- | :--- |
| **`IS NULL`** | 値が空（未定義）である行を抽出 |
| **`IS NOT NULL`** | 値が何か入っている行を抽出 |

ちなみに、Oracle SQLの `DEPARTMENTS` テーブルでは、通常「Contracting」のような一部の部署にマネージャーが設定されていない（NULLである）ケースがあります。この問題のクエリを実行することで、それらの「管理職不在の部署」を除外して、組織図がはっきりしている部署だけをリストアップできたことになります。

この「NULLの壁」を突破できれば、データ抽出の精度はグッと上がります！



<br>
:::message
### **「= NULL」ではなく「IS NULL」と書く理由の詳細**
「= NULL」と書くと常に「NO DATA FOUND」（データが見つからない）になります。その理由は、SQLが採用している **「3値論理（Three-Valued Logic）」** という仕組みにあります。

一言でいうと、**「不明なもの（NULL）と何かを比べても、結果は『わからない（UNKNOWN）』になるから」** です。

詳しく解説します。

<br>
#### 1. SQLにおける3つの「答え」
通常のプログラミング言語では、比較の結果は「真（TRUE）」か「偽（FALSE）」の2つだけです。しかし、SQLにはNULLがあるため、結果が**3種類**存在します。
1. **TRUE（真）**: 条件に合致する。
2. **FALSE（偽）**: 条件に合致しない。
3. **UNKNOWN（不明）**: 合致するかどうかが判定できない。

`WHERE`句は、判定結果が **「TRUE」になった行だけ**を表示する仕組みになっています。

<br>
#### 2. 「= NULL」の計算プロセス
SQLで `column = NULL` と書いたとき、コンピュータの内部では次のような思考が行われます。
* **値が「10」のカラムと比較した場合：**
「10 は『何かわからないもの（NULL）』と等しいですか？」
→ 答えは **「わかりません（UNKNOWN）」** です。
* **値が「NULL」のカラムと比較した場合：**
「『何かわからないもの』は、別の『何かわからないもの』と等しいですか？」
→ 答えは やはり **「わかりません（UNKNOWN）」** です。同じNULL同士でも、中身が不明である以上「等しい」とは断言できないからです。

<br>
#### 3. なぜ「NO DATA FOUND」になるのか
上述の通り、どんな値と比較しても `column = NULL` の評価結果は常に **`UNKNOWN`** になります。
1. データが「10」でも結果は `UNKNOWN`
2. データが「NULL」でも結果は `UNKNOWN`
3. `WHERE`句は **`TRUE` の行だけ**を通す
4. したがって、**どの行も条件を通過できず、1件もヒットしない**

という結果になります。

<br>
#### 4. 正解：なぜ「IS NULL」なら動くのか

`IS NULL` は比較演算子（=）ではなく、**「その状態（NULLかどうか）を判定する専用の述語」** です。

* `IS NULL`：「これは『不明（NULL）』という状態ですか？」
→ はい、そうです（TRUE）
* `= NULL`：「これは『不明』という値と同じですか？」
→ わかりません（UNKNOWN）

このように、英語の「Is it...?（〜の状態ですか？）」と「Does it equal...?（〜と同じ値ですか？）」の違いをイメージすると分かりやすくなります。
:::

# 問題4-2（大小比較） *Lv1*
### HRスキーマ`JOBS`テーブルより`MIN_SALARY`が5000以上10000以下のデータを取得してください。（順不同）

## 期待する結果
| 	JOB_ID	| 	JOB_TITLE	| 	MIN_SALARY	| 	MAX_SALARY	| 
| 	----	| 	----	| 	----	| 	----	| 
| 	FI_MGR	| 	Finance Manager	| 	8200	| 	16000	| 
| 	AC_MGR	| 	Accounting Manager	| 	8200	| 	16000	| 
| 	SA_MAN	| 	Sales Manager	| 	10000	| 	20080	| 
| 	SA_REP	| 	Sales Representative	| 	6000	| 	12008	| 
| 	PU_MAN	| 	Purchasing Manager	| 	8000	| 	15000	| 
| 	ST_MAN	| 	Stock Manager	| 	5500	| 	8500	| 
| 	MK_MAN	| 	Marketing Manager	| 	9000	| 	15000	| 

## 解答例
```sql:例1：betweenを使用
SELECT
    *
FROM
    hr.jobs
WHERE
    min_salary BETWEEN 5000 AND 10000
```
```sql:例2：比較演算子を使用
SELECT
    *
FROM
    hr.jobs
WHERE
        min_salary >= 5000
    AND min_salary <= 10000
```

## 解説
「～から～の間」という範囲指定は、給与、日付、在庫数などのデータを扱う際に非常に多用されます。今回は、そのスマートな書き方と仕組みについて解説します。

### 1. 文法解説：BETWEEN演算子
特定の範囲内に値が含まれているかを判定するには、`BETWEEN` を使うのが最も直感的です。

```sql
WHERE [カラム名] BETWEEN [下限値] AND [上限値]
```

#### ① 境界値（5000と10000）は含まれる？
ここが一番のポイントです。**`BETWEEN` は「以上」「以下」を意味するため、指定した値（境界値）も含まれます。**
つまり、`MIN_SALARY` がちょうど 5000 のデータや 10000 のデータも抽出対象になります。

#### ② 比較演算子の組み合わせ
解答例2のように、比較演算子（`>=`, `<=`）と論理演算子（`AND`）を組み合わせても全く同じ結果が得られます。
* `min_salary >= 5000`（5000以上）
* **かつ（AND）**
* `min_salary <= 10000`（10000以下）

### 2. 実務での使い分け：`BETWEEN` vs `比較演算子`
どちらを使っても結果は同じですが、現場では以下のような基準で使い分けられます。

| 指定方法 | 特徴 | 適したシーン |
| :--- | :--- | :--- |
| **`BETWEEN`** | 読みやすく、コードがスッキリする。 | **数値や日付の範囲**をシンプルに指定したい時。 |
| **比較演算子** | 条件を細かく制御できる（「未満」にしたい場合など）。 | 「5000より大きく、10000ちょうどは含まない」といった**複雑な条件**の時。 |

> **日付での使用には注意！**
> 日付データ（DATE型）に対して `BETWEEN '2023-01-01' AND '2023-01-31'` と指定する場合、時刻情報が含まれていると意図した結果にならないことがあります（例：31日の昼過ぎのデータが漏れるなど）。日付を扱う際は、時刻を考慮した比較演算子の方が安全なケースも多いです。

### 3. SQLをスッキリ書くコツ
今回の問題のように、「同じカラム」に対して範囲を指定する場合は `BETWEEN` を使うと、「どの列をチェックしているか」が一度で済むため、後から見返したときに読み間違いが少なくなります。

期待する結果のリストを見ると、`SA_MAN` がちょうど `10000` ですが、これも `BETWEEN` の範囲内なのでしっかり含まれていますね。

# 問題4-3（否定）   *Lv1*
### **HRスキーマ`JOB_HISTORY`テーブルより`JOB_ID`が 「ST_CLERK」 でないデータを取得してください。（順不同）**

## 期待する結果
| EMPLOYEE_ID | START_DATE           | END_DATE             | JOB_ID     | DEPARTMENT_ID | 
| ----------- | -------------------- | -------------------- | ---------- | ------------- | 
| 102         | 2011-01-13T00:00:00Z | 2016-07-24T00:00:00Z | IT_PROG    | 60            | 
| 101         | 2007-09-21T00:00:00Z | 2011-10-27T00:00:00Z | AC_ACCOUNT | 110           | 
| 101         | 2011-10-28T00:00:00Z | 2015-03-15T00:00:00Z | AC_MGR     | 110           | 
| 201         | 2014-02-17T00:00:00Z | 2017-12-19T00:00:00Z | MK_REP     | 20            | 
| 200         | 2005-09-17T00:00:00Z | 2011-06-17T00:00:00Z | AD_ASST    | 90            | 
| 176         | 2016-03-24T00:00:00Z | 2016-12-31T00:00:00Z | SA_REP     | 80            | 
| 176         | 2017-01-01T00:00:00Z | 2017-12-31T00:00:00Z | SA_MAN     | 80            | 
| 200         | 2012-07-01T00:00:00Z | 2016-12-31T00:00:00Z | AC_ACCOUNT | 90            | 

## 解答例
```sql: 例1：<> を使用
SELECT
    *
FROM
    hr.job_history
WHERE
    job_id <> 'ST_CLERK'
```

```sql:例2：!= を使用
SELECT
    *
FROM
    hr.job_history
WHERE
    job_id != 'ST_CLERK'
```
```sql:例3：^= を使用
SELECT
    *
FROM
    hr.job_history
WHERE
    job_id ^= 'ST_CLERK'
```


## 解説
「～に一致する」という条件と同じくらい頻繁に使うのが、この **「～ではない（除外）」** という条件です。
Oracle SQLには「等しくない」を表現する記号がいくつかありますが、どれも実務で目にすることになるので、ここで整理しておきましょう。

### 1. 文法解説：「等しくない」を表す演算子
SQLで「AとBが等しくない」を表現するには、主に以下の3つの記号が使われます。

| 演算子 | 特徴 | 推奨度 |
| :--- | :--- | :--- |
| **`<>`** | **ISO標準（標準SQL）**。最も一般的で、どのデータベースでも動く。 | ★★★ |
| **`!=`** | プログラミング言語（C系やJavaなど）で馴染み深い書き方。 | ★★☆ |
| **`^=`** | **Oracle独自の書き方**。他のDBでは動かないことが多い。 | ★☆☆ |

#### ① 書き方のポイント：シングルクォーテーション
今回、`ST_CLERK` を **`' '`（シングルクォーテーション）** で囲っています。これは、`JOB_ID` が **文字列型（VARCHAR2）** だからです。
* 囲まないと、Oracleは `ST_CLERK` という名前の「列（カラム）」を探しに行ってしまい、「そんな列はありません」というエラーになります。

### 2. 注意：除外条件とNULLの深い関係
ここが中級者へのステップアップとして非常に重要なポイントです。
**除外条件（`<>` や `!=`）を使うと、その列が `NULL` である行も結果から消えてしまいます。**

たとえば、もし `JOB_ID` が `NULL`（空っぽ）の社員がいた場合：
* `WHERE job_id = 'ST_CLERK'` → 当然ヒットしない
* `WHERE job_id <> 'ST_CLERK'` → **これにもヒットしません！**

SQLの世界では、`NULL` は「比較不能」な存在です。「ST_CLERK ではない」という判定さえも「不明」扱いになり、結果から除外されます。
もし `NULL` も含めて取得したい場合は、以下のように工夫が必要です。

```sql
WHERE job_id <> 'ST_CLERK' OR job_id IS NULL
```

### 3. 実務での使い分け
基本的には、世界標準である **`<>`** を使う癖をつけておくのが一番安全です。

「特定の部署だけ除外してレポートを作りたい」
「テスト用のデータ（ID:9999など）を除いて集計したい」

といった場面で、この演算子は欠かせません。今回の問題で、`ST_CLERK`（店員）以外の役職履歴だけがきれいに並んでいれば大成功です！


<br>
:::message
### 「否定」は人間の脳にも優しくない？
`WHERE job_id <> 'ST_CLERK' AND department_id <> 50` のように否定が重なると、人間はパッと見て「結局どのデータが出るの？」と混乱しやすくなります。条件が複雑になる場合は、あえて「肯定」で書けるように整理すると、バグが減ります。
:::

# 問題4-4（いずれかに一致） *Lv1*
### **HRスキーマ`COUNTRIES`テーブルより、`REGION_ID`が40または50のデータを取得してください。（順不同）**

## 期待する結果
| COUNTRY_ID | COUNTRY_NAME | REGION_ID | 
| ---------- | ------------ | --------- | 
| AU         | Australia    | 40        | 
| EG         | Egypt        | 50        | 
| NG         | Nigeria      | 50        | 
| ZM         | Zambia       | 50        | 
| ZW         | Zimbabwe     | 50        | 

## 解答例
```sql:例1：orを使用
SELECT
    country_id,
    country_name,
    region_id
FROM
    hr.countries
WHERE
    region_id = 40 OR region_id = 50 
```
```sql:例2：inを使用
SELECT
    country_id,
    country_name,
    region_id
FROM
    hr.countries
WHERE
    region_id IN ( 40, 50 )
```
```sql:例3:anyを使用
SELECT
    country_id,
    country_name,
    region_id
FROM
    hr.countries
WHERE
    region_id = ANY( 40, 50 )
```

## 解説
今回は「複数の候補のうち、いずれかに一致する」という条件の書き方です。実務では「この部署と、あの部署の社員だけリストアップしたい」という場面が非常に多いため、非常に利用頻度の高い文法です。

### 1. 文法解説：IN 演算子の仕組み
複数の値を「または（OR）」で繋ぎたい場合、最もスマートで一般的な書き方が `IN` 演算子です。

```sql
WHERE [カラム名] IN (値1, 値2, ...)
```

#### ① OR のショートカット
`IN (40, 50)` は、内部的には `region_id = 40 OR region_id = 50` と全く同じ意味として処理されます。
記述が短くなるだけでなく、カッコの中を増やすだけで「3つ以上」の条件にも簡単に対応できるのが大きなメリットです。

#### ② 比較演算子 = ANY
解答例3にある `region_id = ANY(40, 50)` も同じ結果を返します。これは「リスト内の**いずれか**と等しい」という意味です。
実務で単なるリストを相手にする場合は `IN` が主流ですが、サブクエリ（別のSELECT文の結果）と組み合わせる際に `ANY` を見かけることがあります。

### 2. 3つの書き方の比較

| 書き方 | メリット | デメリット | 推奨シーン |
| :--- | :--- | :--- | :--- |
| **`OR`** | 異なるカラムを組み合わせられる（例：ID=40 OR Name='A'）。 | 候補が増えるとコードが非常に長くなり、読みにくい。 | 条件が2つ程度で、シンプルな時。 |
| **`IN`** | **非常に読みやすい。** 候補が多くてもスッキリ書ける。 | 同一カラムの比較にしか使えない。 | **同一カラムで複数候補がある時の第一選択。** |
| **`ANY`** | `>` や `<` と組み合わせて「どれかより大きい」といった比較ができる。 | `IN` に比べて直感的ではなく、影が薄い。 | 特殊な不等号比較を行いたい時。 |

### 3. 実務で役立つ「NOT IN」
今回の逆で、「40と50**以外**」を取得したい場合は `NOT IN` を使います。

```sql
WHERE region_id NOT IN (40, 50)
```

> **NOT IN と NULL の罠**
> `NOT IN` を使う際、カッコの中に一つでも `NULL` が混ざっていると、結果が **1行も返ってこない** という非常に厄介な仕様があります。
> 例：`WHERE region_id NOT IN (40, 50, NULL)` → 何も表示されない
> 複数の値を除外する際は、リストに NULL が入り込まないよう注意が必要です。

今回の問題で、Oceania (40) と Africa (50) の国々が正しく抽出できていれば完璧です！

# 問題4-5（複数の条件） *Lv1*
### HRスキーマ`EMPLOYEES`テーブルより、下記条件全てを満たすデータを取得してください。（順不同）
* **`JOB_ID' が 'IT_PROG'**
* **`SALARY` が　4500より大きい**
* **`MANAGER_ID` が 102でない**

## 期待する結果
| FIRST_NAME | JOB_ID  | SALARY | MANAGER_ID | 
| ---------- | ------- | ------ | ---------- | 
| Bruce      | IT_PROG | 6000   | 103        | 
| David      | IT_PROG | 4800   | 103        | 
| Valli      | IT_PROG | 4800   | 103        | 

## 解答例
```sql
SELECT
    first_name,
    job_id,
    salary,
    manager_id
FROM
    hr.employees
WHERE
        job_id = 'IT_PROG'
    AND salary > 4500
    AND manager_id <> 102
```

## 解説
複数の条件を組み合わせる「複合条件」のステージです。ここができるようになると、膨大なデータの中からピンポイントで欲しい情報を掘り当てることができるようになります。


### 1. 文法解説：AND 演算子による絞り込み
複数の条件を **「すべて満たす（かつ）」** 行を抽出したい場合は、条件の間を `AND` でつなぎます。

```sql
WHERE [条件1]
  AND [条件2]
  AND [条件3]
```

#### ① フィルタの積み重ね
`AND` を使うたびに、検索結果のふるいが細かくなっていくイメージです。今回の例では：
1. **`job_id = 'IT_PROG'`**: まずプログラマーだけに絞る
2. **`salary > 4500`**: その中から高給取り（4500超）だけを残す
3. **`manager_id <> 102`**: さらに特定のマネージャー（Lex De Haanさん）の下にいない人だけを抽出する


### 2. 演算子のバリエーション
この問題では、これまで学んだ3種類の比較演算子が共演しています。

* **完全一致 (`=`)**: 文字列 'IT_PROG' とぴったり同じ。
* **大小比較 (`>`)**: 境界値（4500）を含まない「より大きい」。
* **否定 (`<>`)**: 特定の値（102）を除外する。

これらの演算子は、データの型（文字列・数値・日付）に合わせて適切に使い分ける必要があります。

### 3. 実務での可読性アップ：コードのレイアウト

解答例のように、`AND` の前で改行してインデント（字下げ）を揃える書き方は、現場でも非常に好まれます。

```sql
-- 読みやすい例
WHERE
        job_id = 'IT_PROG'
    AND salary > 4500
    AND manager_id <> 102
```

こうすることで、「条件がいくつあるか」「何で絞っているか」が一目でわかるようになり、修正やデバッグが劇的に楽になります。

> **注意：演算子の優先順位**
> 今回は `AND` だけなので気にする必要はありませんが、`AND` と `OR` を混ぜて使う場合は注意が必要です。**`AND` は `OR` よりも先に処理される**という優先順位があるため、意図した順番で評価させたいときは `( )`（カッコ）で囲むのが鉄則です。

Bruceさん、Davidさん、Valliさんの3名がしっかり抽出できていれば、複合条件の基礎は完璧です！

<br>

:::message
### **「WHERE 1=1」の謎**
あるプロジェクトで見たSQLスクリプトに「WHERE 1 = 1」と書かれており、何のことか全く理解できず、「これ何ですか？」と聞たことを思い出します。

SQLで `WHERE 1=1` と書くのは、一見無意味（常に正しい条件）に見えますが、実は**プログラムで動的にSQLを組み立てる際の「定石」** として非常に重宝されています。

主な理由は、SQL文を「文字列として連結して作る」ときのコードをシンプルにするためです。
### 1. 動的SQLの組み立てを楽にするため
プログラムで「検索条件がある場合だけ `WHERE` 句を追加する」という処理を書く場面を想像してみてください。
<br>
#### * **`1=1` がない場合**

最初の条件だけは `WHERE` を使い、2つ目以降は `AND` を使う……という「条件分岐」の判定が必要になります。

```sql
-- 最初の条件だけ WHERE で始める必要がある
SELECT * FROM users WHERE name = '田中' AND age >= 20;

-- もし名前の指定がなかったら？
SELECT * FROM users WHERE age >= 20; -- 常に「最初が何か」を気にしないといけない
```
<br>

#### * `1=1` がある場合

**「常に `WHERE 1=1` から始める」** と決めておけば、その後に続く条件はすべて `AND` でつなげるだけで済みます。

```sql
SELECT * FROM users 
WHERE 1=1 
  AND name = '田中' 
  AND age >= 20;
```

プログラム側では、条件がいくつあっても「`" AND column = value"` を末尾にくっつけるだけ」で済むので、ロジックが非常にシンプルになります。

<br>

### 2. デバッグ（コメントアウト）が楽になる
SQLを直接書いてテストしているとき、特定の条件を無効化したいことがありますよね。`1=1` があれば、行頭をコメントアウトするだけで済みます。

```sql
SELECT * FROM products
WHERE 1=1
-- AND category = '家電'  <-- ここを消してもWHERE句が壊れない
   AND price <= 5000
```

もし `1=1` がないと、最初の条件を消すときに `WHERE` というキーワード自体も書き直さなければならず、手間がかかります。

<br>
私は目安として、以下の場合好んで「`WHERE 1 = 1`」を書くようにしています。
（いずれか）
- 複雑で巨大なSQLスクリプト
- 条件が３つ以上ある
- 自身が使用するテスト用スクリプト
:::

# 問題4-6（あいまい検索1） *Lv1*
### HRスキーマ`EMPLOYEES`テーブルより、`EMAIL`に「AB」の文字列が含まれるデータを取得してください。（順不同）

## 期待する結果
| FIRST_NAME | EMAIL   | 
| ---------- | ------- | 
| Ellen      | EABEL   | 
| Amit       | ABANDA  | 
| Alexis     | ABULL   | 
| Anthony    | ACABRIO | 

## 解答例
```sql
SELECT
    first_name,
    email
FROM
    hr.employees
WHERE
    email LIKE '%AB%'
```

## 解説
文字列操作の定番、**「あいまい検索」** の登場です。
「正確な名前は忘れたけれど、途中にあの文字が入っていたはず…」といった、実務でよくある「うろ覚え」の状態を解決してくれる強力なツールです。

### 1. 文法解説：LIKE演算子とワイルドカード
特定の文字列パターンに一致する行を検索するには、`=`（等号）の代わりに `LIKE` を使用し、**ワイルドカード**と呼ばれる特殊な記号を組み合わせます。

```sql
WHERE [カラム名] LIKE '[パターン]'
```

#### ① ワイルドカード `%`（パーセント）の意味
`%` は、**「0文字以上の任意の文字列」** を表します。
今回の条件 `'％AB％'` は、以下のように解釈されます。
* 前に何があってもいい（0文字でも可）
* 途中に `AB` がある
* 後ろに何があってもいい（0文字でも可）

結果として、**「どこかに AB という文字列が含まれているものすべて」** がヒットします。

### 2. ワイルドカードの使い分けパターン
`%` を置く位置によって、検索のルールが変わります。

| パターン | 意味 | 例（一致するもの） |
| :--- | :--- | :--- |
| **`'AB%'`** | **前方一致**（ABで始まる） | **AB**ANDA, **AB**ULL |
| **`'%AB'`** | **後方一致**（ABで終わる） | SCAR**AB**, TAXI**AB** |
| **`'%AB%'`** | **部分一致**（どこかにABがある） | E**AB**EL, AC**AB**RIO, **AB**ANDA |

> **もうひとつのワイルドカード `_`（アンダースコア）**
> `%` が「何文字でもOK」なのに対し、`_` は**「任意の1文字」**を表します。
> 例えば `LIKE 'A_C'` と書くと、「ABC」や「ADC」はヒットしますが、「ABBC」はヒットしません。

### 3. 実務での注意点
#### 大文字・小文字の区別
Oracle SQLでは、引用符 `' '` で囲まれた文字列の**大文字・小文字を厳密に区別します**。
もし `LIKE '%ab%'` と小文字で書いた場合、テーブル内のデータが `ABANDA`（大文字）であれば、1件もヒットしません。
※実務では、`UPPER(email) LIKE '%AB%'` のように、検索前に大文字に変換して比較するテクニックがよく使われます。

#### パフォーマンスへの影響
`LIKE '%AB%'` のように、**パターンの最初に `%` をつける（中間一致・後方一致）と、検索のスピードが極端に遅くなる**ことがあります。
これは、データベースが「索引（インデックス）」を効率よく使えず、全データを最初から最後まで読み込む必要が出てくるためです。大量のデータを扱う際は、可能な限り「前方一致 (`AB%`)」で検索できないか検討するのがプロの技です。

期待する結果にある `ACABRIO`。一見 `AB` がないように見えますが、4文字目と5文字目にしっかり `AB` が隠れていますね。この「隠れた文字」を見つけ出すのが `LIKE` の醍醐味です！

<br>
:::message
### **「とりあえず % で囲む」のは卒業しよう！**
開発環境の少ないデータでは一瞬で終わるクエリーも、本番環境の巨大なデータではシステム全体を止める原因になることがあります。`LIKE` を使うときは、常に「インデックスが使えるか？」をセットで考えるのが、プロのSQLエンジニアへの第一歩です。
:::

# 問題4-7（あいまい検索2） *Lv2*
### HRスキーマ`EMPLOYEES`テーブルより、`EMAIL`が「S」から始まり「S」で終わる７文字のデータを取得してください。（順不同）

## 期待する結果
| FIRST_NAME | EMAIL   | 
| ---------- | ------- | 
| Susan      | SJACOBS | 
| Stephen    | SSTILES | 
| Sigal      | STOBIAS | 

## 解答例
```sql
SELECT
    first_name,
    email
FROM
    hr.employees
WHERE
    email LIKE 'S_____S'
```

## 解説
今回は「あいまい検索」の応用編です。前回の `%`（パーセント）に続き、もう一つの重要なワイルドカードである **`_`（アンダースコア）** の使いこなしがポイントです。

### 1. 文法解説：アンダースコア（_）による文字数指定
`LIKE` 演算子で使えるワイルドカードには、大きく分けて2種類あります。

| 記号 | 意味 | 使いどころ |
| :--- | :--- | :--- |
| **`%`** | **0文字以上**の任意の文字列 | 長さが決まっていない時（「～を含む」など） |
| **`_`** | **ちょうど1文字**の任意の文字 | **文字数を厳密に指定したい時** |

#### ① 「S_____S」の構造分解
今回の条件「Sから始まり、Sで終わる7文字」をパズルにするとこうなります。

1.  最初の **`S`**（1文字目）
2.  中間の **`_____`**（2文字目〜6文字目の、計5文字）
3.  最後の **`S`**（7文字目）

合計で **1 + 5 + 1 = 7文字** というわけです。

### 2. なぜ「%」ではダメなのか？
もし `LIKE 'S%S'` と書いた場合、どうなるでしょうか？

* `SJACOBS`（7文字）：ヒットする
* **`SS`**（2文字）：ヒットする
* **`SUPERSONICS`**（11文字）：ヒットする

`%` は文字数を問わないため、「7文字限定」という条件を満たすことができません。**「特定の文字数で、かつ特定の場所を固定したい」** というときこそ、アンダースコアの出番です。

### 3. 実務での活用テクニック
アンダースコアは、以下のような「フォーマットが決まっているデータ」の検索に威力を発揮します。

* **品番・型番の検索**: `LIKE 'AB-___-99'`（真ん中が3文字の製品コードを探す）
* **日付形式の文字列**: `LIKE '2026/__/01'`（2026年の各月1日のデータを探す ※2026年現在ならまさに旬ですね！）
* **電話番号の特定部分**: `LIKE '03-____-____'`

> **視認性のコツ**
> SQLエディタによっては、アンダースコアが繋がって1本の線に見えてしまい、何個書いたか数えにくいことがあります。実務では `LENGTH(email) = 7` という条件を `AND` で組み合わせるなど、他の方法と併用して読みやすくすることもあります。

期待する結果を見ると、`SJACOBS`、`SSTILES`、`STOBIAS` はいずれも「S...S」の形をした見事な7文字ですね。

<br>
:::message
### **「アンダースコア自体を検索したい時は？」**
もしメールアドレスの中に実際に含まれている `_`（アンダースコア文字）を探したい場合は、そのまま書くとワイルドカードとして扱われてしまいます。その場合は `ESCAPE` 句を使って、「この後のアンダースコアはただの文字だよ！」と教えてあげる必要があります。
（例）商品名に「10%」という文字列が含まれるものを探す場合
```sql
product_name LIKE '%10@%%' ESCAPE '@'
```
:::

# 問題4-8（SELECT文での条件） *Lv2*
### HRスキーマ `COUNTRIES` テーブルより、下記条件にて、「地域」を算出してください。
* **`REGION_ID`=10または20** : 欧米
* **`REGION_ID`=30または50** : アジア・アフリカ
* **上記以外** : その他
* **表示対象は、`COUNTRY_ID`の頭文字がA～Cのもの**
  
## 期待する結果
| COUNTRY_ID | COUNTRY_NAME | REGION_ID | 地域             | 
| ---------- | ------------ | --------- | ---------------- | 
| AR         | Argentina    | 20        | 欧米             | 
| AU         | Australia    | 40        | その他           | 
| BE         | Belgium      | 10        | 欧米             | 
| BR         | Brazil       | 20        | 欧米             | 
| CA         | Canada       | 20        | 欧米             | 
| CH         | Switzerland  | 10        | 欧米             | 
| CN         | China        | 30        | アジア・アフリカ | 

## 解答例
```sql:例1：検索 CASE 式
SELECT
    country_id,
    country_name,
    region_id,
    CASE
        WHEN region_id IN ( 10, 20 ) THEN
            '欧米'
        WHEN region_id IN ( 30, 50 ) THEN
            'アジア・アフリカ'
        ELSE
            'その他'
    END AS "地域"
FROM
    hr.countries
WHERE
    country_id BETWEEN 'A' AND 'CZ'
```
```sql:例2：単純 CASE 式
SELECT
    country_id,
    country_name,
    region_id,
    CASE region_id
        WHEN 10 THEN
            '欧米'
        WHEN 20 THEN
            '欧米'
        WHEN 30 THEN
            'アジア・アフリカ'
        WHEN 50 THEN
            'アジア・アフリカ'
        ELSE
            'その他'
    END AS "地域"
FROM
    hr.countries
WHERE
    country_id BETWEEN 'A' AND 'CZ'
```

## 解説
今回は、SQLの中で「もし～ならA、そうでなければB」という条件分岐を行う**CASE式**の解説です。これが使えるようになると、テーブルに存在しない新しい分類項目を、クエリの結果だけで作り出すことができるようになります。

### 1. 文法解説：CASE式（条件分岐）

SELECT句の中に記述することで、値の状態に応じて表示内容を切り替えることができます。



#### ① 検索 CASE 式（例1）
最も汎用的で、実務でも多用される書き方です。`WHEN` の後に自由な条件式（`IN` や比較演算子）を書けます。

```sql
CASE
    WHEN [条件1] THEN [結果1]
    WHEN [条件2] THEN [結果2]
    ELSE [それ以外の結果]
END
```

#### ② 単純 CASE 式（例2）
特定の列の値が「何か」を判定する場合に短く書ける方法です。ただし、`=`（等号）による比較しかできません。

```sql
CASE [列名]
    WHEN [値1] THEN [結果1]
    WHEN [値2] THEN [結果2]
    ...
END
```

> **どちらを使うべき？**
> 基本的には **「検索 CASE 式」** を推奨します。理由は、`IN` を使って `WHEN region_id IN (10, 20)` とまとめて書けるため、コードが短く読みやすくなるからです。

### 2. 文字列の範囲指定（BETWEEN 'A' AND 'CZ'）
WHERE句の `country_id BETWEEN 'A' AND 'CZ'` という指定も面白いポイントです。

* **文字列の比較**: SQLでは文字列も辞書順で比較されます。
* **なぜ 'CZ' なのか？**: 
    * `BETWEEN 'A' AND 'C'` と書いてしまうと、`CA` (Canada) や `CH` (Switzerland) は「C」よりも後ろと判定され、ヒットしません。
    * そのため、**「Cで始まるものすべて」**を含めるために、`CZ`（Cのなかでほぼ最後に来る文字列）を上限に設定しています。

> もちろん、`LIKE 'A%' OR LIKE 'B%' OR LIKE 'C%'` と書いても正解ですが、`BETWEEN` を使うほうがスマートに記述できます。

### 3. 実務での活用シーン
CASE式は、データの「ラベル付け」に非常に役立ちます。

* **年代別の集計**: `CASE WHEN age < 20 THEN '10代' ...`
* **売上ランク**: `CASE WHEN amount > 1000000 THEN '優良顧客' ...`
* **フラグの変換**: `CASE WHEN status = 0 THEN '未完了' ELSE '完了' END`

期待する結果の表を見ると、本来のテーブルには存在しない「地域」という見出しで、私たちが定義した「欧米」や「アジア・アフリカ」がきれいに表示されていますね。これがCASE式の力です！

条件分岐の感覚は掴めましたか？次は、これらをグループ化して集計する `GROUP BY` などと組み合わせると、さらに強力なレポートが作れるようになります！

# 問題4-9（指定件数のデータ取得）  *Lv1*
### HRスキーマ`EMPLOYEES`テーブルより、任意の5件のデータを取得してください。（順不同）

## 期待する結果
| EMPLOYEE_ID | FIRST_NAME | LAST_NAME | 
| ----------- | ---------- | --------- | 
| 100         | Steven     | King      | 
| 101         | Neena      | Yang      | 
| 102         | Lex        | Garcia    | 
| 103         | Alexander  | James     | 
| 104         | Bruce      | Miller    | 

※任意の５件が取得できていればOK

## 解答例
```sql:例1：ROWNUMを使用
SELECT
    employee_id,
    first_name,
    last_name
FROM
    hr.employees
WHERE
    ROWNUM <= 5
```
```sql:例2：FETCH FIRSTを使用
SELECT
    employee_id,
    first_name,
    last_name
FROM
    hr.employees
--ORDER BY     -- 通常、ORDER BYをつけますが、任意の５件のため、ここでは敢えてコメントアウトしています
--    employee_id
FETCH FIRST 5 ROWS ONLY
```

## 解説
今回は、膨大なデータの中から「とりあえず最初の数件だけ見たい」という時に非常に便利な、**「取得件数の制限」** についての解説です。
開発中にテーブルの中身をサッと確認したい時や、ランキングの上位だけを表示したい時など、実務での出番は非常に多いコマンドです。

### 1. 文法解説：Oracleでの件数制限（新旧2つの方法）
Oracleには、件数を制限する書き方が大きく分けて2つあります。

#### ① ROWNUM（疑似列）を使う方法（例1）
Oracleで古くから使われている最もポピュラーな書き方です。

```sql
WHERE ROWNUM <= 5
```

* **ROWNUMとは？**: 抽出された各行に、上から順番に振られる「仮の番号」のようなものです。
* **仕組み**: 1行目が見つかったら `ROWNUM=1`、2行目は `ROWNUM=2`…とカウントされ、条件（今回は5以下）を満たさなくなった時点で抽出をストップします。

#### ② FETCH FIRST 句を使う方法（例2）
Oracle 12cから導入された、比較的新しく、かつ標準SQLに準拠した書き方です。

```sql
FETCH FIRST 5 ROWS ONLY
```

* **メリット**: 直感的で読みやすいのが最大の特徴です。英語の文章のように「最初の5行だけ取ってきて（FETCH FIRST 5 ROWS）」と指示できるため、`ROWNUM` よりも意図が伝わりやすくなります。

### 2. 重要な注意点：ROWNUMと並び替えの関係
今回は「任意の5件」なので問題ありませんが、**「給与が高い順に5件」**といった**Top-Nクエリ**を作りたいときには注意が必要です。

* **`ROWNUM` の罠**: 
  実を言うと、`ROWNUM` は `ORDER BY` よりも先に処理されてしまいます。
  `WHERE ROWNUM <= 5 ORDER BY salary DESC` と書くと、「適当に5件取ってきた後で、その5件を給与順に並べる」という、意図しない結果になることがあります（正しくはサブクエリを使う必要があります）。
* **`FETCH FIRST` の強み**:
  こちらは `ORDER BY` の後に処理されます。
  `ORDER BY salary DESC FETCH FIRST 5 ROWS ONLY` と書くだけで、正しく「高給取りトップ5」が取得できます。

### 3. 実務での使い分け

| 方法 | 特徴 | おすすめのシーン |
| :--- | :--- | :--- |
| **`ROWNUM`** | 記述が短く、古いバージョンのOracleでも動く。 | データの存在確認や、単純なサンプリング。 |
| **`FETCH FIRST`** | **読みやすく、並び替えとの相性が抜群。** | **ランキング表示や、最新10件の表示**など。 |

> **ROWNUMのちょっとしたクセ**
> `ROWNUM <= 5` は動きますが、`ROWNUM = 5` や `ROWNUM > 5` と書いてもデータは1件もヒットしません。ROWNUMは「1番目」から順に確定していかないと、それ以降の番号も生まれないという性質があるからです。

# 問題4-10（指定範囲のデータ取得）  *Lv2*
### HRスキーマ`EMPLOYEES`テーブルを`EMPLOYEE_ID`の昇順の並べて先頭から10件スキップし、5件のデータを取得してください。（順不同）

## 期待する結果
| EMPLOYEE_ID | FIRST_NAME  | LAST_NAME | 
| ----------- | ----------- | --------- | 
| 110         | John        | Chen      | 
| 111         | Ismael      | Sciarra   | 
| 112         | Jose Manuel | Urman     | 
| 113         | Luis        | Popp      | 
| 114         | Den         | Li        | 

## 解答例
```sql
SELECT
    employee_id,
    first_name,
    last_name
FROM
    hr.employees
ORDER BY
    employee_id
OFFSET 10 ROWS
FETCH NEXT 5 ROWS ONLY
```

## 解説

今回のテーマは **「ページング（Pagination）」** です。
Webサイトの検索結果で「11件目〜15件目を表示する」といった、大量のデータを分割して表示する機能を実装する際に欠かせないテクニックを解説します。

### 1. 文法解説：OFFSET と FETCH による範囲指定
Oracle 12cから導入されたこの構文を使うと、データの「読み飛ばし」と「取得」を驚くほどシンプルに記述できます。

```sql
SELECT ...
FROM ...
ORDER BY [カラム名]
OFFSET [スキップする行数] ROWS
FETCH NEXT [取得する行数] ROWS ONLY
```

#### ① OFFSET [n] ROWS
結果セットの先頭から **n行分を読み飛ばし（スキップ）** ます。
今回の問題では「10件スキップ」なので、11件目からが取得対象になります。

#### ② FETCH NEXT [m] ROWS ONLY
スキップした位置から、**続く m行分だけを取得** します。
「FIRST」と書いても「NEXT」と書いても動作は同じですが、OFFSETと組み合わせる場合は「（飛ばした）次を取る」というニュアンスで **NEXT** がよく使われます。


### 2. 超重要：ORDER BY は「必須」
この構文を使うとき、**`ORDER BY` 句は絶対に省略してはいけません。**

SQLの世界では、並び順を指定しない限り、データの並びは「不定（その時々で変わる可能性がある）」です。
もし `ORDER BY` を忘れてしまうと：
* 1ページ目（1〜10件目）を見た時。
* 2ページ目（11〜15件目）を見た時。
この間でデータの並びが変わってしまい、**「さっき1ページ目にいた人が2ページ目にも出てきた！」** という重複や、逆にデータが漏れる原因になります。


### 3. 昔のOracle（ROWNUM）との比較

この `OFFSET/FETCH` が導入される前は、範囲指定をするために非常に複雑な「3重のサブクエリ」を書く必要がありました。

> **昔の書き方の例（今は覚えなくてOK！）**
> ```sql
> SELECT * FROM (
>   SELECT a.*, ROWNUM rnum FROM (
>     SELECT * FROM hr.employees ORDER BY employee_id
>   ) a WHERE ROWNUM <= 15
> ) WHERE rnum > 10;
> ```

これに比べると、今回の `OFFSET 10 ROWS FETCH NEXT 5 ROWS ONLY` がいかに直感的で、間違いにくい書き方であるかが分かりますね。

### 4. 実務での「ページ番号」計算

プログラムからこのSQLを発行する場合、以下のように計算して値を当てはめるのが一般的です。
（1ページあたりの表示件数を `SIZE`、見たいページ番号を `PAGE` とした場合）

* **OFFSET**: `(PAGE - 1) * SIZE`
* **FETCH**: `SIZE`

> **ROWS と ROW**
> 文法上、`ROWS`（複数形）の代わりに `ROW`（単数形）と書いてもエラーになりません。`FETCH NEXT 1 ROW ONLY` と書きたい時に、英語として自然に見えるように配慮されている、Oracleのちょっとした「優しさ」です。
